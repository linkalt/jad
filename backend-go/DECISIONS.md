# Go backend migration: initial dependency decisions

**Status:** The Go backend implements the OpenAI Responses streaming adapter and staged transcript recovery, a multi-round session runner with native and MCP tool execution, explicit and automatic compaction, the core HTTP/SSE routes, effective session tool discovery, and normalized live UI streaming. Native tools and the MCP client are implemented; OpenAI OAuth is intentionally excluded. Full TypeScript API/config parity and a live differential harness remain outstanding, so this document records current boundaries rather than a claim of complete parity.

**Where JAD runs (2026-10-23):** JAD asks nobody before a tool call. Every enabled tool runs at once, so the container is the security boundary: run JAD inside a container that holds only the project and has no secrets in its environment. `paths` lists and `tools.deny` are in-process limits, not a sandbox. Older chapters below that mention approval or `allow_write` are history; the entries "The approval system is removed" and "`allow_write` is removed" at the end of this file are current.

The module path in `go.mod` (`jad/backend-go`) is a placeholder until the repository's canonical import path is known.

## HTTP server

Use the Go standard library's `net/http` for the local API; the bounded route slice uses a small injectable `http.Handler` to centralize compatibility behavior. It provides request contexts and SSE flushing without an additional server framework. Do not add Fiber or raw `fasthttp` unless measurements show the HTTP server itself is a bottleneck.

`internal/httpapi.Handler` exposes `GET /api/health`, authenticated `GET /api/library` and `GET /api/library/{kind}/{id}`, session catalog/history/message/model/files/tools routes, run start/attach/stop, and session compact/reset/front-compact. The session tools route returns the selected profile's effective native and MCP definitions. Root-library access is injected; responses are `no-store`, and configured library directories are reloaded on each request. Session lookup/config selection and transcript maintenance are injected; auth, CORS, body-size, SSE-buffer, and run-retention settings are explicit inputs. A disconnected start subscriber does not cancel an accepted run. Compaction retains configured request history through a compaction-cache overlay and resets derived caches; reset clears the transcript, backup, and known per-profile caches. Front-compaction removes the active transcript suffix beginning at a user record; configured recoverable mode archives the removed bytes in `<messages.jsonl>.deleted-history`, while permanent mode does not archive, and both invalidate derived caches. Live UI streaming normalizes reasoning and text deltas, function-call announcements and argument deltas, and tool results into cumulative messages; attach/reconnect streams replay the current message and terminal state. Remaining route/config parity is not claimed. Optional `http_debug` captures bounded provider HTTP request/response details asynchronously and redacts sensitive request headers. Bodies are not stored inside the record: with `include_request_body` / `include_response_body` each is a raw sibling file `requestN.body` / `responseN.body`. The response file is appended chunk by chunk as the stream is read (the unparsed SSE bytes, so an interrupted run keeps what arrived); the request file holds the bytes the SDK put on the wire (after its JSON encoding, so key order and escapes can differ from the runner's request JSON, which is the form the provider's prompt cache sees). The record carries `body_file`, `body_bytes`, `body_truncated`; `max_body_bytes` caps each file. This replaces the earlier inline `body` string.

## Filesystem session resolution and bootstrap

Run the current server with `go run ./cmd/jad`. `JAD_API_TOKEN` is required and must be at least 32 bytes; `HOST` and `PORT` override listener settings. Session model files select their API key through `api_key_env` (default `OPENAI_API_KEY`, or `OPENROUTER_API_KEY` for OpenRouter-compatible settings) and may set a custom `base_url`. API-key auth is supported; OpenAI OAuth is intentionally out of scope, and Go rejects `auth_mode: "openai_oauth"` rather than silently accepting it.

Root discovery follows the TypeScript precedence: `JAD_SESSIONS_DIR` selects one `default` root and bypasses root settings; otherwise `JAD_ROOT_SETTING_PATH`, or the first existing of `<cwd>/.jad/setting.json`, `$HOME/.jad/setting.json`, `<cwd>/setting.json` and `<cwd>/../setting.json` (one function, `internal/rootsetting`, used by the session loader and the content library; this order is Go only, TypeScript still looks at `<cwd>/setting.json` and its parent), can provide `session_roots` (or legacy `session_paths`), with `.jad/sessions` as the fallback. Multi-root requests use `root-id:session-id`; an unqualified ID is accepted only when it resolves uniquely. With one root, canonical references stay unqualified.

The resolver reads session `setting.json`/`model.json`, path-profile model and storage selection, prompt documents, and persistence settings for the current runner. It shares a single `TurnStore` per transcript path and serializes runs that use shared storage. Cross-process locking, live TypeScript differential tests, other API route families, and full session-config parity remain out of scope.

## OpenAI client

Use the official `github.com/openai/openai-go/v3` SDK behind a small adapter. The existing backend uses the Responses API, including streaming, custom provider base URLs, and function calls; keep SDK-specific types out of session and persistence code.

The v3.66.0 SDK is pinned in `go.mod` and was tested against an offline HTTP/SSE fixture. It provides `Responses.NewStreaming` and `ResponseStreamEventUnion.RawJSON()`, supplying raw event JSON to the compatibility/persistence layer. Its README states v3.45.0 and later require Go 1.25+. The current environment is Go 1.27.1; confirm the deployment Go version before cutover.

Do not reconstruct persisted provider events solely by marshaling typed SDK structs: preserve unknown response fields and verify the raw-event path in tests.

## JSON

Keep JSON operations behind a small internal boundary. Start with `encoding/json` for the first compatibility implementation. Evaluate Sonic against representative transcript/config/stream fixtures and benchmarks before adding it. Sonic's upstream documentation notes behavior differences from the standard library, including HTML escaping; the OpenAI SDK also performs its own JSON handling, so Sonic will not replace the SDK's decoder.

The `messages.jsonl` observable representation is a compatibility contract. Serialization tests must cover ordering, escaping, numeric values, unknown fields, and the exact line shape before changing serializers.

`internal/transcript.Journal` appends caller-supplied JSON objects, repairs an incomplete final line, supports hash-based idempotent append for a rendered file, and serializes transcript reads with writes. It syncs for `turn`/`strict` durability. `TurnStore` stages `response.output_item.done` items in `items.jsonl` plus `items.index.jsonl`, commits them in output-index order, filters minimal/full response metadata, compacts usage, and writes a hash-tracked canonical completion line. It also appends input batches with TypeScript-compatible batch metadata and expands raw input/`response.completed` records back into request-history items. Offline fixtures cover ordering, unknown fields, metadata modes, large items, duplicate commits, and Node-generated input-batch lines.

The idempotent append keeps an in-memory set of line hashes per `Journal` (`line_index.go`, about 56 bytes per line measured, so roughly 10 MB for a 250 MB transcript, held for the `Journal`'s lifetime) instead of rereading the whole file on every commit (F-07: 46 ms at 50 MB became 0.75 ms). It is dropped when the file's identity changes, the file shrinks, a rewrite goes through the `Journal` (`generation`), or the 4 KiB before the indexed end no longer hashes as before; an append by the `Journal` itself is picked up by reading only the new bytes. An in-place edit in the middle of the file by another process is not detected, which the single-writer rule for a transcript already excludes.

Recovery repairs partial message/item/index tails, retains unfinished turns without a final record, and completes or removes turns whose final record is present, using its hash to avoid duplicate transcript lines. Retained streaming turns are not yet reopened for writing. The `internal/session.Runner` serializes runs, normalizes and persists inputs, derives the next turn number from transcript records, builds requests from model settings and prompt configuration, streams raw Responses events, and commits completed or incomplete responses. Its provider-neutral stream interface keeps SDK types outside orchestration. Function calls execute through the session `ToolCatalog`; results are persisted and may feed follow-on provider rounds within configured limits. Explicit and automatic compaction are supported, with statecontext refresh after successful automatic compaction. Request history is reconstructed from `messages.jsonl` rather than optional history/usage caches, and a live differential harness against a running TypeScript store remains outstanding.

## Cross-process locking

The TypeScript backend has no cross-process session lock: it assumes one server process per session directory and only guards the partial-response cleanup (`responses.partial.cleanup-lock`). The Go backend goes further. `internal/sessionlock` takes an advisory `flock` (`LockFileEx` on Windows) on a hidden `.<file>.jad-lock` beside `messages.jsonl` and `setting.json`, so two Go processes cannot interleave writes to one session. Lock files are persistent and never removed, and workspace file listings hide them.

This is a deliberate superset, not a parity gap. It is the only on-disk difference the differential harness (`tools/differential`) ignores. It does not make mixed use safe: the TypeScript backend never takes these locks, so a TypeScript and a Go process writing the same session concurrently remain unsupported. Making that safe would require the TypeScript backend to take the same locks, which is out of scope for this port.

## Interactions that ask the user

A tool that must ask the user cannot answer itself and cannot read the run stream, so the question waits in a per-run broker: the tool hands over the dynamic JSON it proposes, the run publishes it as **message state** (`WebUiMessage.pending`, so a reload or a second tab still sees it), and the promise settles when the answer endpoint replies, the deadline passes, or the run stops. The tool result then carries the outcome back to the model as an ordinary `function_call_output`, so an interaction adds no transcript item type and `messages.jsonl` keeps its format.

Keep these rules when porting:

- The **in-code definition is the contract**; the shipped document under `sample/tools/native/` is an enablement manifest whose `inputSchema` must equal the code schema exactly (the loader refuses a divergence, and a test asserts the two are deep-equal).
- Dynamic JSON payloads are accepted with **configured bounds** (`max_draft_bytes`, `max_draft_depth`, `max_title_chars`), measured the same way in both places they are checked: the tool before it publishes a question, and the answer endpoint before it applies the user's edit. The limits travel **with the question**, not in a second config lookup, so the check always follows the question that is waiting.
- The **session config owns the wait**: `timeout_ms` is what the run publishes and the model has no argument that could change it. The user may push the deadline out from the drawer — `extend_ms` per press, the whole wait capped at `max_timeout_ms` — and an extension **republishes the question** with its new `expires_at`/`max_expires_at`, so every client shows the same time left.
- Report what the user changed as `changed` — the **paths** the edit differs at, relative to the proposed draft — so the model reads a large edit as a handful of paths instead of a re-read of the whole payload.

## Run streams and how a client learns a run finished

A run outlives the request that started it, and a browser that loses its stream must still end up in the right state. Two streams carry one run — `POST …/run` (the request that started it) and `GET …/run/stream` (attach, for a reload or a second tab) — and **both begin with a `run` frame** naming that run: `{turn_id, started_at, status}`. A client that later reads a session snapshot has to recognize which run the status it sees belongs to; the snapshot reports `run`/`runs_by_profile` with the same `turn_id`, which is how a client whose stream went silent learns that *its own* turn finished instead of waiting for a frame that may never come.

Keep these rules when porting:

- Terminal events are replayed to a subscriber that arrives after the run finished (`ui.message`, then `completed`, then `done`), and the response **ends** after `done` — on both routes. A finished run is retained for `run_state_retention_ms` and then retired; attaching after that answers a single `idle` frame and ends.
- A client may **replace a stream that goes quiet** (the TypeScript client's `run_stream_stall_timeout_ms`): silence is not the same as slowness, because a connection that stops delivering frames neither errors nor ends. Reconnecting is safe at any point in a run — the attach route replays the newest `ui.message` snapshot, so a client that missed every delta is correct from that frame on, and a client that already saw the terminal events finishes immediately.
- A tool that asks for an interaction (`WebUiMessage.pending`) survives all of this: the question is message state, so a reconnecting or attaching client sees it in the snapshot it replays.

## Parallel tool calls and the SSE keep-alive (TypeScript 479509f)

Tool calls of one provider response run with bounded concurrency (`max_parallel_tool_calls`, default 8, range 1–64; `1` restores strict order). The Go port keeps the TypeScript contract:

- Each result is published to the client the moment its call settles, so the stream follows completion order. `messages.jsonl` is unchanged: every result is persisted once, after the batch, in call order.
- After the first error no further call starts; calls already running settle and every result that completed is persisted. A cancelled run cancels all in-flight calls through the shared context.
- A user-decision tool (`request_draft`) in the response still runs alone; the other calls get the `user_decision_required` placeholder.
- A quiet run stream gets a `: keep-alive` SSE comment every `server.sse_heartbeat_interval_ms` (default 5000, `0` disables, max 300000). It carries no event, so a client parser ignores it and only the stall watchdog is reset.
- Slow clients are bounded by `server.read_header_timeout_ms` (default 60000, max 300000) and `server.idle_timeout_ms` (default 5000, max 3600000); `0` disables either. Both backends read the same keys, and the defaults equal Node's `headersTimeout` and `keepAliveTimeout`. Neither backend sets a whole-request or write timeout, because that would cut long-lived SSE run streams.

The Go backend has a structured server log built on `log/slog` (`internal/logging`). It is Go-only: the keys below live in the shared `server` section, and the TypeScript loader ignores them, so one `setting.json` serves both backends, while TypeScript keeps its `console.*` output.

- `server.log_level` (`debug|info|warn|error|off`, default `info`), `server.log_format` (`text|json`, default `text`) and `server.log_file` (default empty = standard error; relative paths resolve against the setting file's directory). The file is opened append-only with mode 0600; a file that cannot be opened stops startup instead of silently dropping records. There is no rotation: use logrotate or the service manager.
- Components receive a `*slog.Logger` by injection (`httpapi.Config.Logger`, `transcript.TurnStoreOptions.Logger`, `httpdebug.Settings.Logger`, `app.WithLogger`). A nil logger discards records; there is no global logger, so the library packages stay quiet in tests and embedders.
- What is logged: a 5xx response with its cause (the response body stays `internal server error`); a recovered panic in a request or a run, with its stack; the run lifecycle (started, finished with status and duration, failed, aborted with its reason); a session skipped from the list for an invalid setting, once per distinct reason (the frontend polls the list, so every skip would repeat); and the existing persistence and cache warnings. At `debug`, one access line per request.
- What is never logged: request or response bodies, prompts, model output, the `Authorization` header, tokens, environment values or query strings. The access line carries a route template (`/api/sessions/{session}/run`), never the raw URL, and a path outside the known routes is `unmatched`, so a client cannot write text into the log through the URL. Provider failure causes are logged server-side only and may name the provider URL or an upstream message; `http_debug` remains the opt-in way to capture bodies.
- Startup and shutdown failures are always written to standard error, whatever the level, because they explain why the process exited.
- Go's process manager and fetch store were already serialized behind a mutex that spans the capacity check and the write, so the two races TypeScript closed (`max_running`, fetch storage capacity) did not exist here; regression tests lock that in.

Go-specific, accepted differences:

- **Order of near-simultaneous results.** Two calls that finish within microseconds publish in an order that depends on the scheduler (a JavaScript microtask queue and Go goroutines differ). Calls whose duration differs by more than scheduling noise publish in the same order on both backends; the differential harness compares only the set for calls that settle together.
- **Heartbeat skipping.** TypeScript skips a frame while earlier output is still queued in the socket. Go writes each frame from one goroutine that blocks on the write, so there is never queued output for the heartbeat to skip behind; a stalled client back-pressures the loop instead.

## Failed runs outside messages.jsonl (TypeScript 3c9a0d7, 7618a15)

`messages.jsonl` is the provider request history: it holds what a provider produced and what the user sent, never an error, so it stays provider-native and cache friendly. A run that fails leaves an orphan user turn there and nothing else. The Go port keeps the failure in its own replaceable cache, like `cursor-cache.json`:

- `staging/run-error-cache.json` (`paths.run_error_cache`) holds `{"schema_version":1,"errors":[{turn, message_id?, turn_id, at, message}]}`, byte-compatible with the TypeScript file. `message` is the client-safe text the browser got as the `error` event, so no response body, path or stack is stored. A missing, corrupt or foreign-version file reads as empty. The file is written atomically under the store lock; a later failure of the same turn replaces the earlier one, and the oldest entries are dropped past `persistence.run_error_cache_max_entries` (default 50, range 1–10000).
- Only `failed` runs are recorded: a user stop is not an error, and a failure before the user input is saved has no turn to belong to. A failed cache write is logged at warn level and never changes the run's outcome.
- `turn` is the session turn whose user message has no answer. `message_id` is `session-user-o<offset>`, the id the web-ui projection gives that user message. `AppendInputItemsAt` reports the offset of the last record of the batch that has visible text, and `PersistedInput` carries it with the turn, so the run hook `RunOptions.OnInputAccepted` fires once the input is stored and before anything that can still fail. An input with no visible text (image only) records the turn without a `message_id`.
- The session snapshot gains `failures` (omitted when empty), the file joins the session etag, and reset, compaction and front-compaction delete the file with the other derived caches, because they re-base turn numbers and message ids. A crash cannot record anything, so a run that died with the process still leaves no trace; the client keeps its "outcome unknown" notice for that case.
- Proof that `messages.jsonl` is unchanged: the same four-run scenario (one provider failure) through the parent-commit binary and the working-tree binary gives byte-identical files (1947 bytes, same SHA-256); the only difference in the session directory is the new `run-error-cache.json`. The differential harness reports all 112 scenarios matching, including the 14 failing-run scenarios that differed before the port.

## Tool approval: removed (2026-10-23, user decision)

This chapter described an `approval: ask` gate before a tool call. It is gone: every enabled tool runs at once, and no setting asks the user before a call. The record of the removal is the entry "The approval system is removed" at the end of this file. What stays of the old design: the broker, the interaction types and `/run/interaction` carry `request_draft` only, and the clearing event `ended` is kept for drafts. ## Run checkpoints and undo (TypeScript 2250d02, design_checkpoint.md)

With `checkpoint.enabled` (off by default) the run records the workspace in a private bare git repository under the session staging directory and the user can undo a run. Nothing is read or written while it is off: no repository, no `checkpoints.json`, no git process.

- **Where it lives.** `internal/checkpoint` has `git.go` (the git commands, the equivalent of `checkpoint-git.ts`), `service.go` (records, snapshots, restore, equivalent of `checkpoint.ts`) and `run.go` (the per-run hooks and `CallChangesWorkspace`). The repository is `<staging>/checkpoints.git` and the list is `<staging>/checkpoints.json`; the record fields are the same as TypeScript's, so either backend reads the other's list. The user's own repository (index, HEAD, refs, stash) is never touched: every git command names its own index file and ignores the user's git configuration.
- **Config.** A top-level `checkpoint` node with `enabled`, `git_binary`, `max_checkpoints` (20), `max_files` (20000), `max_total_bytes` (512 MiB), `timeout_ms` (120000), `include_mcp_tools` (true), `snapshot_on` (`first_mutation` or `run_start`) and `safe_restore` (true). Only an absent key takes a default: `null` and a misspelt value are config errors, so a typo cannot turn undo off. The file and byte limits are placeholders until measured on a large workspace, as in TypeScript. 22 config-parity cases replay settings through the TypeScript loader and compare the messages.
- **The hook.** `Runner.Run` builds the hooks once per run (`checkpoint.NewRun`), takes the checkpoint before the first call that can change files (`write`, `edit`, `bash`, a `process` start, or any MCP tool when `include_mcp_tools`), and closes it in a `defer`, so a run that fails, is stopped or is cancelled still records its end. When a response holds a user-decision tool only that call counts, because the others do not run. A snapshot that fails or is skipped is a record with a warning and never stops the call.
- **Routes.** `GET /api/sessions/{id}/checkpoints` and `POST .../checkpoints/{checkpoint_id}/restore` with `{dry_run?, mode?: "safe"|"full"}`. 404 for an unknown id, 400 for a bad body (the same messages as TypeScript), 409 while a run is active or when the checkpoint has no saved state, 422 when git is unavailable, 401 without the token. The handler refuses a restore during a run before it waits for the cross-process session lock, because a run holds that lock until it ends; waiting first would turn the immediate 409 into a hang. A restore holds the same mutation guard as compaction and reset, so no run starts while files are rewritten, and it records its own `pre_restore` checkpoint so it can be undone.
- **Excluded from a snapshot.** Harness paths that sit inside the workspace (session directory, staging, the task, memory, fetch, process, spill and backup directories) and the `*.bak-<ms>-<hex>` backups, so a restore never rolls back the transcript. A filesystem root or the home directory is refused as a workspace.
- **Differences that are not gaps.** The operating-system wording of "cannot run git" differs between Node and Go; the differential harness compares the prefix. A server restart in the middle of a run is not tested in either backend: the open checkpoint then has no `after_tree`, so only a full restore works for it (the same in both).
- **Proof that `messages.jsonl` is unchanged.** The same scenario (a write and a read in one response, a failing read and an unknown tool, then a second write: 10 records) through the parent-commit Go binary and the working-tree binary gives byte-identical files (3242 bytes) with `checkpoint` absent, `enabled: false`, `enabled: true` (one `complete/run` record written) and `snapshot_on: "run_start"`. Only batch ids, `token=` values, backup names and the temp root were masked. The differential harness reports all 132 scenarios matching, including 8 checkpoint scenarios; with the run hook disabled in a throwaway build 4 of the app integration tests fail.

### A run checkpoint left open by a stopped server is listed as interrupted (TypeScript and Go together)

A record is written `open` when a run takes its snapshot and closed by `Finish`. If the server is killed in between it stays `open` with no `after_tree`. `GET /checkpoints` now reports such a record as `interrupted`, with the warning "The run ended without recording its end (the server stopped or crashed).", whenever no run of the session is live; while a run is live it stays `open`. The state is derived at read time and never stored: the checkpoint service is built per request and cannot know which runs are live, and a write from the list route could race with a run that has just begun and lose its record. Go: `Service.Report(runIsLive)` wraps `List()`, and the HTTP handler passes `run.state() == "running"` from the run registry; a run's status leaves `running` only after the deferred `Finish` has written its end snapshot, so a finishing run is never mislabelled. Applies to `pre_restore` records too. A restore of an interrupted record needs `mode: "full"` (safe answers 409, as for an open one). The stored file keeps `open`. The frontend accepts the new state; an older frontend would reject the list, so the three ship together. Proof: baseline and new code give identical output in 143 of 144 differential scenarios on each backend, and the only difference is the new scenario (`open` becomes `interrupted`).

## Tool call scheduling: ordered by default (TypeScript and Go together)

The calls of one provider response used to start together, so a later call could run before an earlier one on the same file. Measured with edit, edit, edit, read of one file at the default concurrency of 8, 200 runs each: TypeScript applied the edits out of order in 3 (1.5%), Go in 73 (36.5%, because `sync.Mutex` is not first-in, first-out and goroutine start order is undefined), and the read saw the final content in 1 and 2 runs.

New session setting `tool_call_scheduling`, `"ordered"` (default) or `"concurrent"`; only an absent key means the default, `null` and any other value is a config error with the same message in both backends (config-parity cases cover it).

- `ordered`: a response that holds at least one call that can change state runs one call at a time, in the order the model wrote them. A response made only of read-only calls still runs up to `max_parallel_tool_calls` together, so T-008's streaming of results as calls finish is kept for that case.
- `concurrent`: the previous behaviour, with no ordering guarantee between calls.
- "Can change state" is a property of the tool, not of the call: a tool is read-only only when its definition says so (`readOnly` in TypeScript, `ReadOnly` in Go). Native `read`, `grep`, `glob`, `fetch` and `skill` are marked; `write`, `edit`, `bash`, `process`, `task`, `memory`, `request_draft` and every MCP tool are not, so a new tool is serialized until someone marks it. An unknown tool name runs nothing and does not force a serial run.
- A response that holds a user-decision tool still runs only that call; the rest get placeholders, as before.
- `messages.jsonl` is unchanged: results were already persisted in call order after the batch. Only the order results are streamed in, and when each call runs, changes.

### The checkpoint list reports a restore in progress (TypeScript and Go together)

`GET /api/sessions/{id}/checkpoints` answers `{enabled, restoring, checkpoints}`; `restoring` is always sent, as a boolean.

- It is true from the moment a real restore holds the session's gate until the restore ends, and false for a dry run. A restore also holds the gate that compaction and reset share, so the list cannot read the gate itself; each backend keeps a separate set of the keys with a restore in flight (`restoringCheckpoints` in TypeScript, `Handler.restoring` under `mutationMu` in Go) that only the restore route touches.
- The frontend reads a missing value as false, so an older server still works, and rejects a non-boolean. While it is true the panel disables every Restore control and re-reads the list every `checkpoint_restore_poll_ms` (frontend config, 2000).
- `messages.jsonl` is unchanged; this is a list field only.
- **A second restore sent while one runs is refused with 409 ("session profile is already changing") on both backends, real or dry.** Go used to take the per-session keyed lock before the mutation gate, so the second request waited for the first and then ran; the restore handler now takes the gate first and the lock second. Compaction, reset and front compaction used to take the lock first and so queued behind a running restore (measured: reset answered 200 only after the restore ended, 2.1 s) while TypeScript answered 409; they now resolve the session, take the gate, and only then the lock, so all three are refused at once with their own 409 message. A compaction sent during a live run is not changed by this: in a probe it answered 200 on both backends only after the run ended (about 1.5 s), so it waits for the run on both. The probe's reset and front-compaction requests went out after the run had ended, so what they do during a live run was not measured.

## Provider retry: the harness retries the request that opens a response

New session setting `provider_retry` with `max_retries` (default 2, 0 to 10), `initial_delay_ms` (default 500, 1 to 60000) and `max_delay_ms` (default 8000, 1 to 600000). The defaults equal what both SDKs did before the setting existed, so an absent key changes nothing. Only an absent key takes a default: `null`, a wrong type, an out-of-range value, an unknown key, or an `initial_delay_ms` above `max_delay_ms` is a config error with the same message in both backends (26 config-parity cases cover it).

- **What is retried.** Only the request that opens the response stream. After the first event arrives, partial output was already shown and staged, so a failure after that point is never retried; the run fails as before.
- **Which failures.** Status 408, 409, 429 and any 5xx; a connection failure or timeout; the provider's `x-should-retry` header overrides the status. A stop by the user is never retried, and a stop during a wait ends the run at once with the stop's reason.
- **The wait.** `initial_delay_ms` doubled per retry up to `max_delay_ms`, minus up to a quarter as jitter. A `Retry-After-Ms` or `Retry-After` (seconds or an HTTP date) from the provider replaces the backoff, capped to `max_delay_ms`. The SDKs capped a server-directed wait at 8 s and did not read this from the session; the cap is now the setting. On a 429 with no Retry-After, `x-ratelimit-reset` (OpenRouter sends it, as an epoch in milliseconds) is used the same way: the wait is the time until that epoch, capped to `max_delay_ms`. Only a value that is plainly an epoch counts (at least 1e12 is milliseconds, at least 1e9 is seconds); a small number, a duration string such as `6m0s`, an unreadable value or a time already past is ignored and the backoff applies, and a status other than 429 never reads it. A reset further away than `max_delay_ms` is not waited out: the backend waits `max_delay_ms` and retries, as before, so the default still equals the old SDK behaviour; raise `max_delay_ms` (and `max_retries`) to outlast a window. Both backends share the rule (`rateLimitResetMs` in `backend/src/provider-retry.ts`, `rateLimitReset` in `internal/openaiapi/retry.go`).
- **Why each backend runs its own loop.** The Go SDK exposes the retry count but not the backoff curve, so matching the TypeScript SDK's delays exactly needs one loop per backend with the SDK's own retries switched off for that request (`maxRetries: 0` in TypeScript, `option.WithMaxRetries(0)` in Go). With no `provider_retry` given to the client (a test, or another caller) the SDK's defaults apply unchanged.
- **Go.** `internal/openaiapi/retry.go` holds the rules and `Client.openStream` the loop; `internal/app/provider_retry.go` maps the setting and logs each retry (`provider request retry`, with the attempt, status and wait). `fingerprintRunner` includes the setting, so a changed `provider_retry` reaches the next run instead of waiting for a restart.
- **`messages.jsonl` is unchanged.** Failed attempts write nothing, and a run that recovers writes the same records as one that never failed.

### The retry wait is shown to the client: the `provider_retry` run-stream event

While a run waits to retry, nothing else on the stream changes, so the wait looked like a hang. Both backends now send one `provider_retry` event before each wait and one that clears it. There is no setting: the event is always sent, and a client that does not know it ignores it (the frontend's stream reader skips unknown events).

- **Shape.** `{"turn_id": "...", "waiting": {"attempt": 2, "max_retries": 5, "status": 429, "wait_ms": 4000, "resume_at": "2026-01-01T00:00:04.000Z"}}`, or `"waiting": null` when the wait is over. `status` is `null` for a connection failure. `wait_ms` is the wait the loop actually sleeps (backoff, `Retry-After` or `x-ratelimit-reset`, after the cap), and `resume_at` is when it ends, so the UI counts down without trusting the two clocks to agree.
- **When it is cleared.** When the request that opens the stream returns, however it ends: the stream opened, the retries were used up (the clear comes before the `error` event), or the run was stopped. It is sent only when a retry happened, so a request that works first time produces no event.
- **Reattach.** It is run state like the pending question: a client that attaches mid-wait is told about it, a cleared wait is not replayed, and a finished run keeps none. It is never written to `messages.jsonl`.
- **How Go reaches the run.** The client that retries is built once per runner and shared by every run, so it cannot hold a run. The run's notifier travels in the request context instead (`responses.WithRetryNotifier`, set in `internal/httpapi/executor.go`; `Client.openStream` reads it), which leaves the `Streamer` interface unchanged. TypeScript passes an `onProviderRetry` option down `persistOpenAIResponse`.
- **Differential harness.** `resume_at` is a clock reading, so `normalize.mjs` masks it; `wait_ms` is fixed by the scenario's `Retry-After-Ms`, so it and the rest of the payload are compared.

### The event that clears a question says why it ended: `interaction.ended` (TypeScript and Go together)

A question left the run stream as `pending: null`, which could not say whether it was answered in this window, answered in another, timed out or cut off by the run ending. A second tab therefore watched its question vanish with no explanation. The event that clears a question now carries `ended` as well:

```json
{"turn_id": "…", "pending": null, "ended": {"interaction_id": "…", "tool": "request_draft", "outcome": "answered", "decision": "decline"}}
```

- **Fields.** There is no `kind`: only drafts exist (the member was removed together with approvals, 2026-10-23). `outcome` is `answered`, `timed_out` or `cancelled`. `decision` (`accept`, `update`, `decline`) is present only for `answered`: a timeout or a stop is not a decision anybody made, and a late reply that finds the deadline passed reports `timed_out`.
- **Sent once, never replayed.** `ended` rides on the clearing event only. A client that attaches later gets `pending: null` and nothing else, so it can never be shown a stale reason. A question nobody could answer (the run was already stopped) is neither published nor ended, so it has no end to report.
- **No setting, additive.** An older client ignores the extra member; a newer client treats a missing one as "no explanation". It is run state, not transcript: nothing is written to `messages.jsonl`.
- **Who stays quiet is the client's call.** The tab that sent the answer, or asked for the stop, knows why the question ended and shows nothing; any other tab shows one notification. A timeout is shown to every tab, because the countdown was the only warning.
- **Implementation.** TypeScript: `InteractionBroker` passes an `InteractionEnd` to its listener and `SessionRun.setPending` adds it to the event. Go: `Broker.onChange` takes `(*PendingInteraction, *InteractionEnd)` and `activeRun.setPendingInteraction` adds it to the payload.
- **Tested.** Broker tests on both backends (answered, denied, stop, run end, late reply, draft), real-server tests that read the stream (allow, deny, stop), a differential scenario that compares the three runs, and frontend parser and wording tests.

## Run token cap: `max_run_tokens` stops a run between rounds (TypeScript and Go together)

New session setting `max_run_tokens`, an integer from 1 to 1000000000000. **There is no default: an absent key means no cap and changes nothing.** `null`, `0`, a negative or fractional number, a string and anything else is a configuration error with the same message on both backends: `max_run_tokens must be a safe integer between 1 and 1000000000000`.

- **What is counted.** After each provider response the harness adds the tokens the provider reported for it: `usage.total_tokens`, or `input_tokens` plus `output_tokens` when no valid total is given. A response with no usable usage counts as 0, because only reported numbers are trusted. Every round re-sends the history, so the count is what the run was billed for, not the size of the transcript. The count belongs to one run: the next run starts from 0.
- **When it is checked.** Once per round, after the response is committed and only when the model asked for tool calls: if the count has reached the cap (`>=`), no further round starts. A response in flight is never cut, so a run can end above the cap by up to one response. A final answer with no tool calls always completes, because no round is left to refuse.
- **What the transcript gets.** Each call of the refused round receives a `function_call_output` with the code `run_token_limit`, so the history stays valid for the next run, the same way `tool_round_limit` does. Nothing else about `messages.jsonl` changes; with the key absent no record differs.
- **What the client gets.** The run fails with a message that names only numbers the harness counted: `The run stopped before its next round: it used N tokens, which reached the max_run_tokens limit of M.` It is the one run failure whose text is shown, instead of the generic "Response details were withheld" line, and it is kept in the run-error cache like any failed run. Go: `session.RunTokenLimitError`, recognised in `httpapi.clientRunErrorMessage`. TypeScript: `RunTokenLimitError` in `run-token-budget.ts`, recognised in `server.ts`.
- **What it does not do.** It is not a cost cap: it counts tokens, not money, and does not weigh cached input differently. It does not bound a single response (use the model's own output limit), it does not stop a run that never asks for tools, and a run that was already past the cap when this setting was added to a live session stops at its next tool round. It does not apply across runs or sessions. The TypeScript-only `maxToolRounds` run option has no token counterpart.
- **Go.** The value is read per run in `boundRunner.Run` and passed as `RunOptions.MaxRunTokens`, so no runner fingerprint is involved and a changed value applies to the next run. TypeScript reads it from the loaded settings each round.

## Compaction: `compaction.keepbatch.tools` is a total over the kept turns, not a count per turn (Go brought in line with TypeScript)

`compaction.keepbatch.tools` is the number of tool call/result pairs compaction keeps, newest first, **in total across every kept turn**, and only in `assistant_final` mode (`full` always drops them). TypeScript always did this (`compactHistory` collects the pairs of all selected turns, then takes the last N). Go counted per turn: `retainCompactedTurn` picked the last N pairs of each turn on its own, so with `"tools": 1` and `"turn": {"keep": 20}` a session kept one pair from each of the 20 turns, up to 20 pairs. A session that calls a tool in nearly every turn (the `memory` tool, for instance) filled `compaction-cache.json` with those pairs, while the same setting on TypeScript kept one.

- **Fix.** `keptToolPairs` now picks the pairs once over all selected turns and `retainCompactedTurn` only applies that set. A pair still needs both its call and its output among the kept turns; an unmatched call or output is dropped.
- **Result of the fix on existing caches.** A cache written before the fix keeps its extra pairs until the next compaction rewrites it; nothing rewrites it at read time.
- **Tests.** `TestKeepToolPairsCountsAcrossAllKeptTurns` (four cases, fails on the old code) and the differential scenario "compact with keepbatch.tools 1 over several turns" (session `keeptools`, three turns that each call `read`): TypeScript keeps one pair, the old Go kept all three and reported `compacted: false`.

## Compaction: `compaction.keepbackup.min_turns` stops a thin snapshot from replacing a fuller backup (Go only, 2026-10-16)

With `backup_mode: "replace"` every compaction copies the live `messages.jsonl` over the backup. After an earlier compaction, or a long single turn with many tool rounds, the live file holds little, so a later compaction could overwrite a fuller backup with one turn. `compaction.keepbackup.min_turns` (integer 0..1000, default 0 = always overwrite, as before) skips the overwrite when the existing backup holds **at least `min_turns` user turns and the new snapshot fewer than `min_turns`**. The backup is then left as it was; the compaction itself still runs.

- **Turn rule.** Turns are the records with `role == "user"` in the file as written on disk, the rule `CompactHistory` uses to split turns. It differs from the web UI's `readBackupTail`, which merges records that share an input batch id into one turn, so a batch of several user messages counts once there and several times here.
- **Scope.** `replace` only; `append` is unchanged. A missing or unreadable backup or snapshot never blocks the overwrite. The check does not touch `messages.jsonl`.
- **Not chosen.** Prepending older turns to the new backup (mixes two snapshots); making `append` the default (unbounded growth).
- **Tests.** `backup_min_turns_test.go` (guard cases and a `CompactHistory` run), `TestNormalizeCompactionBackupMinTurns`, `TestBackupMinTurnsSchemaMatchesTheLoader`.

## Bash `stdin`: text piped to a command (TypeScript and Go together)

`bash` takes an optional `stdin` string that is written to the command's standard input, which is then closed, so `bash({command: "python3 -", stdin: code})` runs an inline script and `bash({command: "jq .x", stdin: json})` filters data. Without it the input stays closed from the start (`/dev/null`), exactly as before, so a command that reads stdin returns at once instead of waiting.

- **Limit.** `tools.native.bash.stdin_max_bytes` (default 262144, 1 to 10485760) counts UTF-8 bytes. A larger text is refused whole with `invalid_input` / `stdin_too_large` and the command does not run; it is never cut, because a half script is worse than none. An empty string is the same as no `stdin`.
- **A program that does not read its input is not an error.** The write fails with a closed pipe (EPIPE) and that is ignored. TypeScript attaches an error listener to `child.stdin`. Go writes from its own goroutine into its own `os.Pipe` and closes the write end when the call ends, so `Wait` never blocks on a descendant that holds the pipe open.
- **Alias.** `input` is accepted for `stdin` (the named field wins), like `cmd` for `command`.
- **Output is unchanged.** Truncation, spill and the result format are the bash ones; `stdin` adds nothing to a result.
- **Definition file.** The exposed schema gained the `stdin` property, so `sample/tools/native/bash.json` must change in the same step as the binary: both backends require a definition file to match the code schema exactly (`catalog.ts`, `requireNativeDefinition`), and the match fails in both orders (old binary with the new file, new binary with the old file). A session that lists the file therefore cannot be served across the swap; restart the backend right after the file is written.
- **Tests.** TypeScript `bash-tool.test.ts` (7 tests); Go `bash_stdin_test.go`, `native_bash_settings_test.go`; harness scenarios "bash stdin: piped text, pipeline, alias, multi-byte and ignored" and "bash stdin: absent input is closed and an oversize text is refused".

## Process `stdin`: text written once at start (TypeScript and Go together)

`process` takes an optional `stdin` string on a **start**: it is written once to the started command's standard input, which is then closed, so `process({command: "node -", stdin: serverScript})` runs a long-lived inline script with no temp file. Without it the input stays closed from the start, as before. It is deliberately one-shot: there is no `send` action that writes to a running process later. That would need a pipe held open per process, a size and rate cap per send, and a rule for a restart (the pipe is lost and the process becomes `lost`). It is a separate, larger task.

- **Limit.** `tools.native.process.stdin_max_bytes` is its own key, not `bash`'s (default 262144, 1 to 10485760, UTF-8 bytes). A larger text is refused whole with `invalid_input` / `stdin_too_large` before anything starts; it is never cut. An empty string is the same as no `stdin`. The text is not trimmed, because leading and trailing whitespace can belong to a script.
- **Only on start.** `stdin` with `status`, `wait`, `stop` or `list` is refused with `invalid_stdin`.
- **Not stored.** The text is not written to the process manifest. It reaches the process, so anything the process prints (a `cat`, for instance) is in its log as usual.
- **A process that does not read its input is not an error.** The write fails with a closed pipe (EPIPE) and that is ignored. TypeScript attaches an error listener to `child.stdin`. Go writes from its own goroutine into its own `os.Pipe`, closes the read end in the parent after the start, and closes the write end when the managed process ends (`waitForProcess`), so a descendant that keeps the pipe open and never reads it cannot hold the writer goroutine for good. `TestNativeProcessStdinWriterIsReleasedWhenTheProcessEnds` fails with the close removed (goroutine count 3 against 2).
- **Alias.** `input` is accepted for `stdin` (the named field wins), as in `bash`.
- **Definition file.** The exposed schema gained the `stdin` property, so `sample/tools/native/process.json` must change in the same step as the binary (both backends require an exact match, and it fails in both orders). The same single swap as for `bash`.
- **Tests.** TypeScript `process-tool.test.ts` (7 tests); Go `process_stdin_test.go`, `native_process_settings_test.go`; harness scenarios "process stdin: piped text, pipeline, alias, multi-byte and ignored" and "process stdin: absent input is closed, oversize and non-start refused".

## `exec`: inline code in a configured interpreter (TypeScript and Go together)

`bash` with a `stdin` text already runs an inline script, but the model has to know the interpreter's flags and quote its arguments for a shell, and a long output is cut in the middle of a line. `exec({code, lang?, args?, cwd?, timeout_ms?})` takes the code and, optionally, the language; the backend owns the command line.

- **A new tool, not a schema change.** `sample/tools/native/exec.json` is a new file, so an old binary ignores it and there is no single-swap problem (unlike the `stdin` properties of `bash` and `process`). A session exposes `exec` by listing the file in `tool_definition_paths` and by configuring `tools.native.exec`.
- **Everything about how a child runs is `bash`'s.** `exec` requires `tools.native.bash` (a configuration error otherwise) and uses its shell-independent settings: environment allowlist, `env`/`env_file`/`env_deny`, timeouts and the per-call clamp, kill grace, stream budgets, spill files and their retention, ANSI stripping and the path policy for `cwd`. Both tools call one runner, `runShellChild` (Go) / `runShellChild()` (TypeScript), so they cannot drift. The harness credential is removed exactly as for `bash`.
- **No shell.** The program starts with its argv: the interpreter, its fixed flags from the table, then `args`. A quoting mistake cannot reach the program.
- **Interpreter table.** `tools.native.exec.langs` is merged over the built-in `python`, `node`, `bash`, `sh`, `ruby` and `perl` by name; an entry with a built-in name replaces it. An entry has `argv` (required, 1 to 32 non-empty strings), `code` (`stdin`, the default, or `file`), `ext` (extension of the temporary code file) and `aliases`. A name or alias claimed by two entries is refused at load time. Names match without regard to case after trimming, and by alias.
- **Code delivery.** `stdin`: the code is the program's standard input, so the working directory and relative paths behave as in a shell. `file`: the code is written to `code<ext>` in a private directory created per call (`exec-*` under the temporary directory, mode 0600), `{file}` in the argv is replaced by its path, and the directory is removed afterwards whatever the program did. Nothing is written for `stdin` languages besides the result file's directory.
- **Code limit.** `code_max_bytes` (default 262144, 1 to 10485760, UTF-8 bytes) is its own key. A larger text is refused whole with `code_too_large` and the program does not start; it is never cut. An empty or blank code is `invalid_code`. An unknown language is `unknown_lang` and lists the available names.
- **Result channel.** The program may write a short answer to the file named by `$EXEC_RESULT`. If the file is non-empty after the program ends, the result content is `[result]`, the answer (trailing whitespace removed, cut to `result_max_bytes`, default 16384, at a character boundary), then `[output]` and the raw output, or only the `[result]` section when there is no other output. A cut answer reports `result_truncated_bytes`. A missing, empty or blank file is no answer and the content is the raw output exactly as `bash` would show it. The raw output keeps its own budgets and spill files.
- **Line-aware cutting.** `line_aware` (default true) makes a truncated stream end its head and start its tail on line boundaries, so no line is shown half; a window without any line break (one very long line) is left as it is. The bytes this drops are counted in the omitted marker, so `produced = shown + omitted` still holds. It applies to `exec` only: `bash`, `process` and the other users of the collector keep cutting at the byte budget, so their output and `messages.jsonl` are unchanged.
- **Results.** Same shape and fields as `bash` (`exit_code`, `timed_out`, `truncated`, `stdout_full`, `hint`, ...). The "not installed" error names the interpreter and the setting that fixes it: `interpreter_unavailable`, with `interpreter` and a suggestion naming `tools.native.exec.langs.<name>.argv`, instead of `shell_unavailable`.
- **Checkpoints.** An `exec` call takes a run checkpoint like `bash` (it can change files).
- **`lang` is optional, default `bash`.** A real-model trial (30 runs, one model) showed 3 of 25 `exec` calls sent `code` without `lang` and were refused, each costing a round. `lang` is no longer required; a call without it runs `tools.native.exec.default_lang` (default `bash`; a name or alias from `langs`, resolved to the table name at load time, so an unknown name is a configuration error instead of a failing call). It is filled in during argument normalization. `null`, an empty and a blank `lang` count as not given. A named language, or the `language`/`interpreter` alias, always wins. Changing the schema of an existing tool means `sample/tools/native/exec.json` must be swapped together with the binary (both backends require the file to equal the code schema exactly, in both orders). The two sides of the TypeScript registry (`required`, `exampleOperation`) and the Go schema string changed with it.
- **Tolerant names.** `language`/`interpreter` for `lang`, `source`/`script`/`program` for `code`, `argv` for `args`, `workdir`/`dir` for `cwd`; numbers and booleans in `args` become strings. The named field wins.
- **Not done.** No code mode (a bridge that lets a program call the agent's other tools), which would need its own checkpoint and path-policy design. `exec` has no background mode of its own; since 2026-10-25 a call that outlasts `block_ms` becomes an async handle (see "`exec` is an async tool" below); `process` stays the tool for a server that must outlive its session, and also takes a `stdin` text. Nothing was run on Windows; `exec` starts the interpreter by name through the PATH.
- **Tests.** TypeScript `exec-tool.test.ts`, `definitions.test.ts`; Go `exec_test.go`, `native_exec` cases in `config-parity.cases.json` with a golden regenerated from the TypeScript loader; harness scenarios `exec: ...`.

## Run stream: a large final message no longer cuts the stream (TypeScript and Go together)

- **What went wrong.** `server.sse_max_buffered_bytes` (1 MiB by default) bounds what a run stream may hold for a slow client. A run whose final message is larger than half of it writes the closing `ui.message` and `completed` events in one go, so nothing drains between them. TypeScript destroyed the connection on `completed`, and Go closed the queue on the first event after an oversized snapshot, even though the client had read it. The run itself always finished and its answer is in the transcript; only the live stream was cut, and an attach to the finished run got a dropped connection (TypeScript) or an empty body (Go). It started to show with inline `stdin` and `exec` code, where a single response can carry several 100 KB arguments.
- **Terminal events are always written.** `completed`, `error` and `done` end the stream and are finite, so a backend never refuses one for budget reasons. On Go a terminal snapshot still replaces the queued events when it does not fit behind them (the client only needs the final state).
- **An oversized snapshot is not charged to the frames behind it.** A full `ui.message` larger than the budget is the one frame the protocol cannot make smaller, so it does not count against what follows. The frames behind it are still held to the budget, and a second oversized snapshot is refused while the first is still queued, so a stalled client stays bounded (about one snapshot plus the budget). TypeScript tracks this with the bytes written after the snapshot, Go with a flag that the next read clears.
- **No config key.** The budget stays `server.sse_max_buffered_bytes`; only what counts against it changed, so nothing new needed a default or a schema entry.
- **`messages.jsonl`.** Unchanged: this is the live stream, not the transcript.
- **Tests.** TypeScript `sse-writer.test.ts` (4 new or changed); Go `registry_test.go` (3 new); harness scenarios `large stream: ...` read the raw frames of the run's own connection and of a later attach.

## Interpreter `argv[0]` (Go brought in line with TypeScript)

- A script that prints `$0` saw `/bin/bash` on Go and `bash` on TypeScript: Go started the interpreter from the path it resolved through `PATH` and used that path as `argv[0]`, Node passes the configured name. `bash`, `exec` and `process` now start the resolved file with `argv[0]` set to the configured name (`newInterpreterCommand`, Unix and Windows). The command that is run is unchanged.
- **Tests.** Go `TestNativeBashKeepsTheConfiguredNameAsArgvZero`, `TestNativeProcessKeepsTheConfiguredShellNameAsArgvZero`; harness scenario `exec and bash: $0 is the configured interpreter name`. Nothing was run on Windows.

## `subagent`: a read-only child run inside a tool (Go only)

The model can hand a task to a separate agent that has a fresh context and returns only its final answer. TypeScript is frozen and has no such tool, so `tools.native.subagent` is a Go-only key and TypeScript refuses it.

- **A child is an ordinary `session.Runner.Run`, not a session and not a profile.** A profile is a fixed lane chosen in `setting.json` with a transcript that persists; a child wants a clean context on every call and nothing to create in `setting.json` while the parent runs. The child gets its own `TurnStore` under `tools.native.subagent.storage_dir` (default `.subagents`, resolved like the other tool storage), in a folder named after the parent's tool call plus a random suffix. The session's `messages.jsonl` holds only the parent's records.
- **Read-only first.** A child can use only enabled native tools marked `ReadOnly` (today `read`, `grep`, `glob`, `fetch`, `skill`), optionally narrowed by the agent's `tools` list. MCP tools are excluded because none of them is marked read-only. The `subagent` tool is never in a child's catalog, so the depth is one with no counter. A child has no checkpoint and no state context. Why it matters: the parent's checkpoint is taken only before a mutating call, so a child that wrote files would escape it. *Later changed: a child may list change tools, and nothing asks the user (see the approval removal entry).*
- **Config.** `tools.native.subagent` takes `agents` (required, by name), `result_max_bytes` (32768), `max_concurrent` (3), `wait_ms` (120000), `max_wait_ms` (600000), `keep_finished` (50), `max_queued` (32) and `storage_dir`. Each agent takes `description`, `model` (a model file, absent means the calling session's model), `instructions`, `prompt_documents`, `tools`, `max_tool_rounds` (30), `max_run_tokens` (no cap) and `timeout_ms` (600000). Unknown keys are refused with a suggestion. **A child's prompt is its own:** `instructions` first, then each file of `prompt_documents` in order, joined by a blank line, sent as one message with the session's `prompt_role`. The session's `prompt_documents` (for example `CLAUDE.md`) are not passed on, because they tell the model it can write files and use tools a read-only child does not have. Paths follow the session rule (relative to `cwd`, `~` expanded), are read when the settings load so a missing file fails the session at once, and a path listed twice is refused. The tool is off unless the key is present. The definition is `sample/tools/native/subagent.json`; the agent names and descriptions are appended to the tool description at build time. *Superseded for `wait_ms`, `max_wait_ms` and `allow_detached_writers` (2026-10-22): removed; see the async-manager subagent entry at the end.*
- **Agents can live in folders (`agents_dir`).** `tools.native.subagent.agents_dir` is a list of directories; each folder in one is an agent named after the folder (`<dir>/<name>/`). The folder holds `agent.json` (the same keys as an inline agent, schema `sample/schemes/agent.schema.json`) and/or `prompt.md`; a folder with neither is an error, and one with only `prompt.md` is an agent with defaults. The prompt is `instructions`, then `prompt.md`, then `prompt_documents`. Why: with many agents, or the same agent in two sessions, `setting.json` becomes the place where a long prompt sits inside a JSON string and each session has to copy the block; a folder is one unit that can be copied, linked or shared. Rules, each from the existing code and not new: `agents_dir` is resolved from the session's cwd (like `prompt_documents` and the MCP config paths), `~` is expanded, a missing directory is an error and not an empty list, hidden folders and plain files are skipped, a symlink to a folder counts, and everything is read when the session loads. Inside a folder, relative `model` and `prompt_documents` paths resolve from that folder so it stays self-contained. Inline `agents` keeps working and the two sources are merged (inline first, then each directory in order, folders in the order os.ReadDir lists them, which is by name); the same name twice is an error and neither wins silently. `result_max_bytes`, `max_concurrent` and `storage_dir` stay in `setting.json` because they limit a run, not an agent. Not built: a reload without a new session load, per-folder overrides of the run limits, and anything but JSON for `agent.json`. `sample/subagents/explore/` is a working example that a test loads and checks against the schema.
- **MCP tools in a child (2026-10-08).** An agent's `tools` list may also name MCP tools by ID, `mcp:<server>:<tool>` (the `mcp_servers` id and the tool name the server reports; the model-facing name ends in a hash and is not meant to be typed). Nothing from MCP is given unless it is named. **Why named and not "all read-only":** `readOnlyHint` is the server's own claim and the SDK exposes it, but this repo's servers show it cannot be trusted as a guard: betterwright clicks and submits forms, codebase-memory has `index_repository`. The child's read-only guarantee comes from its tool set, so a server's claim does not widen it; the person who writes the list vouches for each tool. **How:** the native catalog, which holds the subagent tool, is built before the MCP servers are listed, so the tool is built with a `SubagentMCP` hook and the resolver calls `Bind(mcpTools)` once the MCP tools are loaded; an agent that lists MCP tools has no catalog (and a call answers `subagent_unavailable`) until then. `Bind` fails the session load, with the loaded IDs listed, when a name is not loaded or comes from a server with `approval: ask` (removed 2026-10-23: an MCP server's `approval: ask` mark no longer exists, so no such refusal remains). A tool with `Source` other than `mcp` is never matched by an `mcp:` ID. **What it does not do:** it does not make an MCP tool safe, the checkpoint does not cover what a child's MCP tool changes (the parent only sees a `subagent` call, which is read-only), and a child's MCP calls share the parent's connection, where `callTool` already serialises calls with one mutex (`callMu`), so two simultaneous calls queue and do not interleave. MCP tools are not marked `ReadOnly`, so inside a child they run one at a time, like in the parent.
- **The agent list shrinks with its size (2026-10-08).** The list of agents sits in the tool description, which is sent on every request, so its cost is paid per request and grows with each agent. Measured from a real line (109 bytes, `code_discovery` plus its description) at about 4 bytes per token, not a tokenizer: 10 agents about 270 tokens, 100 about 2.7k, 100 with 500-character descriptions about 13k. Now `tools.native.subagent.list_max_bytes` (default 4096; 0 never lists inline; at most 1048576) bounds it in three steps: the full `name: description` lines while they fit, else the names alone, else only a count; the last two end with "Call without a task to list them with descriptions." **`task` is no longer required:** a call with no task, or a blank one, returns the list with descriptions (cut at `result_max_bytes`), starts no child and works even where children cannot run. A blank task used to be an error; it now means "list", the same rule `skill` uses for a blank name. With the defaults, 40 agents with one-line descriptions are listed in full, 100 fall back to names (about 1 KB), and 600 to a count. **Cost of the lazy tiers:** a model that sees only a count or names has to call once to read the descriptions, one extra round trip, and may guess; with few agents nothing changes. **Not measured:** how well a model picks among many agents however the list is delivered, and whether the provider caches the tool block (if it does, the standing cost is a cache read). **Other levers, already there:** point each session's `agents_dir` at the folders it needs, and keep descriptions to one line.
- **Smallest call:** `subagent({task})`. `agent` is optional when one agent is configured; a blank `agent` counts as absent.
- **Stop and timeout.** While a call still waits, the child is tied to it: stopping the parent run cancels it and the call returns only after the child has stopped (the runner records a stop, not a tool failure). `timeout_ms` is the child's whole life and ends it with the error code `subagent_timeout`; see the next bullet for what a slow child does before that. A child failure, including a provider error, reaches the parent as a tool result (`subagent_failed`, the reason cut to 400 bytes) and the parent goes on. A child that finishes without text is `subagent_empty_result`.
- **Result.** The final assistant text, cut to `result_max_bytes` on a rune boundary (with `truncated: true`), plus `agent`, `rounds` and `tokens` lines. The child's tool calls and outputs never reach the parent's context.
- **Concurrency.** The tool is `ReadOnly`, so several calls of one response may run together. `max_concurrent` bounds the children running at once, and since children outlive a call the bound is now shared by every session that uses the same `storage_dir` (the session that first creates the manager sets it). A start that cannot get a slot waits as `queued`, up to `max_queued` runs; beyond that it is refused with `subagent_busy`. This replaces the earlier per-run bound.
- **A slow child is handed off, not thrown away (2026-10-08).** A timeout used to drop everything the child had spent, and the model's natural reaction was to start the same task again from zero. Now a call waits `wait_ms` (or its own `wait_ms`, clamped to `max_wait_ms`) and then returns an ordinary `ok` result with a run id (`sub_` plus 8 hex digits) and the text "still running... do not start the task again", while the child keeps working under the manager. `subagent({id, wait_ms})` waits again and returns the answer (or the error the run ended with), `subagent({id, stop: true})` cancels it, and `subagent({})` lists the agents and the retained runs with their state. `wait_ms: 0` hands off at once. A call that is only following up and is cancelled leaves the run alone. The run is cancelled by `stop`, by `timeout_ms`, or when the resolver closes (shutdown closes the managers before MCP). The finished answer is cut to `result_max_bytes` when the run ends, and the newest `keep_finished` finished runs stay readable; a running run is never dropped. The run list keeps an 80-byte preview of each task, not the whole task. *Superseded (2026-10-22): the call takes `block_ms`, and the async tool collects, inspects and stops the run; see the entry at the end.*
- **What a handoff does not do (2026-10-08).** Nothing wakes the master when a child finishes: the answer waits until the model asks, in the same turn or a later one. Run ids survive a restart and a cut-off child returns partial work; see the entries on persisted runs and partial work. Ending the parent's run normally does not stop a handed-off child; see the next two entries for what does.
- **Runs belong to the session that started them, and a stop or reset cancels them (2026-10-08).** `ExecutionContext.SessionKey` (reference plus profile, the HTTP run registry's key) is stamped on every run. `subagent({id})`, `stop` and the run list see only the calling session's runs, so two sessions that share a `storage_dir` cannot read or stop each other's children; another session's id answers `unknown_run`. `POST .../run/stop` and `POST .../reset` now also call `SessionChildren.CancelSessionChildren` (an optional resolver interface, like `SessionProcessLocker`), which asks every queued or running child of that session to stop and returns at once; the run then ends as `stopped` and a later call by id reads that. Stop does this even when no run is active, because the handed-off child outlives the run. The response bodies of both routes are unchanged. A normal end of the parent's run still leaves its handed-off children going, on purpose: collecting them in a later turn is the point. TypeScript has no sub-agents, so there is nothing to port.
- **The subagent state-context provider (2026-10-08).** `statecontext.tools` accepts `subagent` (it needs `tools.native.subagent`). After a compaction the snapshot lists the calling session's runs: id, agent, state, the 80-byte task preview, start and end time, rounds and tokens, never the answer, which the model collects by id. `tools.native.subagent.statecontext` has `states` (default `queued`, `running`; also `done`, `failed`, `timed_out`, `stopped`) and `limit` (default 20, newest first). Over the snapshot budget the oldest item is dropped first and `omitted_by_snapshot` counts them, like the process provider. `lost` is a state it can list too. Runs are restored from their manifests after a restart (see the persisted-runs entry), so the provider lists them again.
- **Partial work when a child is cut off (2026-10-08).** A run that ends as `timed_out` or `stopped` returns the newest assistant text the child wrote in any round (the launcher keeps it from `OnResponseCommitted`), marked `partial: true`, plus the path of the child's `messages.jsonl` as `transcript:`. A search child mostly writes tool calls and its answer at the end, so the text is often empty; then only the transcript path and the counts come back, and the master can read the transcript for the tool results. The text is cut to `result_max_bytes` like an answer, with `truncated: true`. There is no forced final-summary call: it would cost another model call and change how the loop ends. The text is not an answer and the result says so only through the `partial` flag and the status, so a master that ignores both could trust it too much.
- **Persisted runs (2026-10-08).** `tools.native.subagent.persist_runs` (default true) writes one small manifest per run to `<storage_dir>/.runs/<run id>.json`, atomically (temp file, fsync, rename), at start, when the child opens its transcript, and at its end. It holds the id, owner session key, agent, 80-byte task preview, state, times, rounds, tokens, the transcript directory and whether the answer was cut. It holds no answer: after a restart the text is read once from the child's `messages.jsonl` (the final response for a `done` run, the newest non-empty text for any other). A run that was `queued` or `running` when the manifest was last written becomes `lost` on startup, with `subagent_lost` and its partial work; a graceful shutdown ends children as `stopped` first, so `lost` means a crash or kill. Startup skips a manifest that is unreadable, of another version, named differently from its id, in an unknown state or without a start time, and logs it; a transcript path outside `storage_dir` is dropped, so a manifest cannot point the reader at another file. `keep_finished` prunes manifests as well as memory, both at startup and when a run ends; it deletes a child's transcript folder only when `delete_transcripts` is on (below); by default nothing does, so those folders grow without a limit. Owner scoping is stored, so a restored run still belongs to the session that started it. The write is best effort: a failed write is logged and the run goes on. With `persist_runs` false nothing is written and a restart loses the ids, as before. Two servers sharing one `storage_dir` are coordinated only for the startup step (2026-10-09, see "Server identity in run manifests" below); the other limits there stay.
- **Optional transcript cleanup (2026-10-09).** `tools.native.subagent.delete_transcripts` (default false) deletes a child's transcript folder when `keep_finished` drops its run, in the same step that drops the manifest and also during the startup prune. It works with `persist_runs` off too. Only a folder directly under `storage_dir` is ever deleted: a run's folder one level deeper, outside the directory, or the `.runs` folder is left alone, so a bad manifest cannot aim a delete elsewhere. A run that is still going is never dropped, so its folder is never deleted. The delete runs after the manager lock is released and before the waiters wake, so a call that returns from a wait sees the disk settled. A failed delete is logged and does not stop the others. Off by default because the transcript is the record of what a child did; once on, the answer or partial work of a dropped run cannot be read back, but the run itself was already forgotten. A model that was given a transcript path in a `partial` result can lose it when the run ages out.
- **Server identity in run manifests (2026-10-09).** Every manifest records the process that last wrote it: its pid and, on Linux, its start time from `/proc/<pid>/stat` (field 22, counted from the last `)` because the command name may hold spaces and parentheses). At startup a manifest whose server is another process that is still running is left alone: it is not marked `lost`, not pruned by `keep_finished`, not loaded, and its transcript folder is not deleted. A manifest is marked `lost` as before when its server is gone, when the pid is alive but the start time differs (the pid was reused by another program), when it is this process (a manager of an earlier start), or when it has no server (written before this was recorded). `kill(pid, 0)` decides existence; "not permitted" counts as alive. Windows cannot check, so there every run found going at startup is lost, as before. Other systems compare the pid only. What this does not do: a live server does not read the other server's runs at all, so each lists only its own; `max_concurrent` and `keep_finished` count per server; the two servers' ids never clash (random), but a manifest left by a server that has since died is cleaned up by whichever server starts next. The check is the same host only, since a pid means nothing across machines or containers with separate pid spaces. A run is not re-adopted: if the first server dies after the second started, the first server's runs stay `running` on disk until some later server starts.
- **The process tool for children (2026-10-09).** An agent may list `process`, as it may list `bash` and `exec` (`allow_write`, which once gated this, was removed): it counts as a tool that changes files, so the call runs to its end and takes the checkpoint. Three rules keep a child from reaching the parent's processes. (1) **Ownership.** `ProcessStartRequest.Owner` and `ExecutionContext.ProcessOwner` carry the run id; a child's execution context sets it, and the process tool then wraps the shared manager so `list`, `status`, `wait` and `stop` see only processes that owner started. Another owner's id, and the session's own, answer `process_not_found`, exactly as an id that never existed. The owner is kept in memory on the entry and never written to the manifest the model reads. A process known only from a manifest after a restart has no owner, so a child never sees it. (2) **The run's end stops them.** When the child's launcher returns, whatever the state (done, failed, timed out, stopped), the manager stops every running process the run owns before the run is reported ended, with the stop reason `subagent_run_ended`, and the result carries `stopped_processes: N` when N is more than zero. An empty owner stops nothing, so the session's own processes are never a child's to clean up. A child that wants a server to outlive it cannot have one; the alternative, handing the process to the parent, needs a rule for who stops it and was not built. (3) **No `paths`.** A started command runs in a shell and can change any path, so `process` with `paths` is refused at load, like `bash` and `exec`. What this does not do: the capacity limit `max_running` is the session's, shared with the parent, so a child can fill it; a server crash still leaves the processes to the process manager's own restart rule (marked `lost`, not signalled); and changes made through `process` are not in `written_files`, whose empty line now says `bash, exec or process`.
- **A per-child process cap (2026-10-09).** `tools.native.subagent.process_max_running` (default 4, 1 to 1024) is the most processes one child run may have running; a start beyond it is refused with a message naming the limit. It is counted per run id under the manager's lock, together with the session's `tools.native.process.max_running`, which still caps all processes and so wins when it is lower. A child's refused start leaves nothing behind.
- **Orphans after a crash (2026-10-09).** `tools.native.process.stop_orphans` (default true). Each started process gets an `owner.json` beside its manifest (never inside it, the model reads the manifest) with the starting server's pid and start time and the process's own start time. When a later server recovers a manifest still `running`, it stops that process group (SIGTERM, then SIGKILL after `kill_grace_ms`) only if the owner record names a server that is gone and not this process, and the pid's start time equals the recorded one; otherwise it only marks it lost, as before. A stopped orphan has `stop_reason` `backend_restarted_stopped`, and only when the process is gone afterwards; otherwise the reason stays `backend_restarted`. Linux only (start times come from `/proc`); elsewhere nothing is signalled. The signal goes to the group led by the pid, so a process that leads none is never hit through a stale group id. Stopped orphans are not given back to any run: their result is `lost`, as before. Limit: the start time counts from boot, so after a reboot another process with the same pid and the same tick would match. That is very unlikely and this rule does not exclude it.
- **The process child gets bash's environment allowlist (2026-10-15).** Before this, `process` handed its child the whole server environment (minus `JAD_API_TOKEN`, the provider key variable and `env_deny`), so a variable that `bash` and `exec` could not read was readable through a managed process. `buildNativeProcessEnvironment` now keeps only `bashEnvironmentAllowlist` from the server environment (`PATH`, `HOME`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TMPDIR`, `TMP`, `TEMP`, `SYSTEMROOT`, `WINDIR`, `ComSpec`, `PATHEXT`), then adds `tools.native.process.env_file` and `env` (defaults `NO_COLOR`, `GIT_TERMINAL_PROMPT`), then removes `env_deny`, the provider key variable and `JAD_API_TOKEN`. A server that relied on an inherited variable (a proxy, `SSH_AUTH_SOCK`, a toolchain home) must name it in `env` or `env_file`. No new key; the allowlist stays one shared list.
- **A process of another running server is left alone (2026-10-09).** `Recover` used to mark every manifest it found `running` as `lost`. When `owner.json` names a server other than this one that is still running (same pid and start time, `foreignServerAlive`), the process is that server's: `Recover` now skips the manifest entirely. It is not rewritten, not loaded into the manager (so it is not listed, not counted against `max_running`, not pruned, and `stop`/`wait` answer `process_not_found`), and never signalled. The same rule already held for sub-agent runs. A manifest with no `owner.json` is still marked `lost`, since nothing says who owns it; to keep that window shut, `Start` now writes `owner.json` (without the process start time, so it is never signalled) before the manifest first says `running`, and rewrites it with the start time once the process exists. The verdict is taken once per manager: if the other server dies later, this manager does not look again, so that process stays unlisted and its manifest stays `running` on disk until a later server runs `Recover`. A manager of the same process that wrote the manifest still marks it `lost` (`foreignServerAlive` is false for itself). The TypeScript backend has no owner record and still marks every running manifest `lost`.
- **Orphans are recovered at start (2026-10-09).** Recovery of a process storage used to be lazy: the first use of the process tool in a session after a restart, so an orphan lived until then. `server.recover_processes_at_start` (root setting, default true, Go only; the TypeScript backend ignores the key) now makes `Service` start a background scan right after the resolver is built. `Resolver.RecoverProcesses` walks every session root, loads each session's settings, and for the active profile and every other path profile (a profile can keep its tools, and so its `.processes` folder, in its own `tool_storage`) takes the process storage if the session configures the process tool and that directory already exists; a session that never started a process gets no new directory. It builds the same shared manager a run uses, so the recovery is the one the first run would have done; the manager serializes recovery, so a run that starts meanwhile waits for it. Storages are deduplicated by path. A session or profile whose settings cannot be read is logged and skipped and never stops the scan; a failing recovery is counted and logged. The scan runs in a goroutine, so listening is not delayed; the context is checked before each session and each storage, `Service.Close` cancels it and waits for it to end before closing the resolver, and a recovery already going on is not interrupted (it can last the kill grace). Sub-agent run manifests are recovered by the same scan since the next entry. Limit: the scan reads one `setting.json` per session and profile at start; it was not measured on a large session set.
- **Sub-agent runs are recovered at start (2026-10-09).** A run the last server left `queued` or `running` was marked `lost` only when the session's sub-agent manager was first built, so its manifest read `running` on disk until someone touched the session. `server.recover_subagent_runs_at_start` (root setting, default true, Go only; the TypeScript backend ignores the key) adds the sub-agent storages to the start scan. `Resolver.RecoverStorages(ctx, {Processes, SubagentRuns})` replaces `RecoverProcesses` (kept as a wrapper); the two options are independent and one scan serves both, so a session is read once. For each session and path profile with `tools.native.subagent.persist_runs` on and a storage directory that already exists, the scan builds the shared sub-agent manager, which is the recovery a run would have done: interrupted runs become `lost` ("the server stopped while the run was going"), the oldest ended runs beyond `keep_finished` are dropped (with `delete_transcripts`, their folders too), and the runs of another server still alive on the directory are left alone, as before. A session with `persist_runs` off has nothing on disk and is skipped; a missing storage directory is never created. There is no child process to signal, so marking is all that can be done; a process a child's `process` tool started lies in the process storage, which the process option already stops. The scan log line is now `storage recovery at start finished` with `process_storages` and `run_storages`. Limit: building the manager at start also means the pruning and transcript deletion of `keep_finished` happen at start, not at first use, which is the point but is a visible change for a session nobody opens.
- **A sub-agent manager is built outside the resolver lock (2026-10-09).** `Resolver.sharedSubagentManager` used to build a persistent manager (read every run manifest, rewrite interrupted runs, prune beyond `keep_finished`, delete transcript folders) while holding `Resolver.mu`, which every other shared store, the process, task, memory, fetch and MCP managers, `CancelSessionChildren` and `Close` also take; the start scan made that run for every session. Measured on a synthetic directory with 2,000 manifests (1,000 interrupted, 1,000 finished, `delete_transcripts` on, 20 files per transcript folder): the build took 251 ms and another `mu` user waited 250 ms; now the build takes 359 ms and the other user waits at most 3 µs (single runs, one machine; at 400 manifests it was 50 ms and 49 ms before). The build now runs outside `mu` behind a per-directory entry (`subagentBuilds`): a second caller for the same directory waits for it and reuses the result, so a directory's recovery still runs once, and different directories build side by side. A resolver that closes during a build never publishes the manager; the builder closes it, and `Close` waits for pending builds, so no file work of a build outlives `Close`. Not changed: managers are keyed by `filepath.Clean(storage_dir)` without resolving symlinks, so two paths that alias one directory are two managers (as before, but their recoveries can now overlap), and a waiter cannot be cancelled while the builder runs.
- **Write-capable children (2026-10-09).** An agent may list `write`, `edit`, `bash`, `exec` or `process` in its `tools` (it once needed `tools.native.subagent.allow_write`, removed 2026-10-23). The tools must be enabled in the session, and their own path policy applies to the child unchanged. An agent with no `tools` list never gets them: change tools must be named. Four things follow from a child that can change files. (1) **No approval:** the child's calls run at once, like the parent's (the approval gate was removed 2026-10-23). (2) **Checkpoint:** `Tool.MayChangeFiles` is a new per-call hook; the subagent tool stays `ReadOnly` but answers true for a call that starts an agent which can change files, and `roundChangesWorkspace` (checkpoint) and `Catalog.ChangesState` (ordered scheduling) both consult it. The checkpoint is taken before the child starts, and the child's edits fall inside the parent run. (3) **Scheduling:** such a call runs in order with the other calls of its response; a response of read-only agents still runs side by side. (4) **No handoff:** the call waits for the child to end whatever `wait_ms` says, because after the parent run ends there is nobody to ask and no checkpoint to join; `timeout_ms` still bounds it. A stopped, timed-out, failed or lost writer says in its result that some changes may already be made; the run manifest stores that flag (`changes`). The agent list marks such an agent `[can change files; runs to its end]`, and the tool description says agents only read unless marked. **Per-agent `paths`:** an agent may carry `paths: {allow, deny}` (lists of paths, a relative one taken from the workspace root). It narrows where the child's `write` and `edit` may change files, on top of the session's own rules and never instead of them: the call's `tools.PathScope` adds a `Within` condition and extra deny rules to a copy of the tool's policy, so the session's deny rules and its allow list still apply, and the tool's own policy is not changed for the next call. Entries are resolved through symlinks (the part that exists), and the tools already resolve symlinks of the target, so a link inside an allowed folder cannot carry a write out of it. `paths` is refused at startup for an agent that lists `bash` or `exec` (a shell can change any path, so a list of paths cannot confine it) and for an agent that lists neither `write` nor `edit`. **Changed-files list:** the result of a writer child (finished, stopped, timed out, lost or failed) carries `written_files`: each file its native `write` or `edit` changed, once, with the first action (`created`, `updated` or `edited`), in order. A call that left the file as it was, or was refused or failed, is not listed; an empty list says `none (changes made by bash or exec are not listed)`. It comes from a per-call hook (`ExecutionContext.OnFileChange`) that `write` and `edit` call after a successful commit, so it is what the tools did, not what the model says. It is capped by `tools.native.subagent.changed_files_max` (default 100, `0` turns it off); more files are counted in `written_files_omitted`. It is kept in the run manifest as the files change, so a lost run still lists what it had changed. It is information only: restore undoes the whole parent run, and a `bash` or `exec` child's changes are not in the list (the checkpoint tree still covers them). **Not covered:** `process` is not available to a child; two children that write the same path are serialized by the shared path locks, but two that write different files are not ordered; restore still undoes the whole run, not one child (see the changed-files list below); a `bash` child can do anything the session's `bash` can. With `max_concurrent` above 1 and a response holding several writer calls, the calls run one after another (ordered), so the limit only matters across responses.
- **A writer may be handed off, behind `allow_detached_writers` (2026-10-11, requested by the user).** A call to an agent that can change files used to wait for its end whatever `wait_ms` said, so `wait_ms: 0` blocked up to the agent's `timeout_ms` (600,000 ms by default). With `tools.native.subagent.allow_detached_writers: true` (default `false`, `sessionfs/native_subagent_settings.go`, both schemas) a call that **gives** `wait_ms` hands such a run off like a read-only one: the result is `still running` with a run id, plus a note that the run can change files, that a restore may not undo what it does afterwards, and the result says so. A call with no `wait_ms` still waits, so the old behaviour is the default for the model's ordinary call. **Not covered, by choice.** The checkpoint is taken in the parent's run (`checkpoint.Run`) and its end tree is taken when that run finishes (`Service.Finish`), so what a detached writer changes later is in neither tree and a `safe` restore, which compares the two, may not undo it (a `full` restore resets to the before tree; I read this and did not run a restore). The result says so. The user accepted this. Stop and reset already end a detached writer through `CancelOwner`. **Not built:** keeping the checkpoint open while a writer runs, and a bound shorter than the agent's `timeout_ms`. **Tests:** 5 in `tools/native/subagent_write_test.go` (setting plus explicit `wait_ms` detach with no `wait_ms` still waiting, the approval cases were removed with approvals) and 1 in `sessionfs` for the key; eight mutations (ignore the setting, ignore `wait_ms`, never mark detached, refuse without stopping, refuse calls that need no approval, hand off with a question open, keep a reason on a run already stopped, never mark detached again) each broke a test. Also corrected: the `wait_ms` schema text said `0 checks without waiting`, which was false for a writer. *Superseded (2026-10-22): removed. A writer is never a handle and always runs to its end.*
- **Agents can be denied by name (T-025).** `tools.native.subagent.deny_agents` (array of agent names, default empty; `sessionfs/native_subagent_deny.go`, `sample/schemes/setting.schema.json`) removes the named agents, inline or from `agents_dir`, from `NativeSubagentSettings.Agents` right after the folders are loaded and before the `allow_write` check. They are absent from the tool description and the listing, and a launch by name answers `No agent named`; when every agent is denied (`DenyAgents` set, no agent left) the description, listing and launch error say all agents are disabled by `deny_agents` instead of how to create one. The folder of a denied agent is still parsed and validated (a malformed `agent.json` or a duplicate name is still an error); only the later steps (toolset, model and `allow_write` checks) are skipped for it. Names are matched exactly, without trimming. Each entry must be a valid agent name; an empty entry, a duplicate or a bad type is a configuration error; a name that matches no agent is ignored.
- **Refactor.** `prepareRun` was split: `providerAPIKey` and `newProviderStreamer` now build the credential and client for any loaded model, so a child with its own model file reuses them. `session.ResponseTokens` exports the existing token count. The sub-agent directory is added to the checkpoint's harness paths so a checkpoint inside the workspace does not record child transcripts as run changes.
- **Not built, and what it costs.**
  - **Usage.** A child's tokens are in its tool result only. They are not in the session usage, and not counted by the parent's `max_run_tokens`; each agent has its own `max_run_tokens`.
  - **UI.** The user sees one tool call that takes a while. No progress, no view of the child transcript. A child that ran has its transcript on disk only.
  - **Writing children.** Not allowed at that time (later allowed; see the write-capable children entry). They would need a checkpoint before the child starts and path locks.
  - **Resume.** A child that was running when the server stopped is lost; its folder stays on disk and nothing reads it again. Nothing deletes these folders either.
  - **Prompt cache.** A child's model is the one named in its file, so a child that uses the calling session's model shares no cache with the parent's conversation.
- **Verified (2026-10-08).** Unit tests with a fake launcher and an HTTP integration test with a fake provider cover: the child's tool set, its own model and instructions, a fresh context, the answer reaching the parent without the child's tool output, the separate transcript, three children in one response, a provider failure, the timeout, `max_concurrent`, a stop during a child request and a stop while waiting for a slot. Mutation checks: 23 deliberate breaks (12 in the tool, 9 in the launcher, 1 in the stop path, 1 in the checkpoint paths) were each caught by a test in the end. Two were not caught at first: a child allowed to call `subagent` (a test was added) and a timeout that was never applied (the test now has a watchdog instead of hanging). `go test ./internal/... ./cmd/...` passed (23 packages), the affected packages pass under `-race`, and `diff.mjs` reported "all 191 scenarios match". The harness cannot test this tool: it compares with TypeScript, which refuses the key. The `messages.jsonl` golden diff, done against a baseline built from HEAD with a plain read-tool run (3 scenarios, 4,089 bytes after masking batch ids, `token=` values and the temporary root), was byte-identical. This was a text-only provider stub; no real model has used the tool yet.

## `anthropic-adapter`: a Responses front for the Anthropic Messages API (new command, no change to either backend)

- **Why a separate process.** Both backends speak only the OpenAI Responses API. A Claude model is reached by a command that serves `POST /v1/responses` and calls `POST /v1/messages`, so a session only changes `base_url`. One Go implementation serves the TypeScript and the Go backend, instead of the same translation written twice. Code: `cmd/anthropic-adapter`, `internal/anthropicadapter`; config schema `sample/schemes/anthropic-adapter.schema.json`; usage in `cmd/anthropic-adapter/README.md`.
- **Stateless.** The backends send the full history every time and never use `previous_response_id`, so the adapter keeps nothing. `previous_response_id`, `conversation`, `background` and the stored-response routes answer 501. Hosted tools answer 400. A field with no Anthropic equivalent is dropped and reported in `X-Adapter-Ignored-Fields`, or rejected with `unsupported_fields: reject`.
- **Reasoning is carried in `encrypted_content`.** Anthropic requires `thinking` and `redacted_thinking` blocks, signature included, to be sent back unchanged when tools are used. A Responses `reasoning` item has no field for that, so the blocks are JSON-encoded into `encrypted_content`. Both backends store and replay that field without reading it (checked on both). The same scheme is used by LiteLLM's Responses translation. A reasoning item the adapter did not produce, or a block without a signature, is dropped, because Anthropic would reject it.
- **Model rules are data.** Which thinking parameters a model accepts (`adaptive` with `output_config.effort`, or `budget_tokens`, or none), whether it takes mid-conversation `system` messages, and what `display` defaults to differ per model and change with releases. They are in `models[]`, matched by regular expression, first match wins. `sample/anthropic-adapter.json` is the table as read from the Anthropic documentation on the day it was written. It has not been checked against the live API.
- **Thinking drops what the upstream rejects (batch 1 of the gap review).** When thinking is sent, `temperature` is omitted and `top_p` is omitted unless it is within 0.95..1 (extended-thinking docs, "Sampling parameters"); the names go into `X-Adapter-Ignored-Fields`. In `budget` mode, thinking is skipped (and `reasoning` listed as ignored) when the last assistant turn has `tool_use` but no leading thinking block, because manual mode requires one ("Turn structure in manual mode"); adaptive mode has no such rule. Usage `input_tokens_details` also carries `cache_creation_5m_tokens` and `cache_creation_1h_tokens` from `usage.cache_creation`, 0 when absent. Models that reject sampling parameters even without thinking are not handled.
- **Batch 2 of the gap review.** (1) Profile key `fixed_sampling` (default false) drops `temperature` and `top_p` whatever the thinking mode, for models the thinking page lists as rejecting them on every request; it is data like the other profile keys, and the samples set it on the profiles that match that list. (2) Function-tool `strict` goes through to `tools[].strict` (documented top-level tool property). (3) The upstream `request-id` header is returned to the client on success, stream and error responses, and an Anthropic error body's `request_id` is appended to the message (`... (request_id: req_...)`), also for in-stream error events. (4) `user` becomes `metadata.user_id` (max 512 bytes, else dropped and reported); `a profile's extra_body.metadata` replaces the whole object, since the operator's config is the more specific source. (5) `model_context_window_exceeded` maps to `incomplete_details.reason = "model_context_window_exceeded"` instead of `max_output_tokens`, so a caller does not retry with a bigger output limit. (6) Server tools stay unsupported (their output blocks are not translated); the rejection names the type. (7) Thinking between tool calls on `budget` models needs `upstream.beta: ["interleaved-thinking-2025-05-14"]`; the adapter does not set it.
- **Errors keep their meaning.** An HTTP error status from Anthropic (429, 529, 5xx) is returned unchanged with `Retry-After`, before any stream byte, so the backend's `provider_retry` still works. An `error` event after HTTP 200 cannot change the status, so it becomes `response.failed` carrying the Anthropic error type. Both backends treat that as fatal, as they do for any provider. `upstream.stream_retry` (off by default) replays a request whose first stream event is an error, before anything was sent to the backend; it never retries after output.
- **Caching is off by default and has a `history` breakpoint.** The backends append changing state context at the end of every request. Anthropic's automatic breakpoint lands on the last block, so it would sit on that text and never hit. `cache.history` marks the last block that comes from a real conversation item instead.
- **Tool schemas lose their top-level `oneOf`/`allOf`/`anyOf` (found by the first live request, 2026-10-08).** Anthropic answered 400 `tools.7.custom.input_schema: input_schema does not support oneOf, allOf, or anyOf at the top level`. The harness's `fetch` (`anyOf`: url or cursor), `task`, `memory` and `process` (`allOf` of if/then rules) use them. `strip_schema_keywords` (default those three) removes them from the top level only; nested ones, which Anthropic allows, stay. A schema without them is forwarded byte for byte so a prompt-cache prefix does not change. The rule is not lost: the harness validates every tool call against the full schema, and a call that breaks it comes back as a tool error. What is lost is the model seeing the rule in the schema; the tool description still says it. Each removal shows in `X-Adapter-Ignored-Fields` as `tools.<name>.<keyword>`. The fix was checked against the four real schemas from `internal/tools/native`; the request that failed was not replayed, so whether Anthropic now accepts the whole tool list is unconfirmed.
- **The adapter logs failed upstream calls (`log.*`).** The first live request through the subscription token ended in `429 {message:"Error", type:"rate_limit_error"}`, and nothing in the adapter or the backend could say more, because the adapter wrote no log and the caller sees only the body. The adapter now writes one `slog` line to stderr per failed upstream call: the status, the response headers on an allow-list (`request-id`, `retry-after`, `x-should-retry`, `anthropic-ratelimit-*`, `content-type`, `server`, `cf-ray`), the first `log.body_bytes` of the body on one line, and the **names** of the request headers it sent. It covers an HTTP error status, an error event in a stream, a non-stream body for a stream request, and an error body behind HTTP 200. It never logs a request header value, so the token cannot reach the log; a test checks the token, the refresh token and a custom header value against the output. A handler built without `SetLogger` discards the log, so library users and tests stay quiet; `cmd/anthropic-adapter` sets stderr. Success is not logged. Limits: it records what came back, not why; whether the 429 is a real usage limit or a refusal of a request that does not look like Claude Code is still unknown until the headers are read.
- **The subscription token needs the Claude Code system sentence (`upstream.system_prefix`, found by three live probes, 2026-10-08).** The first requests through `credential_file` got `429 {message:"Error", type:"rate_limit_error"}`, and the new failure log showed Anthropic itself answering (`request-id req_011…`, `server: cloudflare`, `x-should-retry: true`) with no `retry-after` or `anthropic-ratelimit-*` header. Adding `anthropic-beta`, `x-app` and a `claude-cli` user agent through `upstream.beta` and `upstream.extra_headers` did not change it. Three requests through the running adapter (`Say OK`, 16 output tokens, no tools): `claude-haiku-5-5` with no system prompt, 429; `claude-haiku-5-5` with the system prompt `You are Claude Code, Anthropic's official CLI for Claude.`, 200 `OK`; `claude-sonnet-5-5` with the same prompt, 200 `OK`. The pi agent's code comment ("we MUST include Claude Code identity") said so; the probe confirms it for this account. `upstream.system_prefix` sends a string as its own first system block, before the caller's instructions, so the harness's instructions are not edited and the prompt-cache marker still lands on the last block. Default empty. This claims an identity the program does not have, which Anthropic's terms may treat as a misuse of a subscription credential; the user accepted that risk for the sign-in and for this step. **Not isolated:** whether the three headers matter once the sentence is there (they stayed on in all three probes). **Not tried:** a request with tools, which pi renames to Claude Code's tool names; whether Anthropic rejects non-Claude-Code tool names is unknown.
- **A subscription token is billed as "extra usage" for a third-party app, so `system_prefix` stays but is discouraged (2026-10-08, same day).** The first real turn after `system_prefix` was set was refused: `400 invalid_request_error`, "Third-party apps now draw from your extra usage, not your plan limits. Add more at claude.ai/settings/usage and keep going.", with `anthropic-ratelimit-unified-overage-disabled-reason: org_level_disabled` and `x-should-retry: false` (request `req_011CfpM53kgq553W8xpEMDQ8`). That is Anthropic's billing rule, stated in its own words: this traffic is classified as third-party and charged to extra usage, which the organization had switched off. It is not an adapter bug, and the 429 gate found just before is a different, earlier check. **Decision.** I did not look for what makes the request look third-party and did not try to remove it: that would be hiding traffic from a billing control to charge it to the plan, and the user's terms are the user's to read. `upstream.system_prefix` is kept as a documented, off-by-default, discouraged key (the user's call): the README, the schema description and `DECISIONS.md` now say it claims an identity the program does not have and does not avoid third-party billing. The advice for Claude in this harness is an API key through `api_key_env`, which needs no other adapter setting. **Unknown:** the earlier three probes returned 200, and the later real turn (tools, long instructions, adaptive thinking, cache markers) did not; which part changed the classification was not isolated. **Unverified:** that enabling extra usage makes the request succeed, and what it would cost. `claude-auth refresh` has not been run against the real issuer. The `claude-auth` command stays as a sign-in tool; the commands and the adapter's `credential_file` are unchanged.
- **The official Anthropic Go SDK is the transport only (`d275aba`, decided 2026-10-11).** `sdk.go` builds `anthropic.NewClient` with the adapter's base URL and HTTP client, the auth header, the configured headers and timeout, and `WithMaxRetries(0)` so that `upstream.stream_retry` is the only retry. The request body is the adapter's own `anthropicRequest` JSON, set with `param.SetJSON`; the typed SDK params carry only `Model` and `MaxTokens`, which the SDK needs for its request setup and timeout. A non-streaming reply is parsed from `message.RawJSON()` into the adapter's `anthropicResponse`. A streaming reply is parsed from the raw `upstream.Body` by the adapter's own SSE parser; the SDK stream object is used for `Err()` and `Close()` only, never `Next()`, so ping events, unknown future events and the stream-retry rule are kept. Only `Messages.New` and `Messages.NewStreaming` are called. **Not chosen:** the SDK's typed `MessageNewParams` and `MessageStreamEventUnion`. That would be a rewrite of the translation and would lose the raw event handling. **Coverage stays what the Responses front can express.** Of the 20 `MessageNewParams` fields in SDK v1.80.0, the adapter sends model, max_tokens, system, messages, tools, tool_choice, stream, temperature, top_p, thinking, `output_config.effort` and `cache_control`. `top_k`, `stop_sequences`, `metadata`, `service_tier`, `container`, `inference_geo` and `diagnostics` are not sent, and tools other than `function` are refused. Content blocks in a reply other than `thinking`, `redacted_thinking`, `text` and `tool_use` are dropped without a message. Full Messages API coverage would need a second entry point (a `/v1/messages` passthrough), which is not built. **Not verified:** which headers the SDK adds on its own (`User-Agent`, `X-Stainless-*`, `anthropic-version`) and whether they change what a subscription token or `system_prefix` setup sends upstream.
- **Not built.** `pause_turn` is not continued: it is returned only for server tools, and the adapter forwards only client `function` tools. Server tools, the Files API, `tool_addition` and structured output are not mapped.
- **Verification and its limits.** 55 Go tests, with mutation checks. Both backends were run through the adapter against a fake Anthropic server (tool call, reasoning replay with its signature, an error event). Nothing ran against the real Anthropic API, and nothing on Windows.

### The adapter sends the caller's token as `Authorization: Bearer`; Claude subscription tokens are out of scope

- **Header.** `upstream.auth_header` is `bearer` (default) or `x-api-key`. Anthropic's authentication page (read 2026-10-08) documents `Authorization: Bearer <key>` for API keys and for Workload Identity Federation access tokens, and calls `x-api-key` legacy but still supported. The first adapter release sent `x-api-key` only. A caller may still send either header to the adapter.
- **Pass-through, no credential file.** The adapter forwards whatever token the backend sends from `api_key_env`. A separate tool does any exchange or refresh and puts the current token in that variable. This differs from the OpenAI OAuth mode below, where the backend reads a file, because here the adapter is a proxy and the backend already has a place to hold the token.
- **Claude subscription OAuth was first left out, then added as an opt-in (see the last section).** The Claude Code legal page (code.claude.com/docs/en/legal-and-compliance, read 2026-10-08) limits those tokens to ordinary use of Claude Code and other native Anthropic apps and says third-party developers may not route requests through subscription credentials or intermediate Claude.ai credentials. The Messages API authentication page lists API keys, Workload Identity Federation and App Attest. Whether using your own subscription in your own tool is allowed is not answered by either page. The first release stayed with documented credentials; the user later chose to build the unofficial path, as for OpenAI.
- **Not verified.** No request with a Bearer token or a WIF token reached the real API. The Bearer form follows the docs; the fake-upstream tests show only that the header is sent. The WIF exchange (`POST /v1/oauth/token`) was read in summary only and nothing implements it.

## OpenAI OAuth: the Go backend reads a credential file (credential use only)

- **Scope.** `auth_mode: "openai_oauth"` in `model.json` makes the Go backend send the same Responses request as an API-key session to a different endpoint, with the access token from a credential file. Sign-in, token refresh and status are not in the backend: a separate tool writes the file. The backend never writes it, so there is no second writer.
- **Not the TypeScript behaviour.** The TypeScript backend gets OAuth from the `openai-oauth` npm library, which refreshes tokens, rewrites the request body (`store`, `include`, `instructions`, no `max_output_tokens`) and reads a model catalog to apply per-model defaults and a "responses lite" rewrite. The Go backend does none of that: the body is untouched. The endpoint is not an official API, so the core comes first. A model that needs the lite rewrite or an `instructions` value has to get it from `request` in `model.json`; whether the service accepts the bare request has not been checked.
- **Config.** `model.json`: `auth_mode`, `oauth_auth_file` (absolute or `~/…`, default `~/.jad/auth/openai-codex.json`), and `base_url`, which means the same as in `api_key` mode: the root the Responses path is appended to. In OAuth mode an absent `base_url` is `https://chatgpt.com/backend-api/codex`; set it to put a proxy in front of the endpoint. The proxy receives the same request and credential headers (`Authorization` and `chatgpt-account-id`) the endpoint would, so it only has to forward them. `api_key_env` is kept only so `bash`, `exec` and `process` still hide that variable. `setting.json`: an `openai_oauth` node with `expiry_margin_ms` (default 300000). The endpoint was first the `openai_oauth.base_url` setting (commit `8d55299`); that key is removed because a setting is per session, while a model file is per model, and the same field meant two things depending on `auth_mode`. Schemas: `sample/schemes/model.schema.json`, `setting.schema.json`. The TypeScript config does not have the `openai_oauth` node, so there are no config-parity cases for it.
- **Credential file.** Read on every request, so a token refreshed by the other tool is used by the next request without a restart. Read: `tokens.access_token`, `tokens.account_id`, `tokens.id_token`; other keys are ignored. The account id falls back to the `chatgpt_account_id` claim (or the first organization) of the id token, then of the access token. `X-OpenAI-Fedramp: true` is sent only when a token claims a FedRAMP account. `Authorization`, `chatgpt-account-id`, `OpenAI-Beta` and `X-OpenAI-Fedramp` are replaced; the SDK's placeholder key never leaves.
- **Expired token.** A token that expires within `expiry_margin_ms` is refused before the request, with an error that names the file and the expiry time. It is checked once when a run starts and again on every request. A token without a readable expiry is sent as it is. The `exp` claim is not the whole story: on 2026-10-08 the endpoint answered `401 token_expired` for an access token whose `exp` was still 6.5 days away and which had been issued 83 hours earlier. The backend does not guess a maximum token age; the tool that refreshes the file decides when to refresh, and a 401 comes back to the client as a failed run.
- **No retry of a credential error.** An unusable file is permanent, so the retry loop (`openaiapi.isRetryableError`) skips any error that reports `Permanent() == true`. Without that, the transport error would be wrapped in a `*url.Error`, count as a network failure, and wait through every retry. An ordinary transport error is still retried.
- **The token stays out of logs.** The credential type prints as `redacted`, credential errors never quote file content, and the HTTP debug logger wraps the OAuth transport, so it records only the SDK's placeholder `Authorization` header. A test fails if the order is reversed. Tests also search every file of a session for the token, the account id and the refresh token.
- **The client sees a generic failure.** A credential error ends the run with the usual "The run failed. Response details were withheld" line; the file path and reason go to the server log. That is the existing rule for every non-provider error, not a new one. A clearer message to the client is open.
- **Verification and its limits.** Go tests for the config, the credential reader, the transport, the retry rule and runs through the HTTP API against a local server that stands in for the endpoint. Harness: all 191 scenarios still match (none exercise OAuth). Nothing has been sent to the real endpoint: whether the service accepts a request without the library's body rewrite is unconfirmed.

### `openai-auth`: the tool that writes the credential file (login, refresh, status)

- **Why a separate command.** The backend must not write the file it reads (above). `cmd/openai-auth` is the only writer, with `internal/openaiauth` as its logic. `internal/openaioauth` (the backend's reader) stays read-only and does not import it; the two share the file layout, and a test (`TestWrittenFileIsLoadableByTheBackendReader`) loads a file the writer produced with the reader.
- **Designed from the Go side, wire facts from the library.** The command structure, the file handling, the exit codes and the config are new. The OAuth wire facts are not OpenAI-documented, so they come from the source of the `openai-oauth` library (2.0.0): issuer `https://auth.openai.com`, client id `app_EMoamEEZ73f0CkXaXp7hrann`, PKCE S256, two extra authorize parameters, callback `http://localhost:1455/auth/callback`, a form-encoded code exchange and a JSON refresh. Each is a key in `sample/schemes/openai-auth.schema.json`, so a change on OpenAI's side needs no code change. OpenAI's Codex authentication page (fetched 2026-10-08) names no endpoint and no client id.
- **One writer at a time.** Every rewrite runs under an exclusive lock on `.<file>.jad-lock` (the same `sessionlock` package the session files use), and a refresh keeps the lock for the whole exchange. A rotating refresh token spent twice fails, which can invalidate the login; a test starts four refreshes at once against an issuer that rejects a reused token and shows one request in flight and four successes.
- **Atomic, private writes.** A temporary file (mode 0600 from `os.CreateTemp`), `fsync`, `rename`, then a directory sync. The backend reads the file on every request, so it sees the old file or the new one. A failed request, a response without an access token or without an account id, and a stale file that appeared during `login` write nothing.
- **Backup.** `keep_backup` (default true) keeps the previous file as `<file>.bak`, one generation, because a refresh replaces the only refresh token.
- **`login --force` does not merge tokens.** A new sign-in may be a different account, so an old refresh token, id token or account id must not survive next to a new access token; other top-level and token keys do. A plain `refresh` keeps old values the response omits (a rotated refresh token replaces the old one, and none in the response keeps the old one).
- **Exit codes.** `refresh` exits 3 when the issuer rejected the refresh token (a 4xx other than 408 and 429) or none is stored, and 1 for a 5xx, a 429 or a network error, so a timer script can tell "sign in again" from "try later". `status` exits 0, 1 or 2 (usable by claims, missing or unusable, access token expired by its claim), also with `--json`.
- **`status` reads claims only.** It makes no request and says so in its output. It cannot see what the server accepts (see the 401 note above).
- **No refresh policy in the backend.** `refresh --if-older-than 55m` is for a timer. 55 minutes is the interval `openai-oauth` uses; it was not measured against the endpoint.
- **Not built.** `clear`/`logout` (deleting the file does not revoke the tokens, so it adds little), a device-code flow (none in the library, so unverified), a background refresher, a live probe in `status`.
- **Verification and its limits.** 47 Go tests in `internal/openaiauth` and 7 in `cmd/openai-auth` (counts at the time of writing), with mutation checks: a mutant that removes the lock, the state check, the old-token reset on `--force`, the 0600 mode, the rejection-to-exit-3 mapping, the exit codes or the PKCE challenge makes a test fail. The tests use a fake issuer. **Nothing was sent to `auth.openai.com`.** `status` was run against the real credential file, and the file was byte-identical afterwards. Windows and macOS were not run.

## Claude subscription sign-in: `claude-auth` and `upstream.credential_file` (unofficial, opt-in)

- **Why it exists.** The user has a Claude subscription (Pro, Max, Team or Enterprise), not a Console account, and chose to build the same kind of unofficial path as for ChatGPT, accepting the account risk. The Console OAuth route (`ant auth login`) that Anthropic documents does not apply to a subscription. Anthropic's legal page says developers may not "collect, store, or intermediate Claude.ai credentials or session tokens" and that it may enforce this without notice; `claude-auth` stores exactly such tokens. The page does not say whether the account owner using their own tool counts. That risk is stated in the command README, the schema description and the package comment, and is the user's.
- **Scope: the core only.** `cmd/claude-auth` (`login`, `login --copy-code`, `refresh`, `status`) writes a credential file; the adapter reads it. Not built, on purpose: the Claude Code identity (a first system block "You are Claude Code, Anthropic's official CLI for Claude.", the `claude-cli/…` user agent, `x-app: cli`) and tool-name renaming that the pi agent applies. They are impersonation beyond the sign-in, and it is not known whether Anthropic requires them. `upstream.beta` and `upstream.extra_headers` can carry the headers if a response asks for them; the system block and tool names are added only then.
- **Wire facts are not Anthropic-documented.** Token URL `https://platform.claude.com/v1/oauth/token` (JSON body), client id `9d1c250a-e61b-44d9-88ed-5944d1962f5e`, six scopes, PKCE S256, authorize parameter `code=true`, loopback redirect `http://localhost:53692/callback` and a copy-code redirect `https://platform.claude.com/oauth/code/callback`, a JSON code exchange that includes `state`, and a JSON refresh. Source: the pi coding agent's `anthropic.js`; the same token URL, client id and scope string were found in the installed Claude Code 2.1.287 binary. Three authorize hosts appear in that binary; `claude.ai/oauth/authorize` is the one pi uses, and which is canonical is unknown. Every value is a config key (`sample/schemes/claude-auth.schema.json`).
- **Not the OpenAI design.** OpenAI's tokens are JWTs with `exp` claims and an account id. Claude's access tokens are opaque, so the tool computes `expires_at` from `expires_in` and stores it; a response without a positive `expires_in` is an error rather than a token with no expiry. The file layout is flat and this project's own (`version`, `access_token`, `refresh_token`, `expires_at`, `scope`, `last_refresh`); it is not Claude Code's file, which is neither read nor written.
- **Same discipline as `openai-auth`.** One writer (`claude-auth`) under a lock file, atomic private writes (file 0600, directory 0700 created before the lock helper can create it with 0755), a one-generation `.bak`, `login --force` carries no old token over, exit status 3 means "sign in again", `status` never prints a token and says it reads the stored expiry only. The adapter's reader (`internal/anthropicadapter/credential.go`) is separate and read-only, as `openaioauth` is.
- **Adapter behaviour.** `upstream.credential_file` empty (default) keeps the old pass-through. When set, the file's token is sent in the header `auth_header` chooses, the caller's credential is ignored, and an unusable file answers 401 `credential_unusable` before any upstream call, for streaming too. The file is read on every request. `upstream.expiry_margin_ms` (default 300000) refuses a token about to end. A pass-through adapter still needs the backend to send some bearer token; it is dropped.
- **`extra_body` lives on the model profile (`models[]` and `default_profile`), not under `upstream`.** Models differ in what they accept, so a global map was wrong; the matched profile alone supplies it, with no merge with another one, and `upstream.extra_body` is now an unknown key (no shim). Validation (owned fields, `cache_control` with `cache.automatic`) runs per profile and names it. The text below describes the merge, which is unchanged.
- **`extra_body` merge (formerly `upstream.extra_body`).** A map of top-level fields merged into the outbound body in `encodeRequestBody` (`sdk.go`), the single place both the streaming and non-streaming paths build their params, so retries send the same body. Values are `json.RawMessage`, so numbers and nested objects are sent as written. Fields the adapter builds from the client request are refused at load, and `cache_control` is refused together with `cache.automatic`. With no extra body the bytes are unchanged. Per-block `cache_control` with its own TTL is not covered.
- **`upstream.extra_headers`.** A new generic map, validated: names must be HTTP tokens, values must hold no line break, and the headers the adapter sets from other keys (`authorization`, `x-api-key`, `anthropic-version`, `anthropic-beta`, `content-type`, `content-length`, `host`) are refused so no header has two sources.
- **`refresh` skip rules.** `--if-older-than` (time since the last refresh) and `--if-expires-within` (time left on the stored expiry). No interval is known for Anthropic; the OpenAI endpoint rejected tokens long before their `exp`, so both rules exist and neither has a default.
- **Verification and its limits.** Go tests in `internal/claudeauth`, `cmd/claude-auth` and `internal/anthropicadapter` against a fake issuer and a fake upstream, with mutation checks: removing `state` from the exchange, the `expires_in` requirement, the refresh-token carry-over, the `--if-expires-within` comparison, the pasted-state check, the carried-over scope and refresh token, the adapter's expiry check, the credential switch, the extra headers, the reserved-header check and the error code each make a test fail. **Nothing was sent to Anthropic, platform.claude.com or claude.ai.** Whether the endpoint, client id and bodies still work, whether the Messages API accepts the token from this adapter, and whether the system block or tool names are needed are all unconfirmed. Windows and macOS were not run.

## `hosted_tools`: provider-side tool definitions in model.json (Go only)

A model file may carry `hosted_tools`, an array of tool objects the provider runs itself, for example `[{"type": "web_search"}]`. The runner appends them after the function tools in every Responses request. There is no tool code behind them: the objects are passed on unchanged, so a provider option (`search_context_size`, `allowed_domains`) needs no code here.

- **Why not `request.tools`:** `request` keeps refusing `tools`, because the function tools come from the catalog and a second source would silently replace them. `hosted_tools` is a separate list that is appended, never replaces.
- **Checks at load:** each entry must be an object with a non-empty string `type`, and `function` is refused (any case, surrounding spaces ignored). Duplicate keys inside one object are not detected: the last `type` is the one checked, and the bytes go to the provider as written. `null` or `[]` means none. The runner repeats the check, because `ModelSettings` can be built without the loader.
- **Only provider-run tools:** the runner answers `function_call` items and nothing else. A tool type that makes the provider wait for a client reply (`custom`, `local_shell`, `computer_use_preview`) is not refused, and its call item would stay unanswered in the transcript. Use the key for tools the provider completes itself, such as `web_search`.
- **Default:** none. Without the key the request is byte-identical to before; `tools` is still absent when there are no function tools either.
- **Sub-agents:** a child sends the `hosted_tools` of the model file it loads. An agent that names a `model` loads that file and sends its own list; an agent that names none loads the parent's model file and so sends the parent's `hosted_tools` too (a test covers both). A read-only child should therefore name a model file without hosted tools that can act (for example `mcp` or `code_interpreter`).
- **Edits apply on the next run:** the key is part of the runner fingerprint.
- **Not for the Anthropic adapter:** it refuses non-function tools with a 400, so the key is for OpenAI-style routes.
- **What the provider sends back:** items such as `web_search_call` and `url_citation` annotations are stored in `messages.jsonl` as they arrive and replayed as input on the next turn. A test shows the round trip against a fake provider; against a real one it is untested.
- **What the Web UI shows (Go only, `internal/webui`; generic, no tool is named in the code):** any response output item that is not `message`, `reasoning`, `function_call` or `function_call_output`, and has an `id` and a `type`, is a provider-hosted tool. It becomes one part `{type: "hosted_tool", callId, name, status?, target?, raw?, truncated?}`: `callId` is the item id, `name` is the item type without a trailing `_call` (`web_search_call` -> `web_search`; `openrouter:web_fetch` stays as it is), `status` is the provider's state, `target` is the first non-empty of `action.query`, `action.queries` joined by `; `, `action.url`, `action.pattern`, `url`, `query`, `title`, and `raw` is the whole item as JSON. A provider tool added later needs no Go or frontend change. A fetch item carries the whole page in `content` (54 KB measured), so `raw` is capped: the longest string values are shortened until the JSON fits `server.max_inline_part_bytes` (default 16384; `0` sends it uncut), the result stays valid JSON, and `truncated.bytes` reports the full size so the frontend's `Load full` loads the whole message. The cap applies to snapshots (`CapMessages`) and to the live stream (`StreamingRun.SetHostedRawLimit`, set by the run executor), so a page is never sent whole in an SSE event. A hosted tool is not a tool step: it never sets a step's `hasTools`. Live (`response.output_item.added/done`) and from the stored transcript the parts are the same; a later, sparser event never erases fields already known (the fuller `raw` is kept). The `url_citation` annotations of an `output_text` item become `citations: [{url, title?}]` on the text part, in order, one entry per URL; other annotation types and entries without a URL are dropped; several `output_text` items of one message merge into one text part with their sources merged. Messages without a hosted tool or annotations serialize exactly as before (`omitempty`). The transcript is only read, never changed. The frontend shows one row per hosted tool (name and target; a `status` ending in `ing`, or `in_progress` or `queued`, is running; `failed`, `incomplete`, `error` or `cancelled` is an error; anything else is complete) and expanding it shows `raw` in a code block like other tools. Sources are a numbered list of links (http and https only; other schemes stay plain text). An older frontend drops a message that carries a part type it does not know, so the frontend must be updated together with the backend. **Limits:** any unhandled item with an id gets a row, including types the client would have to answer (`local_shell_call`, `custom_tool_call`, `computer_call`); `hosted_tools` is meant for tools the provider completes itself. `target` and `status` are not capped. This replaces the `web_search` part of the first version (commit 770c69a), which is gone.
- **TypeScript Web UI:** it knows neither part nor field and drops `web_search_call` and annotations. Hosted tools are Go only, so no run of the frozen backend produces them.
- **Known limit:** with the ChatGPT Codex route (`auth_mode: openai_oauth`), a request with `{"type": "web_search"}` ran the search and then ended with `server_error` in every probe on 2026-10-09 (four models), so the key does not give an answer there today. `mode` is not accepted on that route (HTTP 400).
- **TypeScript:** frozen. It ignores the key; a Go-only feature is not a gap.

## `hooks`: optional checks after `write` and `edit` (Go only)

`hooks` in `setting.json` runs a configured command after the native `write` or `edit` changed a file and appends its outcome to that tool's result, so the model sees a type error in the same round. It is off by default (`enabled` false or no key): then no command starts and the tool result is byte-identical to before. The TypeScript backend does not read the key; this is a Go-only feature and not a gap.

- **Shape.** `hooks.post_edit` is an ordered list of `{name, ext, argv, cwd, on_failure_only}`. Every entry whose extension matches the changed file (case-insensitive) runs, in order. `argv` is run directly with no shell; `{file}`, `{dir}`, `{rel}` and `{reldir}` are replaced in every argument after the program. `cwd` is `file_dir` (default), `workspace` or `nearest:<marker>`, the closest directory from the file up to the workspace root that holds the marker (for example `nearest:go.mod`); with no such directory the check is skipped and the result says so. There is no built-in table: the right check depends on the project, so `sample/hooks.json` only shows examples.
- **The result.** A check adds a content block `post-edit checks for <file>` with one section per check: `[name] passed|failed, exit N (ms, in dir)` and its output. The write or edit keeps its own status: a failing, timed-out or missing check never fails or undoes the call. A check that did not start names `hooks.post_edit[name].argv`; a timeout names `hooks.timeout_ms`; a cut output names `hooks.max_output_bytes`.
- **When it runs.** Only after a call that changed a file (the same moment `OnFileChange` is told). A failed call, a rejected path, an unchanged file and a `bash` or `exec` call run nothing. The wrapper sits around the tool in the catalog, so `write.go` and `edit.go` are unchanged.
- **Runner and limits.** It reuses bash's child runner and the shared environment allowlist, but the child-process settings are the hooks' own keys (`kill_grace_ms`, `kill_deadline_ms`, `drain_after_exit_ms`, `kill_process_group`, `max_line_chars`, `strip_ansi`, `env_file`, `env`, `env_deny`; same meaning and defaults as bash's). Nothing is read from `tools.native.bash`, so `hooks` needs no other tool (it used to be a configuration error without `bash`). The layout default `env_file` does not apply to hooks: name `hooks.env_file` to give checks the same environment file as bash. Its own keys are `timeout_ms` (default 60000, 1000 to 600000) and `max_output_bytes` (default 8192, 256 to 1048576; the start and the end are kept). Output is not spilled to a file.
- **Approval and sub-agents.** The command is part of `setting.json`, the user's own configuration, so a check runs as the user's own configuration. Write-capable sub-agents use the same tools, so a check runs for them too, on the files their `paths` allow (the write is refused first, so no check runs for a refused path). A check runs under the session's settings, not the agent's.
- **Tool events: `pre_tool` and `post_tool` (Go only).** Two more lists next to `post_edit`: `{name, match, argv, on_failure_only}`. A command runs before (`pre_tool`) or after (`post_tool`) any call of a tool its `match` covers. `match` takes the same entries as a profile's `tools.allow` (`*`, a native tool name, `mcp:<server>:<tool>`, `mcp:<server>:*`; default `*`), through `tools.EntryMatches`. There are no placeholders: the command reads the event as JSON on stdin (`event`, `tool`, `tool_id`, `call_id`, `agent`, `workspace_root`, `arguments`; `post_tool` adds `status` and `result`). `hooks.max_payload_bytes` (default 65536, 1024 to 1048576) bounds it: arguments over half of it are replaced by `arguments_omitted`, and the result is cut to what is left with `result_cut`, measured on the encoded JSON. A command runs in the workspace root under the hooks' own child-process keys, with the same `timeout_ms` and `max_output_bytes`.
- **Tool events report; only an opt-in `pre_tool` entry blocks.** A command cannot change the call or its status unless it is a `pre_tool` entry with `blocking: true` (decided 2026-10-14, see the next entry). The report (`pre-tool hooks for <tool>`, `post-tool hooks for <tool>`) is appended to the call's own result: as a content block for a native tool, and as one more `input_text` part for an MCP tool. An output that is not a list of parts is left untouched. A call whose Go `Execute` returns an error runs no `post_tool` command, and a `pre_tool` report is lost with it (the catalog replaces the output with a generic failure); a tool result with status `error` is a normal result, so `post_tool` still runs and sees `status: "error"`. A command is not isolated from a panic of the runner, which is the same as for `post_edit`. `post_tool` sees the result before the report is added.
- **Where they attach.** `WithToolEventHooks` wraps every native tool when `buildNativeTools` returns, the sub-agent tool and the session's and toolsets' MCP tools, covering `Execute` and `ExecuteOutput` alike. A sub-agent reuses the parent's wrapped tools, so its calls fire the events with `agent` set to the agent's name (`ExecutionContext.AgentName`); an agent that names a `toolset` uses that toolset's own `hooks`. With `enabled` false or no event list nothing is wrapped and every result is byte-identical.
- **Run events: `run_start` and `run_end` (Go only, decided 2026-10-14).** Two more lists, `{name, argv, on_failure_only}` with no `match` because there is no tool; at most 32 each. `run_start` runs once per run in `boundRunner.Run`, after the tools are prepared and the state context is built and before the first provider request; `run_end` runs once when the run returns, with `outcome` `ok`, `error` or `cancelled` (a context cancelled run) and, for an error, the error text cut to half of `max_payload_bytes` (`error_cut`). Stdin is `{event, session, profile, turn_id, workspace_root}` plus `outcome`, `error` for `run_end`. They share the hooks' child-process keys, `timeout_ms` and `max_output_bytes`, and run synchronously in the workspace root, so a `run_end` command delays the end of the run by the time it takes. A run that fails during setup (before `run_start`) fires neither. **Where the output goes:** the server log only (`hook run_start` / `hook run_end` at info level, one line per command that has a report); it is not shown to the model and never written to `messages.jsonl`, so the transcript contract is untouched. `run_end` runs on `context.WithoutCancel` of the run's context, so a stopped run still reports. They fire for a session's own runs only: a sub-agent child runs through `session.Runner` directly and fires neither (pinned by `TestRunHooksDoNotFireForSubAgentRuns`). A run hook never changes the run. `pre_compact` and the live notification are in the next entries.
- **Blocking `pre_tool` (decided 2026-10-14).** A `pre_tool` entry may set `blocking: true` (default false; `post_tool`, `run_start`, `run_end` and `pre_compact` reject the key). A blocking command that does not exit 0 (non-zero exit, signal, timeout, could not start, stopped) stops the call: the tool is not run, the later `pre_tool` commands do not start, no `post_tool` command runs, and the model gets a `status: "blocked"` result with `error_code: blocked_by_hook`, `tool`, `hook` and the report as its content, the same envelope an unapproved call gets. The check sits in `WithToolEventHooks`, which wraps the tool inside the catalog. It does not replace `tools.allow/deny`, which stops a call earlier. A non-blocking entry still never changes the call. The blocked result is a new shape in `messages.jsonl` for a run that uses the key; nothing changes for a session that does not. Tests: `hooks_blocking_test.go`, `TestBlockingPreToolHookStopsAChildWriteAndTheModelSeesWhy`.
- **`pre_compact` (decided 2026-10-14).** Same entry shape as `run_start` (`{name, argv, on_failure_only}`, at most 32). It runs before each compaction attempt of the session: an automatic one inside a run (payload carries the run's `turn_id`, `trigger: "automatic"`) and a manual one from the compact request (`trigger: "manual"`, no turn). Stdin is `{event, session, profile, trigger, turn_id?, workspace_root}`; there are no counts or message content, so a command cannot learn what is in the transcript from it. It cannot veto, delay the decision of, or change the compaction, and it runs even when the compaction finds nothing to compact. Its output goes to the server log only. A command delays the compaction by up to `timeout_ms`. A manual compaction holds the session's run lock while it runs.
- **Run-hook reports reach the UI live, never stored (decided 2026-10-14).** `run_start`, `run_end` and an automatic `pre_compact` report are also sent as a `hook_report` event on the run's SSE stream (`{turn_id, event, trigger, report}`), through `session.RunOptions.OnHookReport`. The frontend shows each as a Notifications entry (an error for a failed, timed out or unstartable command). Nothing is stored: they are lost on reload, a client that attaches mid-run does not see earlier ones (the event is not replayed), and the transcript contract is untouched. A manual `pre_compact` has no run stream, so it is log-only.
- **Where `hooks` is set.** A toolset file may carry `hooks` (same shape as the settings key; the schema references it), and so may the settings (defaults, session or profile). Setting it in both is a config error naming the toolset file: one place must not silently override the other (decided 2026-10-14; the toolset is the home, the settings key stays until the legacy loader is gone). A toolset that a sub-agent names is composed on its own, so its `hooks` apply to that child's tools and only there; the settings' `hooks` do not leak into it, and it is a config error if both exist when that toolset is composed. Hooks need no `tools.native.bash`: the toolset is only where the key is read from.
- **Checks that rewrite files.** A formatter may change the file after the write. The result then says `the check changed the file, read it again before the next edit`, also for a passing `on_failure_only` check. Such a rewrite happens inside a call the checkpoint already counts as a change.
- **Limits.** A check runs after the call released its path lock, so it blocks no other tool, but another write to the same file can land while it runs: the check then sees that newer content, and the `the check changed the file` note can be a false alarm. Under the default `tool_call_scheduling: "ordered"` calls that change files run one after the other, so neither happens; under `concurrent` several checks can run at once. A whole-project check (`tsc`, `go vet`) costs its run time on every edit; `timeout_ms` bounds it. No check sees the files the model has not yet written, so a check may fail because the next edit is still to come. A stop of the run cancels a running check (it is terminated like a `bash` command, after `tools.native.bash.kill_grace_ms`) and the result says `stopped before it finished`.
- **Paths.** The file is the one the tool reported: a symlink inside the workspace is resolved, so the extension, `{file}` and `nearest:` use the target's location. A file outside the workspace that a path rule allows is checked with `file_dir` or `workspace`; `nearest:` finds nothing for it and the result says so.
- **Output cap.** `max_output_bytes` applies to stdout and stderr each (start and end kept), so a check that writes to both can add up to twice that.
- **Not covered.** `bash`, `exec`, `process` and MCP tools change files without naming them, so they have no hook. There is no run-end hook and no hook before a call.

## `decide`: typed questions to a hosted classifier (Go only)

**Category (decided 2026-10-16, user request).** `decide` is an *extension* tool, not a native one: it is configured under `tools.extension.decide` (a toolset file's `extension` object), its definition file is `sample/tools/extension/decide.json` (ID `extension.decide`, `source: "extension"`), and its code is `internal/tools/extension`. The model-facing name stays `decide`, so a profile's `tools.allow`/`deny`, a sub-agent's `tools` and stored transcripts are unchanged. Extension tools are the ones that call a provider API (web search, a fetch API, image and sound APIs are planned); `fetch` stays native because it reads a URL itself. A new extension tool is one file under `tools/extension`, one `sessionfs/extension_<name>_settings.go`, a name in `extensionToolNames` and one branch in `buildNativeTools`. **Hard rename, no alias:** `tools.native.decide` is now an unknown key, `native.decide` in `tool_definition_paths` no longer loads, and a settings or toolset file must be edited by hand. For every consumer of the tool source, `extension` behaves as `native` did for `decide`: profile `allow`/`deny` entries, sub-agent tool pools, `tool_smith` scripts and the `applies_to: ["native"]` image resize all still cover it (the resizer is given the source `native` by `decide` itself). `decide` file reading is supplied by the native catalog (`DecideImages.ReadFile`), so the path rules stay in one place and the extension package never imports `native`.

`decide` lets the model ask a fast classifier typed questions about a text: a `predicate` (probability 0 to 1 that a condition holds), a `choice` (the best of the given options, with confidence and the probability of each) or a `score` (a rating against ordered levels, as a probability-weighted index). The classifier returns no free text and runs no tools, so it is not a chat model and cannot be a sub-agent's model; a sub-agent uses the tool like any other. It is off unless `tools.native.decide` is present. The TypeScript backend ignores the key; a Go-only feature is not a gap. Skill `decisions-api` (`.jad/prompts/skills/`) tells a model when to use it and how to write the questions.

- **Two backends, one tool.** `backend` is `openrouter` (default; OpenRouter's alpha `POST /api/alpha/decisions`, model `openai/gpt-6-luna-decisions`) or `openai` (`POST /v1/decisions`, model `gpt-6-luna`). The shapes differ (OpenRouter calls a predicate `noul`, takes `state` and a map of questions, and gives `choice` options and `score` levels as `criteria`; OpenAI takes `input` and an array with `choices` and `levels`), so the tool translates both ways and the model sees one schema. `base_url`, `api_key_env` and `model` default per backend and can be set. A level or choice description is sent as OpenRouter's criterion text (a level as `label: description`, since that endpoint has no separate label).
- **Credentials.** The key is read on each call from the process environment variable named by `api_key_env` (`OPENROUTER_API_KEY` or `OPENAI_API_KEY`), not from the model file: the session's own model may be a chat route, or the ChatGPT OAuth route, which is not known to serve this endpoint. A missing variable gives `api_key_missing` and no request. The key is never written into a result or a log line by the tool; an error shows the provider's message cut to 400 bytes on one line. A redirect is never followed, so the key cannot be sent to another host.
- **Arguments.** `input` is an array of parts, in order: a string or `{type:"text",text}`, or `{type:"json",value}` for structured data (any JSON value except null). A bare string or a single part is accepted and wrapped, so the common call stays small, but the schema the model sees is an array, so image parts can be added later without changing its shape. Images are not supported yet. A blank text and a null JSON value are refused before any request. `max_input_bytes` counts the text plus each JSON value as sent (compact). The parts reach the providers as: all text, one string (parts joined by a blank line); otherwise OpenAI gets one user message of `input_text` parts (a JSON value as its compact text, because that endpoint takes only text and image parts), and OpenRouter gets `state` as a list with a text as a string and a JSON value as itself (the endpoint reads "a plain string, or a JSON object or array of related context"). And `questions` (each `instructions`, and optionally `name`, `type`, `choices`, `levels`). `name` defaults to `q1`, `q2`, ...; `type` is inferred (`choices` gives choice, `levels` gives score, otherwise predicate); `noul`, `boolean` and any letter case are accepted for a predicate. A choice or score with fewer than two options, a duplicate name or option, `choices` on a score, or `levels` on a choice is refused before any request.
- **Result.** One compact JSON line: `{"answers":[{"name","type","probability"|"choice"|"score","level","confidence","probabilities"}]}`, in question order, numbers rounded to four decimals. `level` is the label nearest to `score`. A question the provider refused is `"status":"refused"`, one it did not answer is `"status":"missing"`, and one it answered with the wrong type or a choice without a value is `"status":"unusable"`; none carries a number, so a gap is never read as a probability of 0.
- **Limits (all in config).** `timeout_ms` 30000, `max_questions` 16, `max_input_bytes` 200000 (text and JSON only), `max_response_bytes` 1048576, `max_images` 8, `max_image_bytes` 5242880, and `paths` (the rules for an image given by path; its own, not `read`'s); the first two are checked before the request. Not set up for retries: a failed call is reported (`unauthorized`, `rate_limited`, `request_rejected`, `provider_error`, `timeout`, `cancelled`, `bad_response`) and the model decides.
- **Scheduling, approval, sub-agents.** The tool is read-only (it changes nothing local, so it runs beside other read-only calls); a call costs a small amount (OpenAI lists $0.10 per 1M input tokens for `gpt-6-luna`, no output charge) and sends the input text to the provider. A sub-agent gets it by listing `decide` in its `tools`, or with no `tools` list, since every enabled read-only tool is included then. It needs `decide.json` in `tool_definition_paths`, like every native tool.
- **Status of the providers.** The OpenAI endpoint is in public beta and OpenRouter's is marked alpha, so both shapes may change. The OpenRouter shape was checked against the live endpoint on 2026-10-09 (predicate, choice and score answered, one clear false case returned 0); the OpenAI shape was built from OpenAI's documentation and the `openai-go` v3.74 types and tested against a fake server only, with no key available to call it.
- **Images.** An input part `{"type":"image","path":...}` or `{"type":"image","data":...}` (exactly one of the two) adds a png, jpeg, webp or gif. `path` is read under the same path policy as `read` (`tools.native.read.paths`; without `read` the workspace only, symlinks resolved and a deny rule checked on the real path), or is a `stored-image://<name>` reference read from the image store. `data` is base64 or a data URL. The type comes from the bytes (`http.DetectContentType`), never from a file name. `max_images` (default 8, at most 64) and `max_image_bytes` (default 5 MiB) are config keys; the byte limit applies to what is read, before `image_resize`, and a file is read one byte past the limit and no further. A base64 string is judged by its length before it is decoded. If `image_resize` is on and its `applies_to` has `native`, the image is resized like any native tool image (no new `applies_to` value). OpenAI gets one user message of `input_text` and `input_image` parts; OpenRouter gets `state` as a list in which an image is `{"type":"image_url","image_url":{"url":"data:..."}}`. That OpenRouter shape was checked on the live alpha endpoint on 2026-10-09 with a red and a blue 64x64 png (the blue one was found by "mostly blue" at 1 and "mostly red" at 0, two images together gave 0.07 and 0.48, a text-only prefix and a JSON part next to the image worked, and invalid image data was refused with HTTP 400). The OpenAI shape follows OpenAI's guide and has not been called live. A `messages.jsonl` call holds whatever path or base64 the model wrote; `path` is the cheaper form, since base64 is output tokens.
- **Not covered.** OpenRouter's `provider`, `session_id` and `trace` fields, and `safety_identifier`; an http(s) image URL (only files, stored references and inline data).

## `image_resize`: shrink images between the transcript and the provider (Go only)

- **What it is.** A `setting.json` node, `image_resize`, off by default. The runner builds each provider request from the stored history; with the setting on, `internal/imageresize` rewrites the image parts of that copy first: request -> image_resize -> provider. `messages.jsonl` keeps the original image, so the golden contract and a later change of the limits are untouched. The TypeScript backend does not read the key.
- **Which images.** `applies_to` lists the sources: `mcp` (a tool result of an MCP server, the default and the only one the first version was asked for), `native` (a tool result of a native tool) and `user` (a user message). The source of a tool result is found from the `function_call` with the same `call_id` through `Catalog.SourceOf`; an output whose call is not in the history (a compacted-away call) is not resized, because its source is unknown. An empty list resizes nothing.
- **What is resized.** Only `input_image` parts whose `image_url` is a base64 data URL of png, jpeg or webp (webp can be read, not written). An http URL or file id has no bytes here, a gif may be animated, and anything else has no decoder; those pass through. An image with more than `max_pixels` pixels is not opened (decompression-bomb guard). An image that fits `max_edge_px` and `max_bytes` is sent as it is.
- **Result format.** Transparency stays a png. An opaque image stays a png while the png is no larger than the original; scaling blends flat edges, so a scaled screenshot can be larger as a png than the original was, and then a jpeg is sent (from `jpeg_quality` down to 40 in steps of 15), and when nothing fits `max_bytes` the image is shrunk by 25% up to 4 times. If nothing fits, or an image that did not need scaling does not get smaller, the original is kept.
- **Bytes versus pixels.** The goal is fewer pixels (a provider charges and limits by dimensions), not always fewer bytes. Measured once: a synthetic flat 2880x1800 screenshot of 410 KB (data URL) became a 514 KB jpeg at 1568 px, so the payload grew by 25% while the pixels fell by 70%; at `max_edge_px` 800 it became 137 KB. A test shows the jpeg is chosen over a scaled png that grew past the original, but nothing guarantees the result is smaller than the original in bytes. Set `max_bytes` below the original size to force that.
- **EXIF orientation.** The Go decoder ignores it and re-encoding drops it, so a turned jpeg is rotated upright in the pixels, and a turned jpeg that otherwise fits is still rewritten.
- **Cache.** Results are remembered by the sha256 of the data URL, per run, bounded by `cache_entries` (oldest out). A history is walked every round, so this keeps it to one resize per image and makes every round send identical bytes, which keeps the provider's prompt cache valid. An image that stays as it is is remembered too.
- **Where it runs.** `RunOptions.ImageResizer`, set by the resolver for a run and by the sub-agent launcher for a child from the parent's setting, so a child that calls an MCP tool is covered too. `request-built` in the memory trace records `images_resized` and `image_bytes_saved`.
- **Cost.** The first sight of a large image costs decode, scale and encode (measured once: 0.4 to 0.7 s for a 2880x1800 image on this machine); the memoised round costs about 4 ms. `golang.org/x/image` (webp decoding, CatmullRom scaling) is a new dependency.
- **Not done.** No resize of http URLs or file ids, no gif, no tiling or per-model token budget, no resize of images inside `reasoning` or hosted-tool items, and no limit on the number of images per request.

The TypeScript backend (`backend/`), the differential harness (`backend-go/tools/differential`) and the golden generator (`internal/sessionfs/testdata/gen-config-parity.mjs`) were removed in one commit. Git tag `legacy-final` is the last commit that has them. ## `image_store`: keep large tool-result images out of `messages.jsonl` (Go only)

- **What it is.** A `setting.json` node, `image_store`, off unless `dir` is set. A tool result (MCP or native) that carries a png, jpeg, webp or gif as a base64 data URL is written once to `dir` as `<sha256>.<ext>`, and the transcript keeps `stored-image://<sha256>.<ext>` in the `image_url` field. With no `dir` the transcript is byte-identical to before (checked: same scenario on the parent commit and on the working tree, 12,108 bytes each, identical after masking the batch ids). The TypeScript backend does not read the key.
- **Limits (all keys, with defaults).** `min_bytes` 16 KiB: a smaller decoded image stays inline. `max_file_bytes` 20 MiB: a larger one stays inline. `max_total_bytes` 1 GiB: when the directory holds this much, new images stay inline (a known file is still referenced). The loader refuses `min_bytes > max_file_bytes` and `max_file_bytes > max_total_bytes`. Other types (svg, tiff) stay inline, and so does an image whose first bytes do not match its declared type.
- **Where it runs.** `RunOptions.ImageStore`, set for a run by the resolver and for a sub-agent child by the launcher. Tool outputs are externalised just before `appendToolOutputs`; the live stream and the tool result the model gets in the same round are the original. Every provider request is built from the history after the references are replaced by data URLs again, and before `image_resize`, so the resize step sees real bytes and the model sees the same image. `request-built` in the memory trace records `images_restored` and `images_missing`.
- **Missing or damaged file.** The part becomes `{"type":"input_text","text":"[stored image unavailable]"}`; the run does not fail. Measured on a temp server: with one of two files deleted, the model still answered about the other.
- **Read route.** `GET /api/sessions/{session}/images/{name}`, behind the API token. `{name}` must be 64 lowercase hex digits plus `.png|.jpg|.webp|.gif`; it is never joined from anything else. `Open` refuses a symlink (Lstat and SameFile), a non-regular file, a file over `max_file_bytes` and content whose type does not match the name. The answer has `nosniff`, `Content-Security-Policy: sandbox` and an immutable one-year cache, because a name is the hash of its bytes. 404 when the store is off.
- **No cleanup.** The server never deletes a file. One file can serve several messages, and reset, compaction and front compaction rewrite the transcript without knowing the references. `max_total_bytes` bounds the growth. Deleting the directory is safe for the server (see above) and loses the images.
- **Not done.** User-message images are not stored. A transcript copied to another machine without its `images` directory shows `[stored image unavailable]` for those images. The Web UI shows stored images of tool results and of hosted tools (see below).

- **Generated images (provider-hosted tools, step C).** The same store keeps what a provider generates. Before any other code sees a `response.output_item.done` or `response.completed` event, the runner (`externalizeEventImages`, `runner_response.go`) passes the item through `Store.ExternalizeItem`. An item whose type is not `message`, `reasoning` or `function_call` has every string value rewritten, under any key, when it is a `data:image/...;base64,` URL or a bare base64 string that starts like a png, jpeg, webp or gif (`iVBORw0KGgo`, `/9j/`, `UklGR`, `R0lGOD`) and passes the same checks as a tool image (size limits, type sniffing, base64). A data URL becomes `stored-image://<name>`; a bare base64 string becomes `stored-image-b64://<name>`, so the original form comes back. No tool name is listed: OpenRouter's `openrouter:image_generation` and OpenAI's `image_generation_call` take the same path. The stream, the staged item and `messages.jsonl` all carry the reference. `Rehydrate` restores both forms before every provider request, but only in items that are not message, reasoning or function-call items, so text that quotes a reference is never rewritten. A missing file becomes a one-pixel PNG in the original form; the run does not fail. Measured on a temp server with OpenRouter `openai/gpt-6-luna` and `{type:image_generation}`: a 1,302,922-byte 1024x1024 PNG was written once, `messages.jsonl` held 1,268 bytes for the turn, the largest SSE line was 777 bytes, the route returned the same bytes (`cmp`), and a later turn went through with the full image in the request body (3,475,945 bytes, two copies) and the model answered "Red" and "Yes" about it. With no `image_store.dir` the item stays inline, as before (tested). Partial images (`partial_image` events) are not stored; they are only stream events.
- **Web UI.** A `tool_result` part and a `hosted_tool` part carry `images`, the stored file names found in them (read before the raw JSON is capped). The row shows a thumbnail, the lightbox opens it, and an unreadable file shows "Image unavailable".

## User images in a run request (Go only)

- **Request.** `POST /api/sessions/{s}/run` takes `input` as before (a non-empty string) or an array of parts: `{"type":"text","text":...}` and `{"type":"image","data":<base64 or data URL>}`. The server builds one Responses user message from them (`input_text`, and `input_image` with `detail: auto`). A string input is stored exactly as before (checked: the same two-turn scenario on the parent commit and on the working tree gave a 895-byte `messages.jsonl` each, identical after masking batch ids, timestamps and response ids). The TypeScript backend takes only a string and ignores the new keys.
- **No path, no URL over HTTP.** An image part has `type` and `data` only; any other field is refused with 400 (`unknown field "path"`), so a remote client cannot make the server read a file or fetch a URL. `decide` keeps its `path` form because there the model, inside the workspace policy, asks for it.
- **Checks.** The data is decoded (`internal/imagedata`, shared with `decide`) and its type is judged by its first bytes: png, jpeg, webp or gif; the declared data-URL type is ignored and the stored URL carries the real one. A bad request is a 400 and writes nothing to `messages.jsonl` and sends nothing to the provider (tested). An image over the byte limit is 413.
- **Limits (keys, with defaults).** `server.max_request_images` 8 (0..16; 0 refuses image input) and `server.max_request_image_bytes` 5 MiB (1..25 MiB, decoded). The maximums are low on purpose, for the reason given under the file limits below: 16 x 25 MiB is about 0.5 GiB of base64 on top of the body limit (they were 64 and 64 MiB, about 5.3 GiB). Both are in the schema, the loader tests and `request_images_settings_test.go`.
- **Body limit.** `server.max_body_bytes` (1 MiB) still bounds every route. The run route's reader allows the image data on top of it (`max_request_images` x base64 size of `max_request_image_bytes`), and after parsing the rest of the body (everything but the `data` strings) must still fit in `max_body_bytes`, so a long text is refused exactly as before even next to an image. The differential scenario "run rejects oversized body" caught a first version that let a long text through inside the allowance; a test now covers it.
- **Store and resize.** With `image_store.dir` set, the user's image is written to the store before the message is appended and the transcript keeps `stored-image://`; the next provider request rehydrates it. Without a store the data URL stays inline in `messages.jsonl`. `image_resize` handles the user's image only when `applies_to` lists `user` (default stays `["mcp"]`); the transcript keeps the original.
- **Web UI projection (Go only).** A user message with an image and no text is now visible: its text is `[image]` per image, its text part carries `images` (stored file names; an inline data URL is never sent to the browser). The TypeScript projection hides such a message (`isVisibleUserInput` needs `input_text`); two Go tests that pinned the old rule were changed. This is an intended difference.
- **Not done.** Images by http URL; the Anthropic adapter was not changed (it already maps `input_image`).

## User files (PDF) in a run request (Go only)

- **Request.** The `input` array also takes `{"type":"file","name":<file name>,"data":<base64 or data URL>}`. The server stores it in the same user message as `{"type":"input_file","filename":<name>,"file_data":"data:application/pdf;base64,..."}`, the Responses shape, so the provider gets it as sent. Only these three fields are accepted (`unknown field "path"` is a 400, as for images). `name` is cleaned: last path element (also for `\`), control characters removed, 255 runes at most, empty refused (400). A string input and an image-only array are stored exactly as before (checked: a three-turn scenario, string, text with image, string, gave a 1,337-byte `messages.jsonl` on the parent commit and on the working tree, identical after masking the random batch ids).
- **PDF only.** The type is judged by the first bytes (`%PDF-`); a declared type or a `.pdf` name does not count, a PNG named `.pdf` is a 400, and a data URL declaring another type is stored as `application/pdf`. Other types (text, Office, zip) are refused for now: which provider accepts `input_file` for which type was not tested, and the Anthropic adapter already refuses types it cannot map.
- **Limits.** `server.max_request_files` 4 (0..8; 0 refuses file input) and `server.max_request_file_bytes` 10 MiB (1..25 MiB, decoded). The maximums are low on purpose: the run body limit is `max_body_bytes` plus the base64 of every allowed image and file, and the server holds the body in memory, so the largest allowance for files is 8 x 25 MiB, about 0.27 GiB, in the schema, the loader and `request_files_settings_test.go`. The run body limit grows by both allowances, and the data strings of files count against the allowance like images. Because files default on, `TestRunRequestBodyLimitAllowsAllowedImagesOnly` now turns files off in its "no allowance" case (with files on the parser answers 400 "image input is off" where the reader would have said 413).
- **Where the bytes live.** Inline in `messages.jsonl`. The image store and `image_resize` look only at images and leave a PDF whole (tested with both on). A 10 MiB PDF is about 13.3 MB of base64 in the transcript and is sent again with every later request; a file store like the image store is the way out if that hurts, and was not built.
- **Web UI projection (Go only).** A user message with a file is visible even without text; its text part carries `files` (names in order, repeats kept) and with no text of its own its text is `[file: name]` per file, after the `[image]` placeholders. The bytes never reach the browser (tested: no `base64` in the snapshot). The TypeScript projection ignores `input_file`; this is an intended difference. The two Go tests that pinned "an `input_file` message is hidden" now use an unknown part type (`input_audio`) for that case.
- **Frontend.** An Attach file button (`attach_file_*` keys in `config.json`: accept `.pdf,application/pdf`, 4 files, 10 MiB), a chip with the name and a remove button in the composer drawer, the same chip under the sent message, and a drop zone on the whole composer (`drop_files_enabled`) that sorts images, PDFs and refusals. A dropped text file is no longer read into the draft; "Attach context" still does that.
- **Measured.** On a temp server with OpenRouter `openai/gpt-6-luna`: a hand-made 904-byte two-page PDF with a random code on page 2 only, attached in the composer and sent with Enter, was answered "OZFS-5154", the code in the file. `messages.jsonl` held the `input_text` and one `input_file` (1,236 characters of file data, decoded identical to the original); after a reload the chip came from the server with no `[file:` placeholder and no base64 in the page.
- **Not done / not tried.** Only OpenRouter and a tiny PDF; not the ChatGPT OAuth route, not the Anthropic adapter, not a large or scanned PDF; no file store; no preview or download of a sent file; non-PDF files.

## Profile `tools.allow`: registered tools and the tools a profile's model sees (Go only)

The session registers every tool (`tools.native.*`, `mcp_servers`), and that registered set is what a sub-agent draws from. A path profile may now narrow what its **own model** sees with `paths.profiles.<name>.tools: {"allow": [...]}`. TypeScript is frozen and refuses the key like any unknown profile field (`config-parity` "profile unknown field" still holds); a Go-only key is not a gap.

- **Entries.** A native tool name (`read`, `bash`, `subagent`, ...), one MCP tool as `mcp:<server>:<tool>`, or a whole server as `mcp:<server>:*`. `tools.deny` takes the same entries (see "Profile `tools.deny`" below); there is no per-tool pattern inside a native name. An empty array hides every registered tool. Hosted tools from the model file (`hosted_tools`, such as web search) are not registered tools and are still sent. No `tools` block, or no profile at all, shows everything, so an existing setup is unchanged. The block is required to have `allow`, repeats and unknown keys are refused, and every profile's block is validated, not only the selected one.
- **Where the filter sits.** `buildToolCatalog` builds the registered catalog (native, then MCP, then the sub-agent tool binds the MCP tools) and only then applies the profile filter (`applyProfileTools`, `tools.Catalog.Filter`). The sub-agent tool built its agents' catalogs from the registered tools before that, so **a tool the profile hides stays available to a child that lists it** and the parent does not see it. The `write`/`edit`/`bash`/`exec`/`process` rule: the tools must be registered in the session (`allow_write` was removed 2026-10-23).
- **A hidden tool is hidden for real.** It is missing from the request's `tools` array, and a call the model makes to it anyway is answered `unknown_tool`. Scheduling, checkpoint and hooks run on the catalog the model sees, which is the filtered one; a child's calls use the registered tool with its own path policy as before.
- **An entry that names nothing registered is an error.** A name that is no native tool fails when the settings load (422). A native tool the session did not enable, an MCP tool that is not loaded, or `mcp:<server>:*` for a server the session does not list fails when the catalog is built: `tools.allow lists "x", which is not a registered tool (registered: ...)`. On a run the stream carries the generic error event (as for an unreachable MCP server) and the provider is never called; `GET .../tools` returns the full message with 422. A typo therefore cannot leave a tool quietly missing.
- **The tools route** returns `{"tools": [...]}` as before, plus `"hidden": [...]` (the registered tools the profile does not show) only when the profile hides at least one tool (a restricted profile that hides nothing gets the plain body). Without a restriction the body is byte-identical to before. TypeScript has no `hidden`; the differential harness does not set the key.
- **What a child can use, and what is still open.** A child's `tools` list draws from what the session registers, not from what the parent's profile shows (test `TestProfileToolsHideAToolFromTheParentButNotFromAChild`: the profile shows only `subagent`, the child still reads a file). It was already built from the registered tools before this change; the change makes that useful, because a profile can now hide a tool without taking it from its children. Unchanged: only read-only native tools by default, change tools only when named (`allow_write` was removed), no nested `subagent` (later allowed), and MCP tools only when named in the agent's `tools`. A tool must still be registered in the session; there is no way to give a child a tool the session does not register. Servers still connect on every run (`LoadTools` runs per catalog build); the filter does not stop a server from starting. Not measured: the token cost of a large catalog.


## Profile `tools.deny`: subtract tools from the profile and from its sub-agents (Go only)

`paths.profiles.<name>.tools` now takes `allow`, `deny` or both (an empty block is an error: `tools needs allow or deny`). Entries are the same three forms as `allow`, matched by one function, `tools.EntryMatches` (`internal/tools/entry.go`), which the profile filter and the sub-agent tool both call, so server `docs` does not match `docsx` in either.

- **`deny` wins over `allow`.** A tool is shown when no `deny` entry covers it and, if the block has an `allow`, an `allow` entry does (`profileToolShown`). `ProfileToolSettings.HasAllow` tells "no allow list" (show everything the session registers) from `"allow": []` (show nothing); `deny` alone subtracts from everything.
- **`deny` also limits the profile's sub-agents.** `allow` only narrows what the profile's own model sees; `deny` is a security statement, so a denied tool is in no child's catalog either (`NativeSubagentSettings.DenyTools`, set from the profile in `BuildCatalogWithSubagents`; it is not a key of the subagent section). It is removed from a child's default set, from an explicit `tools` list, and from a `mcp:<server>:*` expansion (`withoutDeniedTools`, the filter in `bindMCP`). A denied change tool (`write`, `bash`, ...) no longer makes its agent a file changer.
- **An agent left with no tool is a load error**, not a silent agent that cannot act: `agents.<name> has no tool to use ... (the profile's tools.deny is in effect: <entries>)`. An agent that lists a denied tool among others just loses it.
- **Checks match `allow`.** A malformed entry fails when the settings load (`tools.deny[i]`, a repeat is refused); an entry that names a tool the session does not register fails when the catalog is built (`paths.profiles.<name>.tools.deny lists ...`), so a typo is not a rule that quietly matches nothing.
- **Schemas.** `setting.schema.json` and `profile.schema.json` describe `deny` and `anyOf: [required allow, required deny]`; `TestProfileToolsSchemaMatchesTheLoader` pins the keys, the `anyOf`, the shared entry pattern and `uniqueItems` for both lists.
- **Not done.** Hosted tools from the model file are not registered tools and are not affected. A per-agent `deny`, and a `deny` in the toolset or the sub-agent section, do not exist. The profile `deny` reaches the sub-agents of the **selected** profile only, because the other profiles' blocks are validated but not loaded.

## Catalog layout: `cwd` at three levels (Go only)

`cwd` is a setting key of the root `defaults`, a session's `settings` and a profile's `settings`, and `session.json` keeps its top-level `cwd`. Precedence, nearest first: profile `settings.cwd`, session top-level `cwd`, session `settings.cwd`, root `defaults.cwd`. Each must be absolute (or `~`) and an existing directory, as before; a relative one is a config error. Without any, a catalog-layout session fails with `cwd is required` and names the places to set it, because the fallback would be the global root (`.jad/`), which holds no project. A legacy session keeps the fallback. A root `"defaults": {"cwd": "~"}` is the usual choice. Why: a profile such as a reviewer may work in another checkout than its session, and a root default saves repeating the project path in every session. `layoutSettingKeys` (Go) and the `propertyNames` enums of the session, profile and root schemas are one list; `TestLayoutSettingKeysMatchTheSchemas` keeps them equal. The migrator still writes a legacy `cwd` to the session's top level.

`env_file` is a setting key of the root `defaults`, a session's `settings` and a profile's `settings`, nearest first. It is the `env_file` of the toolset's `bash`, `process` and `exec` when that tool names none of its own; a tool's own `env_file` wins, and a tool the toolset lacks is not added. A relative path is relative to the folder of the root `setting.json`, like a toolset's `env_file`. Why: one dotenv file (`PATH`, tool-manager variables) usually serves every shell tool, and naming it three times in every toolset invites a tool that misses it. MCP servers do not read it: a stdio server starts with a small inherited set (`HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM`, `USER`) plus its own `transport.env`, so one server cannot see another's secrets; its environment stays in its connection file. `prompt_documents` are relative to the session cwd, for layout and legacy sessions alike.

A sub-agent's `model` is a model ID in a catalog-layout session. A value that does not end in `.json` is `<category>/<name>` of the models catalog; one that ends in `.json` stays a file path (relative to the agent's folder, or absolute), so the shared `.jad/subagents/*/agent.json` files keep working for legacy sessions until they are moved. An agent may name any model of the catalog, not only the ones its caller's profile lists: a profile's `models` narrows the main chat, and a cheap reviewer model would otherwise have to be listed in every main profile. An unknown ID fails the session load and lists the available IDs. A legacy session reads every value as a path, as before. The agent keeps the value as written in `NativeSubagentAgent.Model`; `resolveSubagentModels` (layout_load.go) replaces `ModelPath` after the settings load, because the normalizer does not know the catalog.

## Catalog layout: a relative `env_file` is relative to the root folder (Go only)

`tools.native.bash.env_file` and `tools.native.process.env_file` were resolved against the session folder. A catalog-layout session folder holds only `session.json`, and its toolset is shared by many sessions, so a layout session resolves a relative `env_file` against the global root, the folder of the root `setting.json` (`.jad/`). Absolute paths and `~` are unchanged, and a legacy session still resolves against its own folder (`TestLegacySessionEnvFileIsRelativeToTheSessionFolder`). The base is an explicit parameter of `loadSessionSettingsFrom`. `jad-migrate` copies each session's env file to `<sessions>/<session>/<file>` and writes the toolset path relative to the new root, so two sessions that both name `env` keep their own file.

## `tools.native.exec.env_file` (Go only)

`exec` runs through bash's child-process settings, so by default it has bash's environment (built-in defaults, bash's `env_file`, bash's inline `env`, minus `env_deny`). An optional `tools.native.exec.env_file` gives exec its own dotenv file: for exec runs it **replaces bash's env_file values**; bash's built-in defaults still apply, and bash's inline `env` still wins over the file. Bash itself is not affected. Absent, exec behaves as before. A relative path resolves like bash's (the session folder for a legacy session, the root folder for a catalog-layout session). `NativeBashSettings` now keeps the three parts of its `Env` (`BaseEnv`, `FileEnv`, `InlineEnv`) so exec can swap the middle one. The TypeScript backend has no `exec.env_file`; the parity test drops `env_file, ` from a Go error that lists exec's supported keys, only for `tools.native.exec.` messages.

## `jad-migrate`: removed (2026-10-10)

`cmd/jad-migrate` and `internal/migrate` converted legacy sessions to the catalog layout. The user migrated by hand, so the tool and its tests were removed. The last commit that has them is `d5cacb8` (`git show d5cacb8:backend-go/cmd/jad-migrate`). The layout loader no longer has a counterpart that writes the layout.

## Tool storage lives under the session cwd (Go only)

In the catalog layout, the transcript, its backup, staging and the HTTP debug folder stay under the root state folder, `state/<session>/<category>/<name>/`. The tool storage (bash spill, memory, tasks, fetch, processes, sub-agent runs, write/edit backups) is `<cwd>/<tool_storage_dir>/<session>/<category>/<name>/tools`.
- **Why.** Prompts, sub-agents and tool state are per project; a project can have any cwd. The file tools allow the cwd by default, so the model can read its own bash spill files with no extra `paths` rule. With the storage under the root state folder, a session whose cwd was outside the repo (for example `/tmp/test`) failed to load: "tools.native.bash.spill.storage_dir resolves to a location the model could not read back".
- **`tool_storage_dir`** is a settings key of the root `defaults`, a session's `settings` and a profile's `settings`; the nearest wins. Default `.jad/state`. A relative path is relative to the cwd; an absolute path is used as it is, and then the toolset's `read.paths` must allow it, or the spill check refuses the load.
- **Not moved.** Existing tool data is not copied. For a session whose cwd is the repo and whose old state folder is `.jad/state/<session>/<category>/<name>/tools`, the new path is the same. Any other session starts with empty tool state.
- **Not changed.** `agents_dir` and `prompt_documents` were already relative to the cwd. A missing `agents_dir` folder is still a load error.

## `agents_dir_missing_ok` and `agents_dir_override` (Go only)

Two booleans in `tools.native.subagent`, both default false, so nothing changes unless a toolset sets them. They exist for a toolset that many projects share: it lists a general folder plus a per-project one (for example `.jad/subagents`, relative to each session's cwd).
- **`agents_dir_missing_ok`.** An `agents_dir` entry that does not exist is skipped instead of failing the load. A path that exists but is a file is still an error, and the session then has no agent from it (see "The subagent tool loads with zero agents"). Cost: with the flag on, a mistyped folder name is no longer reported; the tool only says there is no agent.
- **`agents_dir_override`.** An agent folder in a later entry replaces an agent of the same name from an earlier entry; the replaced agent keeps its place in the order. An inline agent in `agents` is never replaced, and without the flag a name defined twice is still an error. Cost: a stale or mistyped duplicate in a project folder silently replaces the general agent, and only the replacing folder's `agent.json` and `prompt.md` count (nothing is merged).
- **Not changed.** `agents_dir` entries are still relative to the session cwd.

## The subagent tool loads with zero agents (Go only)

A project starts with no agent and the model creates its own, so `tools.native.subagent` no longer needs one. Removed: "agents must define at least one agent", "agents_dir holds no agent folder" and the constructor's "needs at least one agent". Kept: the section must name `agents` or `agents_dir` (an empty object or list is fine), so a section like `{}` or a mistyped key is still an error; a missing `agents_dir` folder is still an error unless `agents_dir_missing_ok`; a folder with neither `agent.json` nor `prompt.md` is still an error.
- **No new key.** The behavior is not a switch: with at least one agent nothing changes, and with none the old result was a load failure, which nobody can rely on.
- **What the model sees.** With no agent the tool description, the no-task list and a task call all say "No agents are configured" and name the folders to create one in (`ConfiguredAgentDirs`, which includes folders `agents_dir_missing_ok` skipped, or the inline `agents` key when there is no folder), the files an agent folder holds and the name rule. A task call returns `unknown_agent` with that text, not a crash.
- **When a new agent shows up.** Folders are read each time a message resolves its session (`LoadSessionSettings`), and the tool catalog is built when a run starts. An agent created during a run is therefore usable from the next message, not in the same run. The text says so. Read from the code; not run through a live server.
- **Cost.** A typo in `agents_dir` with `agents_dir_missing_ok` on now loads with no agent instead of failing.

## `read_image`: show an image file to the model (Go only)

`read_image(path)` returns the file as one `input_image` part (`detail: auto`), so the model sees the image instead of bytes it cannot read. The type comes from the first bytes (png, jpeg, webp, gif), never from the name; anything else is refused with `unsupported_image`. It is off unless `tools.native.read_image` is present and `read_image` is in `tool_definition_paths`. It is `ReadOnly`, so a sub-agent can list it. The TypeScript backend ignores the key.

- **One key, no paths.** `max_image_bytes` (default 5 MiB, at most 10 MiB; a larger file is refused with `image_too_large`, read as limit+1 bytes only). `paths` is refused with a message pointing at `tools.native.read.paths`: the tool takes the read tool's resolved path policy, as `grep` and `glob` do, so one rule decides what the model may open. The policy is a copy made at load, not a live reference, so a later change to `read.paths` takes effect on the next load of the session, like every other setting. The tool works without `tools.native.read`; the policy is then the default (workspace only).
- **Stored references.** A `stored-image://` path opens the image store, like `decide` does.
- **No resize, no store in the tool.** The result is an ordinary `input_image` in a `function_call_output`, so `image_resize` (source `native`) and `image_store` apply to it by the existing history steps, and the UI shows it through the stored-image or inline-image route.
- **Shared code.** The file loading of `decide` moved to `readImageFile` (`tools/native/image_file.go`); `decide` calls it with its own limit and part label. Its tests are unchanged and pass.
- **Not changed:** the user's `.jad` files. A session sees the tool only after the manifest is listed and the toolset has the key.

## Tool errors for an unknown id or value list the valid ones (Go only, 2026-10-12)

- **Rule.** A not-found or invalid-value answer adds one `available_*` information line (comma-joined) so the agent can pick a
  valid value instead of guessing. `skill_not_found` and `unknown_agent` already did this with the key `available`.
- **Where.** `memory` (`available_types` after a type error when `allowed_types` is set; `available_refs` after an invalid or missing

- **Bounds.** Memory and task use their `list_limit` setting; process and sub-agent runs are already bounded by their retention

- **Memory errors carry a kind.** `MemoryStoreError.Kind` marks the type and ref errors; message texts are unchanged.

  session is offered only its own ids.

## Tools own their settings; no tool reads another's (Go only, 2026-10-12)

- **Rule.** A native tool takes every value from its own `tools.native.<tool>` block or from the default of its settings shape.
  No tool reads another tool's block. A shape that several tools have (path rules, backups, child-process settings) is defined once in
  the schemas as `$defs` and used by each tool under its own name: `path_rules`, `read_style` (read, grep, glob, `read_image`),
  `edit_style` (write, edit), `child_process_style` (bash, exec, process) and `bash_style` (bash, exec).
- **Removed fallbacks.** grep, glob and `read_image` no longer take `read.paths`; edit no longer takes write's `paths`, backups, fsync
  or `backup_dir`; bash no longer takes write's `paths`; process no longer takes bash's or write's `paths` or bash's stdout and stderr
  budgets; exec no longer takes bash's whole settings and no longer needs `tools.native.bash`.
- **Defaults.** A tool without `paths` gets the empty rule set (the workspace only, as `read` without `paths` always did). It is not a
  load error: the user asked that tools inherit the default of the shape, not that they fail.
- **exec.** `tools.native.exec` accepts every bash key (`nativeBashStyleKeys`) plus its own (`nativeExecOwnKeys`); `env_file` is one of
  them. Its settings are `NativeExecSettings.Child`, built by the parser bash uses (`normalizeBashStyleFields`), and its errors name
  `tools.native.exec`. The layout default `env_file` still applies to bash, process and exec separately.
- **read_image.** It has its own `paths` key; its error text no longer points at `tools.native.read.paths`.
- **Exceptions (checks and wiring, not inherited values).** (1) At load, bash's and exec's `spill.storage_dir` is checked to be readable
  back by the model, using the `read` and `grep` path rules of the session (`bashSpillReadable`); `spill.allow_unreadable` turns it off.
  The rules are not copied into either tool. (2) `decide` has its own `paths` key (`read_style`, as `read_image` does)
  for an image given by path; it no longer takes the `read` rules, and without `paths` it reaches the workspace only. A session that
  relied on `read.paths` for `decide` images needs `tools.extension.decide.paths`. (3) The
  session file list in the UI uses the `read` rules. (4) exec's `spill.storage_dir` defaults to `.exec-output` (and its legacy template default
  to `{cwd}/.exec-output/...`), bash's stays `.bash-output`, so the two no longer share a folder or prune each other's files by
  different `retention_days`. exec's spill files are named `exec-<call>.<stream>.log` (bash's stay `bash-...`); the prefix is
  `NativeBashSpillSettings.FilePrefix`, set by the loader per tool, and an empty value means `bash`. A relative value still resolves under the tool storage root. Spill files already in `.bash-output`
  from earlier exec calls stay there until bash's retention prunes them. Item (1) is kept on purpose: it asks whether the model can
  read the file back with `read` or `grep`, which is a check on those tools' rules, not a value exec borrows.
- **Spill pruning is throttled.** `spill.prune_interval_seconds` (default 3600, 0 to 86400, 0 = scan before every command) sets the minimum time
  between prune scans of one spill directory and filename pattern. Before it, every bash and exec call listed the whole directory twice (once per
  stream); at 3000 files that cost about 16 ms against a 2 ms command. The last-scan times are in memory, so the first command after a backend start scans once.
  It applies to both tools through the shared `bash_style` block. `retention_days` is unchanged, and an expired file now survives up to one interval longer.
- **Hooks.** Post-edit hooks now have their own child-process keys and no longer read or need `tools.native.bash` (see the `hooks` section). The checkpoint harness paths now include exec's own
  spill directory. `messages.jsonl` is not touched.
- **Effect on existing toolsets.** A toolset that relied on the inheritance now has narrower tools until it names `paths`. The user's
  `.jad/tools/jad/default.json` was edited in the same change (own `paths`, process and exec budgets, exec `spill`) so its behavior is
  the same. A toolset that used exec without bash now loads.

## A sub-agent can name a toolset (2026-10-12, user request)

- **Problem.** A child drew its tools from what the session registers, which is the profile's one toolset file. With many tools shared by many agents, that file had to list and configure all of them. (The old `missing.md` text said the profile's `tools.allow` had to list them; that was already untrue, see "Profile `tools.allow`" above.)
- **`toolset` on an agent** (`agent.json` or inline, `"<category>/<name>"`). The agent's tools and MCP servers come from that toolset file instead of the session's. Absent means the session's toolset, so nothing changes for an existing agent. The parent never sees those tools: they are not in its catalog or its `tools` route.
- **How it loads.** `loadAgentToolsets` (`sessionfs/layout_load.go`) composes the session again with the named toolset in place of the profile's own and runs the same normalizers, so defaults, `env_file`, path rules and every error message are the toolset's own and not a second parser. The result is `SessionConfig.AgentToolsets[<id>]`, one per distinct id. Its `NativeSubagent` is dropped (an agent that names a toolset cannot list `subagent`; nesting still works for agents on the session's own toolset) and `statecontext` is not read from it (the providers belong to the session). An unknown id is a config error listing the available toolsets; an error inside the toolset is prefixed `agent <name> uses toolset <id>:`.
- **How it builds.** `buildNativeTools` (`tools/native/catalog.go`) is the old body of the catalog builder, now shared: the session builds its tools with it, and so does each toolset. The stateful stores (process manager, tasks, memory, fetch) come from the resolver (`Resolver.Resources`), keyed by the toolset's own storage directory, so a toolset's tools share state with other sessions that use the same directory, as the session's do. `childToolPools` applies the same rules to either source. The toolset is loaded before the model file is read, so `buildAgentToolsets` copies the running session's `Model` into it; without that its `bash`, `exec` and `process` would hide an empty key variable and the running model's key could reach a child's shell (found by the code review; `TestSubagentToolsetBashHidesTheModelsAPIKeyFromTheChild`). Toolset ids are walked in sorted order, so which error or server comes first does not depend on map order.
- **MCP.** Each toolset gets its own MCP manager (`loadAgentToolsetMCP`), keyed by session, profile and toolset id, so a server that two toolsets use with different `deny_tools` is not closed by the other's run. An agent's `mcp:<server>:<tool>` and `mcp:<server>:*` entries are resolved against its toolset's servers only, never the session's, and the error names the toolset.
- **Rules that still hold.** The profile's `tools.deny` removes a tool from a toolset's children too (the same `AnyEntryMatches`). An agent still has to name a change tool in `tools` (`allow_write` was removed). Each tool keeps its own `paths` from the toolset's file. A child that gets `process` from a toolset starts its processes in that toolset's manager, and its run's end stops them there (`subagentAgent.processes`). `tools` narrows within the toolset.
- **Not built.** Nesting (a toolset that includes another). A tool in a toolset is built every time the session's tools are built, whether or not an agent runs.
- **Cost and risk.** Every named toolset is built with the session, so a bad file fails the session load, which is the same fail-early rule as for `agents_dir` and models. A toolset that registers a path-checked tool with a wider `paths` than the session's gives its agents that wider reach, which is the point; the person who writes the agent vouches for the toolset.
- **Tests.** `sessionfs/native_subagent_toolset_test.go` (loading, errors, one copy per id, statecontext), `tools/native/subagent_toolset_test.go` (tool selection, deny, MCP resolution, process manager), `app/subagent_toolset_integration_test.go` (a child reads with `read` that only its toolset registers; a toolset's MCP server is called; an unknown toolset refuses the run; the profile's deny). Twelve mutations were each caught by a test. A toolset file without `native` or `mcp` cannot inherit the session's: `tools` and `mcp_servers` are not setting keys a session, profile or the root `defaults` may carry (`layoutSettingKeys`), so the composed setting has none before the toolset is added.
- **Statecontext header and empty snapshots (phases 1 and 2 of `design_statecontext.md`).** `statecontext.header` (string) is the first line of every snapshot; the default is the previous fixed text, so the default snapshot is unchanged byte for byte. An empty or blank header, a non-string and a header larger than `max_bytes` are config errors: the header carries the warning that the data below it is untrusted, and a typo must not drop it silently. A snapshot is not written, and not added to the request, when every provider returned no items (`stateContextProviderHasData` in `app/state_context.go`); a provider that cannot count its items counts as having data. Memory's `queries` metadata alone does not count as data. The existing snapshot file is left as it is when a compaction finds nothing, but compaction removes `statecontext.json` before the collector runs, so the old text does not survive it; front-compact keeps it as before. The one exception planned in the design (a single "state is now empty" block after a non-empty one) arrives with the appended sidecar in phase 5, because it needs a block already in the history to be superseded.
- **Statecontext triggers (phase 3 of `design_statecontext.md`).** The flat `statecontext.trigger`, `tools` and `max_bytes` keys are replaced by `statecontext.triggers.<name>`, each with its own `tools` (non-empty) and `max_bytes` (default 65536, 1024 to 10 MiB). `enabled`, `header` and `role` stay at the top. A trigger fires only if it appears under `triggers`; there is no per-trigger `enabled` flag. Triggers: `compaction` (after manual or automatic compaction, as before) and `session_start`. The three old keys are a config error that names the new shape and the trigger names, not a compatibility reader; the root `.jad/setting.json` has no `statecontext`, so nothing of ours broke. An unknown trigger name, an unknown key under a trigger (so `prompt` is refused until phase 4), an empty `triggers` with `enabled: true`, and a header larger than any one trigger's `max_bytes` are config errors. Providers are checked per trigger, and the error names the trigger. `session_start` means the first run that finds no usable stored snapshot (`boundRunner.currentStateContext` in `app/resolver.go`), not server start: there is no session to attach a block to at server start. A stored snapshot is sent only while its own trigger is still configured, so removing `compaction` from the setting stops an old compaction snapshot from being sent, and `session_start` then replaces it. The snapshot is still one file with the old end-of-request placement; the sidecar and appended blocks are phase 5. Tests: `sessionfs/state_context_settings_test.go` (shape, per-trigger providers, removed keys, header per trigger, schema agreement), `app/state_context_session_start_test.go` (a fresh session carries the block from the first run and keeps it, no file when providers are empty, a stale snapshot of an unconfigured trigger is replaced). Mutations: no `session_start` write, and sending a stale snapshot, each fail a test.
- **Statecontext prompt (phase 4 of `design_statecontext.md`).** Each trigger takes an optional `prompt` (inline, non-empty string) and `prompt_documents` (file paths). The text is the inline prompt, then each document, joined by a blank line, and it is placed between the header and the data JSON, never inside the JSON: the header tells the model that values are data, so an instruction inside a value would contradict it. Documents reuse `readPromptDocument` (the reader behind the session `prompt_documents`): `~` is expanded, a relative path resolves from cwd, and an unreadable file is a config error naming the key and path. Files are read when settings load, which happens on every request, so an edit applies to the next snapshot written and not to a block already in the history. The header plus the prompt must fit in the trigger's `max_bytes`, checked at load, and the prompt counts toward the limit when a snapshot is trimmed. A snapshot with no provider data is still not written, whatever the prompt says.
- **Statecontext placement and sidecar store (phase 5 of `design_statecontext.md`).** Blocks are stored in `staging/statecontext.jsonl`, one JSON line each (`schema_version`, `generated_at`, `trigger`, `text`, `role`, `after`), append-only. The text is stored rendered and never re-rendered, so the request before a block stays byte-identical from one request to the next. `after` is how many request-history items precede the block; `BuildRequestWithStateContext` inserts each block after that item, in write order, and a block that follows more items than the history holds is not sent. The anchor is the count of history items, not a message id, because the history is an expanded list and a compaction rewrites it anyway. Why a count is safe: history only grows at the end during a session, and the three rewrites are handled: compaction and reset delete the file, and a front compaction keeps the blocks that still fit and moves only the latest stranded block to follow the last remaining item (an older stranded one is superseded by it). A malformed line is skipped and a missing file is no blocks, as the file is a derived cache. A block of a trigger that is no longer configured is not sent but stays in the file until the next compaction. `session_start` appends only when no block is sent, so a session carries one such block, written after the first user input is stored (its `after` is the item count at that moment). The old single `statecontext.json` is no longer read; it is inert and can be deleted by hand. `messages.jsonl` is unchanged. Tests: `transcript/state_context_test.go` (append order and anchors, malformed lines, rejected input, front-compact re-anchor, compaction and reset clear), `session/state_context_test.go` (block order, prefix stability), `anthropicadapter/cache_test.go` (the history breakpoint skips a block in the middle, with `mid_conversation_system` on and off), `app/state_context_session_start_test.go`. Mutations: compaction or reset keeping the file, skipping or over-keeping the front-compact re-anchor, and placing blocks only at the end each fail a test.

- **Statecontext user trigger (phase 6 of `design_statecontext.md`).** `statecontext.triggers.user` lets the user write a block on demand through `POST /api/sessions/{ref}/statecontext` with `{prompt?: string, preview?: boolean}`. Config: `tools` and `max_bytes` as for any trigger, plus `max_prompt_bytes` (user only, default 4096, ceiling 65536); the header, the configured prompt and `max_prompt_bytes` together must fit in `max_bytes`, so a typed prompt can never push a block past its limit. The typed prompt is trimmed and placed after the header and the configured prompt, outside the data JSON, like any trusted prompt text. It is not stored anywhere else. Without the trigger in the config the route answers 403; an oversized prompt answers 400. The route is refused with 409 while a run is active (the block is anchored to the history that exists now) and takes the mutation gate and session locks as compaction does. `preview: true` renders the block and returns it without storing it, so the UI can show what would be sent. Unlike the other triggers, a typed prompt counts as content: the block is written even when every store is empty. With no prompt and no data nothing is written (`written: false`). Trust: the text goes into a developer or system message, but the API token already allows `bash`, so this adds no power; the size cap bounds the cost. The route name is in `knownSessionRoutes`. Tests: `app/state_context_user_test.go` (preview writes nothing, order header then prompt then data, next run carries it, refusals, empty stores), `httpapi/mutation_handlers_test.go` (body fields, 409 during a run), `sessionfs/state_context_settings_test.go` (default, bounds, user only, fit in `max_bytes`). - **Statecontext run_start trigger (phase 7 of `design_statecontext.md`).** `statecontext.triggers.run_start` (`tools`, `max_bytes`, `prompt`, `prompt_documents`) runs at the start of every run, after `session_start`, and appends a block only when the provider data differs from the latest stored block of any trigger. Each block carries `data_sha256`, the hash of the trimmed provider data without the time, so a changed `generated_at` alone never writes a block. An empty state hashes to one constant: it differs from a block that reported data, so one block with empty providers is written ("state is now empty", decision 6), and an empty state after that or with no block at all writes nothing. Blocks written before the field existed have no hash, so the first `run_start` after an upgrade writes one block. The comparison uses the latest block even when another trigger wrote it, so `session_start` followed by `run_start` over the same data writes one block. A block of a trigger that is no longer configured is not the latest. Cost: each run reads the configured stores; a block is added to the history only when something changed, and then stays untouched, so the request prefix before it stays byte-identical. Tests: `app/state_context_run_start_test.go` (no data, data appears, unchanged, removed, empty again, data back; `session_start` then `run_start`), `sessionfs/state_context_settings_test.go` (accepted, `max_prompt_bytes` rejected).
- **Statecontext memory summary mode (phase 8, memory part, of `design_statecontext.md`).** A `tools.native.memory.statecontext` selector may set `group_by`, a dot-separated field path (identifier segments, at most `max_filter_depth` deep, not `__proto__`/`prototype`/`constructor`). The selector then contributes a `summaries` entry instead of records: `{type, group_by, groups: [{filter, count}], ungrouped?, exclude_any?, at_least?, omitted_groups?}`, counted by `MemoryStore.GroupBy`, which scans in name order under the existing `max_scan_records` and `max_scan_bytes`; a stopped scan sets `at_least` and `has_more`, so every count is a lower bound. Each group's `filter` is the selector filter plus the group value, so it is exactly the `filter` of a `memory` list call that fetches that group (tested by listing it). Groups are ordered by count, then by canonical value; records without the field are counted in `ungrouped`. The mode is per selector and there is no separate `mode` key, so a session can mix record selectors and group selectors (the design's `hybrid`). Config errors: `group_by` with `limit` (a count has no page size), a `group_by` path that is also a filter key (the group would be a single value), a non-string or malformed path. Size trimming drops the smallest-priority entries last-first and records `omitted_groups`, and never removes the summary itself. Default unchanged: no `group_by` means records as before. Values in `groups[].filter` are text the model or user wrote into records, so they stay inside the JSON, not in a sentence (decision 8). The task, process and subagent providers get their own `mode` (see the next entry). Tests: `tools/native/memory_group_test.go`, `app/state_context_memory_test.go` (summary at most a quarter of the item-mode size for 30 records), `sessionfs/native_memory_settings_test.go`.
- **Statecontext task, process and subagent summary mode (phase 8, rest, of `design_statecontext.md`).** `tools.native.task|process|subagent.statecontext.mode` is `items` (default; unchanged output, byte for byte) or `summary`. A summary section carries `counts` (task: `{status, count}`; process and subagent: `{state, count}`) for every configured status or state that has at least one record, in the configured order, and lists in full only the records whose status is in `detail_statuses` (task) or `detail_states` (process, subagent), newest first and at most `limit`. Defaults for the detail list: task `in-progress`, process `running`, subagent `queued` and `running`, each cut to the states the section covers; the list is rejected outside `mode: "summary"`, and every name in it must be one of `statuses`/`states`. Counts and listed records come from one read of the store (task: one `List` with no limit, so the store is read once under its lock), so they cannot disagree. `has_more` means a detail record was left out by `limit`. Over `max_bytes` the trimmer drops listed records first and then counts from the end (`omitted_by_snapshot`, `omitted_counts`), so a count is the last thing to go. A section with only counts is data (it writes a block and changes the `run_start` hash); a section with neither is empty as before. The counts are not the memory `at_least` kind: these stores are read whole, so a count is exact. Values stay inside the JSON (decision 8). Tests: `tools/native/statecontext_summary_test.go`, `app/state_context_summary_test.go`, `sessionfs/native_statecontext_mode_test.go`.
- **Sub-agent automatic compaction and state context (decided 2026-10-14).** Three new agent keys, valid inline and in `agent.json`: `auto_compaction` (bool), `compaction_trigger_tokens` (1 to 10,000,000) and `state_context` (bool, default false). A child never collects a snapshot, since it has no stores and its tools are read-only, and the block is not written to the child's transcript. - **Catalog file routes, profiles first (decided 2026-10-14, phase 4 step 2 of `missing.md`).** `GET /api/catalog/profiles` lists the files with the version of each; `GET`, `PUT` and `DELETE /api/catalog/profiles/{category}/{name}` read, write and remove one. The body of a `PUT` is the raw file; the server checks it with the loader's own rules (strict keys, `schema_version`, `settings` keys, `models`, `model_default`, the checks every profile of a session's scope gets, and that its `toolset` exists) and answers 422 with the loader's message. The version is the strong ETag of the file's bytes. A replace needs `If-Match`, a create needs `If-None-Match: *`, and a delete needs `If-Match`; a missing header is 428 and a wrong one 412. A weak tag never satisfies `If-Match`. A replace is a temporary file and a rename and is refused if the file changed meanwhile; a create is a hard link, so a second creator loses. Writes are always fsynced and run under the resolver's settings lock. Deleting a profile is refused with 409 and the session ids when a session could no longer load without it (it is the active profile and no other profile of the session's scope matches). A profile that does not resolve today is not counted. - **Catalog file routes for sessions (decided 2026-10-14, phase 4 step 5 of `missing.md`).** `GET /api/catalog/sessions` lists the catalog-layout sessions of every root with the version of each `session.json`; `GET`, `PUT`, `DELETE /api/catalog/sessions/{reference}` read, write and delete one. The reference is the session id, or `<root>:<id>` when there is more than one root (the same form `/api/sessions` takes). `PUT` and `DELETE` use the `If-Match` and `If-None-Match` rules and status codes of the profile routes; the precondition check is one function, `checkWritePrecondition`, shared by all three kinds. A write is validated by loading the text as a session from a scratch folder, so the loader's own checks run and nothing is created in the session root until the text is accepted; the loader's messages name the real file. Creating a session writes only `session.json`. **Delete** (accepted option A): after the `If-Match` check the handler stops every run of every profile of the session (and its handed-off sub-agent children), waits up to `server.session_delete_stop_wait_ms` (default 10000, max 300000, `0` does not wait) for the runs to end, and answers `409` if one is still going; only then it removes `session.json`, its lock file and the folder. The folder must hold nothing else, or the delete answers `409` naming the files. The state folder (`<state>/<session>`, every profile's transcript) is kept unless the request says `?state=delete`; deleting it also drops the transcript stores the resolver cached for it, so a session created again under the same name starts empty. Deleting a session that is not stored in the catalog layout is refused as not found. The delete holds the per-session lock, so a run cannot start between the check and the removal. Not done: a session cannot be renamed; a cross-process delete is not coordinated beyond the stopped-run wait (the settings lock file is removed with the folder).

## The root setting is read once at start; profile, session and model files are read per request (2026-10-12)

`.jad/setting.json` (`defaults`, `server`, the storage roots) is loaded when the server starts and kept in memory; nothing re-reads it. So an edit to `defaults` (for example `http_debug`) does nothing until the server is restarted, while the same key under `settings` in a profile or session file reaches the next request. The `defaults` description in `root-setting.schema.json` says so. Not done: reloading the root setting while running, because the roots decide where every other file is found.

Sub-agents already retry like the main agent: `newProviderStreamer` builds a child's client from the child's config, which is the parent's with the agent's model, so the parent's `provider_retry` applies. Only the request that opens a response is retried (see "Provider retry"); a failure after the stream started is not, for a child as for the master.

## The in-process session lock is keyed by the canonical reference (2026-10-13)

`Handler.lockSession` replaces the raw `sessionLocks.lock(reference)` in the ten session writers (run start, catalog PUT and DELETE, settings, reset, compact, front compact, checkpoint restore, state context). It asks the resolver for the canonical reference (`SessionReferences.CanonicalSessionReference`), so with one session root `demo` and `local:demo` take the same lock. A reference that does not resolve keeps its raw key and fails later in the request. Not done: the mutation gate and run registry were already keyed by the resolved session; `?state=delete` still shares `<state>/<session>` between same-named sessions in two roots with a shared state path.

## A run start never waits for the transcript while holding the session lock

`handleRunStart` used to wait for the transcript lock inside `Handler.lockSession`, so a second start on a running session (or a session whose transcript another process held) kept the in-process session lock for the length of that run, and every other writer of the session (settings, state context, catalog, the other profile's start) waited behind it. It now loops: take the session lock, try the transcript lock without waiting (`TryLockSession`, `sessionlock.TryAcquire`), and on `ErrSessionBusy` release the session lock, wait for the transcript with the blocking `LockSession` and release it at once, then try again. A resolver without `TryLockSession` keeps the blocking path.

The invariant that stays: taking the transcript lock and `beginRun` happen in one session-lock section. Reset, front compact, state context and checkpoint restore test `runIsActive` under the session lock and answer 409, and rely on "the transcript is held by a run of this process" implying "the run is registered". Taking the transcript lock before the session lock would break that: a reset could find no run, wait for the transcript and wipe the answer. Compact has no such check, but it takes the same path (`lockSessionAndTranscript`): it waits for the transcript outside the session lock and then holds both locks while it runs.

**Order (added after the first version).** Run starts and compactions of one session and profile go through `turnQueue` (`start_turn.go`), a FIFO keyed by canonical reference and profile. A start or compaction holds the turn until it has taken the locks (a start) or finished (a compaction), so one that arrived later cannot take the transcript each time the 25 ms file-lock poll releases it. A cancelled request leaves the queue. Compact clears its mutation gate before giving back the locks, so a start queued behind it does not meet the gate and get a 409 from `beginRun`. A compaction that finds the session changing is still refused at once, before it queues, as before.

**Queue key.** A request that names no profile is keyed as the session's default profile (`SessionProfiles.CanonicalSessionProfile`, implemented by the resolver), because it resolves to that profile's transcript. Without it, an unnamed start and an explicit `default` start would sit in two queues and could race for the transcript.

**Not in the queue:** reset, front compact, state context and checkpoint restore. They still take the session lock and wait for the transcript while holding it, as before; they are not ordered against the queue. All four check for an active run before they wait, so a queued start behind a running run still gets them an immediate 409. Reset is covered by `TestResetIsRefusedWhileARunIsActiveAndAStartIsQueued`; the other three by `TestHandlersRefuseAtOnceWhileARunIsActiveAndAStartIsQueued`.

**Panics.** `tryStartRun` releases the transcript lock if it panics before the run is registered, and `handleRunStart` finishes the run as failed and releases the lock if it panics before the run goroutine starts.

## `toolset` may be a list: several toolsets per profile and per sub-agent (T-026)

- **Shape.** `toolset` in a profile, an inline agent (`tools.native.subagent.agents[]`) and an `agent.json` is a string or an array of strings. A string is a one-element array, and a one-element result is the same as before. An empty array, a blank or non-string element and the same id twice in one array are config errors; `null` or absent means no toolset, as before. `sample/schemes/profile.schema.json`, `agent.schema.json` and `setting.schema.json` accept a string or an array.
- **Merge.** The toolsets merge in array order and the first wins: per native tool name, per MCP server id (the file name) and for the whole `hooks` object (the first toolset that has hooks wins; the hooks of a later one are dropped whole, not merged). Each clash gives a warning that names the item, the winning toolset and the ignored one. Order is the precedence, so `[a, b]` and `[b, a]` differ. Two MCP files with one name inside a single toolset stay the existing error.
- **Hooks.** `hooks` in the settings AND in a toolset is still a config error (see "Where `hooks` is set" in the `hooks` section); only two toolsets that both carry hooks are a warning.
- **Warnings.** `SessionConfig.Warnings` holds the load-time notices, deduplicated; it is nil when there are none. Only the resolver logs them, when the settings are loaded for a run lock (`lockSession`) or for a resolve. A config reused from `lockedConfigs` does not log again in `Resolve`, and the other callers of `LoadSessionSettings` (catalog, maintenance, storage recovery) stay silent. They are not errors, and `jad check` and the catalog routes do not show them.
- **Sub-agents.** The key of `SessionConfig.AgentToolsets` (and of the MCP manager and the catalog map) is the ids joined with `+`, in order. `+` is safe because an id is `<category>/<name>` from `[A-Za-z0-9._-]`, so it never contains `+`. A one-element key is the id itself, so existing keys do not change. The derived config of a key is already merged by the loader, so the consumers treat the key as an opaque string.
- **No new config key.** `+` is a key format, not a limit, flag or toggle.
- **Tests.** `sessionfs/toolset_list_test.go`, `sessionfs/multi_toolset_test.go`, `tools/native/subagent_toolset_test.go`, `app/multi_toolset_integration_test.go`, and the schema cases next to `TestAgentSchemaValidatesAgentFilesTheLoaderAccepts`.

## Toolset file routes (2026-10-14, phase 4)

`/api/catalog/toolsets` and `/api/catalog/toolsets/{category}/{name}` use the same routes, preconditions, status codes and atomic writes as profiles and models. Not checked: a sub-agent that names the toolset in an `agent.json` (outside the catalog), an MCP server file's own content (the `mcp` routes check the file itself), and whether an MCP server in the toolset can be reached (nothing is connected on write).

Deleting a session removes the file and its lock file, and with `?state=delete` the state folder; the "folder holds other files" refusal is gone. Two roots holding the same id are still refused at start, now by comparing file names. The local sessions `jad` and `test` are moved when the server is restarted with this build, not before: the running server still reads the folder form. The transcripts were already under `<state>/<id>`, so `messages.jsonl` paths and content do not change.

A profile file may set `name` (a string, trimmed; blank counts as unset), the same optional display name a session has (decided 2026-10-15). The ID stays `<category>/<name>` from the path and is what every route, key and state path uses; the name is only a label. `GET /api/catalog/profiles` returns it per entry (left out when unset or not a string), the session list carries `profile_names` (ID to name, for every profile in the session's scope that sets one, left out when none does) and it is part of the list version, so renaming a profile refreshes a client holding the old list. The editor lists profiles by name with the ID beneath, and the sidebar rows and the composer's profile picker show the name. A non-string `name` is refused when a session using that profile loads and when the file is written.

- **`jad check` (decided 2026-10-15, config key lint of `missing.md`).** `jad check` (`cmd/jad`) reads the root setting and every model, MCP server, toolset, profile and session file the way the server would, starts nothing and needs no `JAD_API_TOKEN`. It prints one line per problem, `<kind> <id>: <the loader's message>`, then `checked N files, M problems`, and exits 1 when there is a problem. It reuses the rules a catalog write applies (`validateCatalogFile`) and loads each session once with its active profile and once with every other profile in its scope (`LoadLayoutSessionSettings`), which resolves the references from the session to its profile, models, toolset, MCP servers and sub-agents (`agents_dir`, the agent's model and toolset). It changes no file and creates nothing; it uses the same scratch folders a write does. A session problem whose message a catalog file already reported is left out, so a broken toolset is reported on the toolset and not again on each session (the order is models, MCP servers, toolsets, profiles, sessions); two sessions are never merged, because a message without a path can come from two different files. Not checked: what a write does not check either (an MCP server is not started, an `env_from` variable need not be set, a stdio `cwd` need not exist), and a root setting that the loader rejects stops the command with its error. A session root without the catalog layout is skipped; with none that has it, the command fails. Any other argument is an error, which also means `jad` with an argument no longer starts the server; the server takes none. A failed check exits 1 through `main`, with the problems already on stdout. Tests: `app/check_test.go`, `cmd/jad/main_test.go`.

- **Per-profile turn counts in the session list (decided 2026-10-16).** Each record of `GET /api/sessions` carries `profile_turns`, the turns of every profile in scope by profile ID (`omitempty`, so a session with no profiles has none). The default profile reuses the count the record already has; every other profile is scanned with `scanTranscriptIndex`, and a profile with no transcript file counts 0 without the list creating state for it. A profile that does not load is left out of the map. The list validator adds the other profiles' transcript stamps, empty when there is none, so a run on a profile that is not the default no longer answers 304 with an old count. Cost: one transcript scan per profile in scope, reusing the usage-cache checkpoint. The snapshot route does not carry `profile_turns`; a row opened in the UI reports its own live count.

- **`model_options` in the session list, snapshot and model-default response (decided 2026-10-16).** Each record of `GET /api/sessions`, the session snapshot and the `model-default` response carry `model_options`, one entry per id in the profile's `models`, in that order: `{id, provider, efforts, default_effort}` (`efforts` and `default_effort` are left out when empty; the whole array is left out when the profile lists no models). `models` is unchanged. `SessionConfig.ModelPaths` (id to file) is new; one function, `listingModelOptions`, reads each listed file raw, like `listingModelSummary`: `provider` is the non-empty string or "unknown", `efforts` the string array (anything else counts as none), `default_effort` the string `request.reasoning.effort`. An unreadable or malformed listed file never fails or hides a session (a listed id with no file at all is a config error, as for `models` everywhere). The list validator adds the stamp of every listed model file in `models` order, so editing a model the session does not use now changes the list ETag. Each field is decoded on its own, so a mistyped field (`request`, `request.reasoning`, `efforts`, `provider`) loses only that field and never the others. Cost: one extra file read per listed model per session in a list that is not answered 304; every list or snapshot request, even one answered 304, stats one file per listed model per session (the stamps are in the ETag). No config key.

- **`active_profile` is removed from the session file (decided 2026-10-16).** A session names no profile. Its default is the first profile in its scope by ID (`layoutSessionFile.defaultProfile`), used by the loader, `ReadLayoutProfileInfo` and the check that a profile delete leaves every session loadable; a request that names a profile (`?profile=`) still picks any profile in scope. A scope that matches no profile is a load error ("scope.profiles matches no profile"). `active_profile` in a session file is now an unknown key and fails the load, the editor and `jad check` by name. Removed with it: `POST /api/sessions/{id}/profile`, `SetLayoutActiveProfile`, `ReadProfileInfo`/`UpdateProfile` on the resolver and `writeSessionSettingsAtomic`. Deleting a profile is refused only when the scope no longer resolves without it; deleting a session's default profile moves the default to the next one by ID. The composed internal `paths.active_profile` of the setting-shaped map and the `active_profile` field of the API responses stay: they name the profile the response resolved. Existing session files must drop the key before the server that carries this change starts.

- **No README route (2026-10-16).** `GET /api/sessions/{id}/readme` and `session_files.readme_file`/`readme_max_bytes` were added and removed the same day: the UI shows a Jad usage page bundled in the frontend, so nothing read the working directory's README.

- **Internal constants are not config keys (2026-10-16, audit F-27).** Project rule 3 puts limits, timeouts and toggles in config. These fixed values are not user limits; each is a kill grace, drain or poll interval, or an internal buffer or ceiling that only keeps a child process, a lock wait or a git call from hanging or growing without bound. Every user-visible limit next to them already has a key (`timeout_ms`, `max_*`, `checkpoint.max_files` and `max_total_bytes`). They stay constants, and a new one needs a key only if a user could meaningfully choose a different value:
  - `tools/native`: `bashReadChunkSize` 32 KB, `ripgrepMaxStderrBytes` 8 KB, `processOrphanPollInterval` 25 ms, and the 2 s wait for a killed child after a failed process-manifest write.
  - Moved to keys (2026-10-15, audit B7.1): the post-SIGKILL wait and the post-exit pipe drain of bash, exec and hooks are now `kill_deadline_ms` (default 2000) and `drain_after_exit_ms` (default 500), 1 to 60000, next to `kill_grace_ms`. `process` has its own manager and takes neither.
  - Moved to keys (2026-10-16, audit batch 9): `tools.native.grep` and `tools.native.glob` take `kill_grace_ms`, `kill_deadline_ms` and `drain_after_exit_ms`. Defaults keep the old values: grep 250 / 1000 / 500 ms (the grace is 1 to 60000 because zero would fall back to the default), glob 2000 / 2000 / 500 ms (the glob grace may be 0 and sends SIGKILL at once). The old `globKillGrace` constant is gone; the grep fallbacks (`ripgrepKillGrace`, `ripgrepKillDeadline`, `ripgrepDrainDeadline`) only apply to a settings value built outside the loader. Changed after the earlier decision not to expose them, because the project rule puts timeouts in config and the cost is three optional keys.
  - `sessionlock`: `acquirePollInterval` 25 ms.
  - `checkpoint`: `maxStderrBytes` 4096 (error text kept from a failed git call), `killWait` 5 s, and `maxGitOutputBytes` 256 MB, the ceiling for one git listing or diff, sized for a workspace at the `max_files` ceiling. If `max_files` is ever allowed above its current maximum, raise this ceiling with it.
  - The audit read only constants written as `N * time.X` or `N * 1024`, so this list is not a complete inventory of literals in the module.

- **A run start loads the session settings once (2026-10-16, audit F-28).** `LockSession` needs the config only for the transcript path, and `Resolve` needs all of it, so a run start loaded the same files twice (0.38 to 0.51 ms, 1124 allocations; now 0.24 ms, 633). `LockSession` now keeps the config it loaded, with a `sessionfs.SettingsStamp` of the session file, the profile files, the toolset file and the catalog folders it read, and `Resolve` takes it once. It is used only when all of these hold: the transcript lock was acquired without waiting (`Lock.Waited`), the entry is under `lockedConfigMaxAge` (1 s), and every stamped file and folder still has its size and modification time. Otherwise `Resolve` loads as before. The lock release drops an unused entry, so the checkpoint and mutation routes, which lock without resolving, park nothing.
  - **Stamp timing:** each file and folder is stamped just before it is read (`catalog.ScanObserved` reports each folder before listing it). A file or folder modified within `racyStampWindow` (2 s) of its stamp is never current, because a file system keeps times at a coarse granularity and a same-size edit in the same tick would look unchanged. A run start right after a catalog edit therefore loads twice, as before.
  - **Not stamped:** prompt documents, env files, sub-agent folders and the cwd. A change to only one of those is not seen by a `Resolve` that takes the parked entry. Any `Resolve` of the same session, profile and model within `lockedConfigMaxAge` can take it, not only the run start's own, so a read-only route may see such a file up to 1 s old. `lockedConfigMaxAge` and `racyStampWindow` are internal bounds, not user limits, like the constants in the entry above.
  - **Why not a path-only loader for `LockSession`:** the transcript path comes out of the composition of root defaults, session, profile, models and toolset, and every other profile's storage entry. A second implementation could drift, and then `LockSession` would lock a different file from the one the run writes.

## A silent provider stream and the number of concurrent runs (Go only, 2026-10-15)

A run's context has no deadline and the provider stream had no guard, so a provider that accepted the request and then stopped sending (a half-open connection, a stuck proxy) kept the run, its transcript lock and its goroutine until the user pressed Stop. Nothing limited how many runs could start either.

- **`provider_stream.idle_timeout_ms` (session setting, also in `defaults`, `settings` of a session or profile).** Default 300000 (5 minutes), `0` turns it off, otherwise 1000 to 3600000. An absent key takes the default; a null, misspelt or out-of-range value is a configuration error, like `provider_retry`. The default is five minutes because a reasoning model can be silent for minutes before its first event, and the guard is there for a dead connection, not for a slow model.
- **What counts as idle.** The time since the last stream event, from the moment the request is sent (a provider that sends headers and never an event counts). The guard is stopped while the event handler runs and while a retry waits, so slow persistence or a long `Retry-After` is never mistaken for provider silence. It is a watchdog on a child context of that one provider call, so a stop by the user keeps its own error and reads as a stop.
- **What happens.** `openaiapi.StreamIdleError`. It is not retried: the retry loop covers only the opening request, and output may already have been shown. The run fails through the normal path. The client message names only the configured time (`The model provider sent nothing for 5m0s, so the run was ended. Details are in the server log.`); the log carries the error.
- **The runner identity includes the setting**, so a changed value builds a new client. The anthropic adapter is a separate service and is not changed.
- **`server.max_concurrent_runs` (root setting).** Default `0`, which is no cap and the old behaviour; 1 to 1024 caps the runs running at once across all sessions. A start beyond it is refused with HTTP 429, `Retry-After: 5` and a message naming the setting; the transcript lock is released and nothing else changes. Finished runs, which stay in the registry for `run_state_retention_ms`, do not count. A queued start waiting for its own session's transcript is not a running run and is not counted until it begins. Sub-agent runs are part of their parent run and are not counted. The default stays off because a fixed number would refuse legitimate sub-agent-heavy use; an operator who exposes the server to scripts sets it.
- **Not done here.** A total run deadline (`max_run_duration_ms`) and a `ResponseHeaderTimeout` on a dedicated provider transport. The idle timeout already ends the silent-after-headers case; the header timeout needs a transport clone in `newProviderStreamer` that also changes the OAuth and `http_debug` wrappers.
- **`messages.jsonl` is not touched.** A run ended by the guard is recorded like any failed run, outside the transcript (see "Failed runs outside messages.jsonl").

## Deleting a session releases its children; shutdown has a deadline (Go only, 2026-10-15)

- **Delete closes the session's MCP and process managers.** `DeleteSessionConfig` calls `Resolver.releaseSessionChildren` after the file is removed. MCP managers are keyed by `<setting path>\x00<profile>[\x00toolset\x00<id>]`, so every key with the deleted session's setting path as prefix is closed and evicted, which stops the stdio server children. Before, they ran until the server stopped. This happens for both `state=keep` and `state=delete`, because the session no longer exists to reach them. A session created again under the name builds new managers.
- **Managed processes are stopped with the last session that uses them.** A process manager is keyed by its storage directory, and an explicit `tools.native.process.storage_dir` may be shared by several sessions. `Resolver.processSessions` records which session files use each manager; delete removes the session from the set and closes the manager (stop with reason `session_closed`, as at server shutdown) only when the set is empty. The default storage directory is per session and profile, so normally the first delete closes it. The earlier choice was "survive deletion"; it is reversed because a running process of a session that cannot be reached any more is a leak the user cannot see or stop. A user who wants a process to outlive its session must start it outside the session.
- **Not covered:** the manager's directory and manifests stay on disk (only `state=delete` removes the state folder, and tool storage lives under the session cwd), and sub-agent runs were already cancelled by the delete handler.
- **`server.shutdown_timeout_ms` (root setting).** Default `10000`, 0 to 300000, 0 waits without a limit (the old behaviour). `jad` cancels active runs (`service.Close`), then `Server.Shutdown` waits for in-flight requests at most this long; when it runs out the remaining connections are closed, a warning is logged and the process exits normally. The ordinary exit is unchanged. Before, one stuck request kept the process alive until SIGKILL. The adapter keeps its own fixed 10 s.
- **A transcript store is opened outside `Resolver.mu`.** `sharedStore` used to hold the resolver lock while it created the directory, opened the journal and ran `Recover` (journal tail repair, staging scan), so the first session list after a start, or the first run of a session, made every other resolver lookup wait behind each open in turn. It now inserts a `storeEntry` under the lock, opens the store without it and closes `entry.ready` when done: callers of the same key wait for the one open, other keys proceed in parallel. A failed or panicking open removes its entry, so the next call retries, as before. The cached store and its incompatible-settings check are unchanged. If the session is deleted while its store is opening (`forgetStores` removes the entry), the opener and its waiters get a 404 `session was deleted` and the store is dropped, so a deleted session's `messages.jsonl` is not reopened or recreated.
- **`http_debug` hygiene.** Response headers now go through the same credential redaction as request headers (`Set-Cookie`, `Authorization`, `*api-key*`); the recorded URLs drop the userinfo password and mask the value of query parameters whose name contains `key`, `token`, `secret`, `signature`, `sig`, `password`, `auth` or `credential` (`[REDACTED]`), keeping order and the other parameters. The directory is created `0700` (was `0755`; an existing directory keeps its mode). New `http_debug.max_total_bytes` (session setting, default 268435456, 0 keeps everything, max 1 TiB): when the first request of a process starts logging, the oldest `request<N>`/`response<N>`(`.body`) files beyond it are removed; other files in the directory are never touched, and ids continue after the highest existing one. Pruning runs once per process, so a long run can exceed the cap until the next start. Redaction is by name, so a secret in an unusually named parameter or in a body is not caught; bodies stay opt-in.
- **Not done (the fallback cap was added later, see "The content-cache fallback cap and the SSE write deadline"): a cap on the run content cache fallback (B-C6) and one shared image `Store` per directory (D-9).** The fallback holds the same text `webui.StreamingRun` already keeps in its parts, so a cap would not bound the run's memory, only truncate the replayed snapshot. A long-lived shared image `Store` would count its quota once and never see files removed outside the process, which is worse than the per-run rescan (about 20 ms for 10,000 files, measured once).
- **`messages.jsonl` is not touched.**

- **`native.fetch` reuses connections per validated destination (B-P1).** `tools.native.fetch.keep_alive_ms` (default 30000, 0 to 300000; 0 restores a fresh connection per request) and `max_keep_alive_hosts` (default 8, 1 to 64). The `FetchStore` that sessions share owns a `fetchTransportPool` keyed by scheme, hostname, port **and the validated IP**; every call still runs `validateFetchURL` and pins the dial to that IP, so a DNS change or rebinding produces a different key and a new connection, never a reuse of a connection to an address that was not validated for this call. Idle entries are dropped after `keep_alive_ms` and the least recently used host is closed at the cap. `Resolver.Close` closes the pools; a closed pool makes `Do` fall back to a one-shot transport. Redirects still go through validation and the pool one hop at a time. Measured (loopback TLS, one machine, 300 requests x 3): 1.80-1.87 ms per request fresh, 0.058 ms pooled; a remote handshake costs more, how often one run refetches one host is not measured. Not covered: HTTP/2 (the transport still disables it through the custom dialer), and connections the server closes first are redialed by `net/http`.

- **`native.fetch` gains `user_agent`, `truncate_oversized_response`, `cache_ttl_ms` and the schema lists `include_metadata`/`include_images`.** `user_agent` (string, 1 to 512 chars, no control characters, default `Mozilla/5.0 (compatible; jad-fetch/1.0)`; Go's default agent is often blocked). `truncate_oversized_response` (bool, default false): the stored document is cut at `max_response_bytes` (trailing partial UTF-8 rune trimmed) and marked `truncated: true` on every page, including page 2+ and cache hits; the cursor `<uuid>.<utf16 offset>` indexes the stored Markdown, not the network body, so offsets stay consistent and the cursor format does not change; off keeps `response_too_large`, whose message now names the limit and the key. `cache_ttl_ms` (int, 0 to 86400000, default 0 = off): an in-memory index maps both the requested URL and the `final_url` to a stored document id; a hit returns a new page 1 of that document without a request, after `validateFetchURL` on the requested URL and the cached `final_url` (the store is shared and allow/deny policy may differ per caller); the index is lost on restart and there is no eviction. HEAD pre-checks were rejected: an extra round trip and DNS/pin validation, many servers answer HEAD with 405 or a wrong length, the result can change before the GET, and the decoded size is unknown. `include_metadata` and `include_images` were already accepted by the loader but missing from the schema (`additionalProperties: false` rejected them); the schema now lists them. Known limits of the cache: the key is the raw requested URL and ignores the settings and `user_agent` that shaped the stored document; a hit revalidates only the requested URL and the cached `final_url`, not the redirect hops in between. With defaults the success output of `messages.jsonl` is unchanged; the `response_too_large` error text changed (it now always names `truncate_oversized_response`).

- **Reasoning effort per run (`<model>@<effort>`).** A model file may list `efforts` (for example `["medium","high","xhigh"]`). A model reference written `<category>/<name>@<effort>` (run body `model`, a subagent's `model`) selects that effort for the run: `sessionfs.SplitModelEffort` splits it, `SessionConfig.ReasoningEffort` carries it, and `WithModel` sets `request.reasoning.effort` on the loaded model (other request keys stay). The file's own `request.reasoning.effort` is the default when no `@` is given. **Limits:** an effort not in `efforts`, or `@` on a model without `efforts`, is a client error (400, not a config error); the effort name may hold letters, digits, `-`, `_` and `.`. The effort changes `Model.Request`, so `fingerprintRunner` gives each effort its own runner and nothing is shared across efforts. A model that does not use `request.reasoning` as an object is refused when an effort is chosen. **Not done yet:** the frontend picker, listing `efforts` in the models endpoint, and removing the per-effort model files. **Profile `model_default` may be `<id>@<effort>`.** Effort precedence: run `model@effort` > the profile default's effort > the model file's `request.reasoning.effort`. The default's effort applies only when the effective model id equals the default's id (a run naming another model gets that model's own default; the same id without effort keeps the default's effort). The effort is validated against the model's `efforts` (profile load: config error with the `model_default:` prefix; model-default endpoint: client error). `models` stays plain ids. The echoed `model_default` (snapshot, ETag) keeps `@effort`, and the model-default endpoint persists `id@effort` as written.

## `profile_message`: ask another profile and get its final answer (Go only)

`tools.native.profile_message` lets the model send a message to another profile of the same session (every profile of the caller's session except its own and those in `deny_profiles`) and get that profile's final answer. This entry records the config and the behavior the tool must have; the config side is in `sessionfs/native_profile_message_settings.go`.

- **Config.** `deny_profiles` (optional, null or omitted = empty; unique ids; each is `category/name` only (a bare id is a load error, since profile ids are always `category/name`) with segments `[A-Za-z0-9][A-Za-z0-9._-]*`, the same pattern as `httpapi/handler.go` `profileNamePattern`; ids not in the session are ignored; the old `profiles` key is now an unsupported key). The allowed targets are computed when the tool is built from `SessionConfig.Profiles` minus `deny_profiles` minus the caller's own `SessionConfig.Profile`; an empty result is a config error raised when the tool catalog is built (tools listing returns 422, a run fails with 422), not at session load; `jad check` reports it for every profile of every session (`sessionfs.ProfileMessageTargets` and `ProfileMessageNoTargetsError` are shared with the catalog, so the text is identical). A listed profile may still be uncallable (it shares the caller's transcript: `profile_same_transcript`; it is broken: `profile_failed`); `deny_profiles` is the way out. `timeout_ms` (default 600000, 1 to 3600000) and `result_max_bytes` (default 16384, 1 to `maxNativeToolBytes`). An unknown key is the usual unsupported-key error. Exposed as `SessionConfig.NativeProfileMessage`; schema in `sample/schemes/setting.schema.json`, manifest `sample/tools/native/profile_message.json`.
- **A failed target run reports its client-safe message.** `profile_failed` reads "Profile X failed: <message>", where the message is the one the target run itself reported (`ProfileRun.Failure()`, the `error` event of the run: provider HTTP status, token limit, or the generic withheld-details line). Raw error text never reaches the caller.
- **A busy target queues the message as an async handle (2026-10-24, user decision, replaces "busy target fails fast; `busy_wait_ms` queues").** `profile_message` is an async handle kind (`profile_message`, ids `pm_` + 8 hex digits) like `process` and `subagent`: it takes a flat `block_ms`, returns the answer inline when the target answers within it, otherwise a handle that `async` wait, list, status and stop work on. The owner is the calling session (or the child's run id when a sub-agent has the async tool), so owner scoping, stop, reset and delete fan out through the async manager unchanged, and a handle found running after a restart is `lost`. A message to a target that a user run, another caller's message or a mutation holds does not fail: it is a handle in the `queued` state and starts when the target is free, first come first served per target (`app/profile_message_queue.go`; the line is one `targetQueue` per `session\x00profile`, and while it exists every arrival joins it, so a later caller never overtakes an earlier one). `tools.native.profile_message.max_queued_per_profile` (default 4, 0 to 256) bounds the line; a message over it fails at once with `profile_busy` naming the cap and registers no handle (`0` means a busy target fails at once). **`busy_wait_ms` is kept, with a new meaning:** the longest a queued message may wait for its target before it ends as `failed`/`profile_busy` ("still busy after waiting N ms"); `0` (default) sets no limit of its own and `timeout_ms`, which now bounds the whole life of a message, queue time included, is the limit. Stopping a queued handle removes it from the line; stopping a running one stops the target run (the same stop as the user's). **The result lives in the handle record:** when the target run ends, its final assistant text (else the last text it wrote), cut to `result_max_bytes` and to the manager's status limit, is saved in the record of that call (`asyncmgr.Record.Detail`), so `async wait`/`status` deliver it once even after the target moved on to another caller's task; a failed, stopped or timed-out message keeps whatever text the target had written. A reference to the target's turn (`<session>/<profile>#<turn id>`, `Record.Trace`) is stored for inspection and is never put in an entry. No summary model call is made. **Without the async tool** (a session or a child that cannot collect a handle) the call waits for the end of the message like before and ending the call stops the target run; with no handle to leave behind, a busy target fails at once unless `busy_wait_ms` > 0, which then lets that call queue inline for at most that long. The model-facing schema gained `block_ms`; the tool description says so. The old synchronous `Message` entry point is gone: `ProfileMessenger.Prepare` checks (cycle, chain, same transcript, all before a handle or a run exists) and returns a plan, `Start` queues or starts it. `httpapi.ProfileRunRequest` replaced `BusyWait` with `Wait` and `WaitLimit`, and `ProfileRun.TurnID()` exposes the turn. A message from a sub-agent keeps the chain guard (`max_chain`, cycle) because `Prepare` runs the same checks with the session's profile as the caller.
- **A wait-for loop between profiles is refused as `profile_cycle` (2026-10-24).** The cycle guard looked only at the caller's own chain, so A (busy with a user task) messaging B while B (busy) messages A queued both behind each other until `timeout_ms`. The resolver now keeps, per session, the edges "profile P is blocked on profile T": one for each call that waits for an answer (an inline call, a `profile_message` with `block_ms` above 0, or an `async` wait on a message handle), for as long as it waits. A new blocking message is refused when its target is blocked on the caller, directly or through others. Because an edge exists while the call waits, it covers a target that is running a message from the caller (it is busy because of that waiting call), a target busy with a user turn that is blocked in `profile_message` or in an async wait, and a target whose own message is queued. A handle nobody blocks on (`block_ms: 0`, or after the call returned a handle and nothing waits on it) is not an edge, so it never refuses a message. Edges are counted in memory under the queue set's mutex and removed when the wait ends. **Not covered:** a target blocked on something other than `profile_message` (a long tool, a provider call, a sub-agent), a loop that closes only through an async wait started later (the first message is then already running; the later wait is what makes the edge), and a loop through two sessions (the guard is per session). Those still end by `timeout_ms`.
- **The target runs with its own settings.** The run is an ordinary run with `supports_interaction`: a `request_draft` question is shown in the target's pane and waits for the user, like a user's run.
- **Depth is 1.** A run started by `profile_message` cannot call `profile_message`.
- **The target run is an ordinary run of the target, started through the same code as a user message** (`httpapi.ProfileRunStarter.StartProfileRun` in `httpapi/profile_run.go`: `tryStartRun` then `executeRun` on a goroutine). The message is the user turn of the target's transcript, written by the same `boundRunner.Run`. The run streams on `run/stream` (the target's pane attaches to it), stops with the normal stop route, is retained like any run and releases the transcript lock when it ends. The caller's tool only waits on the run's `done` channel and reads its final response; there is no nested `Runner.Run`, no second failure recorder and no auto-approval.
- **`compact` (`off` default, `on`).** With `on`, the target's transcript is compacted, with the target's own `compaction` settings, before the first `profile_message` call to that target in the caller's current run (one `boundRunner.Run`: a user message and all its tool rounds). Later calls to the same target in that run skip it; a different target compacts once itself; the caller's next run compacts again. Any other value is a config error. The compaction runs in `ProfileRunRequest.BeforeRun`, which `StartProfileRun` calls after `tryStartRun`/`acquireRun` returned (transcript lock held, run registered) and before the target run goroutine starts, so a user send cannot slip in and turn the call into `profile_busy`; `Session.Compact` needs only the in-process `runMu`, which no run holds yet. Compaction does not take the mutation gate: the held transcript lock and the registered run already exclude user sends and mutations. A compaction failure is logged (`profile_message compaction failed`) and the message is sent anyway; nothing to compact counts as done. The "already compacted" set is `Resolver.callerRuns`, keyed by a per-run id (`callerRunKey` in the context) and dropped when `boundRunner.Run` returns. The model-facing tool schema does not change.
- **No `messages.jsonl` format change.** No new record type or marker.
- **A caller without a session key is refused.** `ownerKey` must contain `"\x00"`; otherwise the call fails with `profile_failed` instead of resolving an empty reference.
- **A target run that fails is recorded by `executeRun` like any run** (run-error cache); a stop or cancel records nothing. A failed run gives the caller `profile_failed`.
- **`profile_failed` returns a generic line to the model,** without the error text.
- **A caller stop returns a rendered `cancelled` error result,** not a bare context error.
- **A target that shares the caller's transcript returns `profile_same_transcript`** (`native.ErrProfileSameTranscript`): "Profile X shares this conversation and cannot be called". It is not `profile_busy`, because retrying never helps. The test is equality of the messages path after `filepath.Clean` and symlink resolution (`filepath.EvalSymlinks`, falling back to the resolved parent directory joined with the base name when the file does not exist yet) of the caller's path, carried in the run context by `boundRunner.Run`, and of the target's resolved runner; a missing caller path is an error (fail closed, checked before the target is resolved), not "different". The store cache is keyed by the unresolved cleaned path, so two symlink aliases of one file get two stores; this check only refuses them. There is no second resolve of the caller, and the held run mutex is not part of the test: a target that is merely running is `profile_busy` (`TryLockSession` is the only busy test).
- **A target whose run ends with no answer text returns `profile_no_answer`** (`native.ErrProfileNoAnswer`, a non-OK result "Profile X finished without an answer"), not an empty success. If the final response has no text, the last non-empty text of an earlier committed response of the run is the answer. Unlike a sub-agent, which uses earlier text only after an error, `profile_message` also does this on success, deliberately: returning `profile_no_answer` after the target acted would invite a repeat of its side effects. The caller may therefore get earlier narration of the run. The error is only for a run in which no response had text.
- **The target's transcript is the ordinary (session, profile) transcript,** so the target keeps its context across calls and the user sees the exchange as normal turns.
- **A run whose context ends while it waits for the run lock** returns the context error and stores no input (the input is persisted only once the lock is held); the HTTP layer records the run as aborted. The wait is a 1-slot channel (`runMutex`, `app/run_mutex.go`), not a poll.
- **Maintenance waits on the run lock (compact, reset, front-compact, user state context, checkpoint restore) are cancelled with the request context** (`runMutex.LockCtx`) and return the context error, so nothing is changed; the HTTP layer shows 500 as for any context error.
- **A toolset used by a sub-agent cannot configure `tools.native.profile_message`.** It is a config error naming the toolset ("a sub-agent cannot message a profile"); the key was accepted and silently ignored before.
- **The target run carries `source` `profile_message` and `caller` (the calling profile id)** in `runs_by_profile` and the `run` SSE frame (both omitted for user runs); the frontend uses them for the busy marker only.
- **A profile_message run is NOT counted toward `server.max_concurrent_runs`.** The caller is itself a counted run, so counting the target would make `profile_busy` permanent at cap 1. `registry.beginFrom` skips the cap check and the `running` counter for any run with a source.
- **Stop on the target cancels its run.** The caller gets `profile_stopped` ("Profile X was stopped"); a stop records no run failure. A server shutdown or a session delete also cancels the run, so the caller may be told `profile_stopped` or `cancelled`. A stop or a `timeout_ms` of the caller (ctx end) stops the target run (`ProfileRun.Stop`) and the tool returns the timeout or `cancelled`.
- **The chain is carried by the run, not by the context (2026-10-23, replaces "depth is one").** The target run is detached from the caller's context, so each `profile_message` run records the chain of profile names it descends through (`ProfileRunRequest.Chain`, read back with `RunningProfileRunChain`). A message is refused with `profile_cycle` when the target is already in the caller's chain, and with `profile_chain_too_long` when the chain with the target added is longer than `tools.native.profile_message.max_chain` (default 2, 2 to 8, config only, not visible to the model). The default keeps the old behaviour: A may message B, B may not message C. A chain of two names for a user run is just the caller.
- **No config key was added.** The frontend marks the target row and composer from `source`/`caller` and keeps the marker while the pane streams the run.

- **`profile_message` in a sub-agent (2026-10-23, user decision; design_nesting_and_approval.md part A, step 2).** An agent's `tools` list may name `profile_message` (opt-in like `async`; the session must enable it and have another profile, otherwise the session fails to load with an error that says so). Only the agent's `tools` list governs it: not `allow_write`, not read-only or `SubagentChangeTools`. The call is made as the session's profile (the identity of the root run), over that profile's transcript, so the same-transcript, busy and `busy_wait_ms` rules apply unchanged. The chain starts with that profile, so child → B → child of B → A is refused as a cycle, and the chain cap bounds the rest. A toolset used by an agent still cannot configure `profile_message`. A child that has the async tool gets a handle owned by its run (the run's end removes it and stops the message); a child without it waits for the end of the message and its cancel stops the target run. A child cannot ask for approval, so a `profile_message` with `approval: ask` returns `approval_unavailable` for it.

## `tool_smith`: scripts that call native tools in code (Go only)

`tool_smith` has two operations, `list` (the saved functions in `functions_dir`) and `run` (a TypeScript function body in an external interpreter child that returns one value). Settings are `tools.native.tool_smith`; the tool is off unless that key is present. The config surface is step 3 of `plan_tool_smith.md`; the run and bridge code come in later steps.

- **Keys** are `nativeToolSmithKeys` (`internal/sessionfs/native_tool_smith_settings.go`): the bash-style child keys without `env_file` and `paths`, plus `functions_dir`, `code_max_bytes`, `result_max_bytes`, `nested_result_max_bytes`, `nested_request_max_bytes`, `max_nested_calls`, `max_parallel_calls`, `list_max_results`, `list_max_files`, `list_header_bytes`, `function_max_bytes`, `tools` and `interpreter`. `sample/schemes/setting.schema.json` lists exactly these (`TestExecAndReadImageSchemaKeysMatchTheLoader`).
- **Defaults and ranges** (minimum 1 unless noted): `functions_dir` `.jad/functions` (non-empty); `code_max_bytes` 262144, `result_max_bytes` 16384, `nested_result_max_bytes` 16384, `nested_request_max_bytes` 65536 (each up to 10485760, `maxNativeToolBytes`); `max_nested_calls` 100 (max 10000); `max_parallel_calls` 4 (max 64); `list_max_results` 50 (max 1000); `list_max_files` 200 (max 10000); `list_header_bytes` 2048 (max 65536); `function_max_bytes` 65536 (max 10485760); `tools` `["read","grep","glob"]`, unique native names; `interpreter` `["bun","run","{file}"]`, 1 to 32 non-empty strings, one containing `{file}`. The child keys keep bash's defaults (`timeout_ms` 120000, `max_timeout_ms` 600000).
- **Own `Child` block.** The child-process settings are read from `tools.native.tool_smith` into `NativeToolSmithSettings.Child`; nothing is taken from `tools.native.bash`. `env_file` and `paths` are not keys, so a script child has no env file and no path policy of its own.
- **Scheduling.** The tool is `ReadOnly: true`. `MayChangeFiles` is true only for a call that contains `run`, so a run is serial and checkpointed while `list` can run in parallel.
- **Library `exec` limits.** The saved `exec` function (workspace file `.jad/functions/exec.ts`, not shipped by the repo) removes `TOOL_SMITH_*` and `EXEC_RESULT` from the env it hands to programs. With `background:true` it spawns the job without `detached`, so it stays in the tool_smith child's process group: it survives the call but the run-end sweep (`kill_children_on_run_end`) kills it when the run ends. Anything that must outlive the run belongs in the `process` tool.

- **Sub-agents never get `tool_smith`.** `childToolPools` skips its tool ID explicitly (a `ReadOnly` tool would otherwise land in the sub-agent read-only pool), and the nested catalog of a run applies the same exclusion. `bash`, `exec`, `process`, `subagent`, `tool_smith` and `task` can never be in `tools`, so the bridge never runs them for a script. That list is exported once (`sessionfs.NativeToolSmithExcludedTools`) and used by the loader and the bridge.
- **A value that is too long is cut, not spilled.** A return value over `result_max_bytes` is cut with a visible truncated marker, a nested result over `nested_result_max_bytes` is cut with `truncated` in its info, and a script over `code_max_bytes` is refused, never cut. There is no spill file for the return value in v1.
- **Bridge.** The script reaches native tools through one Unix socket in a private (0700) per-run directory; the socket path and a per-run random token reach the child as environment variables, so there is no extra file descriptor.
- **Listing shows the call expression (2026-10-17).** The saved-function listing prints one legend line, then `fn.<name>(<params>)   <name>.ts — <description>` per function, so an agent types the first column unchanged. `tool_smith` names must match `^[a-z][a-z0-9_]*$`, so every listed name is a valid identifier and there is no bracket form (a file like `my-helper.ts` is reported as malformed, not listed). `fn.<name>` calls the file's `export async function <name>` only, with no member passthrough, which is unlike `exec`. Calling behaviour is unchanged. `filters` still match the name and description.
- **Trust level: a script is as powerful as `exec`/`bash`.** The `run` body is an unsandboxed bun/node program running as the server's user: it can read and write any file, open the network and start processes (`node:fs`, `node:child_process`, `fetch`) without going through the bridge. The `tools` allowlist, `tools.deny`, the excluded list govern only calls made through `tools.*`; they are not a sandbox. Approving a `tool_smith` run is approving arbitrary code. The tool description the model sees says the same (one sentence), and `run` is serialized and checkpointed like `bash` through `MayChangeFiles` while `list` stays parallel.
- **Bridge hardening.** The socket is `chmod 0600` right after `Listen` (failure aborts the run) and the work directory must be mode 0700 after `MkdirTemp`. Same-uid boundary: the token is in the child's environment, readable by any process of the same user (`/proc/<pid>/environ`), so the token and the modes protect only against other users, not against another process of the same uid (which can already do what a script can). A request frame over `nested_request_max_bytes` is answered with `frame too large` and that connection is closed; the server never buffers more than that per frame. The prelude's own input buffer (replies from the server) is not bounded.
- **Nested context.** The bridge forwards `OnFileChange`, `RequestInteraction`, `OnInteractionResolved`, `ProcessOwner` and `ProcessOwnerLimit` of the outer call (like `subagent_call.go` does for a child), so a nested write is reported like any other. `nested_calls` counts calls that got past the gate and ran, not refused or cancelled attempts; a result without an INFORMATION block gets a minimal one when counters exist.
- **No per-call `timeout_ms`.** The `run` schema has no `timeout_ms`; only `tools.native.tool_smith.timeout_ms` (clamped by `max_timeout_ms`) applies. A call that passes it is `invalid_input`.
- **New config key `nested_request_max_bytes`** (default 65536, 1 to 10485760): the largest request frame a script may send over the bridge.
- **No `messages.jsonl` impact.** Nested calls are not written to the transcript; the outer `tool_smith` call and its result are an ordinary tool call and result. A session without the key is unchanged.
- **Known deferrals (review of the first version).** (1) `fn.<name>` is implemented (see the next entry). (2) `list` bypasses the read path rules: it checks workspace containment and symlinks only. (3) The prelude's reply buffer in the child is not bounded. (4) A `bridge_error` without an id (frame too large, malformed frame) fails all pending calls of the script. (5) The number of per-frame goroutines is not bounded before the parallel/writer gate. (6) `nested_calls` counts calls that failed schema validation, because the count happens before `ExecuteFunctionCall` validates. A panic inside a frame is answered with `bridge_error: internal error` and does not end the backend.
- **`fn.<name>(input)` stages a validated copy of the library per run.** Before the child starts, `stageToolSmithFunctions` (`internal/tools/native/tool_smith_fn.go`) resolves `functions_dir` with the `list` rules (workspace containment, symlinks, name regex, `//` header, `export async function <name>` signature) and copies each valid `*.ts` file (at most `list_max_files` scanned) into `<workDir>/fn/` (dir 0700, files 0600). A file larger than `function_max_bytes` counts as malformed and is never copied. A manifest (`fn-manifest.json`, path in `TOOL_SMITH_FUNCTIONS`) lists the available names (cut at `list_max_results`), the malformed files with their problem, and a library error. The prelude exposes `fn` as a Proxy that imports `./fn/<name>.ts` at the first call, and sets `globalThis.tools` and `globalThis.fn` so a saved function can use both. Calling a malformed name throws `function X is malformed: <problem>`; an unknown name throws `no saved function X; available: ...`. An unusable library never fails the run; it only makes every `fn.X` throw. Trade-off: the copy is eager (up to `list_max_files` x `function_max_bytes` of I/O per run even if `fn` is unused), chosen over a lazy import so every path and symlink check runs in Go before the interpreter sees a file. Nested calls from a saved function use the same bridge and count toward `max_nested_calls`. No `messages.jsonl` impact: only the outer `tool_smith` call is recorded.

## The content-cache fallback cap and the SSE write deadline (Go only, 2026-10-16)

Two bounds from the performance audit (P-044, P-045). Both keys are under `server` in the root setting, are in `sample/schemes/root-setting.schema.json`, and are read in `sessionfs/roots.go`; `app/config.go` carries them into `httpapi.Config`.

- **`run_content_fallback_max_bytes`** (default 67108864 = 64 MiB, 1024 to 1073741824). When the `responses.partial` file cannot be created or written, the run keeps the streamed text in memory. That copy now stops at the cap, cut on a UTF-8 boundary. Text after the cut is dropped from the cache only; the live stream, the run's own parts and the transcript still get all of it.
- **What a late subscriber sees at the cap.** `Snapshot` and `SnapshotPrefix` return the kept bytes followed by `runContentTruncationMarker` ("[... output truncated: ...]"), so the cut is visible in the text, not silent. `Length` is the number of bytes that can be read back (at most the cap), which keeps the snapshot-outside-the-lock logic of P-033 consistent. The warning `run content cache truncated` is logged once per run with `limit_bytes`.
- **The committed message is never the cut text.** `setCommittedMessage` used to fill an empty message text from the cache; it skips the cache when `Truncated()` is true, so the marker cannot be written into a message. The committed text comes from the runner's parts, as before. A client that attached late gets the full text from the final `ui.message` (or a reload) once the run finishes.
- **A file that fails after it spilled** switches to the same capped fallback: the bytes read back from the file and the failed batch are added through the cap.
- **`sse_write_timeout_ms`** (default 30000, 0 to 300000, 0 disables). `serveSSE` sets `http.ResponseController.SetWriteDeadline` before every write. A frame larger than 64 KiB is written in 64 KiB chunks with the deadline renewed for each chunk, so the limit measures a reader that makes no progress, not the time a large snapshot needs to drain; a slow but moving mobile client is not cut. On a write error the handler returns, `detach` closes the queue and the frames are released. The deadline is cleared when the stream ends because the connection may serve another request.
- **`http.Server.WriteTimeout` stays zero** (see `app/config.go`); the deadline is per write, set by the handler, so long-lived streams are not cut.
- **Not changed:** terminal frames are still always queued (the budget `sse_max_buffered_bytes` is unchanged). They are released when the dropped handler's queue is closed.
- **No `messages.jsonl` impact.**


- **Sub-agents may use `async`, scoped to their own run (2026-10-22; overrides design_async_manager.md 6.2.1 caveat 2).** A sub-agent definition may list `async` in `tools` when the session enables `tools.native.async` (otherwise the load error says to add `"async": {}` under `tools.native`); `subagent` and `tool_smith` stay refused (no nesting). A child without a tools list does not get `async`. The child's `async` and `process` use the run id as the owner (`ProcessOwner`), so its handles are invisible to the parent and the parent's ids are `unknown_handle` to the child. When the run ends its handles are stopped and removed (`DeleteOwnersWithPrefix(runID)`) and its processes are stopped as before (P-037 group kill unchanged); nothing of the child enters the parent's list, unread signals, SSE counts or prompt notice. Toolsets named by an agent share the session's async host.
- **`subagent` is an async tool (2026-10-22, design_async_manager.md WP3).** A call with a `task` blocks up to `block_ms` (default and cap from `tools.native.async` `default_block_ms` / `max_block_ms`) and then returns a run id while the child keeps working; the start call's context ending stops the wait, never the run. `id`, `stop` and `wait_ms` are removed from the tool, and so are `tools.native.subagent.wait_ms`, `max_wait_ms` and `allow_detached_writers` (clean break, an old key is rejected). `async` `wait`, `list`, `status` and `stop` act on the run, which is a handle of kind `subagent` owned by the session key; `ref` is the child's `messages.jsonl` (else the run record). `ok` is true only for run state `done`; `timed_out`, `stopped`, `failed` and `lost` keep their own state with `ok:false`. A call with no task still lists the agents (the runs are listed by `async`). A start over the async handle cap returns `async_capacity_reached` and creates no run. **Writers stay blocking:** an agent that can change files never gets a handle, never enters the async index and ignores `block_ms`, because its checkpoint belongs to the calling turn; cancelling that call cancels the run. A session without the async tool has no handles either, so its sub-agent calls also run to their end. The `.runs` manifests and `keep_finished` pruning are unchanged; a child's own processes are still owned by its run id and stopped when the run ends. Cancel-on-stop/reset of a session's runs is unchanged (`SubagentManager.CancelOwner`); extending it to every handle kind is WP4.
- **The async tools: config, prompt notice and run-stream counts (2026-10-22, design_async_manager.md WP5/WP6).**
  - **Q7, enforced at load.** A session config that enables `tools.native.process` or `tools.native.subagent` without `tools.native.async` is rejected (`tools.native.<tool> needs tools.native.async ...`): such a session could start work and never collect or stop it. The shared test fixture `layouttest` adds `async` to any native block that has either tool. `sample/jad/tools/coding/full.json` gained `"async": {}`.
  - **New key `tools.native.async.sse_max_ids`** (default 10, 0 to 100, 0 = counts only): the most live handle ids the run stream's `async_state` event carries. Nothing else is new in the settings; the stale process (`wait_timeout_ms`, `max_wait_timeout_ms`) and sub-agent (`wait_ms`, `max_wait_ms`, `allow_detached_writers`) keys were removed in the commits that changed those tools, and `setting.schema.json` text that described the old process actions was rewritten.
  - **`async_state` SSE event.** `{turn_id, active, unread, ids}`: counts and at most `sse_max_ids` live ids (newest first), never summaries. A run publishes it when the session has any handle, then on change, coalesced to one event per `tool_stream_interval_ms`; the last published state is replayed to a client that attaches later, and a session that never had a handle sends nothing. It is run state, not transcript. The manager notifies through `Manager.Watch` (a callback under the manager's lock that only signals a channel); the resolver sums the managers of the session and the HTTP layer owns the coalescing (`httpapi/async_state.go`). `frontend_new` reads it into `onAsyncState` (counts only) and already ignored unknown event names; nothing renders it yet (decided, Q8: no UI in phase 1).
  - **Prompt notice.** `statecontext.triggers.<t>.tools` accepts `async` (it needs `tools.native.async`). The section lists the session's pending handles only (live, or finished and unread): id, kind, state, label, `unread`, at most `list_default_limit` of them, plus `active`/`unread` counts and `has_more`; never summaries or results. It is trimmed like the other providers when the snapshot exceeds `max_bytes`. The process and subagent providers stay as they are; a profile that wants the notice adds `async` to its trigger's tools.
  - **No automatic wake-up.** Nothing here makes the model call `async`: the notice and the event only report counts. A handle is collected by `async wait`.
- **`tool_smith` is an async tool and its schema lost the `list` object (2026-10-22, design_async_manager.md WP7, requested by the user).**
  - **Schema.** `list:{filters}` is gone. A call with no `run` lists the saved functions; `filters` is a top-level array (used only for listing; given with `run` it is ignored and the result says `ignored: filters`). `run` keeps `function` and `input` and gains `block_ms`. A call with neither `run` nor `filters` is a list, no longer `invalid_input`. `ChangesState` is unchanged: only a call with `run` is serialized and checkpointed.
  - **Filters.** Case-insensitive; every filter must match the function name or the description. A filter containing `*` or `?` is a wildcard pattern matched against the whole text (`read*`, `*file*`, `r?ad`), linear time; any other filter is a substring as before.
  - **Async.** `run` blocks up to `block_ms` (default and cap from `tools.native.async` `default_block_ms`/`max_block_ms`); a script still going gets a handle (`smith_<8 hex>`, kind `tool_smith`, owner = session key) that outlives the call. A script that ends within the block returns its result and marks the signal read. The script runs on its own context, so a cancelled call never kills it; only `async stop`, a session stop/reset/delete (the manager fan-out), the script's own `timeout_ms` or server shutdown end it. The result text is written to `<tool storage>/.async/tool_smith/<id>.txt` (the handle's `ref`), swept after the longer of `retention_days`/`unread_ttl_days`. After a restart the handle is `lost`; its work directory and interpreter are gone. Without the async tool (or without a session key) the call runs to its end as before.
  - **Approvals.** None since 2026-10-23: a script's nested tools run at once, in the foreground or the background.
  - **Config.** `tools.native.tool_smith` now needs `tools.native.async`, like process and subagent. No new keys. Nested calls of a handle script still cannot reach `async`, `process`, `subagent`, `tool_smith` (excluded list), and a sub-agent never gets `tool_smith`.
  - **Known gap.** A background script may change files after its turn ended; the turn's checkpoint does not cover them (same as background writers).
- **Writer sub-agents may run as async handles (2026-10-22, requested by the user; overrides "Writers stay blocking" above and design_async_manager.md Q6).** New session keys `tools.native.subagent.background_writers` (default `false`) and `max_background_writers` (default 1, 1 to 32). A call to an agent that can change files is a handle (it honours `block_ms`, registers with the async manager under the session key, and the stop, reset, delete and shutdown fan-out of WP4 applies) only when all of these hold: `background_writers` is on; the session has the async tool; and the session has fewer than `max_background_writers` writer runs going (queued ones count; `SubagentManager.reserveWriter`, kept per owner from the start to the run's end). Anything else keeps today's behaviour: the call runs to its end. **Cap fallback:** a writer over the cap does not fail; it runs to its end and its result carries `background_note` saying why. **Checkpoint gap, accepted for phase 1:** the checkpoint belongs to the parent run, and its "after" tree is taken when that run ends, so what a background writer changes later is in neither tree and a `safe` restore may not undo it. The tool text, the running result (`backgroundWriterNote`) and the setting's schema text say so. **Changed files:** the handle's signal summary and its `status` start with `changed files: ...` (from the run's `OnFileChange` list, so `changed_files_max` above 0 is needed; `none (changes made by bash, exec or process are not listed)` when the list is empty). **Restore:** `POST .../checkpoints/{id}/restore` returns 409 ("cannot restore a checkpoint while a background sub-agent that can change files is running") while the session has one (`httpapi.SessionWriters`, implemented by the resolver over every sub-agent manager); a dry run is allowed. **No path locks (Q-W6):** only `PathLocks` on single write and edit calls exist; the tool text tells the model to leave the writer's paths alone. The agent list marker is `[can change files; may run in the background]` for such an agent and still `[can change files; runs to its end]` for the others. **Restart:** unchanged; a running writer becomes `lost` and its manifest keeps the files recorded so far (a test pins this, for the sub-agent result and for the async status). A child's own processes are still stopped when its run ends. **Tests:** `subagent_background_writer_test.go` (handoff and collection, off by default, ask tool blocks, static check, cap fallback with note, cap per session, stop/reset/delete reach it with a goroutine baseline, list marker, lost writer keeps files), `httpapi/checkpoint_background_writer_test.go` (409, dry run, no writer), settings tests in `sessionfs`; mutations (never hand off, no cap, 409 threshold) each broke a test.

- **Nesting: a child may start children and run scripts (2026-10-23, user decision; design_nesting_and_approval.md part A, step 1).** An agent's `tools` list may now name `subagent` and `tool_smith` (like `async`, they are opt-in: an agent without a list never gets them). Naming `subagent` needs `tools.native.subagent.max_depth` of 2 or more, naming `tool_smith` needs `tools.native.tool_smith` in the session; otherwise the session fails to load with an error that says which. **Config, not visible to the model:** `tools.native.subagent.max_depth` (default 2, 1 to 8; 1 = only the session starts children), `max_runs_per_root` (default 16, 1 to 1024: runs going below one top-level run), `max_runs_per_session` (default 32, 1 to 1024: runs of the session at any depth, counted when a child starts one). `ExecutionContext.AgentDepth` (0 in the session, 1 in a child) and `RootRun` carry the position; a child's `SessionKey` is the session's, so a nested run belongs to the session for the limits, the restore guard and delete. **Fail fast:** a start from inside a child never queues; with no free slot it answers `subagent_busy`, beyond the depth `subagent_depth_exceeded`, beyond a run cap `subagent_limit_reached` (a queued parent that waits for its own queued child could otherwise never be freed). **Ownership:** a handle a child starts is owned by the child's run id (its `async` sees only those); a child without the async tool gets no handle and the call runs to its end. - **`exec` is an async tool (2026-10-25, user request; same pattern as `tool_smith`).**

- **`exec` takes JSON input, saved functions and `argv` (2026-10-25, user request, experimental; `tool_smith` stays JS/TS only and unchanged).** Design: `design_exec.md`. This supersedes the "Interpreter table", "Code delivery" and "Tolerant names" bullets of the `exec` section above.
  - **One input, three modes.** `code` (with `lang`), `function` (a saved one) or `argv` (a program run directly, no shell); none of them, with or without `filters`, lists the saved functions. Giving two names both ("give either code or function, not both"); `lang` with `function` or `argv`, `args` with `argv`, and `filters` with a run are refused naming the keys. The schema is flat and requires nothing, so the executor, not the schema, names what is missing. The near-miss names (`language`, `interpreter`, `source`, `script`, `program`, `command`, `stdin`, `workdir`, `dir`) are no longer rewritten: the schema refuses them with the right key (`RejectedProperties`). One way to say each thing is the lesson of `tool_smith`'s `run`/`function` confusion.
  - **Input is JSON on stdin.** `input` (any JSON value) is written to the program's stdin as one line; without it stdin is empty. Code therefore cannot travel on stdin: `tools.native.exec.langs` became `runners` (the old key is refused with a message naming the new one) and `code` became `mode`: `arg` (default; `{code}` in argv, e.g. `python3 -c {code}`; bash and sh get `exec` as `$0` so `args` start at `$1`), `file` (`{file}`, a 0600 file in the call's scratch directory) or `stdin` (legacy; refused for a call with `input`, naming `runners.<name>.mode`). Code containing NUL is refused in mode `arg`. `args` stays beside `input` (compatibility); `input` is the way to pass data.

The runner is the first one in table order that declares the extension (`.sh` is bash's). The description is the first line of the leading comment block (`#`, `//` or `--`, after a shebang); an optional later `input:` line is shown in the listing. No manifest, so description and code cannot drift; no header overrides of runner or timeout. Listing, filters (`*`/`?` wildcard else substring, every filter must match name or description) and truncation reuse `tool_smith`'s helpers and shape; a malformed file is listed under "malformed files". A call reads the file once from a handle opened without following links, with the same containment checks (inside `functions_dir` and the workspace, regular file, size cap), and runs that text, so an edit during a run changes nothing. An unknown name lists up to 5 similar names; two files with one name are refused.

No config key. Links, files and other modes are left alone. It does not cover a server that shares its temp directory with another live server run for over 7 hours on the same call, which the ceiling excludes.

  - **Not done.** No tool bridge from scripts. No Windows run. `go`/`rust`/`java` runners are not defaults (a toolchain cannot be assumed); add them under `runners` with mode `file`. Edges: a saved function cannot choose a runner other than by extension.

A plain command is `lang` bash with the command as `code`. The folder name is a runner name (not an alias) from the `runners` table and selects the language, so the earlier extension-ownership rule for `.sh` is gone. A helper is any regular file whose name matches `^[A-Za-z0-9][A-Za-z0-9_.-]*$`; dotfiles are skipped; sub-folders stay usable by the language (a Python package). The same name may exist in several languages.
  - **No template, no bridge, no callback.** Nothing is injected around the code. A runner's `lib_env` names the list variable that receives `functions_dir/<runner>` in front of its current value: bash and sh `PATH`, python `PYTHONPATH`, node `NODE_PATH`, ruby `RUBYLIB`, perl `PERL5LIB`; empty turns it off, and a configured runner such as `ts` sets its own. Code then calls a helper the way the language does: a command on `PATH` (the file needs a shebang and the executable bit), `import`, `require("name.js")` (CommonJS only: ESM `import` ignores `NODE_PATH`), `require`, `use`. `JAD_FUNCTIONS_DIR` is the real library root, so a helper reaches another language by a plain subprocess of `$JAD_FUNCTIONS_DIR/<runner>/<file>`. Helpers call helpers the same ways because children inherit the environment. The variable is set only when the library resolves inside the workspace and the runner's folder is a real folder inside it.

A host without `bun` gets the usual "not found" error for `ts` only.

It installs a global `fn`; `fn.<name>` resolves `functions_dir/<runner>/<name>` when read (a helper written by the same program works) and a missing one fails with `no helper fn.<name> in <folder>`. js uses sync `require` (no top-level `await` in a helper; its functions may be async), python and ruby use identifier-like names, `fn["my-helper"]` / `getattr(fn, "my-helper")` for a dash; path-like names are refused. Validation findings are in `design_exec.md` section 4.
  - **Limits stated.** There is no depth counter: a cycle A to B to A ends at the one timeout. Stop, reset, delete and restart kill the child's process group (`kill_process_group`), so helpers that stay in it die with it (tested); one that calls `setsid` escapes, as with `bash`. Only the top process's output is captured (nested stdout is part of it), and one `$JAD_RESULT` file serves the whole tree. The interpreter follows symlinks itself, so containment is checked for the listing and for the folder that goes on the path, not for each import. The container is the boundary.
  - **Listing.** Grouped by runner in table order, `name — description (input: ...)`, same limits and filters as `tool_smith`. Entries outside a runner folder, folders that are not runners, bad names, missing descriptions, oversize files and symlinks out of the library are listed as malformed.
  - **Code.** `planExecFunction`, `planExecArgv`, `loadExecFunction`, extension ownership and the `args` handling are deleted; `shellChildRun` gained `prependEnv`.
  - **Listing shows the call, `fn.<name>` is callable (2026-10-27, user decision).** The exec listing prints the expression to type (`fn.read(...)   read.ts — description`; `fn["my-helper"](...)` for js, `getattr(fn, "my-helper")(...)` for python, `fn.public_send("my-helper", ...)` for ruby, the file name for bash/sh) under a legend that states the rule; filters still match the file name and description. The value of `fn.<name>` is both the module and callable: ts/node call the default export, else the export named like the file (`-`/`.` as `_` or camelCase), else the only function; python the function named like the module, else the only public function defined in it; ruby `self.call`, else `self.<name>`, else the only singleton method, and `fn.<name>` without arguments is still the constant. Sync `require` and the name rules are unchanged; a `_template` override written earlier keeps its old behaviour. design_exec.md no longer says there is no template.

## Native transcript tool (2026-10-27)

- **Single `path` input (rework).** `profile`, `session`, `subagent` and `list` are gone; the old keys fail naming `path`. `path` is `profile:<category>/<name>` (current session), `profile:<session>/<category>/<name>`, `subagent:<run id>`, `subagent:<category>/<name>/<run id>`, `subagent:<session>/<category>/<name>/<run id>` or `path:<file>` (still off unless `allow_path`); no `path` reads the own transcript, and for a sub-agent its own run, found from `ExecutionContext.ProcessOwner` (the run id the manager sets for a child). An unknown prefix, empty segment, `.`/`..`, backslash or NUL is refused with the list of forms. Not found lists the nearest names (`suggest_max`, default 20, replaces `list_max_entries`); the read header prints the exact `path` to reuse; a cursor carries it and is re-checked on every page.

- **Sub-agent grammar follows the layout.** A run lives inside the profile that started it (`<profile tool storage>/.subagents/<call-id>-<hex>/messages.jsonl`, manifest in `.runs/`), so `subagent:<session>/<run id>` is gone and fails with `invalid_path` naming the new forms. `subagent:<run id>` is a run of the caller's profile; `subagent:<category>/<name>/<run id>` and `subagent:<session>/<category>/<name>/<run id>` are runs of another profile, found through the same profile lookup as `profile:` and then the profile's live manager or its manifest on disk. Access switches are unchanged.
- **`transcript` in INFORMATION.** `subagent` (all outcomes with a transcript folder), `profile_message` (target file; the caller's own as `caller_transcript`) and `transcript` (the file read) report the full path of the relevant messages.jsonl under the key `transcript`. It is shown regardless of what the caller may read: the container is the boundary, a path grants nothing, and `transcript`/`read` keep their own path rules. A `profile_message` handle's async `ref` is the target file, as a sub-agent handle's is.
- **Phase 5.** The header reads `turns A-B; the transcript holds turns C-D` (turn numbers, not a count) and adds that the transcript was compacted when C is above 1. Checked by hand against six real transcripts of 18 KB to 1.5 MB: 0.6 to 16 ms a call, output within `response_max_bytes`. Not built: `list` of other sessions and profiles, the `running` flag, a line index cache; (`list` was later removed.)
- **Phase 4.** Selectors `profile` (with `session`), `subagent` and `path` are exclusive (two given: the error names both; `session` alone names `profile`; a cursor already names its transcript and takes none). `profile` goes through the profile messenger's `Profile` lookup (`ProfileMessagesPath` plus the loaded backup path; it loads no run and creates no file). `subagent` resolves the run id with `SubagentManager.RunTranscript` (folder and owning session key); a run of another session needs `allow_other_sessions`, one the caller did not start needs `allow_children`. `path` needs `allow_path` and the read path rules, with symlinks resolved and a transcript check on the first line. A transcript of another profile or session also has to pass the read path rules and the call's path scope (they are checked on the real file, outside the workspace). A cursor carries its selector, so every page is checked again with the current switches. `source: backup` does not apply to `subagent` or `path`.
- **Phase 3.** Filters `role` (user, assistant, tool), `tool` (glob on the tool name; a result is tied to its call by `call_id`), `search` (case-insensitive, with `context` entries around each hit; it matches only entries that pass the other filters) and `source: "backup"` for `messages.backup.jsonl`. A cursor remembers its source, and a different `source` with a cursor is an error.
- **Phases 1-2.** `tools.native.transcript` (off unless the key is present; needs `transcript` in `tool_definition_paths`) reads the caller's own `messages.jsonl` by turn (`turns` N, N-M, -N, N-; `tail`; default the last turn) as text, with a `cursor` to continue a cut response. Design in `design_transcript_reader.md`. Turns are numbered by `session_turn`, so a compacted transcript starts above 1 and the header says so. A cursor holds a hash of the first line and the byte range; a compaction or reset changes the hash and the call fails with `cursor_stale`. Each entry is cut to `entry_max_bytes` (head and tail kept), the response to `response_max_bytes`, a line over `line_max_bytes` is skipped and reported, and a transcript over `scan_max_bytes` is refused. (Output and `entry_max_bytes` are superseded by the v2 section below.)
- **Selectors.** Exactly one of `profile` (with optional `session`), `subagent` or `path`. `path` is off unless `allow_path` is true and follows the read tool's path rules. `subagent` resolves the run id through the sub-agent manager: the subagent result carries the transcript path only for a stopped, timed-out or lost run (and a handle's end), so the id, which the manager always knows, is the reliable key.
- **Settings.** Unknown or old keys are rejected naming the key; `timeout_ms` is capped at 6 hours; the tool has no `paths` key (it reuses `tools.native.read.paths`, like `read_image`). Foreign sessions, profiles and children are readable by default; `allow_other_sessions`, `allow_other_profiles`, `allow_children` turn each off.
- **Read-only scanner (later phase).** The reader opens the file read-only and never uses `Journal.ReadRecordsRange`, which opens the transcript read-write and truncates an incomplete last line.

## `provider_network`: the address family of provider connections (Go only, 2026-10-25)

A host whose direct IPv6 route to the provider is reset mid-stream (a peer reset while reading) while IPv4 works could not be helped: providers used `http.DefaultClient`, and Go only falls back to the other family when a connect fails, not when a read does. HTTP/2 was ruled out as the cause by the report, so there is no HTTP-version option.

- **`provider_network.network` (session setting, also in `defaults`, `settings` of a session or profile).** `"tcp"` (default, either family, nothing changes), `"tcp4"` or `"tcp6"`. An absent key takes the default; a null, non-string, unknown value or unknown key is a configuration error naming the allowed values or the key.
- **Unset changes nothing.** With `tcp` and no OAuth or HTTP debug the provider client stays `nil`, so the SDK keeps `http.DefaultClient`.
- **One base transport.** For `tcp4`/`tcp6` `http.DefaultTransport` is cloned once (proxy from the environment, TLS and `ForceAttemptHTTP2` stay) and only `DialContext` is replaced, with the default dialer's 30s timeout and keep-alive. The OAuth wrapper and the HTTP debug wrapper both sit on that one transport. With an HTTP(S) proxy the family applies to the dial to the proxy, because that is the connection the transport opens.
- **Errors.** A failed dial reads `provider_network.network is "tcp6": <cause>`, so `tcp6` on a host without IPv6 points at the setting.
- **The runner identity includes the setting**, so a changed value builds a new client.
- **Not retried over the other family.** A request that failed after it was sent could have been started by the provider; retrying elsewhere risks a duplicate generation and bill. The user picks the family.
- **Not covered:** the anthropic adapter (a separate service with its own config), the `fetch` tool (pins addresses for SSRF safety), MCP, `decide`, and the OAuth token refresh clients.

## A toolset-based agent may list `subagent` and `profile_message` (Go only, 2026-10-25)

An agent that names a `toolset` could not list `profile_message`: the child pool was built from the toolset's tools only, and the toolset (which must not set `profile_message`) never has it, so loading failed with "the session does not enable tools.native.profile_message". `subagent` already worked, because it is added to the agent's catalog by name. Now the session's own `profile_message` tool is added to the pool of an agent with a toolset, so `tools: ["grep","subagent","profile_message"]` loads and gets all three. A toolset file that sets `tools.native.profile_message` is still a configuration error; the agent's `tools` list still alone decides whether it gets the tool; a session without `profile_message` still fails to load for an agent that lists it. Nesting limits and narrowing are unchanged.

## Native transcript tool v2: a step index and step detail (Go only, 2026-10-28)

Design in `design_transcript_v2.md`. Reading a transcript cost one entry per record, each up to 4 KB, so finding one step meant paying for all of them. v2 has two modes, chosen by `step`.

- **List (no `step`).** One line per step, `turn.step` (`3.2`). A turn starts at a user message (`N.0`); every later assistant message, tool call and reasoning item takes the next number in file order. A tool call and its result are one step. Numbers are the same whatever `turns`, `tail`, filters or cursor select, and compaction does not renumber (turn numbers still come from `session_turn`). A user or assistant line is its text cut to `preview_bytes`; a call line is `call <tool> <ok|error|unknown|no-result> <result bytes> <args>` with each argument value cut to `value_bytes` and the keys whole; a result is not a line (an orphan result is); reasoning is listed nowhere, so numbers have gaps where it was. Filters `role`, `tool`, `search`, `context` stay; search tests the full text, including a call's arguments and result, and prints only the preview.
- **Detail (`step`).** `3.2` or a range `3.1-3.4` (may cross turns), `part` call, result, both (default) or reasoning (never shown unless asked). The text of the steps is one stream paged by byte offset in `max_detail_bytes` (and never above `response_max_bytes`) on rune boundaries; the cursor carries the step range, part, offset and file identity. Not with `turns`, `tail`, `role`, `tool`, `search`, `context`; `full` is rejected.
- **Middle cut.** `midCut` keeps 70% head and 30% tail on rune boundaries with `...+N bytes...` in the middle, total within the budget; a budget too small for the marker returns the bare marker, or the text if that is shorter.
- **Settings.** New `preview_bytes` (200), `value_bytes` (80), `max_list_entries` (100), `max_detail_bytes` (16384), capped. `entry_max_bytes` and `max_turns_per_call` are removed and rejected naming the key.
- **Unchanged.** `path` grammar, access switches, the read-only scanner, `source: backup`, symlink and path-rule checks, cursor identity; the strings `transcripts` prints still work.
- **Known limit.** A detail cursor is a byte offset into text rebuilt for each page; a call that gets its result between two pages (the file only grew) can shift the stream.
- **Measured** on the 323 messages.jsonl files of `.jad/state` that are over 20 KB (57.7 MB): listing every turn took 22.0 MB of output with the old tool (entries cut at 4 KB) and 1.4 MB with the list mode, 6.4% of it.

## Native transcripts tool (Go only, 2026-10-26)

`tools.native.transcripts` lists what `transcript` can read; design in `design_transcripts.md`. It is separate from `transcript` (which dropped `list` on purpose), off unless the key is present, and needs `transcripts` in `tool_definition_paths` (`sample/tools/native/transcripts.json`).

- **Input.** `path` (none: the profiles of the caller's session; `sessions`; `session:<id>`; `profile:<category>/<name>` or `profile:<session>/<category>/<name>`: that profile's sub-agent runs), `filters` (the `tool_smith` rules: substring, or `*`/`?` wildcard, all must match the name; for runs also the agent name and parent call), `status` (runs only), `limit`, `cursor`. An unknown key fails schema validation naming it.
- **Output.** Plain text, newest first by last activity (mtime of `messages.jsonl`, for a run its end or start when it has none), one line per item with the exact `path` to give `transcript` and the full file path, size and time, and for profiles whether `messages.backup.jsonl` exists. No message counts: that would scan every file. The legend line is printed only when there are items. A missing directory lists as empty, never an error.
- **Paging.** The cursor is keyset (last activity and key), so a profile created or a file touched between pages never repeats or drops an unrelated item. It carries the level, filters and status and is checked again against the current switches.
- **Access.** Own switches with the meaning they have for `transcript`: `allow_other_sessions`, `allow_other_profiles`, `allow_children`, all default true, so `transcripts` can be on while `transcript` is off or stricter; a listed path may then still be refused by `transcript`. With the switches off only the caller's own profile and its runs are listed. A run is listed under the rule `transcript` applies to reading it. A file the read path rules deny (`tools.native.read.paths`, narrowed by a sub-agent's scope) is left out and counted under `hidden`.
- **Read-only.** It stats files and reads run manifests (`.runs/<id>.json`); it never opens a transcript and never uses the repairing `Journal` reader. A `messages.jsonl` that is a symlink is followed only while its target stays in its own folder, and a run folder must stay inside the sub-agent storage directory, else the item is listed as `unreadable` with no size.
- **Runs.** Manifests on disk and the live manager are merged (the live state wins). With `persist_runs` off the header says finished runs have no manifest and only runs the running server holds are listed. A profile without the subagent tool says it has no sub-agent storage.
- **Caps.** `max_entries` (default 50, cap 500), `scan_max_entries` (2000, cap 50000; more candidates fail with `too_many` and ask for filters), `timeout_ms` (30 s, cap 6 h). `max_entries` may not exceed `scan_max_entries`.
- **Code.** `TranscriptTarget` gained `PersistRuns`; `profileMessenger` gained `Sessions`; `SubagentManager.allRuns` lists every retained run. `transcript` itself is unchanged.
- **Not covered.** Non-catalog sessions (the profile source refuses them), the `path:<file>` kind, and message counts.
