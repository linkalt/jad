# Go backend migration: initial dependency decisions

**Status:** The Go backend implements the OpenAI Responses streaming adapter and staged transcript recovery, a multi-round session runner with native and MCP tool execution, explicit and automatic compaction, the core HTTP/SSE routes, effective session tool discovery, and normalized live UI streaming. Native tools and the MCP client are implemented; OpenAI OAuth is intentionally excluded. Full TypeScript API/config parity and a live differential harness remain outstanding, so this document records current boundaries rather than a claim of complete parity.

The module path in `go.mod` (`example.com/agent-harness/backend-go`) is a placeholder until the repository's canonical import path is known.

## HTTP server

Use the Go standard library's `net/http` for the local API; the bounded route slice uses a small injectable `http.Handler` to centralize compatibility behavior. It provides request contexts and SSE flushing without an additional server framework. Do not add Fiber or raw `fasthttp` unless measurements show the HTTP server itself is a bottleneck.

`internal/httpapi.Handler` exposes `GET /api/health`, authenticated `GET /api/library` and `GET /api/library/{kind}/{id}`, session catalog/history/message/profile/model/files/tools routes, run start/attach/stop, and session compact/reset/front-compact. The session tools route returns the selected profile's effective native and MCP definitions. Root-library access is injected; responses are `no-store`, and configured library directories are reloaded on each request. Session lookup/config selection and transcript maintenance are injected; auth, CORS, body-size, SSE-buffer, and run-retention settings are explicit inputs. A disconnected start subscriber does not cancel an accepted run. Compaction retains configured request history through a compaction-cache overlay and resets derived caches; reset clears the transcript, backup, and known per-profile caches. Front-compaction removes the active transcript suffix beginning at a user record; configured recoverable mode archives the removed bytes in `<messages.jsonl>.deleted-history`, while permanent mode does not archive, and both invalidate derived caches. Live UI streaming normalizes reasoning and text deltas, function-call announcements and argument deltas, and tool results into cumulative messages; attach/reconnect streams replay the current message and terminal state. Remaining route/config parity is not claimed. Optional `http_debug` captures bounded provider HTTP request/response details asynchronously and redacts sensitive request headers.

## Filesystem session resolution and bootstrap

Run the current server with `go run ./cmd/agent-backend`. `AGENT_API_TOKEN` is required and must be at least 32 bytes; `HOST` and `PORT` override listener settings. Session model files select their API key through `api_key_env` (default `OPENAI_API_KEY`, or `OPENROUTER_API_KEY` for OpenRouter-compatible settings) and may set a custom `base_url`. API-key auth is supported; OpenAI OAuth is intentionally out of scope, and Go rejects `auth_mode: "openai_oauth"` rather than silently accepting it.

Root discovery follows the TypeScript precedence: `JAD_SESSIONS_DIR` selects one `default` root and bypasses root settings; otherwise `JAD_ROOT_SETTING_PATH` or `setting.json` in the working directory/parent can provide `session_roots` (or legacy `session_paths`), with `.jad/sessions` as the fallback. Multi-root requests use `root-id:session-id`; an unqualified ID is accepted only when it resolves uniquely. With one root, canonical references stay unqualified.

The resolver reads session `setting.json`/`model.json`, path-profile model and storage selection, prompt documents, and persistence settings for the current runner. It shares a single `TurnStore` per transcript path and serializes runs that use shared storage. Cross-process locking, live TypeScript differential tests, other API route families, and full session-config parity remain out of scope.

## OpenAI client

Use the official `github.com/openai/openai-go/v3` SDK behind a small adapter. The existing backend uses the Responses API, including streaming, custom provider base URLs, and function calls; keep SDK-specific types out of session and persistence code.

The v3.66.0 SDK is pinned in `go.mod` and was tested against an offline HTTP/SSE fixture. It provides `Responses.NewStreaming` and `ResponseStreamEventUnion.RawJSON()`, supplying raw event JSON to the compatibility/persistence layer. Its README states v3.45.0 and later require Go 1.25+. The current environment is Go 1.27.1; confirm the deployment Go version before cutover.

Do not reconstruct persisted provider events solely by marshaling typed SDK structs: preserve unknown response fields and verify the raw-event path in tests.

## JSON

Keep JSON operations behind a small internal boundary. Start with `encoding/json` for the first compatibility implementation. Evaluate Sonic against representative transcript/config/stream fixtures and benchmarks before adding it. Sonic's upstream documentation notes behavior differences from the standard library, including HTML escaping; the OpenAI SDK also performs its own JSON handling, so Sonic will not replace the SDK's decoder.

The `messages.jsonl` observable representation is a compatibility contract. Serialization tests must cover ordering, escaping, numeric values, unknown fields, and the exact line shape before changing serializers.

`internal/transcript.Journal` appends caller-supplied JSON objects, repairs an incomplete final line, supports hash-based idempotent append for a rendered file, and serializes transcript reads with writes. It syncs for `turn`/`strict` durability. `TurnStore` stages `response.output_item.done` items in `items.jsonl` plus `items.index.jsonl`, commits them in output-index order, filters minimal/full response metadata, compacts usage, and writes a hash-tracked canonical completion line. It also appends input batches with TypeScript-compatible batch metadata and expands raw input/`response.completed` records back into request-history items. Offline fixtures cover ordering, unknown fields, metadata modes, large items, duplicate commits, and Node-generated input-batch lines.

Recovery repairs partial message/item/index tails, retains unfinished turns without a final record, and completes or removes turns whose final record is present, using its hash to avoid duplicate transcript lines. Retained streaming turns are not yet reopened for writing. The `internal/session.Runner` serializes runs, normalizes and persists inputs, derives the next turn number from transcript records, builds requests from model settings and prompt configuration, streams raw Responses events, and commits completed or incomplete responses. Its provider-neutral stream interface keeps SDK types outside orchestration. Function calls execute through the session `ToolCatalog`; results are persisted and may feed follow-on provider rounds within configured limits. Explicit and automatic compaction are supported, with statecontext refresh after successful automatic compaction. Request history is reconstructed from `messages.jsonl` rather than optional history/usage caches, and a live differential harness against a running TypeScript store remains outstanding.

## Deferred integrations

The MCP client is implemented with session-scoped connection reuse, stdio and Streamable HTTP transports, tool discovery, schema validation, and bounded result conversion. OpenAI OAuth remains intentionally unported; the Go backend supports API-key authentication and custom base URLs, and rejects unsupported OAuth configuration explicitly.

## Compatibility gates

Before cutover, test the Go implementation against the TypeScript baseline for:

- `messages.jsonl` output and recovery behavior;
- Responses stream events, including incomplete/failure events and function calls;
- HTTP JSON and SSE event shapes used by the frontend;
- custom provider base URLs and API-key handling;
- cancellation and session/run lifecycle behavior.

Keep test sessions isolated so the two implementations never concurrently write the same session data.

## Cross-process locking

The TypeScript backend has no cross-process session lock: it assumes one server process per session directory and only guards the partial-response cleanup (`responses.partial.cleanup-lock`). The Go backend goes further. `internal/sessionlock` takes an advisory `flock` (`LockFileEx` on Windows) on a hidden `.<file>.jad-lock` beside `messages.jsonl` and `setting.json`, so two Go processes cannot interleave writes to one session. Lock files are persistent and never removed, and workspace file listings hide them.

This is a deliberate superset, not a parity gap. It is the only on-disk difference the differential harness (`tools/differential`) ignores. It does not make mixed use safe: the TypeScript backend never takes these locks, so a TypeScript and a Go process writing the same session concurrently remain unsupported. Making that safe would require the TypeScript backend to take the same locks, which is out of scope for this port.

## Interactions that ask the user

A tool that must ask the user cannot answer itself and cannot read the run stream, so the question waits in a per-run broker: the tool hands over the dynamic JSON it proposes, the run publishes it as **message state** (`WebUiMessage.pending`, so a reload or a second tab still sees it), and the promise settles when the answer endpoint replies, the deadline passes, or the run stops. The tool result then carries the outcome back to the model as an ordinary `function_call_output`, so an interaction adds no transcript item type and `messages.jsonl` keeps its format.

Keep these rules when porting:

- The **in-code definition is the contract**; the shipped document under `sample/tools/native/` is an enablement manifest whose `inputSchema` must equal the code schema exactly (the loader refuses a divergence, and a test asserts the two are deep-equal).
- Dynamic JSON payloads are accepted with **configured bounds** (`max_draft_bytes`, `max_draft_depth`, `max_title_chars`), measured the same way in both places they are checked: the tool before it publishes a question, and the answer endpoint before it applies the user's edit. The limits travel **with the question**, not in a second config lookup, so the check always follows the question that is waiting.
- The **session config owns the wait**: `timeout_ms` is what the run publishes and the model has no argument that could change it. The user may push the deadline out from the drawer — `extend_ms` per press, the whole wait capped at `max_timeout_ms` — and an extension **republishes the question** with its new `expires_at`/`max_expires_at`, so every client shows the same time left.
- Report what the user changed as `changed` — the **paths** the edit differs at, relative to the proposed draft — so the model reads a large edit as a handful of paths instead of a re-read of the whole payload.

## Run streams and how a client learns a run finished

A run outlives the request that started it, and a browser that loses its stream must still end up in the right state. Two streams carry one run — `POST …/run` (the request that started it) and `GET …/run/stream` (attach, for a reload or a second tab) — and **both begin with a `run` frame** naming that run: `{turn_id, started_at, status}`. A client that later reads a session snapshot has to recognize which run the status it sees belongs to; the snapshot reports `run`/`runs_by_profile` with the same `turn_id`, which is how a client whose stream went silent learns that *its own* turn finished instead of waiting for a frame that may never come.

Keep these rules when porting:

- Terminal events are replayed to a subscriber that arrives after the run finished (`ui.message`, then `completed`, then `done`), and the response **ends** after `done` — on both routes. A finished run is retained for `run_state_retention_ms` and then retired; attaching after that answers a single `idle` frame and ends.
- A client may **replace a stream that goes quiet** (the TypeScript client's `run_stream_stall_timeout_ms`): silence is not the same as slowness, because a connection that stops delivering frames neither errors nor ends. Reconnecting is safe at any point in a run — the attach route replays the newest `ui.message` snapshot, so a client that missed every delta is correct from that frame on, and a client that already saw the terminal events finishes immediately.
- A tool that asks for an interaction (`WebUiMessage.pending`) survives all of this: the question is message state, so a reconnecting or attaching client sees it in the snapshot it replays.

## Parallel tool calls and the SSE keep-alive (TypeScript 479509f)

Tool calls of one provider response run with bounded concurrency (`max_parallel_tool_calls`, default 8, range 1–64; `1` restores strict order). The Go port keeps the TypeScript contract:

- Each result is published to the client the moment its call settles, so the stream follows completion order. `messages.jsonl` is unchanged: every result is persisted once, after the batch, in call order.
- After the first error no further call starts; calls already running settle and every result that completed is persisted. A cancelled run cancels all in-flight calls through the shared context.
- A user-decision tool (`request_draft`) in the response still runs alone; the other calls get the `user_decision_required` placeholder.
- A quiet run stream gets a `: keep-alive` SSE comment every `server.sse_heartbeat_interval_ms` (default 5000, `0` disables, max 300000). It carries no event, so a client parser ignores it and only the stall watchdog is reset.
- Slow clients are bounded by `server.read_header_timeout_ms` (default 60000, max 300000) and `server.idle_timeout_ms` (default 5000, max 3600000); `0` disables either. Both backends read the same keys, and the defaults equal Node's `headersTimeout` and `keepAliveTimeout`. Neither backend sets a whole-request or write timeout, because that would cut long-lived SSE run streams.

The Go backend has a structured server log built on `log/slog` (`internal/logging`). It is Go-only: the keys below live in the shared `server` section, and the TypeScript loader ignores them, so one `setting.json` serves both backends, while TypeScript keeps its `console.*` output.

- `server.log_level` (`debug|info|warn|error|off`, default `info`), `server.log_format` (`text|json`, default `text`) and `server.log_file` (default empty = standard error; relative paths resolve against the setting file's directory). The file is opened append-only with mode 0600; a file that cannot be opened stops startup instead of silently dropping records. There is no rotation: use logrotate or the service manager.
- Components receive a `*slog.Logger` by injection (`httpapi.Config.Logger`, `transcript.TurnStoreOptions.Logger`, `httpdebug.Settings.Logger`, `app.WithLogger`). A nil logger discards records; there is no global logger, so the library packages stay quiet in tests and embedders.
- What is logged: a 5xx response with its cause (the response body stays `internal server error`); a recovered panic in a request or a run, with its stack; the run lifecycle (started, finished with status and duration, failed, aborted with its reason); a session skipped from the list for an invalid setting, once per distinct reason (the frontend polls the list, so every skip would repeat); and the existing persistence and cache warnings. At `debug`, one access line per request.
- What is never logged: request or response bodies, prompts, model output, the `Authorization` header, tokens, environment values or query strings. The access line carries a route template (`/api/sessions/{session}/run`), never the raw URL, and a path outside the known routes is `unmatched`, so a client cannot write text into the log through the URL. Provider failure causes are logged server-side only and may name the provider URL or an upstream message; `http_debug` remains the opt-in way to capture bodies.
- Startup and shutdown failures are always written to standard error, whatever the level, because they explain why the process exited.
- Go's process manager and fetch store were already serialized behind a mutex that spans the capacity check and the write, so the two races TypeScript closed (`max_running`, fetch storage capacity) did not exist here; regression tests lock that in.

Go-specific, accepted differences:

- **Order of near-simultaneous results.** Two calls that finish within microseconds publish in an order that depends on the scheduler (a JavaScript microtask queue and Go goroutines differ). Calls whose duration differs by more than scheduling noise publish in the same order on both backends; the differential harness compares only the set for calls that settle together.
- **Heartbeat skipping.** TypeScript skips a frame while earlier output is still queued in the socket. Go writes each frame from one goroutine that blocks on the write, so there is never queued output for the heartbeat to skip behind; a stalled client back-pressures the loop instead.

## Failed runs outside messages.jsonl (TypeScript 3c9a0d7, 7618a15)

`messages.jsonl` is the provider request history: it holds what a provider produced and what the user sent, never an error, so it stays provider-native and cache friendly. A run that fails leaves an orphan user turn there and nothing else. The Go port keeps the failure in its own replaceable cache, like `history-cache.json` and `cursor-cache.json`:

- `staging/run-error-cache.json` (`paths.run_error_cache`) holds `{"schema_version":1,"errors":[{turn, message_id?, turn_id, at, message}]}`, byte-compatible with the TypeScript file. `message` is the client-safe text the browser got as the `error` event, so no response body, path or stack is stored. A missing, corrupt or foreign-version file reads as empty. The file is written atomically under the store lock; a later failure of the same turn replaces the earlier one, and the oldest entries are dropped past `persistence.run_error_cache_max_entries` (default 50, range 1–10000).
- Only `failed` runs are recorded: a user stop is not an error, and a failure before the user input is saved has no turn to belong to. A failed cache write is logged at warn level and never changes the run's outcome.
- `turn` is the session turn whose user message has no answer. `message_id` is `session-user-o<offset>`, the id the web-ui projection gives that user message. `AppendInputItemsAt` reports the offset of the last record of the batch that has visible text, and `PersistedInput` carries it with the turn, so the run hook `RunOptions.OnInputAccepted` fires once the input is stored and before anything that can still fail. An input with no visible text (image only) records the turn without a `message_id`.
- The session snapshot gains `failures` (omitted when empty), the file joins the session etag, and reset, compaction and front-compaction delete the file with the other derived caches, because they re-base turn numbers and message ids. A crash cannot record anything, so a run that died with the process still leaves no trace; the client keeps its "outcome unknown" notice for that case.
- Proof that `messages.jsonl` is unchanged: the same four-run scenario (one provider failure) through the parent-commit binary and the working-tree binary gives byte-identical files (1947 bytes, same SHA-256); the only difference in the session directory is the new `run-error-cache.json`. The differential harness reports all 112 scenarios matching, including the 14 failing-run scenarios that differed before the port.

## Tool approval (TypeScript 18d0d1a, design_approval.md)

A tool whose `approval` is `ask` waits for the user's yes or no before one call runs. It is off by default, and with every tool off nothing is asked and nothing changes. The Go port keeps the TypeScript contract:

- **Settings.** `approval: "off" | "ask"` on `tools.native.write`, `edit`, `bash` and `process` and on each `mcp_servers[]` entry. Only an absent key means `off`: `null`, `"on"` and every other value are config errors, so a typo cannot quietly switch a gate off. `edit` shares `write`'s backup and path settings but never its `approval`. The key is refused (`is not supported`) on tools that cannot ask. A top-level `approval` block holds the shared values: `timeout_ms`, `extend_ms`, `max_timeout_ms` (defaults follow `request_draft`: 300000, 300000, 1800000), `headless` (`deny`, default, or `allow`), `preview_bytes` (4096, 64 to 65536) and `default` (see below).
- **The gate** sits in `Catalog.ExecuteFunctionCall` after the arguments validate and before the tool runs, so a call with invalid arguments is never asked about. `Tool.Approval == "ask"` with no `ExecutionContext.RequestApproval` blocks the call, so a missing wire cannot run it. For `process` only `start` asks; status, wait, list and stop act on what the user already approved.
- **The question** is an ordinary run interaction with `kind: "approval"`; a draft has no `kind` (omitted, so clients that predate approvals see no new field). It appears on the `interaction` event and on `WebUiMessage.pending`. The answer endpoint, the deadline, the extension and the stop signal are `request_draft`'s.
- **One at a time.** The broker holds a single pending question, so `NewApprovalRequester` keeps a mutex that lives for one tool round. A call that needs no approval never reaches it and is not held up.
- **Refusals are results, not failures.** A decline, a missed deadline, a stopped run and an unanswered headless run become a `blocked` function_call_output with `approval_denied`, `approval_timeout`, `approval_cancelled` or `approval_unavailable`, so the model re-plans and the run goes on. The reply endpoint refuses `decision: "update"` for an approval (400), because an edited call would run something the user was not shown, and a decline still needs a reason.
- **Headless runs.** With no client that can answer, `headless: "deny"` blocks the call; `allow` is an explicit opt-out. This differs from `request_draft`, which accepts after its headless timeout, on purpose: a missing user must never approve a command.
- **Differences that are not gaps.** Go's `sync.Mutex` does not promise first-in, first-out, so which of two simultaneous gated calls is asked first can differ from TypeScript; the differential scenario compares the set of questions, the one-at-a-time rule and the persisted order, not the asking order. Approval is a confirmation, not a sandbox: an approved `bash` command runs with the backend user's rights.
- **Proof that `messages.jsonl` is unchanged.** The same scenario (a three-call response with write, read and bash, then two edits and an unknown tool: 12 records) through the parent-commit Go binary and the working-tree binary gives byte-identical files (4738 bytes) with approval absent, and also with write, edit and bash set to `ask` and every question accepted (4 questions). Only random values were masked. The differential harness reports all 124 scenarios matching, including 12 approval scenarios; with the gate disabled in a throwaway build, 10 of them differ.

- **`approval.default` (TypeScript and Go together).** Approval is per tool, so a model refused on one tool can reach the same effect through another that does not ask: with a real model on Go, three timed-out `write` calls were followed by `echo -n "hi" > t.txt` through an ungated `bash`. `approval.default: "off" | "ask"` (default `off`) is the value for `write`, `edit`, `bash`, `process` and every `mcp_servers[]` entry whose own `approval` key is absent. An explicit per-tool value, `off` or `ask`, always wins, and a key that is present but invalid is still an error. It adds no tool the session does not configure, never reaches tools that cannot ask (`read`, `grep`, `glob`, `fetch`, `skill`, `task`, `memory`, `request_draft`), and a process `status`, `wait`, `list` or `stop` still never asks. Only an absent key means `off`; `null` and every other value is a config error with the same message in both backends (`approval.default must be "off" or "ask"`, config-parity cases cover it). Go reads it in `internal/sessionfs/approval_default.go`: the per-tool normalizers are unchanged, and `applyApprovalDefault` runs once after all of them and sets only tools whose key is absent in the raw document. TypeScript passes the value into `normalizeApprovalMode` as its fallback. `messages.jsonl` is unchanged: the same scenario (a write, a read, a bash call, a failing read, an unknown tool, then an edit) on the parent commit and on the new code gave byte-identical files (4,060 bytes, 10 records) with the key absent, `off`, and `ask` with every question accepted, on both backends, and `ask` through the default equals the same three tools set to `ask` one by one. Only the random bash duration was masked, in addition to batch ids, tokens and backup names.

## Run checkpoints and undo (TypeScript 2250d02, design_checkpoint.md)

With `checkpoint.enabled` (off by default) the run records the workspace in a private bare git repository under the session staging directory and the user can undo a run. Nothing is read or written while it is off: no repository, no `checkpoints.json`, no git process.

- **Where it lives.** `internal/checkpoint` has `git.go` (the git commands, the equivalent of `checkpoint-git.ts`), `service.go` (records, snapshots, restore, equivalent of `checkpoint.ts`) and `run.go` (the per-run hooks and `CallChangesWorkspace`). The repository is `<staging>/checkpoints.git` and the list is `<staging>/checkpoints.json`; the record fields are the same as TypeScript's, so either backend reads the other's list. The user's own repository (index, HEAD, refs, stash) is never touched: every git command names its own index file and ignores the user's git configuration.
- **Config.** A top-level `checkpoint` node with `enabled`, `git_binary`, `max_checkpoints` (20), `max_files` (20000), `max_total_bytes` (512 MiB), `timeout_ms` (120000), `include_mcp_tools` (true), `snapshot_on` (`first_mutation` or `run_start`) and `safe_restore` (true). Only an absent key takes a default: `null` and a misspelt value are config errors, so a typo cannot turn undo off. The file and byte limits are placeholders until measured on a large workspace, as in TypeScript. 22 config-parity cases replay settings through the TypeScript loader and compare the messages.
- **The hook.** `Runner.Run` builds the hooks once per run (`checkpoint.NewRun`), takes the checkpoint before the first call that can change files (`write`, `edit`, `bash`, a `process` start, or any MCP tool when `include_mcp_tools`), and closes it in a `defer`, so a run that fails, is stopped or is cancelled still records its end. When a response holds a user-decision tool only that call counts, because the others do not run. A snapshot that fails or is skipped is a record with a warning and never stops the call.
- **Routes.** `GET /api/sessions/{id}/checkpoints` and `POST .../checkpoints/{checkpoint_id}/restore` with `{dry_run?, mode?: "safe"|"full"}`. 404 for an unknown id, 400 for a bad body (the same messages as TypeScript), 409 while a run is active or when the checkpoint has no saved state, 422 when git is unavailable, 401 without the token. The handler refuses a restore during a run before it waits for the cross-process session lock, because a run holds that lock until it ends; waiting first would turn the immediate 409 into a hang. A restore holds the same mutation guard as compaction and reset, so no run starts while files are rewritten, and it records its own `pre_restore` checkpoint so it can be undone.
- **Excluded from a snapshot.** Harness paths that sit inside the workspace (session directory, staging, the task, memory, fetch, process, spill and backup directories) and the `*.bak-<ms>-<hex>` backups, so a restore never rolls back the transcript. A filesystem root or the home directory is refused as a workspace.
- **Differences that are not gaps.** The operating-system wording of "cannot run git" differs between Node and Go; the differential harness compares the prefix. A server restart in the middle of a run is not tested in either backend: the open checkpoint then has no `after_tree`, so only a full restore works for it (the same in both).
- **Proof that `messages.jsonl` is unchanged.** The same scenario (a write and a read in one response, a failing read and an unknown tool, then a second write: 10 records) through the parent-commit Go binary and the working-tree binary gives byte-identical files (3242 bytes) with `checkpoint` absent, `enabled: false`, `enabled: true` (one `complete/run` record written) and `snapshot_on: "run_start"`. Only batch ids, `token=` values, backup names and the temp root were masked. The differential harness reports all 132 scenarios matching, including 8 checkpoint scenarios; with the run hook disabled in a throwaway build 4 of the app integration tests fail.

### A run checkpoint left open by a stopped server is listed as interrupted (TypeScript and Go together)

A record is written `open` when a run takes its snapshot and closed by `Finish`. If the server is killed in between it stays `open` with no `after_tree`. `GET /checkpoints` now reports such a record as `interrupted`, with the warning "The run ended without recording its end (the server stopped or crashed).", whenever no run of the session is live; while a run is live it stays `open`. The state is derived at read time and never stored: the checkpoint service is built per request and cannot know which runs are live, and a write from the list route could race with a run that has just begun and lose its record. Go: `Service.Report(runIsLive)` wraps `List()`, and the HTTP handler passes `run.state() == "running"` from the run registry; a run's status leaves `running` only after the deferred `Finish` has written its end snapshot, so a finishing run is never mislabelled. Applies to `pre_restore` records too. A restore of an interrupted record needs `mode: "full"` (safe answers 409, as for an open one). The stored file keeps `open`. The frontend accepts the new state; an older frontend would reject the list, so the three ship together. Proof: baseline and new code give identical output in 143 of 144 differential scenarios on each backend, and the only difference is the new scenario (`open` becomes `interrupted`).

## Tool call scheduling: ordered by default (TypeScript and Go together)

The calls of one provider response used to start together, so a later call could run before an earlier one on the same file. Measured with edit, edit, edit, read of one file at the default concurrency of 8, 200 runs each: TypeScript applied the edits out of order in 3 (1.5%), Go in 73 (36.5%, because `sync.Mutex` is not first-in, first-out and goroutine start order is undefined), and the read saw the final content in 1 and 2 runs.

New session setting `tool_call_scheduling`, `"ordered"` (default) or `"concurrent"`; only an absent key means the default, `null` and any other value is a config error with the same message in both backends (config-parity cases cover it).

- `ordered`: a response that holds at least one call that can change state runs one call at a time, in the order the model wrote them. A response made only of read-only calls still runs up to `max_parallel_tool_calls` together, so T-008's streaming of results as calls finish is kept for that case.
- `concurrent`: the previous behaviour, with no ordering guarantee between calls.
- "Can change state" is a property of the tool, not of the call: a tool is read-only only when its definition says so (`readOnly` in TypeScript, `ReadOnly` in Go). Native `read`, `grep`, `glob`, `fetch` and `skill` are marked; `write`, `edit`, `bash`, `process`, `task`, `memory`, `request_draft` and every MCP tool are not, so a new tool is serialized until someone marks it. An unknown tool name runs nothing and does not force a serial run.
- A response that holds a user-decision tool still runs only that call; the rest get placeholders, as before.
- Approval gains ordering for free: with a state-changing call in the batch the calls run one at a time, so approvals are asked in the model's order. With `concurrent` the earlier note still applies (approved calls start when approved).
- `messages.jsonl` is unchanged: results were already persisted in call order after the batch. Only the order results are streamed in, and when each call runs, changes.

## Provider retry: the harness retries the request that opens a response

New session setting `provider_retry` with `max_retries` (default 2, 0 to 10), `initial_delay_ms` (default 500, 1 to 60000) and `max_delay_ms` (default 8000, 1 to 600000). The defaults equal what both SDKs did before the setting existed, so an absent key changes nothing. Only an absent key takes a default: `null`, a wrong type, an out-of-range value, an unknown key, or an `initial_delay_ms` above `max_delay_ms` is a config error with the same message in both backends (26 config-parity cases cover it).

- **What is retried.** Only the request that opens the response stream. After the first event arrives, partial output was already shown and staged, so a failure after that point is never retried; the run fails as before.
- **Which failures.** Status 408, 409, 429 and any 5xx; a connection failure or timeout; the provider's `x-should-retry` header overrides the status. A stop by the user is never retried, and a stop during a wait ends the run at once with the stop's reason.
- **The wait.** `initial_delay_ms` doubled per retry up to `max_delay_ms`, minus up to a quarter as jitter. A `Retry-After-Ms` or `Retry-After` (seconds or an HTTP date) from the provider replaces the backoff, capped to `max_delay_ms`. The SDKs capped a server-directed wait at 8 s and did not read this from the session; the cap is now the setting.
- **Why each backend runs its own loop.** The Go SDK exposes the retry count but not the backoff curve, so matching the TypeScript SDK's delays exactly needs one loop per backend with the SDK's own retries switched off for that request (`maxRetries: 0` in TypeScript, `option.WithMaxRetries(0)` in Go). With no `provider_retry` given to the client (a test, or another caller) the SDK's defaults apply unchanged.
- **Go.** `internal/openaiapi/retry.go` holds the rules and `Client.openStream` the loop; `internal/app/provider_retry.go` maps the setting and logs each retry (`provider request retry`, with the attempt, status and wait). `fingerprintRunner` includes the setting, so a changed `provider_retry` reaches the next run instead of waiting for a restart.
- **`messages.jsonl` is unchanged.** Failed attempts write nothing, and a run that recovers writes the same records as one that never failed.

## Run token cap: `max_run_tokens` stops a run between rounds (TypeScript and Go together)

New session setting `max_run_tokens`, an integer from 1 to 1000000000000. **There is no default: an absent key means no cap and changes nothing.** `null`, `0`, a negative or fractional number, a string and anything else is a configuration error with the same message on both backends: `max_run_tokens must be a safe integer between 1 and 1000000000000`.

- **What is counted.** After each provider response the harness adds the tokens the provider reported for it: `usage.total_tokens`, or `input_tokens` plus `output_tokens` when no valid total is given. A response with no usable usage counts as 0, because only reported numbers are trusted. Every round re-sends the history, so the count is what the run was billed for, not the size of the transcript. The count belongs to one run: the next run starts from 0.
- **When it is checked.** Once per round, after the response is committed and only when the model asked for tool calls: if the count has reached the cap (`>=`), no further round starts. A response in flight is never cut, so a run can end above the cap by up to one response. A final answer with no tool calls always completes, because no round is left to refuse.
- **What the transcript gets.** Each call of the refused round receives a `function_call_output` with the code `run_token_limit`, so the history stays valid for the next run, the same way `tool_round_limit` does. Nothing else about `messages.jsonl` changes; with the key absent no record differs.
- **What the client gets.** The run fails with a message that names only numbers the harness counted: `The run stopped before its next round: it used N tokens, which reached the max_run_tokens limit of M.` It is the one run failure whose text is shown, instead of the generic "Response details were withheld" line, and it is kept in the run-error cache like any failed run. Go: `session.RunTokenLimitError`, recognised in `httpapi.clientRunErrorMessage`. TypeScript: `RunTokenLimitError` in `run-token-budget.ts`, recognised in `server.ts`.
- **What it does not do.** It is not a cost cap: it counts tokens, not money, and does not weigh cached input differently. It does not bound a single response (use the model's own output limit), it does not stop a run that never asks for tools, and a run that was already past the cap when this setting was added to a live session stops at its next tool round. It does not apply across runs or sessions. The TypeScript-only `maxToolRounds` run option has no token counterpart.
- **Go.** The value is read per run in `boundRunner.Run` and passed as `RunOptions.MaxRunTokens`, so no runner fingerprint is involved and a changed value applies to the next run. TypeScript reads it from the loaded settings each round.
