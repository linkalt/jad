## 1. Understanding note

The OpenAI Responses client is constructed with the resolver's configured `http.Client`; the OpenAI OAuth wrapper loads the credential file in each `RoundTrip`, clones requests and adds bearer/account headers. The OpenAI auth CLI owns that file, while the auth packages refresh under a per-file lock and publish updated JSON atomically. The Claude CLI follows the corresponding callback/refresh/store path. The Anthropic adapter is a separate HTTP server: its handler translates Responses requests to Messages API requests through the Anthropic SDK and translates the upstream stream itself. Its command binds the configured listener, applies a warning-only non-loopback check, and serves without a caller-auth layer. `responses` holds the retry-notification context contract used by the OpenAI stream retry path.

## 2. Hypotheses

Nine findings are confirmed below (4 medium, 5 low). One additional performance hypothesis remains unmeasured: `openaioauth.Source.Load` performs file stat/read, JSON decode and claim parsing on every OAuth request, trading repeated local work for picking up external refreshes immediately. No benchmark/profile was run, and no caching change is recommended without preserving that freshness behavior. The repeated-request consequence of overflowing `Retry-After` is covered as finding P5-R4-06.

## 3. Findings

### P5-R4-01 — OAuth error callbacks bypass the state binding and can abort login
- severity: low
- lens: B security and boundaries
- location: `backend-go/internal/openaiauth/login.go:172-177`; `backend-go/internal/claudeauth/login.go:230-235`
- evidence: [read] In both callback handlers, the `error` query branch sets `finished` and sends an error on `result` before checking `state`; the success branch checks `code`, constant-time state equality and non-empty expected state. `Login` waits on that result and returns the callback error without exchanging a code (`openaiauth/login.go:83-91`; `claudeauth/login.go:83-99`). The servers bind loopback listeners (`openaiauth/login.go:128-154`; `claudeauth/login.go:186-212`), so this is a local-process or browser-to-loopback denial of sign-in, not token injection.
- suggested fix: Validate the callback state before accepting either success or provider-error responses; add tests for missing/wrong state on `error` and valid-state error handling in both packages.
- effort: S
- prior art: X-1 (REJECTED in `audit_audit.md`; new evidence: the error-response branch bypasses the state check and terminates the waiting login).

### P5-R4-02 — Anthropic upstream SSE events are buffered without a size limit
- severity: medium
- lens: B security and boundaries
- location: `backend-go/internal/anthropicadapter/stream_sse.go:20-61`; `backend-go/internal/anthropicadapter/stream_handler.go:48-52`; `backend-go/internal/anthropicadapter/stream.go:87-96`
- evidence: [read] `respondStream` passes the upstream response body directly to `streamTranslator.run`; `readSSE` uses `bufio.Reader.ReadString` for each line and appends every `data:` value to an unbounded slice until a blank line/EOF, then `strings.Join`s the frame. There is no line, event, or aggregate stream byte ceiling; a configured upstream can send a huge unterminated `data:` line or event and force multi-copy JSON allocations before translation. `MaxRequestBytes` caps the client-to-adapter request, not upstream bytes; the request timeout is a time bound, not a memory bound.
- suggested fix: enforce a hard per-line and/or per-event byte limit while reading and abort the upstream stream on overflow; return a bounded error without retaining or logging the oversized frame. Add a test for an oversized line/frame and for a frame exactly at the limit.
- effort: S
- prior art: new; P-019 was only about per-event flush/syscall cost and did not cover input buffering.

### P5-R4-03 — The unauthenticated adapter returns its credential-file path on credential errors
- severity: low
- lens: B security and boundaries
- location: `backend-go/internal/anthropicadapter/credential.go:30-32,112-126`; `backend-go/internal/anthropicadapter/handler.go:49-54`; `backend-go/internal/anthropicadapter/errors.go:73-83`
- evidence: [read] `credentialError.Error` formats the configured path into its message; when `upstreamToken` fails, it copies `err.Error()` into the `credential_unusable` API message, and `create` writes that error before reading the request body or contacting upstream. `ServeHTTP` has no caller-authentication gate. A caller who can reach the adapter can therefore learn the local credential path when the configured file is missing, unreadable, malformed or expired; the default listener is loopback, so remote reach depends on the existing non-loopback bind setting (A-17).
- suggested fix: return a generic `credential_unusable` message to the caller and keep path-specific detail only in a local diagnostic; test that error bodies never contain the configured path.
- effort: S
- prior art: new (A-17/D-7 is the separate non-loopback relay exposure; this is path disclosure on the credential failure response).


### P5-R4-04 — The standalone Anthropic adapter does not carry `provider_network` to its upstream dial
- severity: medium
- lens: B security and boundaries
- location: `backend-go/cmd/anthropic-adapter/main.go:30-46`; `backend-go/internal/anthropicadapter/handler.go:26-30`; `backend-go/internal/anthropicadapter/sdk.go:15-24`; `backend-go/internal/anthropicadapter/config.go:17-34`
- evidence: [read] The adapter command loads its own `anthropicadapter.Config` and calls `NewHandler(config, nil)`; that constructor replaces a nil client with `&http.Client{}`. `newAnthropicClient` passes that client to the Anthropic SDK and sets only the base URL and SDK retry policy. The adapter config has no provider-network/address-family setting or injected dialer. Commit `0bf03a1` added a family-pinning transport for the app's provider client (`backend-go/internal/app/provider_network.go:18-28`; `backend-go/internal/app/resolver.go:497-522`), but this separate adapter's second-hop request to Anthropic does not use it. When a backend routes provider traffic through this adapter, its selected family can pin the backend-to-adapter connection without pinning the adapter-to-provider connection; this can break family-restricted deployments and bypass the expected egress-family constraint.
- suggested fix: make the adapter's outbound transport configurable for the selected family and pass that setting from the caller, or explicitly document that `provider_network` applies only to the backend's direct provider client and cannot constrain the adapter's second hop. Add a transport-level test that verifies the adapter's outbound dial network for tcp4 and tcp6.
- effort: M
- prior art: new; specifically checked against commit `0bf03a1` per p5 scope.

### P5-R4-05 — Retry classification treats URL-wrapped permanent transport failures as transient
- severity: low
- lens: A correctness and concurrency
- location: `backend-go/internal/openaiapi/retry.go:55-92`; `backend-go/internal/openaiapi/client.go:139-159`
- evidence: [reproduced] After excluding context cancellation, errors marked `Permanent`, and URL parse failures, `isRetryableError` returns true for every error matching `net.Error`. A `*url.Error` wrapping a certificate-verification failure qualifies even though the error cannot recover without configuration/certificate changes; `openStream` then repeats the opening request and waits up to configured `MaxRetries`. A temporary overlay test supplied a URL-wrapped permanent failure and confirmed the current classifier returns retryable (`go test -overlay=/tmp/r4/retry_overlay.json ./internal/openaiapi/ -run '^TestTmp(RetryPermanentURLFailureIsRetried|HugeRetryAfterOverflowsBeforeCap)$' -count=1`, exit 0).
- suggested fix: classify URL-wrapped causes explicitly; retry transient dial/read failures and timeouts, but not TLS verification, unsupported protocol, or other permanent failures. Add cases for certificate and scheme errors alongside the existing retryable transport tests.
- effort: S
- prior art: A-4 (retry/idle-guard follow-up); the permanent transport classification was checked on this path.

### P5-R4-06 — Oversized numeric Retry-After values overflow before the configured cap
- severity: low
- lens: C performance
- location: `backend-go/internal/openaiapi/retry.go:96-100,184-196,208-220`
- evidence: [reproduced] `retryAfter` accepts any finite nonnegative float and converts milliseconds to `time.Duration` before `retryDelay` applies `MaxDelay`. For `Retry-After-Ms: 1e300`, the temporary overlay test confirmed the conversion becomes negative on this build; the cap preserves that negative duration, and `sleepContext` passes it to `time.NewTimer`, which fires immediately. A provider returning such a value can make each bounded retry immediate instead of respecting the cap, multiplying requests during a provider failure. The same targeted command above exited 0.
- suggested fix: cap the parsed float in its original unit before converting to `time.Duration`; apply the same safe conversion to numeric `Retry-After` and rate-limit reset values. Test values beyond the duration range and ensure the wait is nonnegative and capped.
- effort: S
- prior art: new; no equivalent item in the prior-audit notes for this phase.

### P5-R4-07 — Claude OAuth state is armed only after launching the browser
- severity: low
- lens: A correctness and concurrency
- location: `backend-go/internal/claudeauth/login.go:79-83,92-95,178-182,237-242`; caller: `backend-go/cmd/claude-auth/main.go:132-139`
- evidence: [read] In callback mode, `Login` invokes the caller's `OpenBrowser` function before calling `callback.expectState`. The callback server is already serving during that interval; its handler rejects a success callback whenever `c.state` is empty. If the browser flow redirects before `OpenBrowser` returns (or the opener invokes a fast/cached browser), the legitimate one-shot code callback gets HTTP 400 and is not queued, so sign-in waits until timeout. `openaiauth.Login` sets expected state before opening the browser, so the ordering differs between the parallel implementations.
- suggested fix: set the expected state immediately after `NewAuthRequest`, before printing/opening the URL, and retain the existing constant-time check.
- effort: S
- prior art: X-1 (REJECTED; new evidence is the Claude callback-state registration order and the handler's empty-state rejection).


### P5-R4-08 — OAuth transport reattaches credentials after cross-origin redirects
- severity: medium
- lens: B security and boundaries
- location: `backend-go/internal/openaioauth/transport.go:34-49`; caller: `backend-go/internal/app/resolver.go:504-506`
- evidence: [reproduced] `Transport.RoundTrip` clones every outgoing request and unconditionally sets the OAuth `Authorization`, `chatgpt-account-id`, and optional FedRAMP headers before forwarding it to the base transport; it does not bind those headers to the configured API origin or reject redirects. The production OAuth client is an `http.Client` using this transport (`app/resolver.go:504-506`), and the standard client follows redirects by default. A temporary overlay test using two local `httptest` servers on different hostnames returned a redirect from the configured origin and confirmed the redirected server received `Bearer audit-fixture-token` (`go test -overlay=/tmp/r4/overlay.json ./internal/openaioauth/ -run '^TestAuditRedirectReinjectsOAuthCredentialAcrossOrigins$' -count=1`, exit 0). Thus a 3xx response can disclose the OAuth access token and account metadata to a different origin.
- suggested fix: prevent redirects from carrying OAuth credentials across origins (for example, reject cross-origin redirects for this client, or have the OAuth transport bind credentials to the configured origin and fail closed on a change); add a cross-origin redirect regression test.
- effort: S
- prior art: new; verified against the current transport and application client wiring.


### P5-R4-09 — Non-loopback Anthropic adapter exposure is warned about but not access-controlled
- severity: medium
- lens: B security and boundaries
- location: `backend-go/cmd/anthropic-adapter/main.go:37-54,70-77`; `backend-go/cmd/anthropic-adapter/README.md:17-25,51-57`
- evidence: [read] `run` binds the configured `listen` address and serves `NewHandler` without an authentication layer. `warnIfExposed` emits a warning for non-loopback TCP addresses, but returns to `run` without rejecting or protecting the listener. The README documents that `upstream.credential_file` makes the adapter ignore the caller's credential and use its own stored Anthropic token on every request; it also exposes `listen` as a configurable address and does not define caller authentication. Therefore a reachable non-loopback deployment exposes an unauthenticated provider relay using the configured credential (or forwards unauthenticated caller-supplied credentials in pass-through mode), permitting unauthorized provider usage and spend. The default remains loopback, so this is conditional on a non-loopback configuration.
- suggested fix: require caller authentication for network-reachable listeners, or fail startup on non-loopback binds unless an explicit unsafe override is set; add an integration test that proves the unauthenticated route is unavailable in the exposed configuration.
- effort: M
- prior art: A-17; current code still only warns and continues, confirmed against `run` and `warnIfExposed`.
