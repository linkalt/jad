## 1 Understanding

## 4 Performance hypotheses
- H1: `BuildRequestWithStateContext` makes about five passes over the whole history each round: `isJSONObject` (`json.Valid`) per item, `cloneRaw` per item, `json.Marshal(input)` (validates and compacts RawMessage), `Unmarshal` of settings.Request, then `json.Marshal(requestFields)` compacts and validates `input` again, runner.go:340-381, plus `Rehydrate` scan and `ImageResizer.Apply` scan per round (:478-479). workload: 200-1000 history items, 1-10 MB transcript, 8-50 tool rounds. benchmark: `BenchmarkBuildRequestWithLargeHistory` (session/request_benchmark_test.go:30). expected: scales with history bytes x rounds; remove the second validation and the clone.
- H2: per stream event `json.Valid` twice plus `decodeJSONObject` with token decoding and `cloneRaw` of every value (runner_response.go:56-59, runner.go:763-811); `response.completed` (carries the whole output again) is decoded by `decodeJSONObject` twice and re-encoded in `makeCompletedEvent` (:844-901), then `responseTraceDetails`, `responseTokens`, `responseFunctionCalls` unmarshal it three more times (runner.go:506-509, :641). workload: 5k-50k delta events per response, 100 KB-1 MB completed events. benchmark: `BenchmarkRunnerEventDecode` (session/event_decode_benchmark_test.go:12). expected: about 4-6 parses of each completed event; the delta cost scales with event count.
- H3: with auto compaction enabled `automaticCompactionTrigger` decodes event and response with value clones every round (runner.go:664-709) when a cheap usage-only struct would do. workload: compaction on, 1 MB responses. benchmark: new micro-benchmark on `automaticCompactionTrigger` with a 1 MB completed event. expected: one allocation of the event size per round.
- H4: `ImageStore.Rehydrate` reads and base64-encodes every referenced image file on every round (runner.go:478; imagestore/store.go:159-200, cross-phase), and `Resizer.resized` hashes the full data URL with SHA-256 per image per round (imageresize/apply.go:186). workload: 20 stored images of 1-5 MB, 10 rounds. benchmark: new, `Rehydrate` over a 20-image history fixture. expected: scales with image bytes x rounds.
- H5: `listSessionFiles` reads, hashes and unmarshals three times each session file on every call (session_files.go:275-283: `CatalogETag`, `fileDisplayName`, `fileCategory`, `fileScope`), called per UI session list and per `transcripts`/`profile_message` tool call (app/transcript_profiles.go:64,73). workload: 500 sessions of 20-200 KB. benchmark: new `BenchmarkListSessionFiles` with 500 generated files. expected: linear in total bytes per call; one unmarshal would cut about 3x.
- H6: `CollectSessionFiles` runs `EvalSymlinks` + `Stat` + `Info` per regular file and two `EvalSymlinks` per directory (files.go:51,65,111,120), and the sort lowers both names on every compare (:157-159). workload: default 5000 entries / 2000 results, maximum 1M / 100k, depth up to 12-64, called per `@` completion. benchmark: new `BenchmarkCollectSessionFiles` on a 5000-entry tree depth 6 (and a 100k-entry tree). expected: about depth x results lstat calls; the allocations in the sort grow with the largest directory.
- H7: no process-wide ceiling on tool goroutines (B-C8, open): per response up to `max_parallel_tool_calls` (max 64, tool_settings.go:19-20) workers (tool_batch.go:119-123); a child run gets the parent's limit (app/subagent.go:94) and sub-agents run `max_concurrent` (default 3) at a time with nesting depth; sessions run in parallel with no shared semaphore. workload: 20 active sessions x 64 calls x 3 children = about 3,800 worker goroutines each with a tool subprocess or HTTP call. benchmark: `BenchmarkRunToolBatch` (session/tool_batch_benchmark_test.go:11) at limit 64, plus a new test counting peak concurrent `Execute` across N runs. expected: peak scales with sessions x limit, bounded only by tools' own gates.
- H8: `defer checkpointRun.Finish()` (runner.go:441) runs inside `Run` while `r.mu` is held, so the end snapshot (git add of up to 20k files / 512 MiB, timeout up to 1 h per git command) delays the run's completion and the next run of the session. workload: checkpoint on, 20k-file workspace. benchmark: existing checkpoint benchmarks in internal/checkpoint (name not verified) with a 20k-file fixture. expected: end-of-run latency equals one snapshot.
- H9: `image_resize.max_pixels` allows 400M pixels (image_resize_settings.go:17); a decode of 64M (default) is about 256 MB RGBA, 400M about 1.6 GB, with no concurrency cap across runs (imageresize/resize.go:81-85 only checks the size). workload: 4 sessions with large screenshots. benchmark: new memory benchmark on `resizeDataURL` with a 64M-pixel PNG. expected: peak heap near 4 bytes x pixels x concurrent runs.
- H10: `validateSessionFile` creates a temp dir, writes the file and loads the full layout for every session PUT (session_files.go:432-452). workload: bulk import of 500 sessions. benchmark: new `BenchmarkWriteSessionFile`. expected: dominated by catalog scans in the loader.
- H11: `stateContextTriggerPrompt` reads each prompt document (up to 8 MiB each, count not limited) on every settings load before the size check against `max_bytes` rejects it (state_context_settings.go:226-233, readPromptDocument session.go:1120). workload: 10 documents of 8 MiB, settings loaded per request. benchmark: new, `LoadSessionConfig` with oversized prompt documents. expected: reads scale with document bytes per load.
- H12: `listSettingsCache` interplay: `LoadSessionConfig` is called per `ListSessionFiles` request (app/session_settings.go:82) before the walk; whether it is cached was not checked. workload: one `@` keystroke per request. benchmark: HTTP-level loop on the files route. expected: settings parse dominates when the walk is small.
