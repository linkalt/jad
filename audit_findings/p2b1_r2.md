## 1. Understanding note

Phase 2b1 is the settings *loader skeleton*: it decides which files a session's configuration comes from, reads them, and hands one setting-shaped `map[string]json.RawMessage` to the 2a normalizers.

Two entry points converge on one validator. `Load` (`roots.go:202`) resolves the roots: `JAD_SESSIONS_DIR` → one root with no layout, else `JAD_ROOT_SETTING_PATH`/`rootsetting.Find` → `setting.json`, whose `session_roots`/legacy `session_paths`, `server`, `catalogs`, `defaults` and `libraries` are read; a root setting also installs one shared `*Layout` on every root. `Resolve` (`:269`) turns `id` or `root:id` into a `Location` (the `<root>/<id>.json` file plus the root and its layout). `LoadSessionSettings` (`session.go:231`) then dispatches on `Location.UsesLayout()` (`layout_root.go:123`): the catalog path (`layout_load.go:29`) reads `<id>.json` strictly, narrows the profile catalog by `scope.profiles`, composes `defaults` → session `settings`/`cwd` → the selected profile's `settings`, applies the profile's toolsets (`applyToolsets`, first-wins with warnings), rebuilds `paths.profiles` for every profile in scope (each *other* profile read and validated too, DECISIONS 639), and calls `loadSessionSettingsFrom` (`session.go:251`); everything else answers "not a catalog-layout session" (the legacy arm was removed, DECISIONS 625).

Around that: `catalog_files.go` is the HTTP catalog editor (ETag/If-Match, atomic replace via temp+rename, hard-link create, in-use checks before delete), `settings_stamp.go` + `settings_inputs.go` + `catalog_scans.go` are the P-001 change detection (which files and folders a load read, so `app/list_settings_cache.go` can keep the result), `check.go` is `jad check` (every catalog file plus every session once per profile), and `profile_fields.go`/`profile_tools.go`/`model_effort.go` are the per-profile, per-tool and `<model>@<effort>` grammars.

Contracts that matter for judging it: `DECISIONS` 545 (`cwd` precedence and "without any, a layout session fails"), 639 (every profile in scope is read at load), 745 (catalog writes are atomic, fsynced and under the resolver's settings lock), 799/845 (model/effort), and `sample/schemes/*.schema.json` for the root setting, session and profile files.

## 3. Findings

### P2B1-R2-01  Three load-time readers still use an unbounded `os.ReadFile`, so a FIFO in the catalog or in a `prompt_documents` entry hangs the settings load forever
- severity: medium
- lens: A correctness (availability) / D maintainability (the P2A-03 fix reached the 2a siblings, not these)
- location: `internal/sessionfs/session.go:1129` (`readPromptDocument`: session and profile `prompt_documents`), `internal/sessionfs/layout_files.go:172` (`readLayoutFile`: every catalog file — profile, model, toolset, session.json), `internal/sessionfs/session.go:1169` (`readSessionObject`: model files and the legacy path); the bounded reader that already exists in this package: `internal/sessionfs/native_config_file.go:13-38` (`maxConfigTextFileBytes` = 1 MiB, `O_NONBLOCK` open, regular-file check, `io.LimitReader`)
- evidence: [measured]. Probes in a `/tmp` copy of the tree (`/tmp/r2/bg`, `probe*_r2_test.go`) through the real loader (`layouttest` fixture → `Load` → `Resolve` → load, each in a goroutine with a 4 s timeout):
  - `prompt_documents: ["<fifo>"]` (profile or session) → **load HUNG after 4s** (never returned);
  - a FIFO at `<root>/profiles/dev/pipe.json` → **load HUNG after 4s** (`catalog.Scan` lists it: `internal/catalog/scan.go:63-68` filters by `isDir` and the `.json` suffix, not by file type; `compose` reads every profile in scope, DECISIONS 639);
  - a FIFO at `<root>/models/openai/pipe.json` named by the profile's `models` → **`LoadSessionConfig` HUNG after 4s** (`modelFromFields` → `readSessionObject`);
  - a 2 MiB prompt document loads fine: `err=<nil>`, `len(PromptText)=2097162`, while an agent prompt document, a `prompt.md` and an `env_file` are capped at 1 MiB by `readConfigTextFile` (`native_subagent_settings.go:568`, `native_subagent_dir.go:145`, `native_bash_env.go:12`).
  Reach: the local operator/editor of the catalog tree, or the model through `bash`/`exec` (it can `mkfifo` in the project's `.jad/` folder, which the default cwd read/write policy allows). Effect: `app/catalog.go:201` (`ListSessions` → `listSettings`) and every run start block forever with no context check and no timeout, one stuck goroutine per request — a poll loop accumulates them. The other 2a readers were fixed in `336cdf4` (P2A-03); these three were missed in the same commit range.
- suggested fix: route `readPromptDocument` through `readConfigTextFile` (a prompt document is text and 1 MiB is far above any real one), and give `readLayoutFile`/`readSessionObject` the same treatment with its own cap name (a catalog file is also small, but pick the number deliberately and pin it in a test, e.g. `maxConfigJSONFileBytes`); add the FIFO/oversize cases to `native_config_file_test.go`'s table for each of the three readers.
- effort: S
- prior art: P2A-03 (`336cdf4`) fixed exactly this class in `native_bash_env.go`, `native_subagent_dir.go` and `native_subagent_settings.go`; the audit plan's 2b1 risk row lists its own "path handling" concern. Not previously filed for these three readers.

### P2B1-R2-03  A file whose mtime is in the future makes `SettingsStamp.Current()` false forever, disabling the P-001 list cache for that session
- severity: low
- lens: A correctness (change detection) / C performance (every poll reloads)
- location: `internal/sessionfs/settings_stamp.go:51-53` (`racy()`: `f.taken.Sub(f.modTime) < racyStampWindow` is true for a negative difference), `:58-78` (`Current`), consumer `internal/app/list_settings_cache.go:23-35` (`get` → `stamp.Current()`)
- evidence: [measured], `/tmp/r2/bg`: after touching the session file and the profile file to `time.Now().Add(time.Hour)`, a stamped load returns a stamp with `Current()=false` immediately, and a second stamped load of the untouched fixture is `false` again — nothing changed, yet the cache never validates. [read] the consumer: `listSettings` therefore reloads that session on every `GET /api/sessions` poll, and each load re-reads every profile in scope (DECISIONS 639) plus the agents-dir listings. Reach: a session file or catalog file copied with future timestamps (rsync from a machine with a fast clock, a container/VM clock skew, a network share) — no operator intent needed, and nothing logs it.

- effort: S
- prior art: new (P-001/the stamp code is not in the prior audit files I found; DECISIONS has no record of the racy window).

## 4. Performance hypotheses for the measurement step

- H1: every settings load re-reads and re-validates **every profile in the session's scope**, not only the selected one — `layout_load.go:325-346` (`readProfile(other.Path, allModels)` + `checkUnselectedProfile`), a recorded decision (DECISIONS 639, "Cost: one file read per profile per load"). Each of those also runs `catalog.Narrow` and, when its `model_default` carries an effort, `checkModelEffort` → a model file read.
  workload: a list of 200 sessions whose scope selects the whole catalog (30 profiles), i.e. 6,000 profile reads + up to 6,000 model reads per poll that is not answered from the settings cache; one session open = 30 reads.
  benchmark: `BenchmarkLoadSessionConfig` (`internal/sessionfs/settings_load_benchmark_test.go:10`, 1 profile) as the baseline, plus a variant with 30 profiles in scope and 1 selected; `internal/app/list_many_benchmark_test.go:97` `BenchmarkListManySessions` and `profile_turns_benchmark_test.go:81` `BenchmarkListSessionsProfiles` for the poll shape.
  expected: load time linear in the scope size, not in the file size — the selected-profile work is constant, so the hypothesis is "the scope size, not the settings size, dominates a load".
- H2: the model file is read up to three times per load when the profile's `model_default` names an effort (P2B1-R2-05): `layout_profile.go:40`, `layout_load.go:102-107` (result discarded), `layout_load.go:216`.
  workload: any run start (`resolver.go:537`) and three `history.go` paths; a model file is small, so the cost is syscalls, not bytes.
  benchmark: `BenchmarkLoadSessionConfig` with `model_default: "<id>@high"` and a model that lists `efforts`.
  expected: 2-3× the model-file I/O of the no-effort case, which the benchmark should show as a difference in `allocs/op`/time per load if the file read matters at all; if it does not, the finding closes as "confirmed, negligible".
- H3: each `agents_dir` is listed twice per stamped load and every agent folder is stat-stamped — `native_subagent_dir.go:69` (`os.ReadDir` while loading) and `settings_inputs.go:66-80` (`collectAgentFolders` lists again for the stamp, then `inputStamps` stats `agent.json` and `prompt.md` per folder, `:86-91`).
  workload: 5 folders × 100 agents (DECISIONS 310 targets "many agents"), on every load whose stamp is not current (every poll for 2 s after any change, and every poll if a file's mtime is in the future, P2B1-R2-03).
  benchmark: none exists; propose `BenchmarkLoadSessionConfigAgentDirs` with the fixture written by `layouttest` (5 folders × 100 `agent.json` + `prompt.md`).
  expected: 2 `ReadDir` + 200 stat + 200 open/parse per load, linear in the agent count; the double listing is removable only by recording the loader's own directory entries.
- H4: each JSON file is decoded more than once — `parseSessionObject` (`session.go:1179-1195`) decodes into `any` and then into `map[string]json.RawMessage`; `orderedObjectKeys` re-decodes a value every caller already holds (`session.go:1224-1250`, 25 call sites); `selectProfile`/`validateProfileFields` decode the same profile object twice (`session.go:706-721`, `profile_fields.go:27-30`); `mergeSettings` marshals and unmarshals at each nesting level of `compose` (`layout_merge.go:18-31`).
  workload: proportional to the settings size, so it matters for a big `defaults` + profile `settings` + toolset combination, not for the sample.
  benchmark: `BenchmarkLoadSessionConfig` with a large `defaults` (the 20 tool sections fully set) at two sizes.
  expected: a constant-factor saving (one decode instead of two per object); listed so the measurement step can close it rather than leave it unmeasured.
- H5: `jad check` is quadratic in scope — `check.go:100-133` loads a session once per profile of its scope, and each of those loads re-reads every profile in scope (H1), so a session with P profiles costs P×P profile reads and the whole check costs sessions × P².
  workload: 50 sessions × 10 profiles in scope = 500 loads × 10 profile reads = 5,000 reads; the command is a CLI, not a request path.
  benchmark: none; propose `BenchmarkCheckLayout` with that fixture (only if the CLI cost is judged interesting).
  expected: `CheckLayout` can reuse one `CatalogScans` (it does not: each `LoadLayoutSessionSettings` call passes `nil`), which would remove the repeated directory scans but not the per-profile file reads.
