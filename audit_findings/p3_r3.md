### P3-R3-01 Retained runs are still bounded by time only (re-confirmed B-C1)
- severity: medium
- lens: C performance
- location: backend-go/internal/httpapi/registry.go:300, backend-go/internal/httpapi/registry.go:323-356, backend-go/internal/httpapi/registry.go:457-473, backend-go/internal/httpapi/registry.go:786-823

- suggested fix: add a retained-run count/bytes cap beside the time retention (config key with default, `sample/schemes/`, config tests, `DECISIONS.md`); on overflow retire the oldest finished run of that key first. Files: `registry.go`, `serverconfig`, schema/tests.

### P3-R3-03 Oversized snapshot and terminal frames bypass the per-subscriber byte budget
- severity: medium
- lens: C performance
- location: backend-go/internal/httpapi/registry.go:123-171
- evidence: [read] `pushLocked`: when `len(frame) > maxBytes` and `snapshot`, the queue is replaced with that single event, `bytes = 0`, `oversizedSnapshot = true`, return `true` (never charged, never dropped); the follow-up snapshot path also resets `bytes = 0`. `terminalEvent` frames are always appended (only compacted when they do not fit behind existing bytes). A stalled subscriber therefore pins one arbitrarily large `ui.message`/`completed` (e.g. 16 MiB at a 1 MiB budget) plus the run's retained copy, and is never dropped for it. Prior P-045 bounded only the non-oversized path (`StalledSubscriberMemory` 822 KiB queued).
- suggested fix: decide behavior (drop oversized snapshot with `idle`+`done`, or truncate with marker like `runContentTruncationMarker`, or charge it and drop the subscriber); needs UX decision since late join relies on the snapshot. Files: `registry.go`, test `run_lifecycle_test.go`/`memory_retention_benchmark_test.go`.
- effort: M
- prior art: new (extends P-045; P-025/P-043 cover retained copies, not the queue-bypass).
