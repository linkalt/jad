## 3. Findings

### P4-R3-01 Close with StopWait==0 lets Complete write after the final index
- severity: medium
- lens: A correctness
- location: backend-go/internal/asyncmgr/manager.go:594, backend-go/internal/asyncmgr/manager.go:361, backend-go/internal/asyncmgr/manager.go:399
- evidence: [read] trace. `Close` computes `writing := m.completing > 0` (manager.go:592) but only waits `if m.opts.StopWait > 0 && (len(targets) > 0 || writing)` (manager.go:594). `Config.Validate` allows `StopWaitMs==0` (config.go). `Complete` increments `m.completing++` after claiming `finishing` (manager.go:377), writes the record outside the lock (manager.go:399), then decrements (manager.go:424) and calls `writeIndex` via `applyWork(work,true)` (manager.go:422). With `StopWait==0`, `Close` flushes the index (manager.go:619) and waits on `indexMu` (manager.go:621) but does not wait for `completing`; a `Complete` in flight then writes `<id>.json` and rewrites `index.json` after `Close` returned. `Register` refuses after close (manager.go:269) but `Complete` has no closed check. This is the 176fd7d class (commit 176fd7d added the `completing` wait, but only under `StopWait>0`).
- suggested fix: in `manager.go`, either always wait for `completing==0` even when `StopWait==0` (a short join, not a driver wait), or make `Complete` after `closed` drop the file write and only mutate memory / return `ErrClosed`.
- effort: S
- prior art: new edge of 176fd7d (which fixed the `StopWait>0` case); not a repeat.

### P4-R3-02 Dead owners with dropped signals are never removed
- severity: low
- lens: A correctness
- location: backend-go/internal/asyncmgr/manager.go:231, backend-go/internal/asyncmgr/manager.go:498, backend-go/internal/asyncmgr/prune.go:62
- evidence: [read] trace. `forgetLocked` deletes `m.owners[owner]` only `if s.total == 0 && s.dropped == 0` (manager.go:235). `enforceUnreadLocked` and TTL expiry do `s.dropped++` (prune.go:69,89). `Wait` resets `s.dropped=0` only when it delivers or when pending==0 (manager.go:498-504; wait.go pop path). `List` reports `Dropped` (query.go) but never resets it. An owner that overflows `unread_max` and then never calls `Wait` again (only `List`/`Status`) keeps `total==0, dropped>0` forever; `m.owners` grows per session/profile that once overflowed.
- suggested fix: in `manager.go`, reset `dropped` on `List`/`Snapshot` read or delete the owner entry when `total==0` regardless of `dropped` after reporting once; keep the `Dropped` count on the row path if needed.
- effort: S
- prior art: new.

### P4-R3-03 Remote references reject dotted names the local profile IDs allow
- severity: medium
- lens: A correctness
- location: backend-go/internal/remote/target.go:29, backend-go/internal/remoteapi/server.go:484, backend-go/internal/sessionfs/native_profile_message_settings.go:34
- evidence: [read] trace. `segmentsOK` uses `NamePattern = ^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$` (remote/entry.go, target.go:31) — no `.`. `validTarget` on the server uses the same `namePattern` without dots (server.go:486). Local profile IDs allow dots: `profileMessageIDPattern = ^[A-Za-z0-9][A-Za-z0-9._-]*/[A-Za-z0-9][A-Za-z0-9._-]*$` (native_profile_message_settings.go:34). A profile `cat/prof.v2` listed by `Profiles` and matchable by token globs (`path.Match` allows `.`) is then refused as `bad_request` by `handleStart` (`validTarget` false, server.go:341) and unparseable by `ParseProfile/ParseSubagent` (target.go:86-87). Availability, not bypass: dots are rejected on both sides consistently, so no scope escape, but a valid local target is unreachable remotely.
- suggested fix: in `remote/target.go` and `remoteapi/server.go`, allow `.` in category/profile segments (same class as the local pattern), keeping the `..`/empty/`.`/`/` guards in `matchAny` and `SessionPattern`.
- effort: S
- prior art: new; hardening tests in 03f4e94 cover empty/dot segments but not dotted valid names.
