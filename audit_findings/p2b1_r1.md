## 1. Understanding note

`Load` (roots.go) reads the root setting once (`rootsFromSetting`, `layoutFromSetting`, `normalizeServerSettings`) and fixes roots, catalog folders and server limits for the life of the process. A request then goes `Resolve` (session id pattern, `root:id`) → `LoadSessionSettingsScoped` → `loadLayoutSessionSettings`: strict-decode `<id>.json`, scan and narrow the profile catalog, then `layoutCompose.compose` builds a legacy-shaped `setting` map (defaults ⊕ session ⊕ profile settings, toolsets, a synthetic `paths.profiles` entry per profile in scope; every other profile is re-read and checked) and feeds it to `loadSessionSettingsFrom` (session.go:251-652), a 400-line function that calls about 35 normalizers in sequence. After that `loadAgentToolsets` composes and normalizes the whole session once more for every distinct agent toolset. `SettingsStamp`/`CatalogScans` record stat tuples of what was read so `app` can reuse a config (`lockedConfigs`, `listSettingsCache`). The catalog file API (`WriteCatalogFile`, `DeleteCatalogFile`, `WriteSessionFile`) validates with the loader's own rules, writes temp+rename (or temp+link for create) under an if-match etag, and refuses removal of files others need. `CheckLayout` is the `jad check` implementation: every catalog file and every session once per profile in scope.

## 3. Findings

### p2b1-r1-01  Session `prompt_documents`, session/catalog/model files and `server`-adjacent readers use `os.ReadFile` with no regular-file or size check: a FIFO blocks every load of the session, a device or huge file exhausts memory (P2A-03 fixed only three call sites)
- severity: medium
- lens: A correctness (B for the model-writable case)
- location: backend-go/internal/sessionfs/session.go:1129 (`readPromptDocument`, called from session.go:1108 and state_context_settings.go:227), session.go:1169 (`readSessionObject`, model files and agent.json), layout_files.go:172 (`readLayoutFile`: session, profile, toolset, MCP-use, catalog files), roots.go:379 (`readObject`, root setting), catalog_files.go:140,174,233, check.go:81
- evidence: [measured] overlay probe: a FIFO named as `prompt_documents` entry, as model file (`readSessionObject`) and as catalog file (`readLayoutFile`) each still blocked after 1.5 s (the goroutine never returns); a sparse 200 MiB `prompt_documents` file is read completely into memory and into `PromptText` (`len=209715200 err=<nil>`). `readConfigTextFile` (native_config_file.go:17, O_NONBLOCK, `IsRegular`, 1 MiB cap) from 336cdf4 is applied only at native_bash_env.go:12, native_subagent_dir.go:145 and native_subagent_settings.go:568; its comment says "the loaders run on every settings load", which is equally true of the session prompt documents. `LoadSessionSettings` runs on every message, list poll and lock (resolver.go:297), so one blocked read stalls that session's requests and keeps goroutines parked forever; `/dev/zero` as in p2a-r1-03 kills the process by OOM. Reachable by: whoever can create the file at a configured path (a model with `bash`/`exec`, or any user writing a profile with a `prompt_documents` entry to a device); catalog files are inside the catalog folder, so only a local user or the model with write access there. Prompt documents may legitimately be larger than 1 MiB, so a separate cap is needed.
- suggested fix: one helper `readRegularFile(path, max)` (open O_NONBLOCK, `Stat().IsRegular()`, `LimitReader`), used by `readPromptDocument` (cap from a setting or 8 MiB), `readSessionObject`, `readLayoutFile`, `readObject` (cap 1-4 MiB); `readConfigTextFile` becomes its 1 MiB caller. Add a FIFO test per entry point. Files: native_config_file.go, session.go, layout_files.go, roots.go.
- effort: S-M
- prior art: extends p2a-r1-03/L6 (P2A-03 fixed for subagent prompts and env files only)

### p2b1-r1-02  A session write into a second root can create a session id that already exists in another root; the running server accepts it and the next start fails with "share one state folder"
- severity: medium
- lens: A correctness
- location: backend-go/internal/sessionfs/session_files.go:105-142 (`newLayoutSession`), :152-176 (`WriteSessionFile`); invariant checked only at layout_root.go:97-119 (`checkUniqueSessionIDs`, called from roots.go:449 during `Load`)
- evidence: [measured] overlay probe: fixture with roots `local` and `b`, session `session-1` in `local`; `WriteSessionFile(roots, "b:session-1", body, IfNoneMatch "*")` returned `created=true err=nil`; a following `Load` of the same root setting returned `session "session-1" is in session roots "local" and "b"; they share one state folder, so rename one of the sessions` — the server would refuse to start. Meanwhile both sessions write `<state>/session-1/<category>/<name>/messages.jsonl` (layout_load.go:367-374: state path is keyed by session id only), so two sessions share one transcript until the restart. An unqualified reference to the id also becomes ambiguous (`ResolveAmbiguous`) for every client. Reachable by an API client with settings access (`PUT` session file; app/session_catalog_files.go:43 holds only `settingsMu`, which does not span roots check).
- suggested fix: in `WriteSessionFile`, when `!exists`, refuse with `CatalogPreconditionFailed` if any other root already holds `<id>.json` (reuse `SessionFileID`/`os.Stat` over `roots`); add a test next to the multi-root write tests.
- effort: S
- prior art: new

### p2b1-r1-04  `parseLayoutFile` accepts trailing garbage after the JSON object; its own comment and error say otherwise
- severity: low
- lens: A correctness
- location: backend-go/internal/sessionfs/layout_files.go:189-191
- evidence: [measured] overlay probe: `{"name":"a"} garbage` and `{"name":"a"} }` return `err=<nil>`; only a second complete value (`{"name":"a"} {}`) gives `unexpected data after the JSON object`. The check `if _, err := decoder.Token(); err == nil` treats a syntax error from `Token()` as "no more data". - suggested fix: `if _, err := decoder.Token(); !errors.Is(err, io.EOF) { return configError(...) }`; test with the three inputs above.
- effort: S
- prior art: new

### p2b1-r1-05  `server` settings and top-level root-setting keys are not checked for unknown names, unlike every catalog file and every tool section
- severity: low
- lens: A correctness (D for the inconsistency)
- location: backend-go/internal/sessionfs/roots.go:502-704 (`normalizeServerSettings` reads named keys only), roots.go:399-453 (`rootsFromSetting` ignores other top-level keys), sample/schemes/root-setting.schema.json (`additionalProperties: true` on the root and on `server`)

### p2b1-r1-06  Replace/delete of catalog and session files rely on size+mtime and on a read-then-act sequence; an external writer can slip in, and neither path syncs the directory
- severity: low
- lens: A correctness
- location: backend-go/internal/sessionfs/layout_settings.go:174-203 (`writeFileIfUnchanged`: `Stat` compare then `os.Rename`, no `fsync` of the directory), catalog_files.go:476-507 (`createFileExclusive`: temp+link, no directory sync), catalog_files.go:246-305 (`DeleteCatalogFile`: etag checked on an earlier read, then `os.Remove`), session_files.go:152-176
- evidence: [read] in-process callers hold `Resolver.settingsMu` (app/catalog_files.go:79,93; session_catalog_files.go:47,71; session_settings.go:23), so concurrent API requests are serialized; the remaining windows are another process (an editor, `git checkout`): (a) between `Stat` at layout_settings.go:197 and `Rename` at :201 a same-size edit within the mtime granularity is overwritten, although the etag was taken from different bytes; (b) delete removes whatever is at the path after the etag check; (c) with `syncWrite` true the file is fsynced but the rename/link is not made durable (no `Open(dir).Sync()`), so a crash can lose a write that was acknowledged with 200/201 — DECISIONS 387/402 describe the directory sync as the standard for the auth files. Impact is small (files are small, user-edited). Not observed.
- suggested fix: after the rename/link and before returning, sync the parent directory when `syncWrite`; document (a)/(b) as accepted in DECISIONS or re-compare etag by content under the same `Stat`.
- effort: S

## 4. Performance hypotheses for measurement

- H01: `loadAgentToolsets` composes and normalizes the whole session again per distinct agent toolset: `compose` re-reads and re-checks every other profile file (`readProfile`, and a model file per profile that has `@effort`) and `loadSessionSettingsFrom` re-runs ~35 normalizers including `loadPrompt` (prompt document reads) and state-context document reads, layout_load.go:119-164 → :264-352 → session.go:251.
  workload: 20 profiles in scope, 10 agents each naming a distinct toolset, 3 prompt documents per profile, `LoadSessionSettings` once per message and per list poll (cache miss only).
  benchmark: existing `BenchmarkLoadSessionConfig` (settings_load_benchmark_test.go:10) extended with `agents` using `toolset`; compare 0 / 5 / 10 distinct agent toolsets.
  expected: cost grows linearly with distinct toolsets, each step about equal to one full load.
- H02: profile fan-out per load: every profile in the session scope is file-read, strictly decoded, `checkProfile`'d (model catalog narrow + `loadModel` for an `@effort` default) and JSON re-marshalled into the synthetic `paths.profiles` entry, then re-parsed and `validateProfileFields`'d, layout_load.go:325-346, session.go:263-281,710-721.
  workload: 5 / 20 / 100 profiles in scope; `LoadSessionSettings` per message.
  benchmark: `BenchmarkLoadSessionConfig` with N extra profile files (new fixture size parameter).
  expected: linear in profiles (about 1 file read + 3 JSON parses each); at 100 profiles a visible fraction of a load.
- H03: `CheckLayout` loads every session once per profile in scope with no shared `CatalogScans` (`LoadLayoutSessionSettings`, check.go:116,126) and `validateProfileFile` rescans the model and toolset catalogs per profile file (catalog_files.go:370-381): O(sessions x profiles x catalog size) file operations for one `jad check`.
  workload: 200 sessions, 10 profiles each, 50 model files, 30 toolsets.
  benchmark: new `BenchmarkCheckLayout` in /tmp fixture (layouttest.Write plus AddSession loops), compare nil scans against a prototype passing `NewCatalogScans()`.
  expected: catalog directory reads drop from ~sessions x profiles x 4 to ~4; a one-shot CLI, so priority low.
- H04: `orderedObjectKeys` (session.go:1224) decodes every member value into a `RawMessage` just to list keys, and is called about 25 times per load (see grep in p2a-r1 L5; here session.go:272,710, profile_fields.go:23, layout_load.go:565).
  workload: a toolset with 60 MCP entries and an `agents` object of 200 agents.
  benchmark: new micro-benchmark on `orderedObjectKeys` with 200 members of 2 KiB; prototype using `Decoder.Token` depth skipping.
  expected: about one extra allocation+copy per member value, roughly 2x the cost of the unmarshal that follows.
- H05: `CatalogScans.Scan` holds `scanMemo.mu` across the directory scan (`ScanObserved`, catalog_scans.go:55-63), so loads that share a `CatalogScans` serialize on the first scan of each directory; recorder views then append every folder stamp for every `Scan` hit (:64-68), so the stamp of the Nth session of a list request carries the same folder entries again.
  workload: list of 200 sessions through one `CatalogScans`, 4 catalogs of 100 folders each.
  benchmark: existing `BenchmarkListManySessions/conditional/200` (app) and count `len(stamp.files)` per session.
  expected: stamp size ~ folders x sessions; `Current()` then does that many `os.Stat` calls per cache hit (`settings_stamp.go:62-77`), i.e. the cache hit cost scales with catalog size, not with the session.

## 6. Checked and sound

- Name hygiene: `sessionIDPattern` (`^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`) plus `.`/`..` exclusion in `parseReference`, `rootIDPattern`, `catalog.ValidateIdentifier` for category/name (must start alnum), catalog path = `dir/category/name.json` only after both parts validate (`catalogPath`, catalog_files.go:116); profile storage keys collision-checked (`profileKeys`).
- `Resolve`: unqualified ids with several roots stat every root, require a regular file, and return ambiguity instead of guessing; single-root references stay unqualified.
- Atomic writes: temp file in the target directory, chmod before rename, `link` for exclusive create (loser sees `CatalogPreconditionFailed`), temp removed on every path; category-directory create/remove race handled by `categoryDirectoryMu` and a bounded retry.
- `If-Match` semantics (`IfMatchSatisfied`: strong etag or `*`), precondition required for replace/delete/create, in-use checks (`profileUsers`, `modelUsers`, `toolsetUsers`, `serverUsers`) count only things that load today.
- `validateToolsetFile` and `validateSessionFile` load in scratch folders under the OS temp dir and remove them; no tool storage is created in the real tree.
- `layoutCompose`: input maps are copied (`mergeSettings`, `withDefaultEnvFile`), first-listed toolset wins with warnings, hooks in settings and toolset is an error, `approval` refused everywhere through one helper (`rejectRemovedApproval`, `removedApprovalHint`); `layoutSessionFile.refuseModelDefaults` keeps the removed key from being dropped silently.
- `SettingsStamp`: stamp is taken before each file read (`noteFile`) and after the load for config-derived files with the load start as stamp time, so edits during a load are "racy" and never current; presence-only stamp for the working directory; zero-length stamp is never current; documented omission of the root setting is correct (read once at `Load`).
- `CatalogScans`: scan errors are memoized together with the folder states; recorder views share the memo but keep their own list; mutexes never held across callbacks other than the scan itself.
- Numeric validation: `normalizeServerSettings` uses safe-integer reader with min/max for all 25 numeric keys; `normalizePersistence`/`normalizeCompaction` bounded; `SplitModelEffort`/`checkEffortName` accept only `[A-Za-z0-9._-]`, refuse empty id and empty effort; `effortsField` rejects duplicates.
- `isExactOrigin` (roots.go:734-782) round-trips the canonical origin and rejects userinfo, paths, default ports, uppercase/non-ASCII hosts, IPv4-looking hosts; no bypass found by reading.
- `loadSessionSettingsFrom` order: `validateToolSettingsShape` runs before every tool normalizer, and the async-required check (session.go:498-504) catches `process`, `subagent`, `tool_smith` without `async`.
- `go build`, `go vet`, `gofmt -l` clean for internal/sessionfs.
