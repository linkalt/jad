### P6CM-01 (medium, A) A remote sub-agent start skips every local gate — r1-01 — **confirmed by reading**

`startRemote` (`subagent_remote.go:80-184`) validates the remote **name**, parses the reference, reads the entry, checks `entry.Allows`, then registers a handle and calls `startRemoteRun`. It reads `execution.RemoteHops` and nothing else of the run scope. `grep -rn "AgentDepth" internal/tools/native --include=*.go` (non-test) returns exactly `subagent_manager.go:389` (a comment), `:572` (the manager overwriting the child's depth), `subagent_call.go:39` (comment), `:70-71` (the local gate) and `transcript.go:189`, `transcripts.go:169`, `transcript_remote.go:290` (the transcript gate). So the remote path has no depth check, and `max_runs_per_root`/`max_runs_per_session` are read only in `startRun`→`manager.start` (`subagent_call.go:103-105`, `subagent_manager.go:493-509`), which the remote path never reaches. The local gate itself is real: `startRun` refuses when `depth+1 > max(MaxDepth,1)` (`subagent_call.go:69-73`), and `max_depth` defaults to 2 (`sessionfs/native_subagent_settings.go:39`) while `subagent.go:324-325` requires ≥ 2 for an agent that lists `subagent`. So an agent at the configured maximum depth, whose `tools` list contains `subagent` and whose session has remotes, can still start remote agents; the only local brakers are the async handle cap and the remote's own `max_hops`.

The remote's hop counter and the remote's own depth limit are **not** substitutes: the remote run is a fresh depth-0 run on the other server, and `RemoteHops` bounds servers crossed, not runs started. Reach: local user configures `tools.native.subagent.remotes` (off by default) plus a nested agent; the model then decides. Conditional, no leak, no crash → **medium** (r1's rating kept). Left as is for a decision because `design_remote.md` (per r1, :53) says the depth limits apply "to the local call", so adding a remote gate changes a documented behaviour (decision 3).

### P6CM-02 (medium, A) An inline remote sub-agent cancel blocks until the remote answers or is declared lost — r1-02 — **confirmed by reading**

`subagent_remote.go:139-146` is the inline branch of `startRemote`:

    case <-ctx.Done():
        run.Stop("caller_cancelled")
        <-run.Done()
        return "", ctx.Err()

`remoteRun.Stop` (`profile_message_remote.go:222-234`) only records the reason and fires one best-effort HTTP stop on an untracked goroutine bounded by `stopCallTimeout` (3 s, `:17-19`). `run.Done()` is closed by `follow` (`:236-248`) after `client.Follow` returns, and `Follow` returns only on a terminal remote state, `remote.ErrLost` (unreachable for `lost_after_ms`, default 60 000, `remote/entry.go:34`; max 3 600 000, `:36`) or the local timeout (`remote_timeout_ms`, 600 s by default). The profile_message twin returns immediately after `run.Stop` (`profile_message.go:419-425`). Reach: any user stop or reset of a turn whose inline remote sub-agent sits against a slow, partitioned or hung remote; the turn's cancel then waits up to that bound. **medium** kept: a real hang of the cancellation path, conditional on the remote's behaviour, and the fix is one line.

### P6CM-03 (medium, A) A nested run's `owner` is the parent run id — r1-03 — **confirmed by reading, and it is a decision challenge in part**

`handleOwner` (`subagent_call.go:160-166`) returns `execution.ProcessOwner` as soon as it is non-empty, and the manager stamps `ProcessOwner` with the parent run's id for every child (`subagent_manager.go:571-578`). `startRun` passes that value as `owner:` (`subagent_call.go:98`), so for a nested run `run.owner` is `sub_xxxxxxxx`, while `subagentRun.owner`'s own comment (`subagent_manager.go:203-205`) says "the session key of the call that started the run". Consequences, all read:

1. **transcript gate** — `transcript_path.go:186-195`: `ownerSession, _, _ := strings.Cut(owner, "\x00")`; since `owner != execution.SessionKey` for a nested run, the read needs `allow_children`, and since `ownerSession != callerSession` it needs `allow_other_sessions`. Both default **true** (`sessionfs/native_transcript_settings.go:90`), so the default configuration is unaffected; with either turned off, the session cannot read its own grandchild's transcript ("belongs to another session").
2. **visibility** — `ownedRuns(owner)` (`subagent_manager.go:756-766`) filters on `run.owner`, so `list`, `CollectSubagentStateContext` and `CancelOwner(sessionKey)` never see nested runs. (Cancellation is not lost: the nested run's context is a child of the parent's, `subagent_manager.go:505-513`.)
3. **persistence** — the manifest has no `Session` field (`subagent_store.go:32-51`) and `restoredSubagentRun` sets neither `session` nor `root` (`:341-354`), so after a restart the session of a nested run cannot be recovered at all.

**Decision challenge, not a plain defect:** `DECISIONS.md:934` records "a handle a child starts is owned by the child's run id (its `async` sees only those)" — that is the *async handle* owner and it is deliberate. What the record does not cover is re-using the same field as the run record's owner for transcripts and lists. Keep **medium**; the fix is a design choice (a separate `session` field plus persisting it) and is put to the user as decision 1.

### P6CM-04 (medium, A/B) A panic after the launcher call is outside any `recover` — r2-01, r1-05 — **confirmed by reading**

### P6CM-07 (medium, A) A restored run's answer is pinned to the first reader's limit — r3-01, r2-04, r1-08 — **reproduced by execution**

`loadText(limit)` (`subagent_manager.go:356-381`) sets `textLoaded = true` under `run.mu` **before** reading, then stores `r.result.Text` cut to the caller's `limit` and ORs `r.cut`. ### P6CM-08 (medium, A) A remote start can leave the remote run going, unreported — r4-01, r1-09 — **confirmed by reading**

### PH1 in detail, because it is the group with a ceiling and a cap

`recordChange` (`subagent_changes.go:19-35`) appends under `r.mu`, releases it, then calls `r.store.save(r)`, and `save` → `write` (`subagent_store.go:75-114`) marshals the **whole** manifest, `CreateTemp`s it, `Sync`s it, closes it, renames it into place and then `defer os.Remove`s the temp path it no longer owns. Measured, per run:

- **The cap is the whole story at the defaults.** `changed_files_max` is 100, so the 101st distinct path takes the early return (`filesOmitted++`, no save). 1,000 calls at the default cost 3.85 ms against 3.60 ms for 100 calls: **900 further changes cost 0.25 ms in total**, i.e. 0.28 µs each — that is the `for _, known := range r.files` scan over 100 entries and nothing else. The quadratic term is reachable only by raising the cap.
- **With the cap raised it is exactly quadratic in bytes**: 100 changes write 270,350 B in total for a 5,129 B final manifest; 1,000 changes write 24,754,500 B for a 49,230 B final manifest; 10,000 changes write **2,452,545,000 B for a 490,230 B final manifest**. 10x the changes is 100x the bytes, and 490 KB per manifest is what the file holds at the documented maximum.
- **Time follows the bytes on tmpfs** (36 µs → 140 µs → 1.23 ms per change; 3.60 ms → 140.0 ms → 12.26 s in total) but on **btrfs it is the fsync that dominates**: 6.12 ms per change at the default cap and 7.10 ms at 1,000, i.e. 612 ms and 7.10 s for one child's own file list. A single 10,000-change run costs **83.7 s** on the repository's own disk.
- **Syscall counts** (strace, counts only, wall time discarded): 100 calls at the default → **100 fsync, 100 renameat**; 1,000 at the cap 1,000 → **1000 fsync, 1000 renameat, 2009 unlinkat of which 2005 fail with ENOENT** — the `defer os.Remove` after a successful rename costs one wasted syscall per save. That is a note, not a finding: it is ~0.5 µs against the 6 ms fsync beside it.
- **Three children are serialized, not slowed further**: 3 runs x 1,000 changes through one store take 452.5 ms (150.8 µs per change) against 140 µs for one run alone. The store mutex is held across the entire write, so three children's saves are **additive** — 3 x 140 ms — with an 8 % overhead. There is no overlap to lose and no contention blow-up to find at 3 concurrent children; the cost is the sum.
- Allocation: 24.1 MB for 1,000 changes and 5.85 GB for 10,000 (12-24x the bytes written, one `json.Marshal` + one `append(encoded, '\n')` per save).

What this decides: **P6CM-06's context and P6CM-13's sibling are now numbers.** A child that changes 100 files (the shipped default) pays 0.6 s of fsync-bound manifest writes on a real disk, and each of those writes is a full rewrite of a 5 KB file. A child at the cap maximum pays 84 s and 2.45 GB. The fix shape §13 decision 5 implies — cutting the rendered list — does not change this; the manifest rewrite would need the debounce/carry-forward that §13 decision 8's hygiene batch does not currently include, so if PH1 is to be fixed it is a separate item and it needs the user (see the new decision 10 below). Nothing here changes P6CM-06's severity, which is about the *rendered* list (21.7 KB against a 32.8 KB cap), not about the manifest.

### PH8 in detail, because it decides P6CM-13's severity

`finish` (`subagent_manager.go:700-721`) takes `m.mu`, appends the id and, while `len(m.finished) > spec.keep`, calls `dropOldestLocked` → `m.store.remove(id)` → `os.Remove` under `s.mu` (`:152-168`, `subagent_store.go:117-126`). At steady state with `keep_finished` 50 every finish drops exactly one run, so **every** finish takes one `os.Remove` under `m.mu` — and if a concurrent `save` holds `s.mu` across its `Sync`, finish waits for that fsync with `m.mu` held. Every `start`, `list`, `status`, `byID`, `ownedRuns`, `CancelOwner` and `BackgroundWriters` waits behind it.

Measured with the real store on both file systems, 0 / 1 / 3 / 8 goroutines looping `store.save` (which is exactly what `recordChange` ends with) while one `finish` drops two manifests, and a probe goroutine timing every `m.mu` acquisition:

- **tmpfs**: finish 42.2 µs → 281.9 µs → 405.6 µs → 2.00 ms; worst `m.mu` wait 0.11 ms → 1.45 ms → 2.25 ms → 3.11 ms.
- **btrfs**: finish 5.62 ms → 20.1 ms → 26.9 ms → 69.9 ms; worst `m.mu` wait 0.198 ms → 165 ms → 136 ms → 274 ms, with a **672 ms** maximum in the 8-saver case.
- The btrfs `savers=0` figure is the important one: **5.62 ms of `m.mu` per finish with no contention at all**, 133x the tmpfs figure, because two `os.Remove`s on this disk cost 2.8 ms each. The spread on btrfs is wide (finish 68-80 ms, worst wait 160-672 ms) and is reported as measured, not smoothed.

**Severity: P6CM-13 low → medium.** The entry was lowered from r1's medium in §4.13 because the only cost then known was one `os.Remove` under a mutex, and the code's own comment ("a slow disk never holds the lock") made it look deliberate. The measurement says the mutex is held for **5.6 ms per finish at the defaults on a real disk and up to 70 ms with eight children finishing**, and that unrelated callers (`start`, `list`, `status`) see waits of **0.14-0.67 s** in the tail. That is the same order as P6BM-15, which p6b raised to medium on 35 ms per poll, and unlike P6BM-15 it is a pure lock-ordering defect with a two-line fix that the transcript delete in the same function already applies. It is not a correctness fault, so it does not go higher.

At the shipped `keep_finished` 50 a read costs 0.5 ms, which is nothing; at the documented maximum 1000 it is ~9.3 ms and ~2 MB allocated per read. **P6CM-28 stays low**, and its fix is confirmed to be the one-liner §4.28 proposed (compute `ids` inside the `!found` branch). The recovery case §9 wanted is already covered by the existing `BenchmarkSubagentRecoverManifests` (1000/5000 manifests), so it was not re-measured.

**PH3 is confirmed, and its "alternative to measure is a tail read" is only half right.** The full scan (`readTranscriptAnswers`, `subagent_answer.go:58-88`) reads the file with `ReadBytes('\n')`, `bytes.Contains` per line, and up to two `json.Unmarshal` per candidate line. On a tool-result-heavy transcript it costs **788 µs per 1 MiB and 6.09 ms per 8 MiB** (linear: 8x bytes → 7.7x time, ~1.3 GB/s) and allocates **1.15x the file size**. A 64 KiB tail read that starts at the first whole line returns the same text in **42.8 µs and 45.0 µs** — 18x and 135x cheaper, 76 KB allocated. Both are CPU bound: btrfs gives 712 µs and 5.77 ms, within noise of tmpfs.

The probe `TestPH3TailEquivalence` shows where the tail read **stops being equivalent**, and this is the finding that matters for the fix:

- An ordinary finished run whose last response is at the end of the file: full and tail agree on both `last` and `lastNonEmpty` (both 1500 B in the probe).
- A cut or lost run whose newest non-empty text is 1.1 MiB from the end, with an empty final response after it: the full scan finds `"the only answer"`, the 64 KiB tail read finds **`""`**. `loadText` uses `lastNonEmpty` for every state but `done` (`subagent_manager.go:373-378`), so a tail read would **silently turn a cut run's answer into an empty one** — exactly the P6CM-07 symptom the fix is meant to remove.

So the fix shape PH3 decides is: **a tail read is safe for the `done` state's `last`, and must not be used for `lastNonEmpty`** unless the window is bounded differently (store the newest text in the manifest, or scan backwards until the first non-empty response rather than a fixed window). Per-run cost is small anyway — 0.8 ms per restored 1 MiB run, 6.1 ms per 8 MiB run, once per run per process — so **PH3 does not move P6CM-07's severity**: that entry is medium because a first reader pins the stored text at 4 KiB, not because the scan is expensive. The scan cost is a nice-to-have fix, and the cheapest correct one is to keep the full scan for non-`done` runs.

## 13. Needs the user

### Decisions

1. **P6CM-03 — what `subagentRun.owner` means, and does the manifest keep the session?** `DECISIONS.md:934` records that a *handle* a child starts is owned by the child's run id; the same value is also the run record's owner, which `RunTranscript`, `list`/`collect` and the transcript gate read, and the manifest keeps no `Session` at all. **Recommendation:** split the two notions explicitly — keep `owner` as the **session key** (what the transcript gate and the lists want, and what the field's own comment says) and give the async handle its own field/value (the parent run id) where `handleOwner` produces it today; add `Session` (and `Root`) to `subagentManifest` in the same commit so a restart can still place a nested run. Effort M. If you prefer the current behaviour, the alternative is to leave the field as it is and teach `transcript_path.go` and the lists about run-id owners, plus document that a nested run is invisible to `subagent({})` and to the statecontext. **Needs you** because it changes a recorded ownership rule and a persisted schema.

2. **P6CM-05 — what bounds `SubagentManager.Close`'s wait?** **Recommendation:** wait at most the longest kill grace already in the config (`tools.native.process.kill_grace_ms`, or the async stop wait — pick one and reuse it, do not invent a constant), log the ids still running with `slog.Warn`, and return. Same shape as `AsyncHost.waitShellRuns`. Effort S. **Needs you** only for the choice of which existing bound to reuse; a new setting is the alternative and I would avoid it.

3. **P6CM-01 — should the remote start honour `max_depth` and the run caps?** The local path refuses at `depth+1 > max_depth` and on `max_runs_per_root`/`max_runs_per_session`; the remote path honours none of them, and `design_remote.md` (per r1) says the limits apply "to the local call". **Recommendation:** gate the remote start with the **depth** check, shared with `startRun`, and *not* the run counts (a remote run is not a local slot, and counting it would make the two servers disagree about a number neither owns); add a test with `AgentDepth = max_depth` and one at `max_depth - 1` that succeeds. Effort S. **Needs you** because it narrows a documented behaviour, and the alternative (document "remote starts are unlimited") is a legitimate answer.

4. **P6CM-08 — stop the remote run when the follower cannot be registered.** **Recommendation:** on `directory.Go` returning false, issue one bounded `client.StopRun(ctx, view.ID)` with `stopCallTimeout` and say so in the text ("the server is shutting down; the remote run was asked to stop"). Effort S. **No decision needed** — this is a defect fix, listed here only because it changes shutdown behaviour and the wording of one error.

5. **P6CM-06 / P6CM-24 — bound the changed-file list in the tool result.** **Recommendation:** cut the joined list the way the async summary already does (share `changedFilesText`'s 200-byte budget or budget against the run's `result_max_bytes`), report `written_files_omitted` when it is cut, and add the missing test. **Needs you (mildly)** because it changes model-visible tool output, which means a `messages-golden-diff` run in the fix stage.

6. **P6CM-15 — are the run caps "descendants" or "all runs of the session"?** `DECISIONS.md:934` says the session cap counts runs "at any depth", "counted when a child starts one", while `bySession` counts every start and the check applies only to nested ones. **Recommendation:** keep the documented meaning (descendants), stop incrementing `bySession` for depth-0 starts, and add the sentence to the settings text. Effort S. **Needs you** if you want the other meaning (a true session total), because then a session's own top-level starts would start being refused.

7. **Severity confirmations.** Medium: **P6CM-01..08 and P6CM-13** (§12-bis raised 13 on measurement: 9 medium, 19 low); everything else low. Two filings lowered (r1-04 → P6CM-13, r1-13 → P6CM-17), three raised inside merged entries (r1-07 → P6CM-05, r1-09 → P6CM-08, r2-04 + r1-08 → P6CM-07), one sub-item refused (C2). **Recommendation: confirm as merged.** The one that could reasonably go the other way is **P6CM-06 at low** if you hold that a raised `changed_files_max` or long paths are the user's own doing; my measurement puts the defaults at 21.7 KB against a 32.7 KB cap, so the overrun is real but conditional.

8. **Fix batching and order.** Nothing in this phase is fixed yet and no code was touched. The natural split, in this order: (i) **the four one-line-to-small correctness fixes that need no decision** — P6CM-04 (recover + log around `execute`'s body), P6CM-07 (do not let `Detail` choose the storage limit; cut only the return value), P6CM-02 (return after `Stop`, like `profile_message`), P6CM-08 (the bounded stop); (ii) **the boundary batch that needs decisions 1, 3 and 5** — P6CM-03, P6CM-01, P6CM-06 with P6CM-24; (iii) **the shutdown and lifecycle batch** — P6CM-05, P6CM-12, P6CM-14, P6CM-09; (iv) **hygiene** — P6CM-10, P6CM-11, P6CM-13, P6CM-16, P6CM-18, P6CM-19, P6CM-20, P6CM-21, P6CM-22, P6CM-23, P6CM-25, P6CM-28; (v) **maintainability, behaviour-neutral and alone** — P6CM-17, P6CM-26, P6CM-27. Every fix needs its regression test; the phase has none for any of these today (P6CM-27). **Needs you:** authorisation, and the decision on (ii).

9. **Measurement go-ahead for §9's eleven groups — done in §12-bis.** **Result:** PH1, PH2, PH3 and PH8 run serially on tmpfs and btrfs, all four confirmed, one severity moved (P6CM-13), no new finding, `-race` clean. The original recommendation was to run PH1, PH2, PH3 and PH8 as the measurement step for this phase — they cover the only entries whose severity a number could move (P6CM-13, P6CM-28, P6CM-07's cost, P6CM-06's context) — and leave PH5-PH11 to the phase they belong to (`remote`, `app`, `asyncmgr`). **No fix waits on a measurement.**
