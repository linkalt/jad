## 1. Understanding note

`Handler` (`httpapi/handler.go:103`) is the whole HTTP surface: `ServeHTTP` → `observeRequest` (logging + panic answer + optional-interface-preserving writer, `request_observer.go:70`) → `route` (one manual switch over decoded path segments, `handler.go:298`), CORS allowlist first (`:410`), then bearer token compared as SHA-256 with `subtle.ConstantTimeCompare` (`:427`). Bodies are read through `http.MaxBytesReader` on every mutating route; the run route has a raised limit for image/file data and a one-pass in-place parser (`run_body_scan.go`, `run_input.go`).

A run is a `*activeRun` in `runRegistry` (`registry.go:249,297`), keyed `reference\x00profile`, with one entry per start and retention by time (`finish` → `time.AfterFunc(retention, retire)`, `:822`). Concurrency shape: `runRegistry.mu` protects the map and is released before any run-level lock; `activeRun.mu` protects status, latest message/frames, subscribers, interaction/retry/async state, live images; `eventQueue.mu` protects one subscriber's frame queue; `mutationMu` protects only the short-lived mutation/restore gate maps (never held across another lock); `sessionLocks` (keyed locker, `settings_handlers.go:110`) serialises one process's requests for a session; `turnQueue` (`start_turn.go:16`) orders arrivals per transcript; the cross-process transcript lock comes from the resolver. Lock order observed everywhere: `mutationMu` → `runs.mu`/`run.mu` → `queue.mu`, and `sessionLocks` → (gate map, checked and released) → `runs.mu`; `interactions.Broker` never notifies under its own mutex, so `broker.mu` → `run.mu` does not exist. Producers (`publish`, `publishMessage`, `setAsyncState`, `setProviderRetry`, `setPendingInteraction`, `finish`) never block on a subscriber: `eventQueue.push` is non-blocking and a queue over budget is closed and dropped.

SSE: `subscribe` registers a queue in a "hold" state, captures the point P of the stream under `run.mu`, builds the snapshot outside the lock (P-033), then `release` pushes snapshot + state frames + held events in one critical section (`registry.go:83-121`). Terminal frames (`ui.message`, `completed`, `done`) are always queued. `serveSSE` (`handler.go:750`) renews a per-write deadline, chunks writes, and emits keep-alive comments.

Tool-started runs (`ProfileRuns()`/`profile_run.go`) reuse `tryStartRun`/`acquireRun` and the same executor, with `source="profile_message"` excluded from the `max_concurrent_runs` counter. Run state is mirrored to clients as `run`/`ui.delta`/`ui.part`/`ui.message`/`usage`/`interaction`/`provider_retry`/`async_state`/`hook_report` plus `error`/`completed`/`done`.

`webui` is the frontend contract: `StreamingRun` reduces provider events into one cumulative message (delta accumulation through a `strings.Builder`, `streaming.go:38-51`), `Increments` derives `ui.delta`/`ui.part`/full `ui.message` (`types.go:313`), `normalizeTranscript` folds JSONL records into messages for the snapshot/history routes, `CapMessages` bounds inline parts, hosted tools and citations get their own projection.

`httpdebug` wraps a provider transport (opt-in): records per request/response files, redacts URL userinfo and credential-looking query names, redacts sensitive headers on request and response, creates the directory `0o700` and files `0o600`, and prunes the directory to `max_total_bytes` at start. `interactions` is one pending approval/draft per run with a timer, an extend path and a cancel path, publishing state through a callback (`run.setPendingInteraction`). `memorytrace` is an opt-in process sampler with a per-run handle and a generation-guarded ticker.

## 3. Findings

### P3-R2-01  The run's panic boundary starts two calls too late, and the async-state watcher goroutine has none
- severity: medium
- lens: A correctness
- location: internal/httpapi/executor.go:36 (defer `watchAsyncState`) vs internal/httpapi/executor.go:48-56 (the `recover`); internal/httpapi/async_state.go:30-60 (the watcher goroutine, started at :48, no `recover`); internal/httpapi/handler.go:472-475 and internal/httpapi/profile_run.go:125-128 (the goroutines that call `executeRun`, also without `recover`)
- evidence: [read] `executeRun` installs `defer h.watchAsyncState(run, reference, profile)()` at :36 and only then the panic-recovering defer at :48, so a panic in `WatchSessionAsync` (`app/resolver.go:1122`, called synchronously at `async_state.go:33`) escapes the run goroutine unrecovered. The watcher goroutine calls app code (`read()` → `manager.SnapshotLive`, `async_state.go:51-54`) and `run.setAsyncState` with no recover of its own. Nothing between `go func()` and `executeRun` recovers: the request-level recover in `request_observer.go:76-95` runs on the HTTP goroutine, not on these. Consequence of a missed recover here is the D-1 class: the panic reaches the runtime and takes down the whole backend. Reachability requires a panic in app code (low), impact is whole-server (see severity table).
- suggested fix: move the recovering defer to the first statement of `executeRun` (before `watchAsyncState` and before `WithRetryNotifier`), and wrap the watcher goroutine body in the same recover-and-log pattern; no behaviour change otherwise.
- effort: S
- prior art: refines D-1 (fixed) — the boundary exists but has a hole for this goroutine

### P3-R2-02  A panic between registering a tool-started run and starting it leaks the run and the transcript lock
- severity: medium
- lens: A correctness
- location: internal/httpapi/profile_run.go:100-128 (no `launched` guard; `go func()` at :125); compare internal/httpapi/handler.go:459-475 (`handleRunStart` has exactly that guard)
- evidence: [read] `StartProfileRun` takes the transcript/process lock and registers the run in `tryStartRun`/`acquireProfileRun`, then runs `run.supportsInteraction/chain/hops` assignment, `request.BeforeRun(ctx)` (:119-121, supplied by `app/profile_message.go:145` and running a compaction that touches transcripts) and `h.attachContentCache(run)` — all before the goroutine that owns `defer started.processUnlock()`. Any panic in that window returns to the caller (a tool goroutine whose recover is elsewhere) with the run still `running` in the registry and the process lock still held: every later start/stop/compact/restore of that profile answers `ErrSessionBusy`/409 until the process restarts. `handleRunStart` covers the same window with `defer func(){ if !launched { run.finish("failed", nil); processUnlock() } }()`, and `profile_run_test.go` has no test for it (tests listed at profile_run_test.go:108-341 cover success, stop, busy-wait, failure message only).
- suggested fix: add the same `launched` guard to `StartProfileRun` (defer `run.finish("failed", nil)` + `started.processUnlock()` unless the goroutine was started); one test that panics from `BeforeRun` and then starts a second run.
- effort: S
- prior art: new (divergence from the neighbouring pattern)

### P3-R2-03  Log route template does not know the checkpoint, image and live-image routes, so they log as "unmatched"
- severity: low
- lens: D maintainability
- location: internal/httpapi/request_observer.go:126-133 (`knownSessionRoutes`) and :135-162 (`routeTemplate`); the real table is internal/httpapi/handler.go:363-401
- evidence: [read] `route()` serves `GET …/images/{name}` (`handler.go:375`), `GET …/messages/{id}/images/{call}/{pos}` (`:373`), `GET …/checkpoints` (`:389`), `POST …/checkpoints/{id}/restore` (`:391`) and `GET …/run/images/{call}/{pos}` (`:394`). `knownSessionRoutes` lists none of `images`, `checkpoints`, `run/images`, `messages/{id}/images`, and `routeTemplate` only special-cases `messages/{id}`, so every checkpoint request and every image request is logged with `route=unmatched` (`:162`) and all of them look alike in the request log. The duplication is the root cause: two hand-maintained lists of the same routes in the same package, with no test tying them together.
- suggested fix: derive the template from one table used by both `route` and `routeTemplate` (a slice of `{method, shape, template}`), or at minimum add the missing suffixes and a test that walks `route`'s cases.
- effort: S
- prior art: new

### P3-R2-04  `/api/library` returns configuration errors containing absolute server paths
- severity: low
- lens: B security (boundary: error text)
- location: internal/httpapi/library_handlers.go:48-56 (`writeRootLibraryError` passes `ConfigError.Message` through as the 422 body); sources internal/contentlibrary/library.go:209 (`"library directory is not a directory: %s"` with the configured root) and internal/contentlibrary/settings.go:139-151 (`"%s: file is required|empty|invalid JSON"` with the setting file path)
- evidence: [read] the reachable path is `GET /api/library` → `h.library.List` → `ConfigError` → `writeJSONError(w, &StatusError{422, configErr.Error()})`. A session with a mistyped `libraries.prompts` directory answers with, e.g., `{"error":"library directory is not a directory: /home/<user>/notes/prompts"}`, and a broken root setting answers with its absolute path. Who can reach it: a holder of the API token (the local Web UI); not the model and not a remote peer.
- suggested fix: keep the path in the server log (`logging` is available in the handler) and return a path-free message per case ("a configured library directory is not a directory", "the root setting could not be read"); or have `ConfigError` carry a public message plus a detail string.
- effort: S
- prior art: new; the same pattern exists for `sessionfs.ConfigError` (cross-phase lead 5)

### P3-R2-05  A settled interaction can be republished as pending, leaving a stale draft in the stream
- severity: low
- lens: A correctness (ordering)
- location: internal/interactions/broker.go:113-122 (entry installed, timer armed, `b.mu` released, then `b.notify(&pending, nil)` at :119) and :188 (`Extend`); consumer internal/httpapi/interaction_state.go:19-52
- evidence: [read] the timer is armed before the pending notification is published, and the two notifications come from different goroutines. If the timer fires first (`Request` calls `read`-side work through `run.setPendingInteraction`, which snapshots the whole streamed text under `run.mu`, see P3-R2-07), `timeout` → `settleLocked` → `notify(nil, ended)` runs while `r.pendingInteraction == nil`, so `setPendingInteraction` returns early (`interaction_state.go:28-31`) and the clearing event is **dropped**; the late `notify(&pending)` then sets `r.pendingInteraction` for a question that already timed out. The client shows an approval dialog whose `expires_at` has passed and nothing clears it until the next interaction or the end of the run (`finish` → `interactions.Cancel` finds `entry == nil` and returns without notifying). Window: `question.TimeoutMS` ≥ 1 ms (`broker.go:79`) against a notify that can take milliseconds; narrow but deterministic with a 1 ms timeout.
- suggested fix: publish the pending state inside the `b.mu` critical section that installs the entry (or mark the entry "announced" and have `settleLocked` remember that a clearing notification is still owed), so a settle that happens before the announce still emits the clear.
- effort: S
- prior art: new

### P3-R2-06  Every decoded inline image of a run is retained until the run is retired, with no count or size cap
- severity: low
- lens: C performance (memory retention)
- location: internal/httpapi/live_images.go:15-34 (`keepLiveImages` fills `r.liveImages[callID]`); cleared only in internal/httpapi/registry.go:754-756 (`disposeContent`, called from `retire`)
- evidence: [read] `OnToolResult` calls `keepLiveImages` for every tool result (`executor.go:111`), which base64-decodes each inline image of the result and stores the bytes per call id. Nothing prunes the map during the run and nothing bounds the number of calls or the total bytes; the images stay reachable through `activeRun` for the whole run plus `run_state_retention` (default 30 s). A run that reads N images of S bytes each holds ΣS decoded bytes on top of the transcript. Quantify with PH-03.
- suggested fix: bound the map (most recent K call ids or a byte budget taken from an existing setting) and serve only what is still bounded; drop an entry once the result is in the transcript if the message-image route can serve it.
- effort: S
- prior art: new

### P3-R2-07  Interaction publish builds the whole streamed-text snapshot under the run lock
- severity: low
- lens: C performance (lock held across I/O and a full copy)
- location: internal/httpapi/interaction_state.go:56-57 (`r.snapshotMessageLocked()` inside the `r.mu` critical section) → internal/httpapi/registry.go:697-704 → internal/httpapi/run_content_cache.go:121-146 (`Snapshot`: flush + `ReadAt` + `string(content)`)
- evidence: [read] the remaining instance of the P-033/P-045 class after `c2c071d`: `setPendingInteraction` holds `run.mu` while the content cache flushes its pending bytes, reads the partial file and copies the text (twice: `readStableLocked` slice + `string(...)`), then marshals it. While that happens `publishMessage`, `cacheContent` (once per provider delta, `executor.go:98`) and `state()` are blocked, i.e. the run's own event path stalls. Frequency is low (once per pending interaction and once per settle), so severity is low; the same pattern also exists in the test-only helper `currentMessage` (P3-R2-10).
- suggested fix: reuse the P-033 shape — copy the message and the cache pointer (pin) under the lock, build the snapshot and the frame outside it, then assign and push under the lock, exactly as `beginSubscribe`/`finish` now do.
- effort: S
- prior art: re-confirmed P-033/P-045 for a path their fix did not cover

### P3-R2-08  Switching the content cache to its memory fallback reads the whole partial file into memory
- severity: low
- lens: C performance (memory spike on the failure path)
- location: internal/httpapi/run_content_cache.go:460-476 (`switchToFallbackLocked`) with :442-456 (`readStableLocked`) and :170-185 (`appendMemoryLocked` caps only after the read)
- evidence: [read] on any write/read failure the cache reads the entire partial file (`make([]byte, c.fileBytes)`), converts it to a string for `appendMemoryLocked` and only then applies `fallbackMax` (64 MiB default). A 128 MB streamed answer therefore allocates ~128 MB + up to 128 MB during the conversion at the moment the disk fails, when the intent of P-044 was to cap exactly this. The final retained size is correctly capped (`c.total` is reset to `len(c.memory)`), so this is a transient spike, not a leak.
- suggested fix: read only the first `fallbackMax` bytes (plus a read to know whether more existed) and set `truncated` when the file is longer; that also matches what the late subscriber is told.
- effort: S
- prior art: extends P-044 (fixed) to its recovery path

### P3-R2-09  `acquireRun` retries without backoff and would spin if the resolver offers only half of the lock adapter
- severity: low
- lens: A correctness (hardening, unreachable with the app resolver)
- location: internal/httpapi/start_turn.go:90-115 (the `for { tryStartRun … }` loop) with internal/httpapi/process_lock.go:23-49
- evidence: [read] `busy` is only possible when the resolver implements `SessionProcessTryLocker`; the loop then calls `lockSessionProcess`, which is a no-op returning `func(){}` (`process_lock.go:5-8`) when the resolver does **not** implement `SessionProcessLocker`. A resolver that implements the try-form only would loop on `tryStartRun` as fast as the CPU allows while another run holds the transcript, with no sleep and no attempt counter. `app.Resolver` implements both, so this is a hardening item, not a live bug.
- suggested fix: return a `StatusError` (or take the blocking lock) when `lockSessionProcess` yields the no-op release and the loop is about to retry; or add a small backoff via a timer.
- effort: S
- prior art: new (hardening, unreachable)

## 4. Performance hypotheses for the measurement step

- H01: the transcript projection parses every tool output three to four times per record, webui/normalize.go:254-275 (`toolResult`) with :279-299 (`storedImageNames`), :301-327 (`toolOutputForUI`) and webui/inline_images.go:16-40 (`inlineImageURLs`)
  workload: one `GET /api/sessions/{s}` snapshot (or history page) of a session with 1,000 records, of which 200 are `function_call_output`, each output 1 KB–2 MB (inline-image outputs the large ones); each of the three passes unmarshals the same `output` array, and the two image passes decode the full data-URL strings.
  benchmark: none exists for `webui.normalize.go` (`audit_performance_plan.md` §"Not measured" (2) says so explicitly). New `BenchmarkNormalizeTranscript` in `webui` with a fixture of 100/1,000 records and 0/10 inline-image outputs, `-benchmem`; report ns/op, B/op and allocs/op per record.
  expected: 3–4x the single-pass parse cost per tool result and a byte count proportional to the sum of the data-URL lengths; scales with records × output size.

- H02: serving one inline image normalises a whole turn, httpapi message-image route (`handler.go:373`) → app/history.go:131-161 (`ReadMessageImage`) → webui.FindInlineImage (webui/inline_images.go:66-78)
  workload: a turn with 20 inline images of 2 MB each; the browser fetches all 20 (20 × full turn normalisation, each normalisation re-parsing every tool output including the base64 payloads).
  benchmark: new `BenchmarkFindInlineImage` (normalise N records, find the last image) plus a `BenchmarkReadMessageImage`-style fixture with 1/10/20 images per turn; the same shape as H01 gives the per-record cost.
  expected: linear in images × turn size, i.e. quadratic in the number of images in the turn; the useful comparison is "cost(image 20) / cost(image 1)".

- H03: `keepLiveImages` retention (P3-R2-06), internal/httpapi/live_images.go:15-34
  workload: a run of 50 tool results, each with one 2 MB inline image (100 MB of base64 in the transcript).
  benchmark: new `BenchmarkKeepLiveImages` reporting retained bytes per image and total (mirror `BenchmarkMemoryRetention`, httpapi/memory_retention_benchmark_test.go:1-175, which already measures retained run state); assert with `runtime.ReadMemStats` after GC as that benchmark does.
  expected: retained bytes ≈ decoded size × number of image results, held for the run plus the retention window.

- H04: interaction/state publishes stall the run's event path (P3-R2-07), internal/httpapi/interaction_state.go:56-57
  workload: a run whose streamed text is spilled (1 MB and 8 MB) with one pending interaction; measure the wait of a concurrent `run.state()` poll or of `cacheContent` while `setPendingInteraction` runs.
  benchmark: reuse `BenchmarkLateSubscribe`'s measured shape (P-033: 4.34 ms at 1 MB, 31.7 ms at 8 MB for the same snapshot work) and the existing `BenchmarkRunLockWaitDuringLateSubscribe` harness with `setPendingInteraction` in place of `subscribe()`; `-benchmem`.
  expected: the same cost as P-033 per interaction event, i.e. milliseconds per approval on a large stream.

- (no new hypothesis) the per-event pipeline cost (P-023 fixed, P-024 skipped) and the eager full-message frame (P-025 fixed) are not re-opened; `SSEDeltaEventEncoding`, `PublishMessage/*`, `RunStateWhilePublishing`, `FinishedRunRetention` and `StreamingRunTextDeltas` already cover that ground.

## 6. Checked and sound (evidence gathered, no finding)

- Slow-subscriber publisher path (the `4fb4d51` question): `eventQueue.pushLocked` (`registry.go:123-171`) has no blocking operation and no lock that a reader holds; an over-budget queue is closed and removed from `r.subscribers` by the publisher. `TestSlowSubscriberIsDroppedAndDoesNotHoldBackThePublisher` passes on this tree (rc 0).
- Subscriber-attach ordering (hold/release, `registry.go:73-121`): the queue is registered under `run.mu` before the snapshot is built, held events keep arrival order, `holdSuperseded` drops a snapshot that a newer full-state frame replaced, and `oversizedSnapshot` is cleared exactly when the uncharged frame leaves the queue — byte accounting stays consistent in every branch I traced.
- Terminal frames: `ui.message`/`completed`/`done` are queued regardless of budget, the oversized terminal snapshot replaces what is queued (documented), and `serveSSE` ends the loop on `done`.
- `serveSSE` (`handler.go:750-803`): per-write deadline renewed before each 64 KiB chunk, cleared on return, keep-alive comment frames on idle, `error` from a write ends the handler; `http.ResponseController` reaches the real writer through `observedWriter.Unwrap`.
- `request_observer`: panic recovery answers 500 only when nothing was written, re-panics `http.ErrAbortHandler`, preserves `http.Flusher`/`Hijacker`/`Unwrap`, logs causes only for ≥500 and never logs client-supplied path segments.
- Auth/CORS: bearer token hashed and compared constant-time, minimum length 32 and no CR/LF, allowlist fail-closed, `WWW-Authenticate` sent, `/api/health` the only unauthenticated route.
- Body limits: every mutating route uses `http.MaxBytesReader`; `readAllChunked` has no realloc doubling past 1 MiB; the run body allows only image/file data above `max_body_bytes` and re-checks the rest; the one-pass scanner (`run_body_scan.go`) is only entered after `json.Valid`, all indexes are bounds-checked, and `jsonStringView`'s `unsafe.String` never escapes the request buffer.
- `run_input.go`: base64 decode is bounded by `MaxImageBytes`/`MaxFileBytes`, type is sniffed from the bytes (`imagedata.Sniff`), filenames reduced to a base name without control characters, unknown part fields refused.
- Path handling: `decodedPathSegments` unescapes per segment, so an encoded `/` cannot forge a segment; `sessionReferencePattern`/`profileNamePattern` refuse slashes; catalog ids need exactly `<category>/<name>` and are re-validated by `sessionfs.catalogPath`.
- Images: `writeImage` sets `nosniff`, CSP sandbox, explicit `Content-Length` and the right cache policy (immutable only for content-addressed stored files).
- Mutation gate + locks: the gate is a map entry under a mutex never held across another lock; `beginMutation` before `lockSession`, `runIsActive` checked before the process lock, gate cleared before the locks are released; `keyedLocker` keeps a refcount so an entry cannot be deleted under a waiter; `turnQueue.leave` is `sync.Once` and only ever closes the next element's channel.
- Interactions: notifications are always sent outside `broker.mu` (so no `broker.mu` ↔ `run.mu` inversion), `settleLocked` sends exactly one answer into a capacity-1 channel, timers are stopped on settle, `Extend` re-arms the timer without a premature timeout, a cancelled `Request` still returns an answer, and `run.finish` cancels the broker before taking `run.mu`.
- `httpdebug`: request records redact userinfo and credential-shaped query values, both request and response headers use `sensitiveHeaderPattern`, bodies are capped before write, files are `0o600` in a `0o700` directory, ids are reserved under a mutex and files are written off the request path; retention prunes oldest-first at start. D-5 verified fixed.
- `memorytrace`: generation counter prevents a stale ticker goroutine from writing after a restart, `Stop` is idempotent, `write` recovers from a panicking consumer, `Mark` refuses details after the run ended.
- Tolerant session listing (cde80dd) end to end: the handler answers `{"files":[…],"truncated":bool}` (`catalog_sessions_handler.go:44-53`); an unreadable entry is `{id, error}` with an empty `etag` because `CatalogFileInfo.ETag` has no `omitempty` (`catalog_files_handlers.go:12-24`), which a client can tell apart from a real version; it is **not** a dead end, because `GET /api/catalog/sessions/{ref}` still returns the file's bytes and its ETag (`app/session_catalog_files.go:35-43`), so the file can be repaired with a conditional `PUT`. No finding.
- `webui/streaming.go appendDelta`: the amortised `strings.Builder` is safe on reuse because `Builder.Reset` nils the buffer (checked in go1.27.3 `strings/builder.go`), so no previously returned part text is aliased by a later write.
- `run_content_cache`: pin/unpin + deferred close is balanced on every path I traced (`beginSubscribe` pins under `run.mu` before any `setCommittedMessage` can close), the spill writes roll back on a short write, the fallback cap keeps `total` equal to what can be read back, and the truncation marker never reaches the committed message (`setCommittedMessage` checks `Truncated`).
- `webui.CapMessages`/`Increments`/`partsEqual` (P-023 fix): the typed comparison covers every `Part` field, nil vs empty slices are distinguished, and the truncation cut is UTF-8 safe.
