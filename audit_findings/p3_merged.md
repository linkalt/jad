## 3. Verification of the medium findings

### P3-01 (medium, A) An answer's clearing event can arrive before the question's announce — r1-02, r2-05, r4-01 — **confirmed by execution**
- the producer side: `Request` installs the entry and arms the timer **under `b.mu`**, unlocks, and only then calls `b.notify(&pending, nil)` (`broker.go:114-127`); `Extend` does the same for its re-announcement (`:158-190`, notify at `:188`). The settle side (`Reply` `:130-156`, `Extend` `:158-191`, `timeout` `:208-223`, `Cancel` `:193-206`, `settle` `:225-239`) calls `settleLocked` — which sets `b.entry = nil` (`:245`) — unlocks, then calls `b.notify(nil, ended)` at `:143/154/172/205/222/234`. Two goroutines therefore publish state that a third observes in arrival order, not in the order the transitions happened. r1 states it for `Extend` vs `Reply`, r2 for the timer beating the announce, r4 for `Extend` vs `Reply` again: one root cause, two triggers.
- the consumer side: `setPendingInteraction` (`interaction_state.go:19-80`) accepts a non-nil pending whenever `r.status == "running"` — it has no way to know the question was already settled — and returns **early, dropping the clearing event**, when `next == nil && r.pendingInteraction == nil` (`:30-33`). That is exactly the state a clear finds if the announce has not arrived yet.
- **executed**: a probe in `/tmp/p3work` (overlay test in package `httpapi`, nothing written in the tree) wires a real `interactions.NewBroker` to a real `activeRun.setPendingInteraction`, holds the announce at a gate, answers with `broker.Reply(id, accept)` while the announce is in flight, and then releases it. Observed: `reply status=answered` · `at the clear, pendingInteraction=nil: the clearing event found nothing and was dropped` · `request returned outcome=answered` · `stale pending installed AFTER the answer: id=1c8e6fb2-…` · `broker entry is gone: run.finish -> interactions.Cancel returns without a clearing event` · `subscriber frames (1): interaction {"pending":{"id":"1c8e6fb2-…","tool":"request_draft","tool_call_id":"call-1",…}}`.
- the window is not theoretical: the announce's own work is the P3-05 path (the run lock plus a full-message snapshot and marshal, milliseconds on a long answer), and the timer is armed before it; r2 makes the same point from the timeout side. The probe shows the same result from the `Reply` side, which needs no timer at all.
- consequence: a client is shown an approval dialog for a question that was already answered or has timed out (its `expires_at` is in the past), answering it answers nothing (`Reply` finds no entry), and no clearing event ever follows — `finish` → `interactions.Cancel` returns without notifying because `b.entry == nil`. Late subscribers replay it, because `beginSubscribe` replays `pendingInteraction` when `interactionKnown` (`registry.go:552-562`). DECISIONS "The event that clears a question says why it ended" promises the opposite ("a client that attaches later gets `pending: null` and nothing else, so it can never be shown a stale reason", `DECISIONS.md:210-213`).
- **severity: medium** (r1 and r4 medium, r2 low). It is a user-decision path that leaves permanent stale state in the stream and violates a written contract, and it is now reproduced. Not high: the client is misled, no data is lost, and the answer endpoint refuses safely.
- fix (S): carry a monotonic sequence with each broker transition (installed → settled) and have `setPendingInteraction` drop an announce older than the state it already applied; a late clear must still be able to arrive, so the sequence is compared per interaction id, not globally. Publishing **inside** `b.mu` is smaller but puts the run's message snapshot inside the broker lock, so `Reply`/`Extend` would wait for it (no lock cycle exists today — `finish` cancels the broker before taking `r.mu`, `registry.go:787-791`, and no call site holds `r.mu` while calling the broker — so the cycle is avoidable either way). Regression test: the probe shape above, in `interaction_state_test.go`.

### P3-02 (medium, A) Shutdown cancels runs and returns — r1-01, r3-05 — **confirmed by reading**
- `runRegistry.close` (`registry.go:444-455`) sets `closed`, copies the run list and calls `run.stop()` on each; `stop` (`:825-833`) only cancels the context and returns. Nothing waits on `run.done`, although `done` is closed by `finish` (`:815`) and is the natural join point.
- `Service.Close` (`app/service.go:108-127`) then closes remote, `s.api` (which is `Handler.Close`) and immediately `s.resolver.Close()` — MCP managers and stores — while `executeRun` goroutines are still in their deferred work (terminal commit, `recordRunFailure`, `finish`). `cmd/jad/main.go:122-125` calls `service.Close()` **before** `ShutdownHTTPServer`, so SSE handlers are still being served from a closed resolver.
- r1's and r3's accounts agree; r1 adds the ordering argument, r3 the missing join. The class is the `176fd7d` one (`asyncmgr` Close-wait, fixed there and not here), and p1's r1 already recorded this exact pair as cross-phase lead L3 — it was deferred to p3, not fixed and not filed, so this is the first p3 filing of it, not a repeat of a closed item (§7).
- consequence: a run's final transcript commit and failure record can race a resolver that is closing its stores; a run can be left half-finished at exit. On a normal SIGTERM the HTTP server's own deadline (`server.shutdown_timeout_ms`, `DECISIONS.md:835`) bounds the *request* drain, not the run goroutines.
- **severity: medium** as filed by both. Not high: shutdown only.
- fix (S): wait for the runs the registry cancelled, bounded by the shutdown timeout — collect `run.done` channels in `close` and select with a timer, exactly as `stopSessionRuns` already does for a session delete; keep `stop()` non-blocking. Test: a run blocked in a fake tool, `Handler.Close()` returns only after `run.done` closes (r1's suggested test).

### P3-03 (medium, A) The panic boundary starts after the async-state watcher — r2-01 — **confirmed by reading**
- `executeRun` (`executor.go:30`) installs `defer h.watchAsyncState(run, reference, profile)()` at `:36` and the panic-recovering defer at `:48-56`. A deferred call's *arguments* and its function call are evaluated at the `defer` statement, so `watchAsyncState`'s body runs at `:36` — before the recovery exists — and it calls `source.WatchSessionAsync(reference, profile, …)` synchronously (`async_state.go:32-33`), i.e. app resolver code at `app/resolver.go:1122`. A panic there escapes the run goroutine unrecovered.
- the watcher goroutine started at `async_state.go:48` has no `recover` of its own: its `publish` closure calls `read()` (app code) and `run.setAsyncState`. A panic there takes down the process: goroutine panics are not caught by another goroutine's `defer recover`.
- nothing between `go func()` (`handler.go:472`, `profile_run.go:125`) and `executeRun` recovers; `request_observer.go:76-95` recovers on the HTTP goroutine, not on these.
- consequence: the D-1 class ("a panic must fail the run, not the process") is defeated in the one goroutine where the boundary was installed, and in a second goroutine that was never covered. r2 states the reachability honestly: it needs a panic in app code, so the trigger is rare; the impact is the whole backend.
- **severity: medium** as filed. Compared with `P2B2-23` (callbacks with no boundary at all, rated low) this is different: the boundary exists, is documented as the D-1 mechanism, and is placed 13 lines too late — a defect in the implementation of a decided fix, and a one-line move.
- fix (S): move the recovering defer to the first statement of `executeRun` (before `defer watchAsyncState` and before `WithRetryNotifier`), and wrap the watcher goroutine body in the same recover-and-log pattern; no behaviour change. No test can reasonably force a resolver panic, so this stays read-verified (r2 says the same).

### P3-04 (medium, A) A panic between registering a tool-started run and launching it leaks the run and the transcript lock — r1-08, r2-02 — **confirmed by reading**
- `StartProfileRun` (`profile_run.go:89`) registers the transcript lock and the run (`:97-116`), then assigns interaction flags, chains and hops under `run.mu` (`:117-119`), calls `request.BeforeRun(ctx)` (`:120`) — supplied by the caller, and in production `app/profile_message.go:145-156` runs a compaction — sets `run.onCommitted`/`onResult` and calls `h.attachContentCache(run)` (`:124`), and only then starts the goroutine that owns `defer started.processUnlock()` (`:125-128`).
- `handleRunStart` covers the same window with `launched := false` and `defer func(){ if !launched { run.finish("failed", nil); processUnlock() } }()` (`handler.go:459-465`) — and r2 notes correctly that no test covers the profile-run half (`profile_run_test.go` covers success, stop, busy-wait and failure message only).
- consequence: the run stays `running` in the registry with `done` never closed, and the process lock is never released, so every later start, stop, compact, restore or delete of that profile answers `ErrSessionBusy`/409 until the process restarts — a permanent wedge from a transient fault, reached by code the project does not own (`BeforeRun`).

### P3-10 (low, B) `http_debug` redaction: three holes — r1-05, r4-02 — **confirmed by execution**
- **the transport error string keeps the URL.** On a `RoundTrip` failure the record stores `redactURL(request.URL)` at `transport.go:102` and `err.Error()` verbatim at `:103`. net/http's `*url.Error` prints the request URL with only the userinfo password stripped, so a credential in the query survives. Probe in `/tmp/p3work` (overlay test in package `httpdebug`, a fake `RoundTripper` returning the `*url.Error` net/http produces): the written record is `{"direction":"response","error":"Get \"https://provider.invalid/v1?api_key=sk-secret-value\": dial tcp: lookup provider.invalid: no such host","timestamp":"…","url":"https://provider.invalid/v1?api_key=[REDACTED]"}` — the field `redactURL` documents as "so a key in a configured base_url does not reach the debug files" (`:205-206`) is defeated by the neighbouring field.
- **the header pattern misses credential names.** `sensitiveHeaderPattern` is `authorization|api[-_]?key|cookie|set-cookie|proxy-authorization` (`:28`), while the query pattern is wider (`key|token|secret|signature|sig|password|passwd|auth|credential`, `:31`). Probe: headers `Authorization`, `X-Api-Key`, `X-Auth-Token`, `X-Secret` are captured as `map[authorization:[REDACTED] x-api-key:[REDACTED] x-auth-token:tok-value x-secret:secret-value]` — a custom provider that authenticates with `X-Auth-Token` writes the token to disk.

A `Transport` is built in `providerHTTPClient` (`app/resolver.go:508-522`) for each session config load, so the directory is pruned per load, not per file; between loads the directory can grow past `max_total_bytes` without bound (r1 and r4 agree; r4's H02 is the measurement). Severity: **low** — as the class was recorded (ACCEPT-LOW, `audit_audit.md:25`: no provider in this tree puts a key in a query, so this needs a user-configured `base_url`; the files are `0600` in a `0700` directory). r4's medium is lowered with the reason in §2: his new evidence is real but it changes the fix's completeness, not the exposure. ### P3-12 (low, A) The mutation gate is released after the session lock in four handlers — r1-06 — **confirmed by reading**
`handleSessionReset` registers `defer h.endMutation(key)` (`mutation_handlers.go:79`) before `defer unlock()` (`:81`) and `defer processUnlock()` (`:95`); front compact (`front_compact_handler.go:35,37,48`), state context (`state_context_handler.go:48,50,60`) and checkpoint restore (`checkpoint_handlers.go:96,98,117`) do the same. ### P3-14 (low, C) An oversized snapshot frame is never charged to the subscriber budget — r3-03 — **confirmed by reading; severity and framing corrected**

### P3-16 (low, C) The content-cache fallback reads the whole partial file before applying the cap — r2-08 — **confirmed by reading**

### P3-17 (low, A) `acquireRun` retries without backoff — r2-09 — **confirmed by reading, unreachable with the app resolver**

## 12. Needs the user

### Decisions

1. **P3-01 — how to order interaction state transitions.** Three shapes: (a) a monotonic sequence per interaction id, compared in `setPendingInteraction` so a late announce is dropped and a late clear still applies; (b) publish inside the `b.mu` critical section that installs/settles the entry; (c) drop the announce entirely when the broker no longer holds that id (the run asks the broker before publishing). **Recommendation: (a).** It keeps the "notify outside `b.mu`" property the design relies on (no `broker.mu → run.mu` nesting, so `Reply` never waits for the run's message snapshot), it is four lines plus a field, and it makes the wrong order impossible rather than merely unlikely. Whichever shape you pick, the DECISIONS entry "The event that clears a question says why it ended" should gain one sentence: the announce and the clear are ordered, and a clear that finds nothing is still delivered. A behaviour question hides in the same place: today a clear that finds no announcement is **dropped**; should `finish` therefore always emit a clearing event when `r.pendingInteraction != nil`? **That half should be added regardless of the ordering fix** (r1's second suggestion) — it covers every other way the state can be left stale, including a client that never learns the run ended.

2. **P3-02 — what shutdown should wait for.** Wait on `run.done` in `runRegistry.close`, bounded by an existing timeout, or leave it and rely on process exit. **Recommendation: wait**, in `close`, using the same shape `stopSessionRuns` already uses (one shared timer, ctx-aware), bounded by `server.shutdown_timeout_ms` so no new setting appears. Rationale: the resolver is closed immediately afterwards (`app/service.go:118-127`) and a run's final commit and failure record go through it; "cancel and return" makes that ordering a race by construction. If you prefer no wait, the alternative is to move `resolver.Close()` after `ShutdownHTTPServer`, which is smaller but still leaves the run goroutines unjoined. Tests: a run blocked in a fake tool must be waited for; a run that ignores cancellation must not hang shutdown past the timeout.

3. **P3-03 + P3-04 — approve the two panic-boundary fixes as one batch.** Move the recovering defer to the first statement of `executeRun`, add a recover to the async-state watcher goroutine, and give `StartProfileRun` the `launched` guard `handleRunStart` has. **Recommendation: yes, all three, in one change.** They are the same defect (a boundary that does not cover the code it was written for) and together they close the D-1 class in this phase; each is a handful of lines. Note the small behaviour change in P3-04's guard: it also fixes P3-15 if you pass `failureEvents(...)` instead of `nil` (see P3-15), so decide both together.

4. **P3-05 + P3-06 — how far to take the lock-scope work.** Apply the approved P-033 shape to `setPendingInteraction` only, or to it plus `setAsyncState`, `setProviderRetry` and `beginSubscribe`. **Recommendation: P3-05 now** (it is the measured cost, it fires twice per approval during a long answer, and the shape is already implemented 60 lines away in `beginSubscribe`/`finish`); **P3-06 only if the same change touches those three functions** — their frames are small, so moving them is tidiness with a regression risk in the subscribe path, which is the one place where frame order matters.

5. **P3-10 — is the redaction promise absolute?** The `redactURL` comment promises that "a key in a configured base_url does not reach the debug files", and the `error` field breaks it (executed, §P3-10). **Recommendation: fix all three gaps and keep the severity low**: redact the error string (strip the URL, keep the transport cause), widen `sensitiveHeaderPattern` to the query pattern's vocabulary (`token|secret|auth|key|cookie`), and prune inside `reserve` when the file count or byte total crosses the cap. Raise it to medium only if you want the comment to be a hard contract.

6. **P3-08 — when may a finished run drop what it holds?** `disposeContent` clears the content cache **and** `r.liveImages`. **Recommendation: split the two.** Close and drop the content cache as soon as the committed message is in the transcript (`setCommittedMessage` already closes it on that path; a failed/aborted run never commits, so for those keep it until `retire` unless you accept losing the late-subscriber text), and keep `liveImages` until `retire` for any run whose terminal `ui.message` references images — a client that attaches after `finish` replays that terminal frame and then fetches `/run/images/{call}/{pos}`, so dropping the map in `finish` would break a feature added for exactly that window. ### 12-bis.3 What the measurement corrected

- **PH1's "3-4×" is 3.0-3.1× for any message above 100 KB** and 4.0× only at 2 KB, where the two encoded terminal frames are a fixed overhead the message does not dominate. The number that matters for §12 decision 7 (B-C1 retention) is the shape the hypothesis added: a **failed** run keeps its uncommitted content cache (**1.15× the cached text**) and its decoded images (**2.35× the decoded bytes**) on top of the message. So "retention by time only" is worth 3× per completed run but **5-6× per failed run with a large answer and images**, and `run_state_retention_ms`'s 24 h maximum would hold all of it.
- **PH2 confirms the medium and fixes its shape.** One interaction publish is **3.9 ms at 1 MB and 29.6 ms at 8 MB** of streamed text, and it holds `r.mu` for all of it: the poll's p50/p99 stay at 30-40 ns/41-160 ns because the publisher is only occasionally in the lock, but the **max is the whole publish (9.5 ms at 1 MB, 69 ms at 8 MB)**. That is the P-033 magnitude reproduced on the path this finding names, and it is what makes P3-05 medium rather than low. It also settles the "how big is the second half" question in §12 decision 4: the *other* state publishers cost **2.2-4.5 µs** (PH3), i.e. 1,700× less at 1 MB.
- **PH3 is real but negligible.** 2.2-2.3 µs with no subscribers and 4.4-4.6 µs with eight, of which the frame encode is ~1.9 µs and each attached subscriber ~0.27 µs. They hold the lock for microseconds while marshalling ~200-400 B frames, so decision 4's "P3-06 only if the same change touches those three functions" is now backed by measurement rather than judgement.
- **PH4's doubling is exact, and the cost is in the comparison, not the frame.** `appendOnlyPartIndex` and `messageFrames` each call `webui.Increments`, and `Increments` reaches `appendedText`, whose `strings.HasPrefix(after, before)` **memcmps the whole text of the changed part** (`webui/types.go:296`). One pass is 3.9 µs for a 200 KB part and 69 µs for a 20-part message of 200 KB parts; the pair is 9.9 µs and 137 µs. Because `Increments` also scans parts from index 0 with `partsEqual`, a message with many parts pays the whole text again on every delta — the 20-part 4 MB message costs **137 µs per delta** against 1.46 µs for the SSE encoding alone. End to end, 2,000 deltas of a 200 KB answer cost **53 ms, 31.5 MB and 229.7 k allocations** in the run route.
- **PH5 is linear and cheap in absolute terms**: ~185 ns and ~320 B per retained run per `GET /api/sessions`, so 1,000 retained runs cost 190 µs and 322 KB per poll. The finding's worry (poll latency grows with the retained set) is confirmed as a shape and small as a number; what makes it matter is a client polling often at a large retention window, not the per-run cost.
- **PH6's pass count is four**, and the cost is 4.3× the output bytes: the record-level `map[string]json.RawMessage` decode (which already parses the output), then `toolOutputForUI`, `storedImageNames` and `inlineImageURLs`, each decoding the same output array again. 200 outputs of 200 KB cost **225 ms and 171 MB** per listing; the marginal 1.08 ms per 200 KB output is 5× one typed decode of the same bytes, because the array decodes go through `[]map[string]json.RawMessage`/anonymous structs with map allocation.
- **PH7 is a per-fetch whole-turn cost, not a per-image cost**: 17-19 ms and 1.6× the turn's base64 per fetch, whatever the index, because `FindInlineImage` runs `normalizeTranscript` over every record first. 20 inline images of 2 MB therefore cost ~3.5 s of CPU for the 20 fetches and nearly 7 GB of allocation.
- **PH8's "pinned per subscriber" is refuted; its "outside the budget" is confirmed.** The queue charges **0 B** for the oversized frame and flags `oversizedSnapshot`, exactly as the comment says, but the frame is one `[]byte` shared by every queue: the marginal cost of the 100th stalled subscriber is **164 KB**, not 16 MiB. So P3-14 stays a documentation item (decision 9's "document, do not change" is now the measured answer), and the memory ceiling is one frame per run, not per subscriber.
- **PH9 confirms the maximum-body transient**: ≈112 MB of JSON takes 487-503 ms, allocates 420 MB and peaks at 293-320 MiB — the largest transient in the phase, and 3.8× the body rather than the hypothesis's "about 4×" (that part was right).
- **PH10's mechanism is confirmed and its risk is bounded by the shipped default.** Two goroutines and 8.7-11.2 MiB per stalled client for a 2 MiB message, all released when the peer closes. But `serverconfig.DefaultSSEWriteTimeoutMS` is **30 s**, so an ordinary deployment drops a non-reading subscriber at the first timed-out write; the unbounded case needs `sse_write_timeout_ms: 0`, an explicit opt-out. This is the one hypothesis whose finding-worthiness the measurement removes.
- **PH11 confirms the prune gap with a rate**: 1,000 KiB of debug files per round against a 1 MiB cap, **19.5× the cap after 20 rounds**, and a fresh transport (a new process) prunes back to ≈2× the cap and starts over. `prune` is called only from `initialize`, which runs once per `fileLogger` (`sync.Once`), so within a process the directory is bounded only by the cap per run times the runs since start.
- **PH12 confirms the retention of live images**: 2.34× the decoded bytes, released only at `retire` (13 KiB left afterwards). The attribution test shows the retained set is the decoded copies (2,048 KiB per 2 MiB image) plus ≈1.34× more that stays reachable with the run — the test does not pin the retainer, which is recorded in 12-bis.6 rather than guessed at here.

### 12-bis.4 The numbers behind PH2's lock hold, PH4's memcmp and PH6's passes

**PH2, per KB of streamed text.** The publish reads the spilled partial file through `Snapshot`, injects it into a copy of the latest message, and re-encodes the whole message as one `ui.message` frame, all inside `r.mu`:

| streamed text | `setPendingInteraction` (median) | per KB | allocated per call | alloc factor |
|---|---|---|---|---|
| 64 KB, in memory | 282 µs | 4.4 µs | 293-305 KB | 4.6× |
| 1 MB, spilled | 3.88 ms | 3.8 µs | 4.6-5.7 MB | 4.6-5.7× |
| 8 MB, spilled | 29.6 ms | 3.6 µs | 37.9-45.1 MB | 4.7-5.4× |

The per-KB cost is flat, so the file read is not the dominant part: the copy plus the JSON encode of the whole message are, and the lock is held across both. A concurrent `state()` poll shows p50 40 ns, p99 100-160 ns, **max 9.5 ms (1 MB) / 69 ms (8 MB)** — the tail is the whole publish.

**PH4, where the time goes.** Both halves of the per-delta frame path call `webui.Increments`, and one `Increments` call on an append-only delta is one `stepsEqual` plus, per part scanned, `partsEqual` (which short-circuits on the length of the changed text but **memcmps** every unchanged part) plus, on the changed part, `appendedText`'s `strings.HasPrefix(after, before)` over the entire text:

| message | one `Increments` | the pair (frame path) | SSE encode alone | memcmp bytes per pass |
|---|---|---|---|---|
| 1 part × 200 KB | 3.92 µs | 9.90 µs | 1.46 µs | 200 KB |
| 20 parts × 200 KB (4 MB) | 68.7 µs | 137 µs | 1.46 µs | 4 MB (19 parts memcmp'd + 1 prefix) |
| 100 parts × 2 KB (200 KB) | 6.1 µs | 13.8 µs | 1.46 µs | 200 KB (99 parts memcmp'd + 1 prefix) |

At ~50 GB/s for cache-resident memcmp, the measured 3.9 µs for 200 KB and 68.7 µs for 4 MB agree with the byte counts, which is what identifies the comparison as the cost rather than the encode.

**PH6, the four passes.** With a 2 MB output, the marginal cost per output is 10.6 ms against 2.19 ms for one typed `[]struct` decode — 4.9×, matching four decodes at the reference's rate (the three array decodes are the slower map-shaped ones, so the ratio is a slight overestimate of the pass count and a slight underestimate of the per-pass cost). The 1,685 MB allocated for 400 MB of outputs (4.2×) is the independent confirmation.

### 12-bis.6 Limits, what was not measured, reproducibility

- **tmpfs, one machine, not idle** (load 0.9-2.3). Absolute µs move a few percent between commands; every conclusion rests on a ratio between two shapes measured in the same command, on a per-item cost, or on a stage decomposition taken in one process.
- **Synthetic fixtures throughout.** No benchmark used `sample/jad`, a real transcript or a real provider: PH2's streamed text is `x` repeated, PH6/PH7's outputs are one repeated letter inside a JSON array and their images are a PNG signature followed by a deterministic byte pattern (valid for `http.DetectContentType`, not a real photo), PH8's message is `x` repeated, PH10's runner returns immediately, PH11's bodies are repeated bytes. Real content moves PH2/PH4/PH6 upward (more distinct values, real UTF-8 boundaries) and leaves PH7's and PH11's ratios alone.
- **Not measured**: any group under `-race`; PH1/PH12 under GC pressure (allocation totals are reported, pause attribution is not); PH12's retention over a *real* retention window (the benchmark retires explicitly, it does not wait for the timer); PH10 with the shipped 30 s timeout (the probe deliberately used the unlimited setting, which is the case the hypothesis is about) and with many subscribers on *one* run (each client in the probe starts its own run); PH9 concurrently with other requests (decision 12's `max_request_*` transients were measured one at a time); PH11 with concurrent requests (one goroutine, so `reserve`'s prune inside the critical section was not exercised); PH6/PH7 behind the HTTP route (the webui functions were called directly, the route's own cost is `BenchmarkRunRouteStreamingDeltas`'s for the streaming path only); PH5 with a live publisher churn beyond the in-tree 16-run control; PH3 inside a real async-state watch (`WatchSessionAsync` was not started).
- **PH12's retained composition is not fully explained**: 2.34× the decoded bytes is measured and reproducible to 0.001, the attribution test attributes 2,048 KiB to the decoded copy and 2,747 KiB to the base64 item, and **≈2,750 KiB more stays reachable with the run and was not traced**. The magnitude is what feeds P3-08; the mechanism behind the extra third is left for a fix that changes this code.
- **Reproducibility**: the five probe files are listed in 12-bis.1 and were removed with `/tmp/p3m`. All of them build only on package-local or exported symbols (`newRunRegistry`, `registry.begin`, `publishMessage`, `cacheContent`, `setContentCache`, `keepLiveImages`, `setPendingInteraction`, `setAsyncState`, `setProviderRetry`, `subscribe`, `detach`, `state`, `finish`, `retire`, `SessionRuns`, `runContentCache`, `AsyncState`, `webui.Increments`, `webui.Message`, `messageFrames`, `appendOnlyPartIndex`, `NormalizeTranscript`, `FindInlineImage`, `TranscriptRecord`, `NewTransport`, `Settings`) and re-create in one file per package; the three that need a live server (`PH10`) reuse `testHandler`, `runnerFunc` and `fakeResolver` from `handler_test.go`.
- The probe file `internal/httpapi/p3m_liveimages_test.go` keeps one `fmt` import it does not need; it is scratch, and it was removed with the copy.

### 12-bis.7 Decisions this measurement opens

1. **P3-05's fix — proceed, with the number as the design target.** **Recommendation:** apply the P-033 shape to `setPendingInteraction` (copy the message and pin the cache under the lock, build the snapshot and both frames outside it, re-check `pendingInteraction` under the lock before publishing). A fix that leaves the encode inside the lock would still cost 3.9 ms at 1 MB, because the encode is 4.6× the text in allocation, not the file read. Add a benchmark shaped like `BenchmarkP3MInteractionPublish` when the fix lands, so the 3.9 ms / 29.6 ms pair becomes the regression guard.
2. **P3-06 (the three other state publishers) — do not touch them on performance grounds.** 2.2-4.5 µs, ~200-400 B frames. **Recommendation:** confirm decision 4's "only if the same change touches those functions", and leave the subscribe/emit ordering alone.
3. **P3-14 / PH8 — document, as decision 9 recommends.** The frame is shared, so a hard per-subscriber bound would not buy memory; it would only make the accounting honest. **Recommendation:** add one sentence beside `sse_max_buffered_bytes` saying one snapshot frame per run may exceed the budget and is not charged, and do not change the queue.
4. **P3-07 / B-C1 — keep open at low, but the shape to bound is the failed run.** 3.0× per completed run is what P-043 measured; a failed run with a 1 MB answer and 5 images keeps ~3.7 MB, and a 25-image run keeps 122 MB. **Recommendation:** leave the default as is (decision 7), and if a cap is ever added, make it a **retained-byte** cap that counts caches and live images, not a run count.
5. **P3-08 — the split, with a budget on the images.** Keeping `liveImages` until `retire` is what the `/run/images` window needs, and it costs 4.9 MiB per 2 MiB image. **Recommendation:** keep the map for the terminal frame's images only, and bound it by a per-run byte budget (default derived from an existing setting rather than a new key) or by the last K call ids. Drop the content cache at commit as today.
6. **P3-10 — fix the error field and the header list, and prune inside `reserve`.** The prune gap's rate is now known (1,000 KiB per round, 19.5× the cap in 20 rounds, once per process). **Recommendation:** as decision 5, with the prune moved into `reserve` under `l.mu` when the file count or the byte total crosses the cap; keep it low.
7. **PH4 — one cheap change if any performance work is scheduled.** The doubling is two `Increments` passes, and a pass is dominated by `appendedText`'s whole-text `HasPrefix`. **Recommendation:** compute the delta once per push (the emitter already knows the previous message) and, in `appendedText`, reject by length first and compare only the appended tail (a suffix check) instead of the whole text; both are local to `webui` and `message_stream_emitter.go`, and neither changes a frame's content — but they are *performance*, so schedule them only with `messages-golden-diff` available. If no such batch exists, leave it: 53 ms per 2,000-delta answer is not a defect.
8. **PH5 — no code change.** 190 µs per listing at 1,000 retained runs. **Recommendation:** leave `SessionRuns` as it is; if a client ever polls a very long retention window, the answer is the retention setting (decision 7), not the listing.
9. **PH6 + PH7 — one decode per tool output, if `webui` is touched for another reason.** Four passes per record and a whole-turn normalisation per image fetch are the phase's worst per-byte costs. **Recommendation:** do not open a batch for this alone; when `webui/normalize.go` is next changed, parse each `function_call_output` once and pass the parsed parts to the three consumers, and give `FindInlineImage` a cheaper path (it only needs the record whose `call_id` matches). `messages-golden-diff` is mandatory for either.
10. **PH9 — nothing to do; the number is a bound to keep in mind for `max_request_*`.** A maximum body is 0.5 s of CPU and ≈300 MiB of peak heap per concurrent start. **Recommendation:** do not change a limit; if `max_concurrent_runs` is ever revisited (decision 11 of p2b2's §12-bis / B-C8), this is the per-run transient to multiply.
11. **PH10 — change no default; document the setting instead.** `sse_write_timeout_ms: 0` pins 2 goroutines and ~4.3-5× the message per stalled client indefinitely. **Recommendation:** keep the 30 s default (it is what bounds the case), and add the measured cost to the setting's documentation so the opt-out is an informed one. No finding.
12. **PH11 — the third gap of P3-10 is the only one with a growth rate.** **Recommendation:** treat P3-10's three holes as one change (error string, header pattern, prune in `reserve`), and add a test shaped like `TestP3MPH11PruneOnce` that asserts the directory stays within `max_total_bytes` after N rounds — it fails today at 19.5× the cap and passes after the prune move.
13. **PH12 — the retained image cost needs a decision only if P3-08 is taken.** **Recommendation:** no standalone change; the number belongs to decision 5 above.
