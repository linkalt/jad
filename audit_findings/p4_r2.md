## 1. Understanding note

- **asyncmgr** is one manager per tool-storage folder, shared by every session on that storage (`app/maintenance.go:47`). It owns the in-memory `rows` (one `*row` per handle), the persisted `<id>.json` record and the coalesced `index.json`, and it starts **no goroutine** except a delayed index-flush timer. Drivers (process, subagent, tool_smith, profile_message) register a handle, are asked to `Stop` (must not block) and report the end through `Complete`. `Wait` blocks on a `changed` channel closed on every completion. Data flow on completion: `Complete` → claim under `mu` → write the record under `ioMu` (atomic temp+rename) → mutate the row, enforce `unread_max`, prune, notify → file work after the lock. Handles left `running` by an earlier server become `lost` at `Open` (`recover.go:54-70`) unless another live server wrote them.
- **remote** is the client: a per-`remotes/` folder `Directory` over a process-wide `Hub` that caches one `*Client` per (folder, name) while the parsed entry is unchanged (`hub.go:58-73`), follows runs on hub goroutines, and closes everything at `Close`. A `Client` is a plain-http `http.Transport` (no proxy, no redirects, per-entry in-flight semaphore, response cap, retries only where a repeat is safe), a token from `token_env` or a 0600 `token_file` read per request, and a bounded/scrubbed error type.
- **remoteapi** is the server: one `ServeHTTP` for `/api/remote/v1` that authenticates first, then dispatches to profiles / messages / subagents / transcript(s) / runs / stop. The token table is a 0600 JSON file of SHA-256 hashes, re-read on content-or-mode change at most every 250 ms under an `RWMutex`; a broken table refuses everything. Runs are held in `s.runs` (+ a `token\x00request_id` idempotency map), owned by the token that started them, bounded by `max_runs` and `max_runs_per_token`, and evicted/swept oldest-finished-first.
- **checkpoint** is a shadow-git service per session staging dir: a bare private repo elsewhere, every git command naming its own index file and a pinned config/env, `add --all` → `write-tree` → `ls-files` for a tree, `commit-tree` + `update-ref` to keep it, `diff-tree` to plan a restore. Services that share a staging dir share one mutex and one cached repository size (P-015).
- Ordering that matters for lifetimes: `Resolver.Close` closes the remote hub first, then sub-agent and process managers, then the async hosts (`app/resolver.go:972-988`), so children report their end before the manager closes. `176fd7d` made `Manager.Close` wait for `Complete` calls that are still writing records.

## 3. Findings

### P4-R2-01  `Manager.Close` can still return while `.async` files are being written (two sites the `176fd7d` fix does not cover)
- severity: low
- lens: A correctness
- location: `internal/asyncmgr/manager.go:566-623` (Close), `internal/asyncmgr/prune.go:29-44` (applyWork), `internal/asyncmgr/wait.go:43,68,90`, `internal/asyncmgr/prune.go:153-158` (Prune), `internal/asyncmgr/query.go:248-258` (consume), `internal/asyncmgr/store.go:137-145` (flush timer callback)
- evidence: [read] trace. `176fd7d` counts only `Complete` in `m.completing` and `Close` waits for `liveTotal+completing` (manager.go:591-611). Every other file writer runs *outside* the lock and is not counted: `Wait` (wait.go:43,68,90), `Prune` (prune.go:157), `consume`/`MarkRead` (query.go:257), `DropUnread` and `DeleteOwnersWithPrefix` (manager.go:507,466) all call `applyWork`, which does `updateRecord`/`removeRecord` (ioMu) and `writeIndex`. `Close`'s final barrier waits on `indexMu` only (manager.go:620-622), and that barrier can be passed *before* a `flushIndexNow` that was started by the timer callback: the callback loads `indexClosed` (store.go:141) before `Close` stores it (manager.go:612), so the callback's `flushIndexNow()` runs entirely after `Close` has returned. Effect: a record file or `index.json` is created/rewritten in a folder the caller believes is closed — the same failure shape as the `.async: directory not empty` flake, which the baseline no longer shows (0 of 2 runs), so no impact is observed today; at process exit it is harmless. `TestCloseWaitsForACompleteThatIsStillWritingItsRecord` covers only the `Complete` site (ran it: pass).
- suggested fix: make the guarantee real instead of partial — hold `flushMu` across the `indexClosed` check and the `flushIndexNow()` call in the timer callback (store.go:137-145), and count `applyWork` in the same in-flight counter `Complete` uses (increment where `pruneWork` is returned under `mu`, decrement after `applyWork`), so `Close`'s wait loop covers it.
- effort: S
- prior art: `176fd7d` fixed the `Complete` site only; these two sites are new.

### P4-R2-03  A failed restore leaves the workspace half-reverted and records no undo checkpoint
- severity: medium
- lens: A correctness
- location: `internal/checkpoint/service.go:655-693`
- evidence: [read] trace. `restore` keeps the undo commit (`keep(undo.ID,"before",…)`, :659) and then writes the workspace (`checkout`, :662; `os.Remove` loop, :666-674) **before** the undo `Record` is appended to `checkpoints.json` (:691). If `checkout` fails (git timeout at `timeout_ms`, default 120 s, on a large workspace), or the second `capture()` fails (:675), the function returns an error and the undo record is never written: the workspace is a mix of restored and un-restored paths, `RestoreResult.UndoCheckpointID` is empty, and the only trace is an orphan `refs/checkpoints/<undo>-before` object that no code path can name. The original checkpoint record is untouched, so re-running the restore recovers, but the user is told nothing about the partial state. Nothing in the package tests a failing `checkout` (`service_test.go` has no failure injection for it).
- suggested fix: append the undo record as `StateOpen` with `BeforeTree` *before* touching the workspace, then update it to `complete` (or `failed` with the error in `Warning`) afterwards, so a partial restore is visible and undoable.
- effort: S
- prior art: new

### P4-R2-04  The restore delete step is a lexical prefix check: a symlinked parent redirects `os.Remove` outside the workspace
- severity: low
- lens: B security
- location: `internal/checkpoint/service.go:665-674`
- evidence: [read] trace. `target := filepath.Join(workspace, filepath.FromSlash(change.Path))` then `strings.HasPrefix(target, workspace+separator)`. `filepath.Join` cleans the path lexically, so the check passes for `<ws>/link/etc-passwd` where `link` is a symlink to `/etc`; `os.Remove` then follows the parent symlink and deletes outside the workspace. Reachable path: the model creates `link -> /etc` with `bash`/`exec` (an approved command), a checkpoint is taken, the run ends, and the user restores it in `full` mode — the "path exists now, not in `before`" set (`plan`, :703-715) then contains `link/...` only if git recorded a file under it, which it does not for a symlink. The window that is genuinely reachable is therefore the TOCTOU one: `current` is captured (:636) and the removals run after the checkout (:662), so a directory can be replaced by a symlink in between by a still-running `bash` handle of the same session. Narrow, same-user, and the user's own files, hence low; the git half (`checkout-index`) has the same property and is not fixed by a lexical check either.
- suggested fix: before `os.Remove`, re-resolve the parent with `filepath.EvalSymlinks` and re-check containment (or `lstat` each path component); the same guard belongs in front of `checkout-index`.
- effort: S
- prior art: new (P-053 batch 0 touched `checkpoint/service.go:345` only)

### P4-R2-05  `GET /api/remote/v1/profiles` tells any token holder whether a session exists
- severity: low
- lens: B security
- location: `internal/remoteapi/server.go:283-292`, `internal/app/remote_api.go:33-46`
- evidence: [read] trace. `handleProfiles` validates `session` and calls `Backend.Profiles` *before* the token's `profiles` globs are applied (:288-298). `remoteBackend.location` maps every `sessionfs.ResolveError` to `remoteapi.ErrNoSession` (:36-38) and `backendError` turns that into `404 no_session` (`server.go:509-510`), while an existing session the token cannot see returns `200` with `"profiles": []`. This is the same oracle that `a6150e3` removed for profiles and runs ("a run outside it answers exactly like a missing run", `DECISIONS.md:1031`), so the route diverges from the phase's own standard. Who can reach it: the holder of any valid remote token with `message`, `subagent` or `transcripts`.
- suggested fix: in `handleProfiles`, answer `200 {"session": <as sent>, "profiles": []}` when the backend reports `ErrNoSession`, so "no such session" and "nothing visible" are one answer (the client only lists what it can reach).
- effort: S

### P4-R2-07  Checkpoint git commands ignore the caller's context
- severity: low
- lens: A correctness
- location: `internal/checkpoint/git.go:143-145`
- evidence: [read] trace. `shadowGit.run` builds `context.WithTimeout(context.Background(), g.timeout)`; no `context.Context` reaches `Service.Begin/Finish/Restore` at all, so a client disconnect (the restore route), a cancelled run (`Finish` at run end) or server shutdown cannot stop a git command; it ends only at `checkpoint.timeout_ms` (default 120 s) or the 5 s `killWait`. Bounded and deliberate-looking (the package documents per-command timeouts), but it is the checklist's "context not propagated" case: during shutdown `Resolver.Close` does not wait for it either, so a `git add --all` on a 20,000-file workspace (P-015: 200 ms per capture) can outlive the server's close path by up to `timeout_ms`.
- suggested fix: thread a `context.Context` through `Service.Begin/Finish/Restore` → `capture/keep/checkout` → `shadowGit.run`, and combine it with the per-command timeout (`context.WithTimeout(ctx, g.timeout)`); callers pass the run/request context.
- effort: M
- prior art: new (`audit_performance_plan.md` P-015 measured the cost, not the lifetime)

### P4-R2-08  Process-lifetime maps keyed by staging dir are never pruned
- severity: low
- lens: C performance (also A: stale state)
- location: `internal/checkpoint/service.go:161-170`
- evidence: [read] trace. `repoSizes` and `locks` are package-level `sync.Map`s with one entry per `filepath.Clean(StagingDir)` ever used; `NewService` only ever `LoadOrStore`s. ### P4-R2-10  "Can this call change the workspace?" is answered by two mechanisms that must be kept in sync
- severity: low
- lens: D maintainability
- location: `internal/checkpoint/run.go:12-39` (`CallChangesWorkspace`: hard-coded `write`, `edit`, `bash`, `exec`, `process`+`command`, and `source=="mcp"`) vs `internal/tools/catalog.go:90-98,253-285` (`Tool.MayChangeFiles` per call), combined at `internal/session/runner_tools.go:176`

## 4. Performance hypotheses for the measurement step (5.3)

- H01: `List` sorts every matched row per call and copies nothing — `internal/asyncmgr/query.go:94-139` (sort at :114, `m.rows` scan at :110 for `state != active`).
  workload: `keep_finished` can be set to `maxNativeAsyncValue` = 10,000,000 (`internal/sessionfs/native_async_settings.go:10,83`); the existing benchmark fixture is 10,000 finished handles.
  benchmark: existing `BenchmarkListPage10Of10kRows` (`internal/asyncmgr/scale_test.go:635`), plus the same fixture at 100k rows.
  expected: O(n log n) per `list` call, n = retained rows; a page of 10 costs the same sort as a page of 10,000.

- H02: every index flush marshals all rows — `internal/asyncmgr/store.go:150-188` (`flushIndex` builds and marshals `len(m.rows)` `indexRow`s).
  workload: 10,000 retained handles with `index_flush_ms` = 150 while a run completes handles; one flush per 150 ms.
  benchmark: new `BenchmarkIndexFlush10kRows` (fixture: `Open` + 10k `Register`/`Complete`, then time one `flushIndex`), modelled on `BenchmarkOpenRebuild`.
  expected: linear in retained rows per flush; the write itself is one atomic rename of a growing file.

- H03: `pruneLocked` plus `recomputeExpiryLocked` scan every row whenever the guard lets them run — `internal/asyncmgr/prune.go:77-150` (guard at :79, full scan at :95-99 and :145-150).
  workload: 10,000 retained rows and `retention_days`/`unread_ttl_days` set, so `nextExpiry` is crossed regularly; `Wait`/`Complete` call it.
  benchmark: new `BenchmarkPrune10kRows` (10k finished rows, one expired), or reuse the `BenchmarkOpenRebuild` fixture.
  expected: O(rows) per prune that does work, on the completion path.

- H04: `Begin`/`Finish` hold the per-staging-dir mutex across ~14 git processes — `internal/checkpoint/service.go:503-529,532-564` under `s.mu` (`service.go:169-183`), per P-015's measured 203 ms per capture at 20,000 files.
  workload: two profiles of one session (or a restore during a run) with checkpointing on and a 20,000-file workspace.
  benchmark: existing `BenchmarkBeginFinishSteady` (`internal/checkpoint/steady_benchmark_test.go`) with a second goroutine calling `List`/`Report` (unlocked, expected free) and a second `Service` on the same staging dir (expected fully blocked).
  expected: the second capture waits for the first; `List` stays off the lock.

- H05: the workspace-change decision parses the call JSON up to three times per tool call — `internal/checkpoint/run.go:20-37` (`json.Unmarshal` of the call, of the `arguments` string, then of the arguments object), called per tool call from `internal/session/runner_tools.go:176`.
  workload: a round with 64 parallel calls (`BenchmarkRunToolBatch` fixture), checkpointing off (the function is still called).
  benchmark: new `BenchmarkCallChangesWorkspace` (100 calls, `write`/`process`/`read`), plus `BenchmarkRunToolBatch` 1/8/64 with and without the checkpoint hook.
  expected: constant per call, ~3× the cost of one unmarshal; only visible at 64 calls per round.

- H06: every remote HTTP call re-reads and re-parses the entry file and re-reads the token file — `internal/remote/hub.go:50-56` → `entry.go:302-315` (`ReadFile` + `json` decode + `DisallowUnknownFields`) and `client.go:152` → `entry.go:251-285` (`Stat` + `ReadFile`).
  workload: a follow loop polling every `poll_ms` (20,000 ms default, 100 ms minimum) per live remote handle, and a transcript burst; 4 syscalls + 1 JSON parse per call.
  benchmark: no `remote` benchmark exists (section 2 lists it as a gap): new `BenchmarkClientRoundTrip` against `httptest` with the entry/token files in `b.TempDir()`, plus a variant with the parse hoisted out of the loop.
  expected: adds a fixed per-call cost that dominates a loopback round trip; the entry read is a recorded decision (`DECISIONS.md:1019`), so the measurement is only informative — the token-file read is the part that could be cached without changing a documented behaviour.

- H07: every status poll and every start scans all held runs — `internal/remoteapi/server.go:385-424` (`sweepLocked` + the live-count loop) and `:519-531` (`lookup` → `sweepLocked`).
  workload: `max_runs` 256 (default) with a client polling once per second per followed run.
  benchmark: new `BenchmarkStatusPoll256Runs` (server with 256 finished entries, `GET /runs/<id>`).
  expected: O(max_runs) per poll, i.e. 256 map iterations per second at the default — negligible unless `max_runs` is raised to 10,000.

- H08: the token table is re-hashed and re-parsed every 250 ms under a write lock — `internal/remoteapi/tokens.go:239-266` (`refresh`), with `Authenticate` (`:271-302`) taking the `RWMutex` on every request.
  workload: a table at the 1 MiB cap (thousands of rows) and a client polling once per second: 4 `ReadFile`+SHA-256+JSON parses per second, each blocking every concurrent `Authenticate`.
  benchmark: new `BenchmarkAuthenticate1000Tokens` (1,000 rows, `StaticTokenTable` for the compare path; a file-backed table for `refresh`).
  expected: the compare loop is already constant-time over all rows (O(tokens) per request, no early exit); the refresh is the part that takes the write lock.

## 6. Checked and sound (hypotheses dropped, with the reason)

- **Client redirect/proxy/scrub (H10).** `Proxy: nil` with a comment (`client.go:86`), `CheckRedirect` returns `http.ErrUseLastResponse` (`:119-121`) and a 3xx is `ErrRedirect` (`:230-231`); the token is only in the `Authorization` header; every returned error goes through `scrub` (`:189`) and `networkText` unwraps `*url.Error` so the URL never appears (`:291-307`). Tests: `TestClientRefusesRedirectAndNeverForwardsToken`, `TestClientIgnoresProxyEnvironment`, `TestClientErrorsNeverContainTheToken`, `TestNetworkTextHidesTheRequestURL`.
- **Response cap and in-flight cap.** `io.LimitReader(body, limit+1)` then an explicit `ErrResponseTooLarge` (`client.go:222-228`); one semaphore slot per in-flight request, released by `defer` (`:156-161`); `MaxIdleConns(PerHost) = max_in_flight`.
- **Unix socket boundary.** `Lstat` + `ModeSocket` + owner/root + non-world-writable parent before every dial (`socket_unix.go:17-32`, `client.go:96-108`); `socket_other.go` is a documented no-op off unix.
- **Server auth and validation (H11).** `Authenticate` runs before any route is matched (`server.go:221-226`), compares SHA-256 digests with `subtle.ConstantTimeCompare` over *all* rows without an early exit (`tokens.go:284-289`), refuses revoked/expired with the same error as unknown (`:293-300`), and a broken or too-open table refuses everything (`:254-259`, `:228-230`). Every id is pattern-checked (`runIDPattern`, `sessionPattern`, `namePattern`, `validTarget`), the body uses `DisallowUnknownFields`, `MaxBytesReader` and a single-object check (`server.go:320-336`), and errors are static texts with the backend error only logged (`:507-517`).
- **Run ownership and idempotency.** `lookup` requires `entry.token == token.ID` (`server.go:519-531`); a repeated `(token, request_id)` returns the same run and waits on `ready`, a different fingerprint is `409 request_id_reused` (`:385-408`); a start that finishes after `Close` is stopped (`:437-442`); `Close` stops every held run.
- **Per-token cap (H13).** `max_runs_per_token` counts live runs only, and `evictFinishedLocked` drops the asking token's own finished run first, so a full table never locks other tokens out (`server.go:409-418,454-471`); covered by `TestOneTokenCannotFillTheServerWithFinishedOrLiveRuns`.
- **asyncmgr accounting (H21).** `track`/`untrack` keep `ownerStats.total`, `live`, `unread`, `liveTotal` and `finished` exact on every transition, including `endRemove` (`mutateLocked` then `forgetLocked` cancel out) and `recover`; `noteExpiryLocked` only ever lowers `nextExpiry`, and `recomputeExpiryLocked` is deferred from the prune that consumed it.
- **`popLocked`'s `*r.rec` deref (H3).** `s.unread` only ever holds rows with `rec != nil`: `Complete` sets `rec` and `unread` together (`manager.go:398-411`), `recover`/`adopt` set `rec` whenever `unread` (`recover.go:30,89-91`), and `markReadLocked` clears both (`prune.go:47-56`).
- **One signal, one waiter.** `popLocked` marks taken signals read under `mu`, so two concurrent `Wait`s get each signal once (`TestTwoWaitersGetEachSignalOnce`, and a cancelled `Wait` consumes nothing).
- **`Manager.Close` waits for `Complete`.** `TestCloseWaitsForACompleteThatIsStillWritingItsRecord` ran and passed; the `completing` counter is decremented after `applyWork`, so the wait covers the record write.
- **Session-prefix fan-out (H4).** `sessionKey(reference, "")` is `reference + "\x00"` (`app/resolver.go:136`), so `DeleteOwnersWithPrefix` cannot match `s10` when deleting `s1`.
- **`View.Text` (H12).** `clean()` bounds state/kind/code/message/reason only (`run.go:44-50`); both callers cut the text (`tools/native/profile_message_remote.go:265` → `profile_message_async.go:236`; `subagent_remote.go:221`), so no unbounded text reaches the model today — the invariant is implicit, not enforced in the type.
- **`values[0]` before the length check (H14).** `remoteapi/server.go:675` reads `values[0]` before `len(values) != 1`; unreachable because `url.Values` from `ParseQuery` never holds an empty slice.
- **Checkpoint git isolation.** `fixedConfig` pins autocrlf/fileMode/symlinks/fsmonitor/hooksPath/gc.auto/maintenance, inherited `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE`/… are stripped, the global and system config are disabled and `GIT_TERMINAL_PROMPT=0` (`git.go:72-113`); every command names its own index file, so the user's repository is untouched (`TestTheUsersOwnGitRepositoryIsUntouched`).
- **Checkpoint limits and exclusions.** Output caps (`limitedBuffer` cancels the command on overflow, `git.go:115-135,163-168`), `killWait`, `max_files`/`max_total_bytes` gates that become a `skipped` record rather than a run failure, filesystem-root/home workspaces refused (`service.go:406-413`), harness paths (state dir, lock file, tool storages, spill dirs) excluded (`:228-302`), the size cache re-measured after every snapshot and when the repository is gone (`:426-457`, `size_cache_test.go`).
- **No goroutine without an owner.** `asyncmgr` starts none but the index timer, which `Close` stops; `Hub.Go` registers with a `WaitGroup` and `Hub.Close` waits (`hub.go:80-113`); the remoteapi per-run goroutine ends with its run (`server.go:443-448`).
- **Test quality of the new commits.** Every commit named in the prompt has tests beside it (per-token cap, `request_id` reuse with other content, close-during-start, token-file 0600/reload/interval/race, socket owner, removed TLS keys, character-class globs, P-015 size cache, `176fd7d`). 18 `time.Sleep` calls exist in the four packages, all of the "let a goroutine reach its blocking call" kind (`manager_test.go:174,280,305`, `server_test.go:266,457,483,490`) — the advisory P-055 class, no new evidence of flakiness.
