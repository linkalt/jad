### P1-R4-01  Concurrent Unix-socket startup can replace another live listener
- severity: medium
- lens: A correctness
- location: backend-go/internal/app/remote_listen.go:47-56, 61-81, 93-97; backend-go/cmd/jad/main.go:125-129
- evidence: [read] `ListenUnix` checks/removes an existing socket before creating a temporary socket, then unconditionally `os.Rename(staged, path)`. Two starts can both observe an absent/stale path and bind separate listeners before either rename; the later rename replaces the earlier listener pathname. `unixListener.Close` then removes whichever socket currently occupies that pathname (only checks `ModeSocket`), not necessarily its own inode, so closing the first listener can unlink the second listener. No race test or reproduction run.
- suggested fix: reserve the destination without replacement (using a platform-appropriate no-replace publication/serialization) and record/check the created socket identity before removing it on close.
- effort: M
- prior art: new


### P1-R4-02  Existing log files retain permissive mode
- severity: low
- lens: B security
- location: backend-go/internal/logging/logging.go:72-76
- evidence: [read] `os.OpenFile(..., 0600)` applies its mode only when creating the file; when `server.log_file` already names a broader-mode file (for example 0644), the existing permissions remain unchanged. The logging contract says the file is mode 0600 (`backend-go/DECISIONS.md:98`), and it records server-side error causes/provider URL or upstream messages (`DECISIONS.md:100-101`), so a local user permitted by the old mode can read the log despite that contract. The existing test checks only creation mode (`internal/logging/logging_test.go:104-105`). No test was added or run for an existing permissive file.
- suggested fix: after opening, use the file descriptor to enforce 0600 or reject a file whose mode is broader, and add a regression test that starts with an existing permissive file.
- effort: S
- prior art: new


### P1-R4-03  Adapter startup logs an upstream URL without redaction
- severity: low
- lens: B security
- location: backend-go/cmd/anthropic-adapter/main.go:53; backend-go/internal/anthropicadapter/config.go:270-274
- evidence: [read] The command writes `config.Upstream.BaseURL` verbatim to stderr. The config check accepts any parseable HTTP(S) URL with a host and does not reject userinfo or query parameters. If an operator embeds a credential in either component, readers of stderr/service logs receive it. No reproduction or test was run.
- suggested fix: log only the upstream host, or redact userinfo and all query values before logging; add a command-level test using a URL containing a dummy secret.
- effort: S
- prior art: B-S2 (the `http_debug` URL sink was accepted/fixed; this is a distinct adapter startup log sink)

### P1-R4-04  Shutdown leaves new-run admission open while waiting for storage recovery
- severity: medium
- lens: A correctness
- location: backend-go/cmd/jad/main.go:122-130; backend-go/internal/app/service.go:107-127; backend-go/internal/app/storage_recovery.go:43-54, 75-84, 155-168
- evidence: [read] On SIGTERM, `run` calls `service.Close()` before `ShutdownHTTPServer`. `Service.Close` cancels start-time recovery but waits for the recovery goroutine before calling `remote.Close()` and `api.Close()`. Until `api.Close`, the HTTP run registry remains open; the main listener also continues serving until the later HTTP shutdown. `RecoverStorages` checks cancellation between sessions/storages, but documents that an already-running storage recovery is not interrupted and may last through the configured kill grace. Thus a main or remote API request can start a new profile run after the shutdown signal while close is waiting, and that run is only stopped when the handlers are closed after recovery. This is distinct from D-3: the configured deadline still bounds the later HTTP drain, not admission during resource teardown. No direct concurrency reproduction was run; `go test ./internal/app -run "^TestServiceClose" -count=1` passed, but its tests cover recovery cancellation/wait rather than run admission.
- suggested fix: close remote and HTTP run admission immediately after cancelling recovery, then join the recovery scan before closing the resolver/managers; add a test that holds one recovery operation and attempts a run after shutdown begins.
- effort: S
- prior art: new

### H06 — command entrypoints
