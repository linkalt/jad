## 1. Understanding note

Phase 2a is the *vocabulary* of the tool settings: 20 `tools.native.<tool>` sections (plus `tools.extension.decide_systemone`, out of this phase), each with a `normalizeNative*Settings` function that turns `map[string]json.RawMessage` into one typed struct, and 25 `Native*Settings`-family types (21 `…Settings` structs, plus `NativeBashStreamBudget`, `NativeMemoryStateContextSelector`, `NativeSubagentAgent`, `NativePathPolicy`).

The pipeline is: session/profile/toolset files → `layoutSettings` → `setting map[string]json.RawMessage` → `loadSessionSettingsFrom` (`session.go:251`) → `validateToolSettingsShape` (`tool_shape.go:31`, which allows only `native`/`extension`/`mcp`, canonicalises `"native": null` to `{}`, and allows only the 20 known tool names) → the 20 normalizers, in a fixed order (`session.go:377-497`) → cross-section rules (`session.go:498-508`: process/subagent/tool_smith need `async`; `state_context_settings.go` needs the provider configured) → `SessionConfig`.

Every normalizer has the same shape: check `setting["tools"]` exists, `decodeConfigObject` it, check `tools["native"]`, `decodeConfigObject` it, check `native["<tool>"]` exists, decode the section object, allow-list its keys (either a `[]string` list with `containsString` or a `switch` with a `default:`), then read every key through a shared helper (`configuredInteger`, `bashString`, `bashBool`, `nullableField`, `optionalSubagent*`, `normalizeRemoteNames`, `normalizeSessionGlobs`, `normalizeNativeStateContextMode/Detail`, `normalizeNativeBashStream`, `normalizeNativeBashSpill`, `normalizeNativePathPolicy`, `loadConfiguredEnvFile`), and finally the section's own cross-field rules (`max_timeout_ms >= timeout_ms`, `list_limit <= max_list_limit`, `latest_total_bytes >= latest_bytes` via `asyncmgr.Config.Validate`, `allow_remote` ⇔ `remotes`, …). A section's presence is what enables the tool.

The contract with the outside world is `sample/schemes/setting.schema.json` (the tool block is `$ref`'d by `toolset.schema.json`, DECISIONS 709); the repo pins that contract with `TestNativeToolSchemasAgreeWithTheLoader` (an accept/reject table run through both the schema and the loader) and `TestExecAndReadImageSchemaKeysMatchTheLoader`/`TestFetchSchemaListsTheKeysTheLoaderAccepts` (key-name parity for 7 sections and 5 fetch defaults).

`layouttest` is the test-fixture writer for a catalog-layout session (root setting, catalogs, models, profiles, toolset, session file); 61 test files (33 in `internal/app`, 28 in `internal/sessionfs`) import it, including most of the 2a tests.

- severity: low
- lens: A correctness (config validation) / D maintainability (divergence)

## 4. Performance hypotheses for the measurement step

- H1: every settings load decodes `tools` and `tools.native` once per section; `internal/sessionfs/session.go:377-497` calls the 18 normalizers of this phase, each of which runs `decodeConfigObject(setting["tools"])` and `decodeConfigObject(tools["native"])` (18 × 2 = 36 `map[string]json.RawMessage` decodes of the same two objects) and 14 of the 18 files then re-parse the same section object with `orderedObjectKeys` to check its keys (e.g. `native_exec_settings.go:150-157`, `native_transcript_settings.go:77-84`; the package has 25 `orderedObjectKeys` calls in total).
  workload: one load per session open or per settings-stamp change (P-001 caches it); the cost matters at 200 sessions × 1 load, and for `POST …/attach` bursts.
  benchmark: `BenchmarkLoadSessionConfig` (`internal/sessionfs/settings_load_benchmark_test.go:10`) as it stands, and one variant whose toolset enables 10 sections (all keys set) so the per-section decode dominates.
  expected: a fixed cost per section, independent of file size; the parent decodes are removable (a `nativeSections(setting)` helper) so the hypothesis is "N% of `BenchmarkLoadSessionConfig`", not a scaling claim.
- H2: `agents_dir` handling does 3 syscalls and 2 parses per agent folder per load (P2A-R2-06), and `withSubagentOverrides` (`native_subagent_settings.go:186-201`) is O(agents²) when several folders contribute.
  workload: 5 folders × 100 agents (DECISIONS 310 targets "many agents"); every session load redoes it.
