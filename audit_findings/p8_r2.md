## 1. Understanding note

The package is the durable core under the session runner. `Journal` (jsonl.go) is one file = messages.jsonl plus one mutex, an optional fsync per durability mode, an in-memory per-line SHA-256 index for idempotent appends, and a tail repair that truncates a torn last record. `TurnStore` (turn.go) owns staged responses: BeginTurn creates staging/<turnID>/ with a manifest, StageOutputItem appends the item to items.jsonl plus an offset/length record to items.index.jsonl, Commit renders final.jsonl from the staged items, fsyncs in order, then appends it to messages.jsonl idempotently and removes the staging directory; Recover (recovery.go) reconciles leftovers at session open. Reads are `ReadRecordsRange`/`ReadCompleteRecordsRange` (record framing plus tail repair), and three layered caches make reads incremental: the journal line index, the per-run `InputHistory` memo (64 KiB tail checkpoint, input_history_memo.go) and the persisted cursor index (1 MiB checkpoint, cursor_cache.go). History is an overlay: after a compaction the retained turns live in compaction-cache.json (with source_bytes/source_sha256 of the file they came from) and messages.jsonl holds only the preserved active tail; a compaction cache whose source is the current file is authoritative, otherwise its items are prepended to the transcript records. maintenance.go holds compaction, backup, reset and the derived-file invalidation; front_compact.go holds the delete-from-message rewrite (archive then prefix replace); state_context.go, run_error_cache.go and partial_cleanup.go are sidecars. The media packages are leaf-like: imagestore externalizes large images out of the transcript into <sha256>.<ext> files with a quota, imageresize shrinks outgoing images with a bounded memo and EXIF orientation, imagedata decodes and sniffs, contentlibrary reads Markdown prompt/template/skill trees for the root library.
Lifecycle and trust boundaries: everything is a single-writer in-process store per session (documented on Journal and TurnStore); the writers are the run path, the mutation routes (reset, compact, front compact) and recovery at open. Inputs that reach this phase are model/provider events (staged items), user input items, tool outputs (image externalization), library files on disk under admin-configured roots, and the persisted files themselves.

## 3. Findings

### P8-R2-01  Reset and compaction publish in an order that can make the next read serve a state the caller did not report
- severity: medium
- lens: A correctness (crash or half-written state, idempotent recovery)
- location: internal/transcript/maintenance.go:656-681 (Reset: ReplaceRecords, then removeDerivedFiles), internal/transcript/maintenance.go:174-181 (CompactHistory: writeCompactionCache, then ReplaceRecords), internal/transcript/input_history.go:169-225 (the overlay), internal/transcript/maintenance.go:820-838 (cacheSourceIsTranscript)
- evidence: [read] trace of the publish order against the read path. readInputItemsWithCache prepends cache.Items whenever a compaction cache exists, and returns cache.Items plus cache.ActiveTail alone when cacheSourceIsTranscript is true. (a) Reset publishes the empty transcript first and deletes the compaction cache second; a death between the two leaves messages.jsonl empty and the cache on disk with source_bytes equal to the pre-reset size, so cacheSourceIsTranscript is false and every later read returns cache.Items, that is the conversation the user deleted, and the model receives it on the next run. The window is two unlink calls in removeDerivedFiles (maintenance.go:683-712), but the state after it is permanent and self-consistent, so nothing repairs it. (b) The mirror case: if ReplaceRecords fails after writeCompactionCache succeeded (ENOSPC on the rename or the temp write), CompactHistory returns Compacted=false, the HTTP response says nothing was compacted, and the next read nevertheless returns the compacted view (source matches) while messages.jsonl keeps growing. No transcript byte changes in either case, so the messages-golden contract does not cover it. Callers: POST session reset and compact (httpapi/mutation_handlers.go:59-100, app/maintenance.go:132-150).
- suggested fix: in Reset delete (or rename aside) the compaction cache before publishing the empty transcript; in CompactHistory write the cache to a temporary path and rename the cache and the transcript in the order ReplaceRecords-then-cache, or store a "source replaced" flag in the cache that the read path treats as stale. Both keep the crash-safety property that source_bytes was introduced for.
- effort: S
- prior art: new (source_bytes came with a627a85/F-02; the ordering predates it)

### P8-R2-02  A failed BeginTurn or Commit leaves a staging directory that nothing ever removes
- severity: low
- lens: A correctness (error paths that leave partial files)
- location: internal/transcript/turn.go:170-190 (Mkdir of the turn directory, then error returns from persistManifest or syncTurnEntries with no cleanup), internal/transcript/turn.go:339-422 (Commit failure paths, including the ones after the manifest is persisted as ready or committing), internal/transcript/recovery.go:107-160 (recoverTurn retains any turn without a durable final.jsonl, and a manifest in status failed is retained too), internal/transcript/partial_cleanup.go:39-95 (the only other cleanup removes responses.partial* files, never a turn directory)
- evidence: [read] + [verified as source] BeginTurn creates staging/<turnID>/ before it can fail and returns before `turn.registered = true`, so no map entry and no owner knows about the directory; grep of internal/transcript and internal/app for RemoveAll shows only recovery.go:139,151 and turn.go:410 (both success paths) plus session-level deletion. Each abandoned directory is counted as RetainedTurns by Recover at session open and left in place for the life of the session, and it holds items.jsonl up to (number of items x persistence.max_item_bytes, default 10 MiB).
- suggested fix: remove the turn directory when persistManifest or syncTurnEntries fails in BeginTurn (one defer keyed on success), and add a bounded sweep to Recover: a turn directory older than a configured age, or beyond a count, is reported and removed.
- effort: S
- prior art: new

### P8-R2-03  The renames that publish messages.jsonl and its sidecar caches are not made durable, unlike the append path and the cursor cache
- severity: low
- lens: A correctness (durability) plus D maintainability (five atomic writers, two behaviours)
- location: internal/transcript/jsonl.go:84-131 (ReplaceRecords: temp file Sync, then os.Rename at :126, no directory sync), internal/transcript/front_compact.go:186-284 (ReplaceWithPrefix: archive rename :248 and prefix rename :279, no directory sync), internal/transcript/maintenance.go:594-654 (backupTranscript), internal/transcript/maintenance.go:752-790 (writeCompactionJSONAtomic), internal/transcript/turn.go:698-723 (writeJSONAtomic). Contrast: internal/transcript/jsonl.go:200-208 and :524-530 sync the parent directory after creating a transcript, and internal/transcript/cursor_cache.go:267-285 syncs it after publishing the cursor cache.
- evidence: [read] 710aef2 ("Sync parent directories in turn and strict durability modes") added the directory sync to the append paths only; no caller of the five writers above syncs the parent. Reachable consequence: front compaction with delete_mode=permanent (internal/transcript/front_compact.go:39 and :131-147, reached from the HTTP front-compaction route) can be undone by a power loss in the commit window: the user is told the messages were deleted and messages.jsonl comes back with them. For compaction and reset the restart state stays self-consistent (the cache records source_bytes, see P8-R2-01), so only work is redone. The five helpers also diverge: three of them differ only in whether the temp file is synced, and none has the directory step.
- suggested fix: one unexported publisher in the package (writeTemp, Sync when durability is not process, Rename, sync parent when durability is not process) used by all five, keeping today process-mode behaviour (no syncs).
- effort: S
- prior art: new for transcript; the same question is open for the sessionfs layout writes (phase 2b1) and should be deduplicated at merge

### P8-R2-04  Every transcript read takes the write lock, opens the file O_RDWR and can truncate it
- severity: low
- lens: B security and boundaries (file modes, read path that writes) plus A
- location: internal/transcript/jsonl.go:286-306 (withRepairedFile: O_CREATE|O_RDWR|O_APPEND under j.mu, then repairTrailingPartialLine :576-620, whose Truncate is at :612)
- evidence: [read] every history read goes through it: ReadRecordsRange (jsonl.go:255-284) and the per-run memo (input_history_memo.go:82) call withRepairedFile, so a run needs write permission on messages.jsonl and on its directory (O_CREATE) even when the file is intact. Consequences: a transcript made read-only (chmod 0444, a read-only bind mount, a session archive, a backend running as another uid) fails the run with "open transcript for reading: permission denied" rather than being read, and a read of a missing transcript creates an empty one. The truncating read itself is a documented reader hazard (design_transcript_reader.md:16), so only the permission and creation consequence is new. The cursor index avoids this: it uses os.Open (read-only) in ReadCompleteRecordsRange (jsonl.go:345-380).
- suggested fix: open the file read-only for reads, check the last byte and the size, and take the O_RDWR path only when the tail actually needs repair; drop O_CREATE from the read path.
- effort: M (the repair must stay under the same lock)
- prior art: partial (design_transcript_reader.md documents the truncating read; the permission consequence is new)
