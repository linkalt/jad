## 3. Findings

### P4-R4-01  Group-writable Unix-socket directory can bypass the token-destination check
- severity: medium
- lens: B security
- location: `backend-go/internal/remote/socket_unix.go:18-32`; `backend-go/internal/remote/client.go:96-107`; test `backend-go/internal/remote/client_test.go:275-287`
- evidence: `[read]` The client `Lstat`s the socket and then calls `checkSocketOwner` before dialing. The helper rejects a parent only when `Perm()&0o002 != 0` (unless sticky); it ignores group-write (`0o020`). A local user with write access through the parent group can replace a root/current-user-owned socket in the gap between the check and `DialContext`, causing the configured bearer token to be sent to the replacement listener. Existing coverage exercises mode `0777` and sticky `01777`, not non-sticky group-writable mode such as `0770`.
- suggested fix: reject group-writable as well as other-writable non-sticky socket parents (and consider validating the connected peer to close the check/dial race); add a group-writable regression test that asserts no request reaches the listener.
- effort: S
- prior art: new follow-up to the socket-owner check in `559ca62`

### P4-R4-02  Reset/delete can miss a handle whose `Complete` is still writing
- severity: medium
- lens: A correctness
- location: `backend-go/internal/asyncmgr/manager.go:361-380,398-415,442-467,470-489`
- evidence: `[read]` `Complete` sets `r.finishing` and snapshots `r.after` under the lock before writing the record. `cancel` skips `finishing` rows, and `DeleteOwnersWithPrefix` also skips them in its terminal-row removal pass. If `Complete` claims first and pauses in `writeRecord`, a reset can run `DropUnread` before the result is queued, or delete can return without setting `endRemove`; after the write resumes, `Complete` uses its captured `endKeep`, queues an unread result, and leaves the row behind. This breaks the documented reset/delete behavior for a live handle at that interleaving. Existing lifecycle tests cover the non-overlapping path, not this in-flight completion case.
- suggested fix: coordinate reset/delete with in-flight completions: have completion apply the final end action at commit time and ensure already-finishing rows are subsequently marked read/removed, or wait for completion before the reset/delete cleanup finishes. Add deterministic tests that hold the record write while reset/delete runs.
- effort: M
- prior art: new; separate from the `Close`/`Complete` wait fix in `176fd7d`

### P4-R4-03  Recovery can leave a terminal record permanently live when the index is stale
- severity: medium
- lens: A correctness
- location: `backend-go/internal/asyncmgr/manager.go:398-422`; `backend-go/internal/asyncmgr/store.go:127-145`; `backend-go/internal/asyncmgr/recover.go:15-32,54-69`; test `backend-go/internal/asyncmgr/index_flush_test.go:48-79`
- evidence: `[read]` `Complete` persists the terminal record before scheduling the index update. `writeIndex` intentionally coalesces updates (default `index_flush_ms` is 150 ms). If the process stops before that timer writes the index, recovery builds the row's state from the stale index, reads the terminal record into `loaded`, then skips that record at `recover.go:55-57` without reconciling the row. The manager retains the handle as live and does not queue its completion signal; `Status` can consequently disagree with `List`/`Wait`. The existing stale-index test covers record files absent from the index, not a known ID whose record advanced to terminal.
- suggested fix: reconcile every record opened for a nonterminal index row before deciding it is lost, treating the record state/unread fields as authoritative; add a test with a stale running index row and a terminal record.
- effort: S
- prior art: new

### P4-R4-04  A failed restore can modify files without publishing its undo checkpoint
- severity: medium
- lens: A correctness
- location: `backend-go/internal/checkpoint/service.go:655-695`; happy-path coverage `backend-go/internal/checkpoint/service_test.go:210-235`
- evidence: `[read]` Restore creates an in-memory `pre_restore` record and saves its `before` Git ref, then runs checkout/removals and captures the after-state. It writes the record to `checkpoints.json` only at line 691, after all mutations succeed. Any partial `checkout-index` failure, an error partway through the removal loop, a later capture/commit failure, or metadata write failure returns without a discoverable undo record, even though some workspace changes may already have happened. The successful-restore test verifies undo only after the full operation succeeds.
- suggested fix: persist the open `pre_restore` record before the first workspace mutation and finalize it afterward; on failure leave a recoverable open/interrupted record with its `BeforeTree`. Add failure-injection coverage for partial restore and metadata failure.
- effort: M
- prior art: new

### P4-R4-05  `max_total_bytes` is only checked before adding the next snapshot
- severity: medium
- lens: B security
- location: `backend-go/internal/checkpoint/service.go:439-457,503-520`; test `backend-go/internal/checkpoint/size_cache_test.go:75-95`
- evidence: `[read]` `capture` rejects only when the cached repository size is already over the configured limit. It then stages the entire workspace, measures the resulting size, and returns success without comparing that size to `MaxTotalBytes`; `Begin` can therefore retain a checkpoint whose repository has crossed the limit by the size of a newly added object (potentially a large model-created workspace file). Later captures are skipped, but the overshoot is already on disk. The existing test checks only a repository that was over the limit before the second capture. `MaxFiles` is likewise checked after `git add`/`write-tree`/`ls-files` (lines 445-450), noted separately as H01.
- suggested fix: enforce the byte limit against prospective snapshot growth before staging, or otherwise prevent/clean up an over-limit snapshot before accepting it; add a regression test where the repository starts below the limit and one new file crosses it. If this is intentionally a one-snapshot overshoot allowance, document that instead of calling it a maximum.
- effort: M
- prior art: new; distinct from P-015's repository-size caching optimization

### P4-R4-06  Deleted owners with dropped signals remain in the manager map
- severity: low
- lens: C performance
- location: `backend-go/internal/asyncmgr/manager.go:60-65,231-237,454-467`; `backend-go/internal/asyncmgr/prune.go:58-71,83-90`
- evidence: `[read]` Overflow/TTL pruning increments `ownerStats.dropped`. `forgetLocked` deletes an empty owner only when `dropped == 0`; `DeleteOwnersWithPrefix` removes the owner's rows but never clears `dropped`. A deleted owner whose signals previously overflowed or expired therefore leaves its `ownerStats` and two maps in `m.owners` indefinitely; if the owner key is reused, the stale dropped count is also reported to the new owner. Repeated session deletion can grow this map.
- suggested fix: when deleting an owner prefix, clear/remove zero-row owner stats irrespective of dropped count; add a deletion test after an expired/overflowed signal.
- effort: S
- prior art: new

### P4-R4-07  Checkpoint service registries retain every staging directory seen
- severity: low
- lens: C performance
- location: `backend-go/internal/checkpoint/service.go:161-170,187-197`
- evidence: `[read]` `NewService` `LoadOrStore`s a mutex and `repoSize` in package-global `sync.Map`s keyed by cleaned staging path. There is no production eviction/release path in the package, so each distinct session staging directory remains referenced after that session is deleted. `ForSession` creates the service wrapper for checkpoint operations; memory grows with unique session paths over one server lifetime.
- suggested fix: add lifecycle-aware release/reference counting when a staging directory is deleted, without evicting entries still used by concurrent services; add a churn test that asserts registry size returns to baseline.
- effort: M
- prior art: new

### P4-R4-08  The `176fd7d` Close regression test has a scheduling false-pass window
- severity: low
- lens: D maintainability
- location: `backend-go/internal/asyncmgr/manager_test.go:411-451`
- evidence: `[read]` The test locks `ioMu`, starts `Complete`, and confirms `completing > 0`, but after launching `Close` it relies on `time.After(150ms)` without a handshake that the Close goroutine reached the wait. If that goroutine is not scheduled during the interval, an implementation that returns immediately can pass this assertion; the post-unlock check only proves eventual completion. The targeted test passes on this run, but this synchronization does not reliably prove the intended condition.
- suggested fix: synchronize on the fake driver's `Stop`/Close progress (or another explicit test hook) before asserting that Close remains blocked while the record write is held; avoid the fixed-delay-only assertion.
- effort: S
- prior art: new test-quality observation on `176fd7d`

## 4. Performance hypotheses for measurement

- H01: `checkpoint.max_files` skips only after a full Git snapshot. `backend-go/internal/checkpoint/service.go:445-450`.
  workload: 100,000 workspace files with `max_files=20,000`.
  benchmark: proposed `BenchmarkCaptureOverMaxFiles`, comparing against existing `BenchmarkBeginFinish` / `BenchmarkBeginFinishSteady` fixtures.
  expected: `git add`, `write-tree`, and full `ls-files -z` work grows with the oversized workspace before the call reports skipped.
- H02: a snapshot can exceed `max_total_bytes` by one large workspace delta. `backend-go/internal/checkpoint/service.go:439-457`.
  workload: repository just below the cap; one new file/blob larger than the remaining allowance.
  benchmark: proposed `BenchmarkBeginOversizedDelta`; record actual repo bytes and peak disk growth.
  expected: accepted repository size can exceed the setting by the newly added object size.
- H03: checkpoint global maps grow with deleted session paths. `backend-go/internal/checkpoint/service.go:161-170`.
  workload: 10,000 unique staging paths created then deleted in one server lifetime.
  benchmark: proposed `BenchmarkNewServicePathChurn`, recording registry entries and heap after churn.
  expected: two process-lifetime map entries per unique path; no cleanup plateau.
- H04: async dropped-count owner stats survive deletion. `backend-go/internal/asyncmgr/manager.go:231-237,454-467`.
  workload: many owners with a TTL-expired/overflowed unread signal, followed by owner deletion.
  benchmark: proposed `BenchmarkDeleteOwnersAfterDroppedSignals`, recording `len(owners)` and heap.
  expected: owner-map size grows with deleted owners that have nonzero dropped counts.
- H05: remote Hub clients have no per-entry eviction when a remote file disappears. `backend-go/internal/remote/hub.go:44-72,95-114`.
  workload: call one remote from many ephemeral remotes directories, then remove those entries while keeping the process alive.
  benchmark: proposed `BenchmarkHubClientChurn`, recording retained clients/transports and idle connections.
  expected: `Hub.clients` retains one client per historical `(directory,name)` until `Hub.Close`.
