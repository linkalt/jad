## 1. Understanding note

p2b2 is two halves. (a) sessionfs leaf settings: ~20 small normalizers that turn setting.json nodes into typed configs. The established in-repo pattern is strict: every sibling normalizer (checkpoint, hooks, image_*, openai_oauth, provider_*, remote_api, extension_decide, all native_* in p2a) rejects unknown keys ("is not supported") and null-with-meaning, with table tests asserting both; the runtime JSON schema in sample/schemes is test-only, never enforced at runtime. (b) The session runner: `Runner.Run` (runner.go) serializes runs per session under `Runner.mu`, loops provider-round -> persist -> tool-batch (`executeToolRound`/`runToolBatch`) with `MaxToolRounds` (0..50000) and `MaxRunTokens` caps, checkpoint hooks, and image/store/trace collaborators that are all nil-receiver-safe. Tool-batch panics are recovered per call (D-1 fix present). Per-batch concurrency is `min(limit, len(calls))` with limit <= 64; there is no cross-run ceiling in this package (B-C8 remainder lives in phase 3's run registry / `server.max_concurrent_runs` default 0).

### P2B2-R3-02  Listing policy matches deny/allow rules against unresolved paths
- severity: low
- lens: B security
- location: backend-go/internal/sessionfs/files.go:199-214 (allowedByNativeReadPolicy)
- evidence: [read] Deny/allow matching uses `PathWithin(rule.Path, path)` where `path` is the unresolved `filepath.Join(root, ...)` string, while containment uses EvalSymlinks-resolved paths (files.go:24,51,65,120). Neither side is canonicalized: rules are only Clean(Abs(...)) (file_settings.go:213-219, no EvalSymlinks) and `root` (settings.WorkingDir via app/session_settings.go:89) is never EvalSymlinks'd (no such call in session.go/roots.go/layout_load.go). Concrete case: workspace root `/tmp/ws` (-> /private/tmp/ws, routine on macOS via /tmp->/private/tmp) with deny rule `/private/tmp/ws/secret`: the listed path `/tmp/ws/secret/f` never string-matches the rule, the in-root shortcut (files.go:205) allows it, and the folder/file is listed despite the deny. Reverse (symlinked rule, canonical root) fails the same way. Precondition (symlink in root-or-rule plus deny rules) is narrow, and the read tool re-enforces its own policy at open time, so impact is filename disclosure in the listing.
- suggested fix: in allowedByNativeReadPolicy, also test `PathWithin(rule.Path, resolvedPath)` for deny rules (fail closed), i.e. compare against the resolved path, not only the unresolved join.
- effort: S
- prior art: new

### P2B2-R3-03  Run has no recover boundary around its caller callbacks
- severity: low
- lens: A correctness
- location: backend-go/internal/session/runner.go (OnEvent call in runner_response.go:81-85; post-persistence OnToolResult loop in runner.go; OnResponseCommitted in runner_response.go:122-126; RefreshStateContext/OnHookReport/OnTurnStarted in runner.go)
- evidence: [read] In-batch `publish` panics are swallowed into call errors by runOne's recover (tool_batch.go:95-106), but the same logical callback invoked after persistence (runner.go OnToolResult loop), and OnEvent/OnResponseCommitted/RefreshStateContext, run unguarded in Run's goroutine. A panic there unwinds the whole run (checkpoint Finish still runs via defer; transcript stays consistent since outputs were already persisted). Callbacks are same-trust server code so this needs a caller bug to trigger, and net/http recovers per-connection upstream; impact is an aborted run rather than a returned error. Inconsistent with D-1's per-call recovery one layer down.
- suggested fix: either document that RunOptions callbacks must not panic, or add one deferred recover in Run converting a callback panic to an error (keeping the already-persisted state authoritative).
- effort: S
- prior art: new (D-1 verified fixed underneath; this is the remaining above-layer boundary)

### P2B2-R3-04  No cross-run ceiling on tool-batch goroutines (B-C8 remainder)

- H4: concurrent-run tool worker fan-out (see P2B2-R3-04). workload: N concurrent runs x 64-call batches. benchmark: PROPOSED new (multi-Runner x BenchmarkRunToolBatch shape); existing BenchmarkRunToolBatch covers single-batch only. expected: workers = runs x min(limit, calls); measures whether the default-0 run cap matters.
- H5: readLimitedDirectory sorts a truncated slice per directory (files.go:157-163) — minor; covered by H1's benchmark, no separate run needed.
- H6: validateAllStoragePaths resolves all profiles' paths per session load (storage_paths.go:115-147, O(profiles)). workload: 1 vs 16 path-profiles. benchmark: existing BenchmarkLoadSessionConfig with profile count varied. expected: linear in profile count; likely negligible (no I/O, pure path ops) — cheap to confirm and close.
