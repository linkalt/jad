### P1-R3-01 sharedStore waiters ignore cancellation
- severity: medium
- lens: A correctness
- location: backend-go/internal/app/resolver.go:857
- evidence: [read] `sharedStore` fast path: `r.mu.Unlock(); <-entry.ready` with no `select` on `ctx.Done()`. A second `Resolve`/`ReadSessionSnapshot`/`readTurnRecords` for the same `MessagesPath` while the first `buildStore` (MkdirAll+NewJournal+Recover) runs cannot abort; `ctx` cancel/timeout is only checked on entry and after wake. Same pattern for `subagentBuilds` wait at resolver.go:648 (`<-build.done`). Targeted test `TestProfileMessageReachesAProfileOfAnotherSession` passes but does not cover cancel-during-build.
- suggested fix: `select { case <-entry.ready: case <-ctx.Done(): }` + keep entry for others; same for `subagentBuilds` wait. Files: backend-go/internal/app/resolver.go
- effort: S
- prior art: new (B-C9 rest was about I/O under mu, closed by Phase 4 measurement; this is waiter-cancel, different)

### P1-R3-02 subagent manager build wait ignores cancellation
- severity: medium
- lens: A correctness
- location: backend-go/internal/app/resolver.go:648
- evidence: [read] `sharedSubagentManager` loop: `r.mu.Unlock(); <-build.done; continue` with no ctx check. A resolver `Close()` during build is handled (builder closes manager), but a caller `ctx` cancel while waiting is not; the call blocks until the build (file recovery, manifest loads) finishes. `finishSubagentBuild` releases waiters via `close(build.done)` on all exits including panic, so no hang, only un-cancellable wait.
- suggested fix: select on ctx in the wait loop; on cancel return ctx.Err() without consuming build. File: backend-go/internal/app/resolver.go
- effort: S
- prior art: new

### P1-R3-03 shutdown closes managers before HTTP drain
- severity: medium
- lens: A correctness
- location: backend-go/internal/app/service.go:86, backend-go/cmd/jad/main.go:81
- evidence: [read] `cmd/jad run()`: `service.Close()` then `ShutdownHTTPServer(server)`. `Service.Close` stops remotes hub, subagent/process managers, async hosts, MCP, fetch stores while `server.Serve` still accepts. In-flight runs hold `runMu` + `sharedSession` but their tool catalog references closed managers; `Resolver.Close` sets `closed=true` so new `AsyncHost`/`mcpManagerFor`/`sharedStore` fail with 503 during drain. D-3 fixed the deadline (ShutdownTimeout), not the order. `Service.Close` itself is `closeOnce` only for recovery scan; double-serve-error path re-closes safely via `closed` flag.
- suggested fix: drain first (`ShutdownHTTPServer` both listeners), then `service.Close()`; keep `stopRecovery` cancel before drain or after as today but document. Files: backend-go/cmd/jad/main.go, backend-go/internal/app/service.go
- effort: M
- prior art: D-3 fixed deadline only; order is new evidence, not a repeat
