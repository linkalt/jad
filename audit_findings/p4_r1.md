## 1. Understanding

asyncmgr is a lock-and-file state machine: rows in memory (`mu`), one record file per handle plus a delayed, coalesced `index.json` (`ioMu`, `indexMu`, `flushTimer`). Drivers call `Complete`; `Close` stops live handles and waits `StopWait` for them and for `completing` writers (176fd7d). remote is the client (Client/Hub/Follow/StartRun/StopRun); remoteapi is the server (token table, run table keyed by token + request id); checkpoint snapshots the workspace into a private bare git repo (`add --all`, `write-tree`, `commit-tree`, refs) and restores by tree diff.

### P4-R1-01  A stop sent while every in-flight slot is held by followers never reaches the remote
- severity: medium
- lens: A correctness
- location: remote/client.go:156-161 (slot taken in `Do`, same pool for polls and stops), 116 (`slots` = max_in_flight), remote/run.go:131 (Follow polls hold a slot for poll_ms, default 20 s); cross-phase callers tools/native/profile_message_remote.go:224-234 and 300-305 (stop uses a 3 s `stopCallTimeout`)
- evidence: [measured] scratch test TestStopStarvedByFollowers (copy of remote sources): max_in_flight=2, two `Follow` goroutines against a server that holds the poll open; `StopRun` with a 3 s context returned `context deadline exceeded` after 3 s and the server saw 0 stop requests. With the defaults (8 slots, 20 s polls) it needs 8 followed runs of one remote at once. Effect: user stop, local timeout and shutdown (`stopRemote`) are silently dropped while the remote run keeps going; the local handle ends as stopped/timed out.
- suggested fix: give stop its own small reserve (second semaphore, or let `StopRun` bypass `slots`); remote/client.go only.
- effort: S
- prior art: new

### P4-R1-02  A crash inside the index flush delay leaves a finished handle `running` forever
- severity: medium
- lens: A correctness (crash/restart, idempotent recovery)
- location: asyncmgr/recover.go:18-33 (row state taken from the index, record read but its state ignored) and 55-62 (loop skips records that are terminal, so no `lost` marking); asyncmgr/store.go:127-145 (index write delayed index_flush_ms, default 150 ms); manager.go:361-428 (`Complete` writes the record at once, the index later)
- evidence: [measured] scratch test TestStaleIndexAfterCrash: register (index says running), `Complete` with a long flush delay, reopen without Close. After the restart `Counts` = Active 1, and `List` shows the handle `running`. A second clean restart keeps it (Active 1). Only another `Complete` call (which nobody makes) clears it. It counts against `max_handles` and `max_handles_total` and `Wait` reports it as pending. Window = index_flush_ms after every state change; any kill -9 or crash in it triggers it.
- suggested fix: in `recover`, when the record read for a non-terminal index row is terminal, take its state, ok, ended time and unread flag into the row (one `mutateLocked`); asyncmgr/recover.go. Add the restart test next to the existing recovery tests.
- effort: S
- prior art: new (cd606e0 introduced the delay)

### P4-R1-03  `MarkRunning` can overwrite a terminal record with a stale `running` one
- severity: low
- lens: A correctness

- suggested fix: write the record from MarkRunning under `ioMu` after re-checking the row is still non-terminal and not `finishing`, or use `updateRecord` with a state guard.
- effort: S

### P4-R1-07  Pruning checkpoints frees no disk, so `max_total_bytes` is eventually hit for good
- severity: medium
- lens: C performance, A (feature stops working)
- location: checkpoint/service.go:471-482 (`prune` deletes refs only), 440-442 (skip when repository size is over the limit), git.go:79 (`gc.auto=0`)
- evidence: [measured] scratch repo, 3 commits of 200 KB random files, then `update-ref -d` on all refs: `count-objects -v` identical before and after (9 loose objects, 648 KiB). `design_checkpoint.md:51` records "git gc is not run automatically" but nothing says what happens at the limit. [read] consequence: size only grows; after 512 MiB (default) every `Begin` and `Finish` becomes `skipped` ("over checkpoint.max_total_bytes") and undo silently stops working until someone runs gc by hand. This is a decision challenge on the "no gc" line plus a defect in its consequence.
- suggested fix: after `prune` dropped refs, run `git gc --prune=now` (or `prune --expire=now` plus `repack -d`) when the measured size is over a fraction of the limit; one more git call in the prune path, checkpoint/service.go. Document in DECISIONS.md.
- effort: M
- prior art: P-015 (b27c663) cached the size; this consequence is new

### P4-R1-08  `max_files` is checked after the whole workspace was already staged
- severity: medium
- lens: C performance, A
- location: checkpoint/service.go:444-451 (`snapshot()` first, count compared with `MaxFiles` afterwards); git.go:208-221
- evidence: [read] a workspace with a million files (no ignore rules, `node_modules` without `.gitignore`: design_checkpoint.md:79 says untested) runs `git add --all` over everything (up to `timeout_ms`, 120 s default) and writes every new blob into the object store; the check then skips the checkpoint, and the objects stay (see 07). ## 4. Performance hypotheses (for measurement; none measured by me)

- H01: `Complete` and every state change rebuilds and rewrites the whole `index.json` (all rows, sort, marshal, CRC) after the delay, asyncmgr/store.go:166-188; and `recomputeExpiryLocked` scans all rows on each prune pass, prune.go:144-150, `pruneLocked` sorts all finished rows each pass, prune.go:94-108.
  workload: keep_finished 200 plus unread 100 per owner, 64 live handles, 20 completions per second.
  benchmark: new `BenchmarkCompleteWithRows` in asyncmgr (fixture rows 500 / 5,000, `Complete` loop, index_flush_ms 0 and 150).
  expected: per-Complete cost grows linearly with rows when index_flush_ms is 0; one full rewrite per 150 ms otherwise.
- H02: `Wait` and `popLocked` allocate and sort every unread row of the owner per wake and per poll (`sortedRows`, wait.go:115), and `encodedSize` marshals each entry just to measure it (entry.go:62-68, 3 marshals per entry in `fitEntry`).
  workload: unread_max 100, wait_max_signals 10, 50 waiters waking on every `notifyLocked` (wake-all channel, manager.go:240-243).
  benchmark: existing asyncmgr scale_test.go if it has a Wait loop, otherwise `BenchmarkWaitManyWaiters`.
  expected: thundering herd: cost scales with waiters x unread rows per completion.
- H03: `List` with a non-active filter copies and sorts every row of every owner (`m.rows` loop, query.go:109-119) while holding `mu`.
  workload: `state: all` with 5,000 retained rows, many owners.
  benchmark: `BenchmarkListAll` in asyncmgr.
  expected: O(total rows log n) under the global lock, blocking `Register`/`Complete`.
- H04: client `Follow` performs one HTTP request per poll with a fresh JSON decode and a `Token()` call per request that stats and reads the token file every time (remote/entry.go:262-277 via client.go:152).
  workload: 8 to 64 followed runs, poll_ms 20 s (mostly idle) or 100 ms floor when the remote answers at once.
  benchmark: `BenchmarkClientDo` with `token_file` and with `token_env` against httptest.
  expected: one extra stat plus read per request; small, only matters at the 100 ms floor.
- H05: `Directory.Client` reads and parses the entry file on every call and `reflect.DeepEqual`s it against the cached entry (remote/hub.go:50-65).
  workload: every remote tool call and every transcript read.
  benchmark: `BenchmarkDirectoryClient`.
  expected: one file read + JSON parse per call; microseconds, fine unless called in a loop.
- H06: remoteapi `begin` scans all runs under the server mutex for the per-token live count and `sweepLocked` scans all runs on every request and lookup (server.go:409-414, 473-482, 523-525).
  workload: max_runs up to 10,000 (MaxMaxRuns), polling clients every 100 ms to 20 s.
  benchmark: `BenchmarkRemoteAPIPoll` with 256 and 10,000 held runs.
  expected: O(held runs) per request under the global lock.
- H07: `Authenticate` loops all tokens with a constant-time compare and does not stop at the match (tokens.go:285-289), plus a `refresh` file stat at most every 250 ms; the periodic check always reads and hashes the whole file (`read()` at tokens.go:253, 215-236), it does not stat first.
  workload: any request rate; table of 1 to 1,000 tokens.
  benchmark: `BenchmarkAuthenticate` (table sizes 10 / 1,000) and a file-reload variant.
  expected: one ReadFile + SHA-256 + (when changed) parse every 250 ms; negligible below 1 MB table.
- H08: checkpoint does 14 git processes per run on top of a full `git add --all` over the workspace twice per run; `Finish` re-hashes unchanged files only via the index, so the cost is the workspace scan (service.go:422-458, git.go:208-221).
  workload: 20,000 files (the max_files default), and a 100,000-file workspace for the post-check problem of P4-R1-08.
