## 1. Understanding note

`app` is the composition root. `cmd/jad` → `app.LoadConfig` (root `setting.json` + `HOST`/`PORT`/`JAD_API_TOKEN` env, `app/config.go`) → `app.NewService` (`Resolver` + `httpapi.Handler` + optional `remoteapi.Server`) → one TCP `http.Server` (plus a dedicated unix-socket server when `server.remote_api.listen_unix` is set). `Resolver` owns every long-lived in-process object: transcript stores per messages path (built outside `mu` through `storeEntry.ready`), sub-agent managers (built outside `mu` through `subagentBuilds`), async hosts, process/task/memory/fetch/MCP managers, `lockedConfigs` (run-start config reuse with `sessionfs.SettingsStamp`), `listSettingsCache` (session-list parse reuse), `profileTurnCounts`, `skippedSessions`, and the `profile_message` queue/edge set.

Read path of the UI: `Resolver.ListSessions` / `ReadSessionSnapshot` / `ReadSessionHistory` → `listSettings`(cached by stamp) → `sessionVersion[…ForCatalog]` (one `statx` per stamped file + `json.Marshal` of run summaries) → ETag compare → `sharedStore` → `scanTranscriptIndex` (`readTurnStarts` from the persisted cursor index + one incremental usage pass, which **writes** `usage-cache.json` when new bytes were seen) → `webui` projection.

Write paths: `LockSession`/`TryLockSession` (settings load, then `flock` of the transcript; parks the config for the following `Resolve`), `LockSessionSettings` (flock of `setting.json`, used only by the model-default route), `settingsMu` (one resolver-wide mutex for catalog and session writes), `runMu` (per transcript store, context-cancellable).

Shutdown: `service.Close()` (recovery scan → remote hub → run registry → resolver managers) and then `Server.Shutdown` with `server.shutdown_timeout_ms` per listener.

### P1-R2-01  A failed usage-cache write fails the session list, the snapshot, compaction and every run start of that session
- severity: medium
- lens: A correctness
- location: `internal/app/usage.go:129-212` (`writeUsageCacheCheckpoint`, every error path returns an error), `internal/app/catalog.go:621-626` (`scanTranscriptIndex` turns it into an error), `internal/app/catalog.go:238-241` and `:386-389` (the list and the snapshot return it), `internal/app/compaction_usage.go:33-36` and `:56-59` (`compactPreservingUsage` / `frontCompactPreservingUsage` fail *after* the transcript was rewritten), `internal/app/bound_runner.go:37-51` (`nextSessionTurn` → `scanTranscriptIndex`, closed over into `session.PersistInputWithImages`), `internal/session/runner.go:195-198` (the run start fails before the input is stored), `internal/session/runner.go:529-532` (an automatic compaction error fails the run)
- evidence: [read] trace. `scanTranscriptIndex` calls `writeUsageCacheCheckpoint` whenever the usage cache was invalid or the transcript grew (`catalog.go:621`), and returns `fmt.Errorf("write session usage cache: %w", err)` on any failure. Consequences, in order of impact: (1) `ListSessions` returns that error for the whole list (`catalog.go:238`), so `GET /api/sessions` is a 500 while the data itself is readable; (2) `ReadSessionSnapshot` fails the same way; (3) `boundRunner.Run` computes the next session turn through `nextSessionTurn` before `session.PersistInputWithImages`, which returns the error as `read next session turn: …` (`session/runner.go:195-198`), so **no run of that session starts and the user's message is not stored** — the deliberate invariant stated at `bound_runner.go:47-50` ("the user input is stored before anything that can still fail") is broken by a cache write; (4) `compactPreservingUsage` returns an error after `store.CompactHistory` already rewrote the transcript, and an automatic compaction failure fails the run (`session/runner.go:529-532`). Reachable causes for the write itself, without the transcript itself being unwritable: `<state>/<session>/<profile>/usage-cache.json` replaced by a directory, or a permission/path problem specific to it (`os.CreateTemp`/`os.Rename` at `usage.go:176-197`, `os.MkdirAll` at `:173`), and ENOSPC when only the cache write fails (the transcript append may still succeed in the same window). A wholly read-only state root reproduces (1) and (2) exactly, since the list needs no write of its own. The corresponding read path (the cache is optional: `readUsageCacheState` ignores any invalid cache at `usage.go:45-81`) shows that losing the cache is harmless — only the failure to *write* it is fatal. `git log -S "write session usage cache"` shows the text dates from the initial port (`31a67ac`), so this was never decided; no test pins it.
- suggested fix: make the usage-cache write best-effort on the read/run paths: in `scanTranscriptIndex`, log the error once (through the resolver logger) and leave `wroteUsageCache` false instead of returning it, exactly as `compaction_usage.go:27-31` already does when the transcript cannot be stat'ed; keep the error for `writeUsageCacheCheckpoint` itself so a caller that wants it still can. Do the same in `compactPreservingUsage`/`frontCompactPreservingUsage` (the compaction has happened; the next scan rebuilds the cache). Files: `internal/app/catalog.go`, `internal/app/compaction_usage.go`, plus tests for a read-only state dir.
- effort: S
- prior art: new

### P1-R2-02  The async manager is opened (index read/rebuild) while `Resolver.mu` is held
- severity: medium
- lens: C performance (concurrency), A correctness of lock scope
- location: `internal/app/resolver.go:602-618` (`AsyncHost` holds `r.mu` across `native.NewAsyncHost`), `internal/tools/native/async_host.go:57-72` → `internal/asyncmgr/manager.go:109-129` (`Open` runs `m.recover()`)
- evidence: [read] trace, with the existing benchmarks as the size of the work: `BenchmarkOpenFromIndex` and `BenchmarkOpenRebuild` (`internal/asyncmgr`) measure exactly this recovery. `Resolver.mu` is the resolver-wide lock used by `sharedStore`, `sharedProcessManager`, `sharedTaskStore`, `sharedMemoryStore`, `sharedFetchStore`, `sharedMCPManager`, `asyncManagers`, `Close` and `releaseSessionChildren`; the first run start, `GET /tools` or session tool listing of a session with `tools.native.async` therefore blocks every other session's store lookup and run start for the length of one async index read — and for a full rebuild (missing or stale index) that is the expensive case the `OpenRebuild` benchmark covers. The same pattern was already fixed for transcript stores (`storeEntry.ready`, `resolver.go:842-892`) and sub-agent managers (`subagentBuilds`, `resolver.go:642-717`), which proves the intended shape; the async host was added later (`86552a4`) and did not follow it. This is the "B-C9 rest" item that `audit_performance_plan.md:87` left as `[inferred: cheap]`: it is not cheap here, while the other constructors it names are (`NewConfiguredProcessManager` `process_manager.go:193-199`, `NewTaskStore` `task_store.go:201-203`, `NewMemoryStore` `memory_store.go:143-155`, `NewFetchStore` `fetch_store.go:82-84`, `mcpclient.NewManager` `manager.go:90-97` do no I/O).
- suggested fix: mirror the `subagentBuilds` pattern for async hosts: insert an entry with a `done` channel under `mu`, run `native.NewAsyncHost` outside it, publish (or close it) under `mu` on exit. Files: `internal/app/resolver.go` (one map + one type, ~30 lines).
- effort: S
- prior art: re-confirms B-C9 (rest) with new evidence; `audit_performance_plan.md:87` marked the remaining constructors "not read"

### P1-R2-03  Session delete holds the resolver-wide settings lock across sequential process-kill waits
- severity: medium
- lens: A correctness (lock held across blocking work) / D
- location: `internal/app/session_catalog_files.go:71-84` (`r.settingsMu.Lock()` … `r.releaseSessionChildren` at `:82`), `internal/app/session_catalog_files.go:100-154` (`releaseSessionChildren` closes MCP and process managers after unlocking `r.mu` but still under `settingsMu`), `internal/tools/native/process_manager.go:525-549` (`Close` stops every running process **sequentially**), `internal/tools/native/process_manager.go:482-522` (`Stop` waits `kill_grace` for SIGTERM, then `kill_grace` again after SIGKILL), `internal/sessionfs/native_bash_settings.go:14-15` (`kill_grace_ms` default 2000, max 60000)
- evidence: [read] trace. `settingsMu` is one mutex for the whole resolver: `UpdateModelDefault` (`session_settings.go:23`), `WriteSessionConfig` (`session_catalog_files.go:47`), `DeleteSessionConfig` (`:71`), `WriteCatalogFile` (`catalog_files.go:79`), `DeleteCatalogFile` (`:93`). A `DELETE /api/catalog/sessions/{ref}` therefore blocks every other session's settings write and every catalog write for as long as the deleted session's processes take to die. A managed process that ignores SIGTERM (the model can start one through the `process` tool: `bash -c 'trap "" TERM; while :; do sleep 1; done'`) costs one full `kill_grace` plus up to another one after SIGKILL, i.e. up to 4 s at the default and up to 120 s at the configured maximum, **per process**, sequentially. The delete handler already holds the in-process session lock (`httpapi/catalog_sessions_handler.go:79/113`), which is the lock that actually excludes the session's other writers, so `settingsMu` adds nothing here for the delete itself while it is held across the kill waits.
- suggested fix: narrow the lock: take `settingsMu` only around `sessionfs.DeleteSessionFile` and the cache drops, and call `releaseSessionChildren` after releasing it (the child managers are collected under `r.mu` inside it, which is independent of `settingsMu`). Alternative: make `ManagedProcessManager.Close` stop its processes concurrently with a single bounded wait. Files: `internal/app/session_catalog_files.go` (and optionally `internal/tools/native/process_manager.go`).
- effort: S
- prior art: new (D-2/B-C9 touched the *set* of things closed, not the lock scope)

### P1-R2-04  The session list and every resolve create the state directory of sessions that never ran

- location: `internal/app/catalog.go:234` (`r.sharedStore(candidate.config)` in `ListSessions`), `internal/app/resolver.go:401` (`Resolve`), `internal/app/resolver.go:905-908` (`openSharedSession` → `os.MkdirAll(filepath.Dir(config.MessagesPath), 0o755)`)

### P1-R2-06  `readTurnStarts` holds the transcript's turn-start mutex across a journal read and per-record JSON decoding
- severity: low
- lens: A concurrency / C performance
- location: `internal/app/turn_starts.go:41-92` (`shared.turnStartsMu` is locked at `:41` and held through `shared.store.ReadCompleteRecordsRange` at `:56-92`, which does file I/O plus one `json.Unmarshal` per record); `internal/app/turn_starts.go:174-181` (`invalidateTurnStarts` takes the same mutex)
- evidence: [read] trace plus the prior measurement of the work done under the lock: `audit_performance_plan.md:290` (F-29(a)) measured 0.4 to 1.6 ms per appended turn for the scan passes. The lock is per transcript store, so it serialises concurrent readers of one session (list + snapshot + message page can arrive together) and blocks `invalidateTurnStarts`, which compact/reset/front-compact call on the *run* path (`maintenance.go:90`, `:149`, `front_compact.go:33`). It is not a correctness bug (the cache fields are recomputed under the lock) and the amount of I/O under it is incremental.
- suggested fix: read the new records outside the mutex (the offset is already read from the cursor index before the lock), decode outside it, then take the mutex only to append the new starts and reconcile the cache generation (re-run the scan if the generation changed meanwhile). Files: `internal/app/turn_starts.go`.
- effort: M
- prior art: F-29 (its passes were left separate by decision; this is the lock scope, not the pass merge)

## 6. Checked and sound (no finding)
