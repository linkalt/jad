### P2B1-01 (medium, A/B/D) The unbounded `os.ReadFile` readers — r1-01, r2-01, r3-02, r4-01 — **confirmed by execution and by reading every site**
- still unbounded at `51f35cf` (`grep -n os.ReadFile internal/sessionfs/*.go`, non-test): `session.go:1129` (`readPromptDocument`), `session.go:1169` (`readSessionObject`), `layout_files.go:172` (`readLayoutFile`), `roots.go:379` (`readObject`, the root setting), `catalog_files.go:140/174/233`, `check.go:81`, `native_subagent_dir.go:116` (`agent.json`), `session_files.go:44` (`ListSessionFiles`) and `:146`. The load path reaches the first five; `readPromptDocument` is called from `session.go:1108` (the composed setting's and the profile's `prompt_documents`; `instructions` is inline text, not a file) and from `state_context_settings.go:227` (statecontext trigger documents).
- the reader the P2A-03 fix added is `readConfigTextFile` (`native_config_file.go:13-38`): `O_NONBLOCK` open, `Stat` on the handle, `IsRegular` refusal, `LimitReader` at `maxConfigTextFileBytes` = 1 MiB. It has exactly three call sites: `native_bash_env.go:12`, `native_subagent_dir.go:145`, `native_subagent_settings.go:568`. `336cdf4` touched those three files and `native_config_file.go` only — not `session.go`, not `layout_files.go`, not `roots.go`.
- **executed, FIFO**: a FIFO named as a profile `prompt_documents` entry left the load blocked after 3 s (`HUNG: the load is still blocked after 3s in os.ReadFile on the FIFO`) while the test's 3 s watchdog fired; the goroutine never returned. This is the same shape r2 measured for a profile FIFO, a model FIFO and a session prompt-document FIFO (`/tmp/r2` probes, 4 s each), and r1 measured for `readSessionObject` and `readLayoutFile` (1.5 s each). Since `readObject`, `readLayoutFile` and `readSessionObject` are literally the same single `os.ReadFile` call, the hang does not need a per-site reproduction: one blocked open per entry point, forever, with no context check.
- **executed, size**: a 3 MiB `prompt_documents` file loads whole (`err=<nil>`, `PromptText len=3145800`), i.e. the 1 MiB config cap does not apply to this path. r2 measured 2 MiB (`len(PromptText)=2097162`) with the same result. `/dev/zero` as a document is r1's and r2's measurement, not re-run here (it OOMs by construction; p2a §12.4 measured the same shape at ~2.3 GB/s on the native path).
- reach: whoever can create the file at a configured path — a model with `bash`/`exec` writing into the session `cwd` (prompt documents resolve from there, `session.go:1124-1128`), or any operator. Catalog files need write access inside the catalog folder (a FIFO there is admitted because `catalog.Scan` filters with `isDir` and the `.json` suffix only, `catalog/scan.go:63-68,100`), and `ListCatalogFiles`/`CheckLayout` read every listed file. Effect: every load of that session (every run start, every `GET /api/sessions` poll that misses the cache, `jad check`) blocks forever with one parked goroutine per attempt; `/dev/zero` kills the process.
- **severity: medium**, as three of four reviewers filed it. Not high: the trigger needs write access to a config path, and prompt documents are the only site a model can reach without it. Not low: it is an availability defect on the default path of every session, and the fix is a reuse of a helper that already exists.
- fix (S): generalise the helper rather than adding a second one — `readRegularFile(path string, max int64) ([]byte, error)` in `native_config_file.go` holding the `O_NONBLOCK`/`IsRegular`/`LimitReader` body, with `readConfigTextFile` becoming its 1 MiB caller; route `readPromptDocument`, `readSessionObject`, `readLayoutFile` and `readObject` through it. The cap for prompt documents has to be chosen deliberately (a document above 1 MiB is legal today and loads; my probe shows 3 MiB), so this needs either a documented setting or one shared internal ceiling — see §11 decision 1. Add one FIFO/oversize test per entry point; today only `native_config_file_test.go` mentions a non-regular file at all (`grep -l 'Mkfifo\|NamedPipe' internal/sessionfs/*_test.go` → that file alone).

### P2B1-04 (low, A) The stamp does not cover the model file the load reads — r1-03, r3-01 — **confirmed by execution; r3's toolset and MCP halves refuted (C2)**
- the load stamps four kinds of file: `layout_load.go:32` (the session file), `:269` (the selected profile), `:331` (every other profile in scope), `:456` (each toolset file). `inputStamps(config, started)` then adds the derived inputs (documents, env files, `agents_dir` folders with `agent.json`/`prompt.md`, the cwd presence stamp). Model files are never `noteFile`d, but `checkProfile` → `checkModelEffort` → `loadModel` (`layout_profile.go:40`, `model_effort.go:68-78`) reads one whenever a profile's `model_default` carries an `@effort`, and `layout_load.go:102-107` reads it again (P2B1-12).
- **executed** (profile `model_default` = `<model>@high`, model lists `efforts: ["low","high"]`, tree backdated an hour so nothing is in the racy window): `effort="high" current=true files=23 modelFileStamped=false`, then after rewriting the model to `efforts: ["low"]`: `stamp.Current()=true` while a fresh `LoadSessionSettings` returns `model_default: model gpt-6-luna does not offer the reasoning effort "high" (available: low)`. Control in the same probe: after editing the *profile* file the same stamp reports `Current()=false`, so the gap is specific to the model file.
- consequence: `app/list_settings_cache.go` keeps serving the session as healthy and `lockedConfigs` reuses a config the loader would now refuse; the run then fails at `WithModel` instead of at load. Narrow: only profiles/sessions that use `@effort`. Nothing else in the loaded `SessionConfig` comes from the model file's *contents* (`ModelPath`/`ModelPaths` are catalog paths, and the app re-reads the model at run start), so the cached config is stale only in its "would this load succeed" verdict.
- **r3's broader claim is partly refuted** (C2): toolset files *are* stamped (`layout_load.go:456`, before the read), and MCP server files are not a load input at all — they are read by `mcpclient` at run time and validated at write/`jad check` time, so the stamp does not owe them. What remains is the model file, which both r1-03 and r3-01 named first.
- **severity: low** (r1's rating; r3 filed medium): the effect is a delayed failure, not a wrong or dangerous configuration, and it is bounded to `@effort` profiles.

### P2B1-05 (low, C/A) A future mtime disables the settings cache — r2-03, r4-05 — **confirmed by execution; r4-05 is not independent (C8)**
- `racy()` is `f.exists && !f.presence && f.taken.Sub(f.modTime) < racyStampWindow` (`settings_stamp.go:51-53`). A modification time later than the stamp gives a negative duration, which is always `< 2 s`, so `Current()` returns false before it compares size and time (`:58-78`).
- **executed**: backdated tree → `current=true`; `session file mtime +24h` → `current=false`; and after editing that future-dated session file, the next stamp is `current=false` again. r2 measured the same on a session and on a profile file.
- one correction to r2's phrasing "the cache never validates" (C8): each load builds a *fresh* stamp with `taken = now`, so once the wall clock has passed the file's mtime the comparison turns positive again and a new stamp is current. The cache is disabled **until the wall clock catches up**, which for a genuinely far-future stamp (a bad clock, a network share, `rsync --times` from a machine ahead) is effectively forever, but it is not a permanent property of the file.
- reach: no operator intent needed — a copied tree, a clock skew in a container, a share. Nothing logs it. Effect: that session reloads (every profile in scope, every `agents_dir` listing) on every poll.
- fix (S): bound the window on both sides — `delta := f.taken.Sub(f.modTime); return delta >= 0 && delta < racyStampWindow` — and let a later mtime fall through to the ordinary size+time comparison (a real later edit still moves the mtime, so a change is still seen). Optionally log one notice when a stamped file's mtime is ahead. Add the future-mtime case to `settings_stamp_inputs_test.go`, whose `backdateTree` helper only ever moves files into the past.

### P2B1-06 (low, A/D) Write durability, the replace window and the delete window — r1-06, r2-04, r3-04, r3-07, r4-03 — **confirmed by reading; no crash injection (a merge may not)**
- `writeFileIfUnchanged` (`layout_settings.go:174-203`): temp file in the target directory, `Chmod`, `file.Sync()` **only when `syncWrite`**, close, `Stat` + size/mtime compare, `os.Rename`. `createFileExclusive` (`catalog_files.go:476-506`): the same, `os.Link` instead of the rename. Neither opens the parent directory for a `Sync` — `grep -n 'Sync()' internal/sessionfs/*.go` finds exactly two, both on the file (`catalog_files.go:492`, `layout_settings.go:190`). The precedent in the same repo does sync the directory: `app/usage.go:187-212` (file for every durability but `process`, directory for `strict`) and `internal/transcript/jsonl.go:59,205` (`directory.Sync()`).
- DECISIONS 745 says catalog "Writes are always fsynced and run under the resolver's settings lock". Two gaps: (a) `WriteCatalogFile` is called from `app/catalog_files.go:81` with `syncWrite=true`, so catalog writes do sync the file but never the directory; (b) `SetLayoutModelDefault` is called with `settings.Persistence.Durability` (`app/session_settings.go:52`), whose default is `"turn"` (`session.go:727`, validated at `:745`), and `layout_settings.go:120` passes `durability == "strict"` — so under the **default** durability the acknowledged model-default write is not synced at all.
- the replace window: the ETag came from an earlier `os.ReadFile` (`catalog_files.go:233`), the size/mtime compare is at `layout_settings.go:198` and the rename at `:201`; another process (an editor, `git checkout`) can write between them, so a same-size edit inside the mtime granularity is overwritten rather than answered with 412. In process, `Resolver.WriteCatalogFile`/`DeleteCatalogFile` hold `settingsMu` (`app/catalog_files.go:79-95`), so API requests are serialized; cross-process is the documented gap (r2 H-A6).
- the delete window (r3-07): `DeleteCatalogFile` reads the file, checks the ETag, scans for users (`profileUsers`/`modelUsers`/`toolsetUsers`/`serverUsers`) and then `os.Remove`s (`catalog_files.go:246-305`); nothing couples the scan to the unlink, so a writer that adds a reference between them deletes a file now in use. The next load fails closed with a missing-file config error, so this is a "delete a file that something needs" not a corruption.
- **severity: low** for all five filings together: no data loss is observed, files are small and user-edited, the in-process paths are serialized, and DECISIONS already documents the cross-process gap. It is one finding because one change (a directory sync in the two helpers, `durability != "process"` for the model-default write, and a documented or locked delete) closes it.
- fix (S): after `os.Rename`/`os.Link`, sync the parent directory when `syncWrite` (the `app/usage.go:199-212` pattern); pass `durability != "process"` in `SetLayoutModelDefault`; either hold a per-path lock across precondition→write→unlink or record both windows in DECISIONS. Reach: `session_files.go:169` reuses `writeFileIfUnchanged` "under the same preconditions as WriteCatalogFile", so the fix reaches session writes too.

### P2B1-08 (low, A/D) Unknown keys at the root-setting levels — r1-05, r3-03 — **confirmed by execution; r3's medium reduced (C6)**

- **executed**: `{"extra":1,"session_roots":[{"path":"s1","id":"a","lable":"typo"}],"libraries":{"other":{}},"server":{"port":8080,"ports":8080,"allowed_origin":["http://x"]}}` → `rootsFromSetting err=<nil> roots=1`, `normalizeServerSettings err=<nil> allowedOrigins=[] port=8080`. So this is a documented contract, not schema drift; r2 (H-A8, §6) and r4 (§6) both audited it and filed nothing. Everything that must be strict is strict: `defaults`/`settings` (`checkLayoutSettings`), catalog files (`DisallowUnknownFields`), profile `tools`, MCP uses.
- **severity: low** (r3 filed medium, r1 low): the surprising part is `session_roots[].lable`, which is neither a setting nor a documented leniency, and the cost is a misconfiguration that loads. The decision, not the defect, is the deliverable (§11 decision 4).

### P2B1-09 (low, A) `parseLayoutFile` accepts trailing garbage — r1-04, r4-02 — **confirmed by execution**
- `layout_files.go:189-192`: `if _, err := decoder.Token(); err == nil { … error }` — a syntax error from `Token()` is read as "no more data".
- **executed**: `{"name":"a"} garbage` → `err=<nil>`; `{"name":"a"} }` → `err=<nil>`; `{"name":"a"} {}` → `unexpected data after the JSON object`; `{"name":"a"}\n` → `err=<nil>` (correct). - fix (S): `if _, err := decoder.Token(); !errors.Is(err, io.EOF) { return configError("%s: unexpected data after the JSON object", path) }`; test the three inputs above. r1 and r4 propose the identical fix independently.

## 4. Verification, unique findings

### P2B1-02 (medium, A) A session write can duplicate an id across roots — r1-02 — **confirmed by execution**
- `WriteSessionFile` (`session_files.go:155-176`) resolves the target with `newLayoutSession` (`:113-138`), which only checks that the *named* root exists and uses the layout; it never looks at the other roots. The "one state folder" invariant lives in `checkUniqueSessionIDs` (`layout_root.go:97-119`) and runs only inside `Load` (`roots.go:449`).
- **executed**: two roots `local` and `b` sharing one layout, session `default` in `local`; `WriteSessionFile(roots, "b:default", data, IfNoneMatch:"*", false)` → `created=true err=<nil>`; loading the new session → `err=<nil>`; the next `Load` of the root setting → `session "default" is in session roots "local" and "b"; they share one state folder, so rename one of the sessions`. The state folders are `…/.jad/state/default` for both (`layout_root.go:140-145` joins the layout's one `State` with the session ID), so until the restart both sessions append to one `messages.jsonl`.
- severity: **medium** as filed. The write is accepted with 201/200, the running server serves a session whose transcript another session writes, every unqualified reference to the id becomes ambiguous, and the defect only surfaces as a *refusal to boot* on the next start. Reach: an API client with settings access (`app/session_catalog_files.go:41-58` holds `settingsMu`, which orders writers but does not span roots). No model reach.
- fix (S): in `WriteSessionFile`, when `!exists`, `os.Stat` the same `<id>.json` in every other root and refuse with `CatalogPreconditionFailed`/`CatalogInUse` naming both roots (the `checkUniqueSessionIDs` message is the model); add a test next to the multi-root write tests. r1's L2 notes `app/session_catalog_files.go:43-58` as the other place this could be enforced.

### P2B1-03 (medium, A/D) `"cwd": null` falls back to the global root — r2-02 — **confirmed by execution; rating raised from low**
- `compose` checks only that the *key* exists: `if _, set := setting["cwd"]; !set { … "cwd is required" }` (`layout_load.go:287-291`), with the comment "Falling back to the root folder would run tools inside .jad/". A JSON `null` passes that check, and `sessionCWD` (`session.go:1136-1152`) then unmarshals `null` into a `string`, which encoding/json treats as a no-op ("To unmarshal JSON into a pointer, … null sets the pointer to nil"; for other types null is ignored and leaves the value), so the value stays at its fallback — `location.Root.GlobalJadRoot` (`session.go:299`), the folder holding `setting.json` and the catalogs (`roots.go:418,445`).
- **executed**, three shapes, through the real loader:
  - session top-level `cwd` deleted, `settings: {"cwd": null}` → the load gets past the required check and fails only later on a path that resolves from the cwd: `prompt_documents[0] could not be read: <globalRoot>/CLAUDE.md` (the fixture's `CLAUDE.md` lives in the session cwd, not in the global root), i.e. the cwd was the global root;
  - `defaults: {"cwd": null}` → same, failing later on `tools.native.subagent.agents_dir[0] is not a directory: <globalRoot>/.jad/subagents`;
  - control (a real `cwd`): no error, and the tool storage is under the session cwd (`toolStorage=<cwd>/.jad/state/default/dev/coder/tools`).
  So the session runs its shells in the config tree and its tool storage (spill, memory, tasks, subagent runs) moves to `<globalRoot>/.jad/state`, while `TestLayoutRequiresACWD` (`layout_load_test.go:1023`) only deletes the key and `TestLayoutToolStorageIsUnderTheCWD` only asserts the normal case.
- this is exactly what DECISIONS 545 forbids: "Without any, a catalog-layout session fails with `cwd is required` … because the fallback would be the global root (`.jad/`), which holds no project."
- severity: **medium**, raised from r2's low (§5 C7). The loader's whole job at this spot is to fail closed on a config that names no working directory, and it does not. The effect is a documented-invalid configuration that loads and puts the model's tools and per-session state inside the folder that holds `setting.json` and the catalogs. Not high: it needs a settings writer that emits `null` (no model can set it), and I did not verify whether the resulting cwd lands the catalogs inside the model's write policy — that is phase 6/7's path-confinement question, and it is what makes the rating a judgement rather than a measurement.
- fix (S): test the value, not the key — `if raw, set := setting["cwd"]; !set || strings.TrimSpace(string(raw)) == "null"` — or make `sessionCWD` reject a raw `null` with its existing "cwd must be a non-empty string". Add a `null` case to `TestLayoutRequiresACWD` and to `TestLayoutCWDComesFromDefaultsThenSessionThenProfile`.

### P2B1-07 (low, B) A catalog read follows a final-component symlink — r4-04 — **confirmed by execution; rating lowered from medium**
- `catalogPath` (`catalog_files.go:116-126`) validates both identifiers and joins, then `ReadCatalogFile` (`:169-182`) and `ListCatalogFiles` (`:129-147`) call `os.ReadFile` on the result with no `Lstat`, no `O_NOFOLLOW` and no regular-file check; `check.go:81` does the same for `jad check`.
- **executed**: `models/openai/leak.json` symlinked to a file outside the catalog containing `TOP-SECRET` → `ReadCatalogFile(model, "openai/leak") err=<nil> data="TOP-SECRET"`, and `ListCatalogFiles` lists it (`entries=4`, `name=""` because the target is not JSON). So a token holder who opens that catalog entry in the editor receives any file the server process can read.
- this is **not** a re-raise of the rejected B-C4 concern: B-C4 is about *category folders* being symlinks, which `catalog/scan.go:112-115` documents as intended ("isDir follows symlinks, so a linked category folder works"). This is the final component of a file path.
- severity: **low**, lowered from r4's medium: the attacker must already be able to create a symlink inside the catalog folder (the same access that lets them plant a catalog file), and the reader must request that exact id. It is a disclosure of server-readable files to an authenticated settings user, not a privilege escalation.
- related, and observed in the same probe but **not filed by any reviewer**: `SessionFileID` refuses a symlinked `<id>.json` in a listing (its `entry.Type()` is a symlink and `DirEntry.Info()` reports the link itself — probe: `linked.json type=L--------- -> SessionFileID("", false)`), yet `Location.UsesLayout` uses `os.Stat` (`layout_root.go:123-129` — probe: `UsesLayout for the symlinked file = true`), so the same file is invisible in `GET /api/sessions` and loadable by an explicit `root:id`. r4 saw this and did not file it ("the root symlink boundary remains a residual assumption"); r3 filed the opposite conclusion as H10 (C3). Worth one decision, not a finding.
- fix (S): in the two readers, open with `O_NOFOLLOW` (or `Lstat` + refuse a symlink) and require a regular file; that also folds into the shared helper of P2B1-01 if the helper takes the decision. Add a regression test that reads a planted symlink.

### P2B1-10 (low, D/A) `JAD_SESSIONS_DIR` yields a root that cannot serve a session — r2-07 — **confirmed by execution**
- `Load` (`roots.go:220-235`) builds one `Root` from `JAD_SESSIONS_DIR` with `Layout` unset; `layoutFromSetting` is only reached through a root setting. `defaultSessionRoots` (`:354-376`) has the same shape for the no-root-setting fallback.
- **executed**: `Load` with `JAD_SESSIONS_DIR` set → `roots=1 layout=<nil>`; `Resolve` succeeds (`err=<nil>`, `UsesLayout=false`); `LoadSessionSettings` → `<dir>/s1.json: not a catalog-layout session; it needs a <session id>.json file in a session root and a root setting.json that names the catalogs`. The server therefore starts, lists every session as a per-session config error (`app/catalog.go:203-207`) and can never run one.
- DECISIONS 19 still documents the env var as a supported root selection ("`JAD_SESSIONS_DIR` selects one `default` root and bypasses root settings") and does not say that a root without a layout is dead; DECISIONS 625 removed the legacy loader that made it useful; `internal/contentlibrary/settings.go:129-131` still treats the variable as "no root setting".
- severity: **low** — an operational trap, no data effect. The no-root-setting fallback is harmless in the ordinary case (an empty `.jad/sessions`), which is why r2 filed one entry for both.

### P2B1-12 (low, C/D) The model file is read up to three times per load — r2-05 — **confirmed by reading**
- read 1: `checkProfile` → `checkModelEffort` → `loadModel` (`layout_profile.go:40` → `model_effort.go:68-78`), only when the profile's `model_default` carries an `@effort`; read 2: `layout_load.go:102-107`, which calls `config.WithModel()` and **throws the result away** (`if _, err := config.WithModel()`), to refuse an effort the model no longer offers; read 3: `LoadLayoutSessionConfig` (`layout_load.go:207-217`) → `WithModel` again when the caller needs the model, and `LoadSessionConfig` (`session.go:654-662`) likewise.

Measure-or-close with PH8/§9.

### P2B1-13 (low, D) No `did you mean` on layout unknown-key errors — r3-05 — **confirmed by reading**
- `checkLayoutSettings` (`layout_files.go:196-211`) sorts the offenders and answers `settings may not carry %s; it has its own file or field in the catalog layout`; `normalizeProfileTools` in the same phase uses `unsupportedToolKey` (`profile_tools.go:39`), and the native tool sections do too (P2A-05, P2A-07). So `{"settings":{"cwdx":"/x"}}` names the wrong key but not the right one, while `{"tools":{"native":{"bash":{"timeouut_ms":1}}}}` suggests.

### P2B1-14 (low, B) Absolute server paths reach API clients — r1-09 — **confirmed by reading and by the probe error texts**

- severity: **low**, hardening. No fix required; if wanted, strip the catalog/root prefix in `mapCatalogFileError`.

## 5. Contradictions, disagreements and refuted claims

### C1 (factual) r1-07 against r2 and r3 on duplicate session-root directories — **r1 refuted; not a defect**
r1-07 reports that an entry whose cleaned directory equals an earlier one is dropped with `continue` before its id is recorded (`roots.go:436-438`), so `[{"id":"a","path":"s"},{"id":"b","path":"s/"}]` yields one root `a` and `b:<id>` becomes "session root not found". That is exactly what the code does, and exactly what `TestLoadRootSettingAliasesDeduplicatesPathsAndHonorsSessionsDir` (`roots_test.go:171-188`) pins: it loads `session_paths` with `{"id":"one","path":"sessions"}` and `{"id":"two","path":"./sessions"}` and asserts `len(config.Roots) == 1 && Roots[0].ID == "one"`. r2 (H-A7) and r3 (H08) reached the same conclusion independently, and r2 calls it deliberate. The observation stands; the **defect** does not, because a pinned behaviour with a test is the project's contract. If the aliasing should be refused instead, that is a behaviour change with its own decision, not a bug fix. No merged id.

### C2 (factual, partly) r2's "the settings stamp covers what the loader reads" and r3-01's toolset/MCP halves — **both partly refuted**
r2 §6 lists "the session file, profile/model/toolset files (stamped by the scans and `noteFile` before each read, `catalog_scans.go:74-82`)". The model file is not stamped at all: the four `noteFile` sites are the session file, the selected profile, the other profiles and the toolset files (§3 P2B1-04 probe: `modelFileStamped=false` over 23 stamped files). r3-01 goes the other way and says toolset **and MCP** files are also only covered by their parent folder's `statStamp`; the toolset file *is* `noteFile`d immediately before the read (`layout_load.go:456`), and MCP server files are not a load input (they are validated at write/`jad check` time and read by `mcpclient` at run time), so the stamp owes neither. What survives from both is the model file, which is P2B1-04.

### C3 (factual) r4's sound-line and r3's H10 on `SessionFileID` and symlinks — **r4's fact is right, its conclusion is not; r3's fact is wrong**
r4 §6 says "`SessionFileID` rejects symlink session entries during listing", and it is right: `entry.Type()` for a symlink is not regular, and `os.DirEntry.Info()` "reports the information about the link itself, not the link's target", so the fallback at `layout_root.go:85-90` sees a symlink and refuses. Probe: `linked.json type=L--------- -> SessionFileID("", false)`. r3's H10 states the opposite ("`SessionFileID` follows symlinks via `Info()` fallback") and is simply wrong about `Info()`. The residual fact neither draws is that `Location.UsesLayout` uses `os.Stat` (`layout_root.go:127`) and *does* follow: probe `UsesLayout for the symlinked file = true`. So a symlinked `<id>.json` is hidden from the session list and loadable by an explicit `root:id`. Recorded under P2B1-07 rather than filed; it needs a product decision, not a fix order.

### C4 (factual) r3-03 and r1-05 against r2's H-A8 and r4 on unknown root-setting keys — **the schema settles it in r2's and r4's favour**
All four agree on the fact (the loader ignores unknown keys at the root-object, `session.*`, `session_roots[]` and `libraries` levels — my probe reproduces it). They disagree on whether it is a defect. `sample/schemes/root-setting.schema.json` sets `additionalProperties: true` on all four (read programmatically here), and the strictness that matters is elsewhere (`defaults`/`settings`, catalog files, profile `tools`, MCP uses). So this is a documented contract with a lenient default, not loader drift: **r3's medium and "no test asserts an error" framing is refuted as a defect report**, and P2B1-08 survives as a low finding about the *shape* of that contract (`session_roots[].lable` is arguably a typo trap even under `additionalProperties: true`). The open item is a decision (§11 decision 4), not a defect.

### C5 (severity) r3 filed three mediums (r3-01, r3-02, r3-03) — one survives as merged medium
r3-02 becomes the core of P2B1-01 (medium). r3-01 becomes P2B1-04 (low): its toolset and MCP halves are refuted (C2) and the remaining effect is a delayed failure. r3-03 becomes P2B1-08 (low): the schema pins the leniency (C4). r3 is also the only reviewer that rated an unbounded read with lens B (security) rather than A; the security framing applies to the prompt-document site a model can reach through `bash`, which is where P2B1-01's `A/B` comes from.

### 12.3 What the measurement corrected

- **PH1's mechanism was wrong in the merge and in all three filings that proposed it.** The hypothesis was "every load re-reads and re-validates every profile in the session's scope". The read is only a fifth of it: `readProfile` + `checkUnselectedProfile` = 9.6 µs per profile, while the fan-out costs ~46 µs. The rest is `loadSessionSettingsFrom` walking the composed `paths.profiles` a second time (`validateAllStoragePaths`: `rawObject` + `resolveStoragePaths` + 9 `filepath.Clean` per profile, 23.9 % of the run), `selectProfile`/`validateProfileFields` decoding the selected profile again (27.6 %), and the `paths.profiles` rebuild (30.7 % `compose`). The fan-out is therefore **two independent O(profiles) passes**, not one expensive read — a fix that only caches `readProfile` would recover about a fifth of it.
- **PH1 is bigger than "unmeasured" suggested at request scale**: a settings list of 200 sessions with 20 profiles in scope costs **200 ms and 78 MiB** of allocation per poll, because each session pays the full fan-out. That is the one number in this section with a plausible production shape (the sample has 2 profiles; 20 is a large but not absurd scope) — but it is deliberate work (the app needs `paths.profiles` to list the profiles of a session), so it stays a measurement and not a finding.
- **PH2 is confirmed and is multiplicative, not additive**: an agent toolset pays one whole compose *and* the profile fan-out again (5 agents × 20 profiles = 6.94 ms against 1.57 ms at 1 profile). The cost is configuration-size shaped: `agents × profiles`.
- **PH3's split is now attributed**: 98.5 % of `jad check` is the session half, and inside it the driver is the number of *loads* (sessions × profiles), not the profile reads — 5 000 reads are only 11 % of 438 ms. The catalog half (6.6 ms for 91 files) is negligible at this size, so the "validateProfileFile rescans the catalogs per file" half of the hypothesis matters only for a very large catalog: PH5's 11 µs/file says a 1 000-file catalog would cost ~11 ms per full scan, and `validateProfileFile`/`validateToolsetFile` scan per profile file.
- **PH5's per-file cost is 11 µs at 1 KiB and 1.78 ms/MiB** — the cost is dominated by bytes, so the ETag-triggered UI poll is fine for a normal catalog (135 µs for 10 files) and only hurts with large files (100 MiB of catalog = 180 ms per list). There is **no cap on how much a list reads**; that is `P2B1-01`'s reach, not a new item.
- **PH6 is confirmed in both halves and the stamp arithmetic is now measured**: 1.32 µs per `stat`, so a cache hit over a 1 313-entry stamp costs 1.81 ms before any load is skipped, and one poll of 200 sessions with 20 folders per catalog spends **30 % of its time re-stat'ing** work it already did. The "agents_dir listed twice" claim is now a syscall count (+1 opendir, +2 `getdents64` per load per agents_dir).
- **PH4's ordering is inverted from the merge's wording**: the expensive decode is the *first* one (`into any`, 119 µs) not the second (`into map[string]json.RawMessage`, 36 µs). The `any` decode exists only to answer "is this a JSON object", which `json.Valid` or the `RawMessage` decode's own nil check answers for a third of the cost.
- **PH7 is unchanged** — the only group where the hypothesis needed no correction, which is expected because p2a had already measured it.
- **`P2B1-12`'s cost is now known**: a `model_default` with `@<effort>` makes the load read the model file under the stamp; one `loadModel` of a 300-byte file is **13.6 µs** and the load goes **220.9 µs → 258.7 µs** (+37.8 µs, +17 %). The extra read is real but small; §11 decision 9 can be closed as "confirmed, cheap to fix, not urgent".

A session with N agent toolsets therefore lists the profile, model and toolset catalogs **N+1 times per load**, and the run path re-does it per message. The cost is proportional to the catalog size, which is why it doubles at 101 folders and is invisible at 11.

### 12.6 Limits, what was not measured, reproducibility

- **tmpfs only, one machine, not idle** (load 0.8-1.6). Absolute µs are ±a few percent; every conclusion rests on a ratio between two sizes measured back to back, or on a per-item cost. Four rows are above the 5 % spread line and are marked in 12.1; the 31 % one (`PH3 sessions/5-profiles/10`) is the only figure whose median I would not quote to three digits.
- **Synthetic fixtures.** No benchmark used `sample/jad`; the trees are minimal valid layouts with the requested counts. Real profiles carry more keys, which moves PH1's per-profile cost up (PH4's 65-key profile: 157.8 µs for the two decodes alone) and real toolsets carry more per-section configuration, which moves PH7 up. The *shapes* (linear in profiles/sections/files, quadratic in profiles for `jad check`, 1.3 µs per stat) are what the measurements establish.
- **Not measured**: any of these under `-race` (benchmarks ran without it for the reasons §9 gave); PH1/PH2's memory behaviour under a real GC workload (allocation totals are reported, GC pause attribution is not); PH5 on a cold page cache or a real btrfs (the 557 MB/s is read+SHA-256 CPU on tmpfs); PH3 with a catalog large enough for its `validateProfileFile` rescans to matter (estimated from PH5's per-file cost, not measured); the `mcp` catalog scan in PH6 (my fixtures name no MCP server, so 3 of the 4 catalogs are stamped — a real config with toolset MCP entries adds a fourth); and the HTTP/app layer entirely — every number is at the library boundary the phase owns.
- **The `pprof` attribution in 12.2 is one profile** (`-cpuprofile`, 3 s of `profiles/100`, 4.99 s of samples, 121 % because of GC workers), used only to rank the passes, not to quote per-function times.
- **P2B1-15 is a performance idiom, not a correctness bug**, and it is filed at low with executed evidence; if the fix step prefers, it can ride along with PH2's caching work.
- Reproducibility: the fixture writer and the five benchmark/probe files are listed in 12.1 and were removed with `/tmp/p2b1m`; they build only on exported-or-package-local symbols of `internal/sessionfs` (`Load`, `Resolve`, `LoadSessionSettings*`, `CheckLayout`, `ListCatalogFiles`, `readProfile`, `checkUnselectedProfile`, `decodeConfigObject`, `orderedObjectKeys`, `loadModel`, `CatalogScans`, `SettingsStamp.files`) and re-create in one file pair for the fix step.
