## 1. Understanding note

`internal/sessionfs` turns the raw `setting.json`/layout objects into the typed `SessionConfig` leaves; p2b2 holds every leaf node except the tool-owner settings of p2a and the loader/roots/catalog machinery of p2b1. Three of the twenty files are not normalizers: `files.go` (the `@path` completion walk), `session_files.go` (the session-file CRUD the settings routes use) and `storage_paths.go` (which transcript/cache/staging path each profile gets). All validation is pull-based: each node decodes with `decodeConfigObject`, bounds its integers, and rejects unknown keys with a suggestion — except where noted below.

`internal/session` is the run loop: `Runner.Run` (one mutex per session, one provider round per iteration, automatic compaction and the run-token cap between rounds), `runResponse` (per-event stream callback, staged output items, commit), `executeToolRound`/`runToolBatch` (bounded fan-out of one response's function calls, panic recovery on each worker) and `run_token_limit.go` (usage parsing). The runner starts exactly one kind of goroutine (the tool-batch worker); everything else is synchronous under `Runner.mu`.

## 3. Findings

### P2B2-R2-01  The per-round `decisionAnswer` pointer is written from concurrent tool workers without a guard
- severity: medium
- lens: A correctness and concurrency
- location: internal/session/runner.go:585-595 (write), internal/session/runner.go:635 (read), internal/session/runner_tools.go:234-256 (the workers)
- evidence: [read] trace. `Run` declares `var decisionAnswer *tools.InteractionAnswer` (runner.go:585) and installs a closure that assigns it (`decisionAnswer = &recorded`, :590) on the `tools.ExecutionContext` handed to `executeToolRound`. That closure is invoked from inside a tool call, i.e. on a `runToolBatch` worker goroutine (`tool_batch.go:107-118`). The only production caller of `OnInteractionResolved` is `tools/native/request_draft.go:109-113`, and `tools/native/tool_smith_bridge.go:232` forwards the handler into the nested tools a script may call (`request_draft` is *not* in `nativeToolSmithExcludedTools`, `sessionfs/native_tool_smith_settings.go:41`). With `tool_call_scheduling: "concurrent"` (a supported value, `tool_settings.go:87-96`) two `tool_smith` calls that both run `request_draft` resolve on two workers at once → two unsynchronised writes to the same pointer variable (a data race, and "last answer wins" for the run-ending decision read at :635). With the default `ordered` scheduling a batch containing a `tool_smith` call is serialised (`tool_smith` has `MayChangeFiles` true when `code` is given, `tool_smith.go:67,74-77`), so the race needs the concurrent setting or two nested-drafting scripts.
- suggested fix: make the recorded answer a guarded field, e.g. a `sync.Mutex` around the assignment plus a getter used at runner.go:635, or `atomic.Pointer[tools.InteractionAnswer]`; same file. Add a regression test that runs two concurrent calls which both invoke `OnInteractionResolved` (`go test -race`).
- effort: S
- prior art: new

### P2B2-R2-02  File-listing deny rules are matched against the unresolved path, so the listing can show names the read tool refuses
- severity: low
- lens: B security and boundaries
- location: internal/sessionfs/files.go:199-204 (deny/allow match), internal/sessionfs/files.go:120-127 (call site passes `resolvedFile` but it is used only for containment)
- evidence: [read]. `allowedByNativeReadPolicy` tests `PathWithin(rule.Path, path)` with the *unresolved* `filepath.Join(root, relative)` for both deny and allow, and only uses `resolvedPath` for the `PathWithin(workspaceRoot, resolvedPath)` clause. The read tool checks both forms (`tools/native/path.go:42,63,66` match the candidate *and* the `EvalSymlinks` result). Concrete input: workspace reached through a symlinked ancestor (`/home/u/ws` where `/home` → `/mnt/home`) with `tools.native.read.paths: {deny: ["/mnt/home/u/ws/secrets"]}`; `GET <session>/files` lists `secrets/…` names, while `read` on the same path answers `path_denied`. Who can reach it: the local UI user or a token holder who asks for the listing; the names inside a policy-denied subtree inside the workspace are exposed. Without a symlinked ancestor (or a differently spelled root) the two forms coincide, hence low.
- suggested fix: match the rules against `resolvedPath` too (deny first, then allow) in `allowedByNativeReadPolicy` — the resolved path is already a parameter; add a case to `files_test.go` with a symlinked workspace root.
- effort: S
- prior art: new (distinct from REJECTED B-C4, which is about *following* symlinks)

### P2B2-R2-03  The listing walk cannot be cancelled, and the schema-allowed maxima are 200x the defaults
- severity: low
- lens: C performance (with an A correctness edge: no cancellation)
- location: internal/sessionfs/files.go:22 (no `context.Context`), internal/app/session_settings.go:74-91 (the only caller, `ctx` used only by `requireSettingsContext`), internal/sessionfs/file_settings.go:11-14 and 78-83 (the maxima), sample/schemes/setting.schema.json:2057-2058
- evidence: [read] + extrapolation. The walk honours `max_entries` (default 5,000, schema maximum 1,000,000) and `max_results` (default 2,000, maximum 100,000) but takes no `ctx` and never checks one, so a client disconnect or shutdown does not stop it. P-008 measured `BenchmarkCollectSessionFiles1000Entries` at 10.25 ms / 2.18 MiB / 23,070 allocs per 1,000 entries; at the allowed maximum that is ≈10 s and ≈2 GiB of allocation in one request goroutine [extrapolated from the prior measured per-entry cost; not measured by me]. This is not a repeat of B-C7/P-008 (which measured the *default* cap and proposed a cache the user rejected): the new part is the missing cancellation and the maxima being reachable through configuration.
- suggested fix: give `CollectSessionFiles` a `ctx` and check `ctx.Err()` once per directory level (files.go:41-43), returning `Truncated` plus the entries collected so far; pass the `ctx` the resolver already has from `app/session_settings.go:89`. Optionally lower the schema maxima or document the cost next to them.
- effort: S
- prior art: B-C7 / P-008 (default cost, rejected) — new aspects only

### P2B2-R2-04  `tools.native.read.default_limit` accepts up to 2^53-1, unlike every neighbouring byte/count bound
- severity: low
- lens: B security and boundaries (bounds of a leaf setting)
- location: internal/sessionfs/tool_settings.go:168 (`configuredInteger(..., 1, maxSafeInteger, ...)`), consumed at internal/tools/native/read.go:281,416
- evidence: [read]. Every other integer in this file has a concrete ceiling (`max_bytes` ≤ 10 MiB :160, `max_file_bytes` ≤ 1 GiB :164, rounds ≤ 50,000 :43, parallel calls ≤ 64 :72); `default_limit` alone is bounded only by `maxSafeInteger`, and it is the line count a `read` uses when the model passes no `limit`. A setting of `9007199254740991` turns every unqualified `read` into "all lines of a file up to `max_file_bytes`" (64 MiB default, 1 GiB allowed), which is the F-12 shape (whole-file read) at the operator's chosen ceiling.
- suggested fix: bound it like the fetch tool does (`native_fetch_settings.go:153` ties `default_limit` to `max_limit`/`max_document_chars`), e.g. a `maxNativeReadLimit` constant (say 100,000) in tool_settings.go:25 and use it at :168.
- effort: S
- prior art: new (F-12 fixed the read implementation, not this bound)

### P2B2-R2-06  Three different integer parsers among the leaf settings, so the same value is accepted by one node and rejected by another
- severity: low
- lens: D maintainability
- location: internal/sessionfs/tool_settings.go:190-208 (`configSafeInteger`, used by checkpoint, hooks, provider_*, image_resize, statecontext, extension, remote_api, openai_oauth), internal/sessionfs/file_settings.go:245-259 (float64 + `math.Trunc`), internal/sessionfs/image_store_settings.go:83-87 (`json.Unmarshal` straight into `int64`)

The error texts of the three paths also differ for the same mistake. Graph check: `trace_path configSafeInteger` (inbound) = 17 direct callers (including `configuredInteger`, `normalizeCheckpointSettings`, `normalizeHooksSettings`, `normalizeImageResizeSettings`, `normalizeOpenAIOAuthSettings`, `normalizeProviderRetrySettings`, `normalizeProviderStreamSettings`, `normalizeRemoteAPI`, `normalizeMaxToolRounds`, `normalizeMaxRunTokens`, `normalizeMaxParallelToolCalls`), while `sessionFileInteger` has no edge to it — the two implementations really are separate.
- suggested fix: use `configSafeInteger` in `image_store_settings.go:83` and in `sessionFileInteger` (file_settings.go:245), keeping the existing bounds and messages.
- effort: S
- prior art: new

## 4. Performance hypotheses for the measurement step

- H01: every round clones and re-marshals the whole history, so a run is quadratic in transcript size
  location: internal/session/runner.go:311-355 (`cloneRaw` per item + `json.Marshal(input)`), called once per round from runner.go:480
  workload: 1,000 history items / 5 MB transcript, 8 tool rounds (default `max_tool_rounds`)
  benchmark: `BenchmarkBuildRequestWithLargeHistory`, `BenchmarkRunRoundsHistory` (session)
  expected: bytes/op and allocs/op grow linearly with history and are paid per round, i.e. quadratic per run

- H02: the committed response event is fully decoded four times per round
  location: internal/session/runner.go:506 (`responseTraceDetails`), :507 (`responseTokens`), :509 (`responseFunctionCalls`), :514 (`automaticCompactionTrigger`) — each `json.Unmarshal`s the envelope and materialises `response.output`
  workload: a response with 100 output items / 200 KB (a round with many tool calls)
  benchmark: `BenchmarkRunRoundsHistory` (session), or a new `/tmp` `BenchmarkResponseEventDecode4` with that fixture
  expected: 4 full parses and 4 copies of `output` per round; the compaction trigger and the trace details need three scalars

- H03: every provider stream event is validated and tokenised twice before the observer sees it
  location: internal/session/runner_response.go:56-62 (`json.Valid`, then `decodeJSONObject` which calls `json.Valid` again and `cloneRaw`s every field, runner.go:763-811)
  workload: a 200 KB answer as ~2,000 `response.output_text.delta` events
  benchmark: `BenchmarkRunnerEventDecode` (session, exists — the benchmark body mirrors the callback)
  expected: cost per delta ~2 scans of the event plus one allocation per field; removing the redundant `json.Valid` should cut ~1/3

- H04: the session list re-reads and parses every session file three times per request
  location: internal/sessionfs/session_files.go:44-52 (`readRegularFile` + `CatalogETag` + `fileDisplayName` + `fileCategory` + `fileScope` = 1 read, 1 sha256, 3 `json.Unmarshal` per file), reached from internal/app/session_catalog_files.go:21
  workload: 200 session files of 2 KB, polling list (`BenchmarkListSessions` already has 4/20/200)
  benchmark: `BenchmarkListSessions` (app), `BenchmarkLoadSessionConfig` (sessionfs)
  expected: linear in sessions with 4 passes over the same bytes; one `json.Unmarshal` into a struct with the three fields would cut it to one pass

- H05: prompt documents are read from disk on every settings load, and settings load happens per request
  location: internal/sessionfs/state_context_settings.go:212-236 → `readPromptDocument` (session.go:1120-1136, `readRegularFile` up to `maxPromptDocumentBytes`)
  workload: 4 trigger documents of 100 KB each, settings loaded per run start and per settings route
  benchmark: `BenchmarkLoadSessionConfig` (sessionfs)
  expected: 400 KB of file I/O per load, uncached; DECISIONS ("profile, session and model files are read per request") makes that per request

- H06: a run start parses the entire history to find tool calls without a result
  location: internal/session/runner_tools.go:18-70 (`pendingToolCalls` unmarshals every item twice: once for the object, once for `type`)
  workload: 2,000 history items
  benchmark: `BenchmarkReadInputItems1000Records` (transcript), `BenchmarkRunRoundsHistory` (session)
  expected: linear in history items, paid once per run start (and again after `repairPendingToolCalls` appends)

- H07: the listing walk pays ~4 syscalls per entry although symlink entries are skipped
  location: internal/sessionfs/files.go:88-90 (symlinks skipped), :111-127 (`entry.Info()` + `containedRegularFile` → `EvalSymlinks` + `Stat`), :51,65 (each directory resolved twice), :167-197
  workload: 5,000 entries (the default `max_entries`), 12 levels
  benchmark: `BenchmarkCollectSessionFiles1000Entries` (sessionfs, exists; P-008 measured 10.25 ms / 23,070 allocs per 1,000 entries)
  expected: the per-entry `EvalSymlinks`+`Stat` dominates; deriving the file's resolved path from the already-verified directory resolution (and keeping the before/after directory check that guards TOCTOU) should remove 2 syscalls per entry. Do **not** drop the double directory resolution: audit_design1.md:37 records it as a deliberate guard.

- H08: one slow publish serialises the completion of every other call in the batch
  location: internal/session/runner_tools.go:246-253 (`mu.Lock()` then `publish(cloneRaw(output))`), publish = `options.OnToolResult` → `httpapi/executor.go:112-120` (webui message build + emitter push)
  workload: 8 parallel calls, one publish taking 5 ms (slow subscriber / big result)
  benchmark: `BenchmarkRunToolBatch` (session, exists) with a non-trivial `onFinished`
  expected: the map write is microseconds; if publish is slow the serialisation is the whole batch's tail latency — measure before moving the call outside the lock

## 6. Checked and sound (do not re-file)

- **D-1 panic recovery (verify request): fixed and well tested.** `tool_batch.go:95-106` recovers both `execute` and `onFinished` on the worker goroutine, turns the panic into that call's error, keeps the stack out of the model-visible text and exposes it to the log through `slog.LogValuer` (`:13-22`). Regression test `TestRunToolBatchTurnsAPanicIntoTheCallsError` (`tool_batch_test.go:167-206`) covers both callbacks, asserts the error text carries no stack, and asserts the log line does.
- **Tool-batch workers are bounded and joined.** `workers = min(limit, len(calls))`, `wg.Wait()` before return, no timer, no detached goroutine (`tool_batch.go:107-124`); `grep -rn "go " internal/session` finds exactly this one goroutine start.
