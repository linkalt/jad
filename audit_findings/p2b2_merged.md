### P2B2-01 (medium, A) Duplicate `call_id` runs the tool twice — r1-01 — **confirmed by execution**
- `executeToolRound` (`runner_tools.go:204-265`) builds `toExecute` from every call whose `call_id` is non-empty; there is no `seen` set. `runToolBatch` then claims each entry and calls `catalog.ExecuteFunctionCall`. The finished outputs land in `byCallID[outputID]` — the second overwrites the first — and `round.Completed` is rebuilt by iterating `calls`, so a duplicated id appears twice. `appendToolOutputs` (`:112-146`) builds `completedByCallID`, then emits **one output per call**, so the duplicate id is persisted twice; `Output = encodeFunctionCallOutput(callID, …)` takes the id from `execution := call`, i.e. `ExecuteFunctionCall` sets `execution.CallID = callID` (`tools/catalog.go:315-326`), so both records carry the same `call_id`.
- **executed**: calls `dup, other, dup` through `executeToolRound` (limit 8, `ordered`, a read-only echo tool) → `executions=3 completed=3 published=[dup dup other]`, and `completed[0].call_id="dup"`, `completed[1].call_id="other"`, `completed[2].call_id="dup"`. So the tool ran three times for two ids, and three results — two of them for `dup` — were published and then persisted.
- the model controls call ids, and nothing upstream de-duplicates: `responseFunctionCalls` (`runner_tools.go:72-94`) collects the calls in the order the provider sent them, and `pendingToolCalls` (`:18-70`) keys a map by id only for the *repair* path, which is not consulted here.
- consequence: a side-effecting tool (`edit`, `write`, `bash`, `tool_smith`) runs twice — under `concurrent` scheduling in parallel, which for a state-changing call means two `edit`s racing on one file inside the same "ordered" contract. The transcript then holds two `function_call_output` records for one `function_call`. `transcript` does not reject that (`validateInputFields` only requires a non-empty string `type`, `input_history.go:223-233`), so the next provider round receives a history the Responses API is likely to refuse as a duplicate tool result. That last step is **not verified** — it is provider behaviour, not code in this tree (r1 says "likely").
- **severity: medium** as filed. It is a model-reachable correctness defect in the tool loop, the transcript is left inconsistent, and the fix is small. Not high: the trigger needs the model to repeat an id, and a well-behaved provider does not.
- fix (S): in `executeToolRound` answer the second and later occurrence of a `call_id` with `missingToolOutput(callID, "duplicate_call_id", …)` and skip it in `toExecute`, so exactly one execution and one output per id; add a regression test beside `TestRunnerDefersEveryCoBatchedCallUntilUserDecisionIsResolved` (`runner_tools_test.go:139`), which is the existing test that already builds a mixed batch. Grep confirms no test today uses a duplicate id.

### P2B2-02 (medium, A) One unreadable session file empties the whole list — r1-02 — **confirmed by execution; the FIFO example corrected (C3)**
- `listSessionFiles` (`session_files.go:25-57`) returns `(nil, configError("%s: could not be read: %v", …))` for the first file whose read fails **when `onUnreadable` is nil**; the exported `ListSessionFiles` passes `nil` (`:19-21`), while `ProfileSessions` passes a handler (`:309`). `app/session_catalog_files.go:21-24` maps the error out to the HTTP session list, and `app/transcript_profiles.go:64` and `:73` do `files, _ := sessionfs.ListSessionFiles(...)`, i.e. they drop the error and iterate an empty slice.
- **executed**: a root with `good.json`, an oversized `big.json` (4 MiB + 1) and a FIFO `fifo.json`: strict `ListSessionFiles` → `files=[] err=…/big.json: could not be read: … is larger than 4194304 bytes`; the tolerant path → `onUnreadable: big: … 4194304 bytes` and `files=[good] err=<nil>`.
- **correction to r1's example (C3)**: a FIFO named `x.json` does *not* reach the read. `SessionFileID` (`layout_root.go:80-94`) refuses any entry whose `Type()` is not regular and whose `Info()` is not a regular file — probe: `entry "fifo.json" -> id="" session=false`, while `big.json`/`good.json` are accepted. So the reachable triggers are a file over `maxInternalJSONFileBytes` (4 MiB) and a permission error, not a FIFO or a symlink. r1's own suggested fix is unaffected.
- consequence: one bad file makes every session disappear from the UI — including the session needed to fix the file — and the `transcripts`/`profile_message` tools silently answer "no sessions" with no log (the `, _` in both app callers). The two behaviours in one package disagree, which is the defect.
- **severity: medium** as filed: an availability failure of the session list with no operator-visible cause, triggered by a file the loader itself considers legal to exist.
- fix (S): make the exported path tolerant — pass a handler that records the unreadable file (the field already exists for `ProfileSessions`) and either drop it from the list or carry a per-file error, keep strict only for write/delete preconditions, and log in the two `app/transcript_profiles.go` callers. Add a test with an oversized file next to `TestListSessionFilesListsOnlyIDDotJSONFilesOfRootsWithALayout`.

### P2B2-03 (medium, A/B) A hook `match` naming nothing registered never fires — r1-03 — **confirmed by reading**
- `normalizeToolEventHook` (`hooks_settings.go:364-419`) validates `match` against `hookMatchPattern` only — `^(\*|[A-Za-z0-9_-]{1,64}|mcp:…)$` — which `bsh` satisfies. `toolEventHooksFor` (`tools/native/hooks_events.go:105-113`) then keeps a hook only if `hook.Match == "*" || tools.EntryMatches(hook.Match, definition)`, so a name that matches no registered tool is kept by nobody and simply never runs.
- the same package's profile-tool path does exactly the check that is missing here: `checkProfileToolEntries` (`app/profile_tools.go:46-54`) refuses an entry "which is not a registered tool", with the comment "so a typo shows up as a configuration error and not as a tool that is quietly missing". The hooks node's own doc comment (`hooks_settings.go:140-142`) states the same intent for its keys — "a typo cannot quietly turn a check off".
- consequence: for `pre_tool` with `blocking: true` the guard the operator believes is in place is absent, and nothing logs it. This is the one finding in the phase where the failure mode is a *missing* check rather than a wrong value.
- **severity: medium** as filed. Not high: no data is exposed and the operator authored the typo. Not low: a silently absent blocking guard is exactly the class the project's own comments say must not happen.
- fix (S, but not in `sessionfs`): the tool registry does not exist at `sessionfs` level (`nativeToolNames`/`extensionToolNames` are a declared list; MCP servers come from the catalog), so validating `match` belongs next to `checkProfileToolEntries` where both the catalog and the hooks are built, or `sessionfs` can only check "a native name or `mcp:<server>:…` syntax" and must leave the name to the app. That is the decision in §12 D2.

### P2B2-05 (medium, A) `decisionAnswer` written from concurrent workers — r1-07, r2-01 — **confirmed by execution (`-race`); r3's "no race" is refuted (C1)**
- the code: `Run` declares `var decisionAnswer *tools.InteractionAnswer` (`runner.go:586`) and installs `toolExecution.OnInteractionResolved = func(…){ recorded := answer; decisionAnswer = &recorded; … }` (`:588-594`), read at `:635` after `executeToolRound` returns. - **executed, `-race`**: a probe installs the closure body verbatim (it is inlined in `Run`, so it cannot be called in isolation) on an `ExecutionContext`, registers a read-only tool that calls `execution.OnInteractionResolved` and prints its own result, and runs two such calls through the product's `executeToolRound` with `concurrent`. The two writes are unordered, so the race detector fires; the read at `:635` is *not* part of the race (it happens after `wg.Wait`).

## 5. Contradictions, disagreements and refuted claims

### C1 (factual) r3's "`decisionAnswer` has no race" — **refuted by execution**
r3's §6 states: "decisionAnswer has no race: written synchronously inside tool execution (`tools/native/request_draft.go:109-110`), read after wg.Wait joins workers." The second clause is right and irrelevant: the read after `wg.Wait` is fine, the **two writes** are not. r1-07 and r2-01 name the same line and the same mechanism, and the probe in §3.5 reproduces `WARNING: DATA RACE` on two writes to that variable from two `runToolBatch` workers. r3 reached the conclusion by reasoning about one writer (the synchronous single-tool case) and did not consider two nested drafts, which `tool_smith_bridge.go:232` makes possible. **The finding stands (P2B2-05); r3's entry is wrong.**

### C2 (factual) r3-03's `OnResponseCommitted` half — **refuted; the rest survives**
r3-03 lists `OnResponseCommitted` among the unguarded callbacks. It is guarded: `CommitWithObserver` calls the observer through `callCommitObserver`, which recovers and logs (`transcript/turn.go:424-433`, "response commit observer panicked; staging cleanup deferred"). r1 independently verified the same ("commit observer panics are contained in `transcript.CommitWithObserver`"). What remains of r3-03 — `OnEvent`, the post-persistence `OnToolResult` loop, `RefreshStateContext`, `OnHookReport`, `OnTurnStarted` — is confirmed by reading and is carried as P2B2-23.

### C3 (factual, partial) r1-02's trigger — **the FIFO example is corrected; the finding stands**
r1-02 says "a file over 4 MiB, a permission error or a FIFO named `x.json` (readRegularFile rejects it) makes `ListSessionFiles` return `(nil, err)`". The first two are right; the FIFO one is not: `SessionFileID` (`layout_root.go:80-94`) refuses any entry whose `DirEntry.Type()` is not regular and whose `Info()` is not a regular file, so a FIFO is skipped before the read (probe: `entry "fifo.json" -> id="" session=false`). ## 12. Needs the user

### Decisions

1. **P2B2-01 — what a repeated `call_id` should mean.** Refuse every repeat after the first with a `"duplicate_call_id"` error output and skip its execution (fail closed, one output per id), silently drop the repeat, or pass it through and leave the transcript as it is. **Recommendation:** refuse + skip. It keeps "one call, one output" as an invariant, tells the model why, and needs no transcript change. Add the duplicate-id case to the golden diff.
2. **P2B2-03 — where a hook `match` is validated.** `sessionfs` cannot see the tool registry (native names are a declared list, MCP servers come from the catalog), so validating the *name* belongs where `checkProfileToolEntries` already runs (the app, which builds both), or `sessionfs` validates only the shape and the app refuses an unmatched name. **Recommendation:** the app, next to `checkProfileToolEntries`, refusing at load with the same "is not a registered tool (registered: …)" message; `sessionfs` keeps the shape check. Decide also whether a `match` that names a *disabled* MCP server is an error or a warning.
3. **P2B2-04 — tighten the loader or relax the schema.** `setting.schema.json` says `additionalProperties: false` for `session_files`; the loader accepts anything. **Recommendation:** tighten the loader to the schema for `session_files` and for each `mcp_servers` entry (and reject `null` for its booleans), keeping `http_debug`/`statecontext` lenient as documented. If `mcp_servers` entries are meant to be extensible, add them to the schema as `false` too rather than leaving the question open.
4. **P2B2-02 + P2B2-09 — the listing contract.** Make `ListSessionFiles` tolerant with a per-file error (r1's fix) and give it a budget: a configured `max_sessions`-style key with a default and a truncation flag (the project's own rule: no hardcoded limits), or an internal ceiling like the prompt-document one. **Recommendation:** tolerant by default (drop the unreadable file, expose it), plus **one** internal aggregate budget with a documented constant and a `Truncated` flag — no new user-facing setting until someone actually hits it — because the two changes touch one signature and a setting would need schema + parity work for a non-problem. Both changes are `session_files`-scoped and must keep write/delete strict.
5. **P2B2-10 — how to bound prompt documents.** Reuse the existing `statecontext.max_bytes` as a *read* budget (stop before the document that would cross it) and reject a duplicate path, or add a `max_prompt_documents` count setting. **Recommendation:** reuse `max_bytes` (no new setting, no schema change, and it makes the documented ceiling true), plus the duplicate-path rejection, since repetition is the cheapest amplification.
6. **P2B2-05 — the fix shape and the semantics.** `atomic.Pointer[tools.InteractionAnswer]` (last answer wins, as today, only race-free) or a mutex with "keep the first decline". **Recommendation:** the mutex, and prefer the first *negative* answer — a decline, a timeout or a cancellation must never be overwritten by a later accept, which is the only ordering that is safe; state it in the comment and test both orders. This is a small behaviour change (today the last answer wins), so it needs your sign-off.
7. **P2B2-11 — validate before externalizing, or roll back.** **Recommendation:** validate the batch before `images.Externalize` (a reorder, no rollback machinery, no cleanup path to test). If you want the externalize-then-append order kept for some reason, the alternative is a rollback of the blobs written in this call, which is more code and more failure modes.
8. **P2B2-12 — how far the storage check should go.** Extend the distinctness check to the three directory-ish fields (S, no behaviour risk). This is a fail-closed change with no configuration surface.

Lower the schema maxima (1,000,000 entries / 100,000 results) or keep them? **Recommendation:** keep them (they are contract, and a lowered maximum is a schema+parity change) and let the `ctx` plus a log line at `Truncated` carry the operational risk.

### 12-bis.3 What the measurement corrected

- **PH1 is 3.2×, not "several clones" without a number, and the passes are over the whole history three times**: one validity scan plus copy per item (`isJSONObject`/`cloneRaw`), one `json.Marshal(input)`, and one `json.Marshal(requestFields)` which compacts the `input` value again. The reference rows show the last pass alone is 261 µs at 200 items while the whole build is 766 µs, so **~two thirds of a round's request build is avoidable copying, not encoding**. Per item it is remarkably flat at 3.8-4.1 µs and allocation is 4.4-5.6× the transcript bytes.
- **PH2's "4-6 decodes" is 7, and its proposed cheap alternative is not cheap.** `decodeJSONObject` clones every value it returns, so decoding the event into fields (which copies the whole 200 KB `response` value) and then decoding `response` again (which copies all 100 items) costs **698 µs** — indistinguishable from `automaticCompactionTrigger`'s 694 µs. The win is a *single typed* decode that skips the output array, i.e. the `responseTokens` shape at **120 µs (25× cheaper)**. Any fix that keeps `decodeJSONObject` on the completed envelope buys nothing.
- **PH3's second `json.Valid` is only 4.6 %** of an event; the cost is the streaming decoder plus the per-field clone (51 allocs for a 140-byte event, 20× the payload in allocation over an answer). Removing the redundant validation is free but not the fix; not re-decoding/copying per event is.
- **PH4's scan is the dominant part of a run start**: at 2,000 items `pendingToolCalls` is 6.96 ms against `BuildRequest`'s 8.14 ms for the same history — i.e. the start of a run spends about as much on "find a call without a result" as on building the whole request.
- **PH5's serialization is exact**, not asymptotic: `ceil(calls/limit)` × publish. A publish on the observer path therefore adds its latency once per worker wave, and a client-slow observer turns an 8-call batch into 8 × its latency at 64 calls.
- **PH7's syscall count is 6 `stat` per entry, not ~4**, and the walk is flat at 10.4 µs/entry to 20,000 entries: the cost is per entry, so the 5,000-entry default is ~52 ms per listing and the 1,000,000-entry schema maximum would be ~10 s.
- **PH8's amplification is the cheapest attack in the phase**: because the same path may be listed repeatedly and nothing is deduped or capped in aggregate, a 10-line profile turns one settings load into **10 MB read and 43 MB allocated (9.3 ms)**; at the 8 MiB per-document ceiling, ten references are **80 MB read and 339 MB allocated (54 ms)** per load. Every listing request and every run start pays it.
- **PH11 needs splitting three ways.** (a) The per-round re-read half is **confirmed but small**: 20 images of ~140 KB cost 2.29 ms and 4.1 MB per round. (b) "Rehydrate/Apply re-read **and SHA-256** every referenced image each round" is **refuted**: SHA-256 happens in `putPayload` (`imagestore/store.go:475`), i.e. when an image is externalized, not at `Rehydrate`, which only reads the file and base64-encodes it. (c) `max_pixels` is a **refusal guard**, not a decode commitment: an image above the limit is rejected in 76.6 µs without being decoded, so the 400 M ceiling only costs 1.6 GB if an operator configures it that far (default 64 M, ≈256 MB RGBA per decode). What the hypothesis missed is the real cost of the step: **`encodePNG` uses `png.BestCompression` (`imageresize/resize.go:183`) and is tried first for every image**, which at 1.8-2.0 MP costs **1.0-7.6 s of CPU and 114-315 MB of allocation per image**, on the request path, before the provider is called.
- **PH12's open premise is answered**: `app/session_settings.go:82` calls `sessionfs.LoadSessionConfig` directly and `listSettingsCache` is consulted only from `r.listSettings` (`list_settings_cache.go:72`, one caller: `catalog.go:201`), so the files route is a cache miss, 167 µs per request, and the two halves of PH12 are both real.

The PNG encoder, not the pixels, is what varies: at `BestCompression` a noisy 1.8 MP image took 7.6 s in one case and 1.0 s in the other, while JPEG at quality 85 took 62-70 ms in both. The benchmark rows (7.823 s and 1.761 s, `-count=3`) agree with the staged totals to within noise.

### 12-bis.5 New finding and status after measurement

**`P2B2-27` (low, performance, measurement-derived; found in this step, not by a reviewer).** `encodePNG` runs with `png.BestCompression` (`internal/imageresize/resize.go:183`) and is attempted first for every image the resize step touches, so one image of 2-20 MP costs **1.0-7.6 s of CPU and 114-315 MB of allocation**, on the round's critical path (`Resizer.Apply` runs in `Run`, `session/runner.go:479`, before the provider call). Measured: 7.805 s for a 3 MP and 1.739 s for a 20 MP PNG-of-noise, of which the PNG attempt is 97 % and 59 %; extrapolation to the configured ceiling is ~5.5 s and ~1 GB at the 64 M default and ~34 s and ~6 GB at the 400 M maximum (extrapolated, not measured). Location: `resize.go:183` (`pngEncoder`), `:127` (`encodeFitting`'s first attempt), `apply.go:218` (`Resize`). Evidence: executed (12-bis.2, 12-bis.4). Filed because §9's PH11 attributed the image risk to `max_pixels` and to re-reads, and the measurement puts the cost in the encoder. Action (S): use `png.DefaultCompression` (or `BestSpeed` for an image above a pixel budget) and/or try JPEG first for an opaque image; the result is cached per resizer (`cache_entries`, default 64), so the cost is once per image per session, and the step is off by default — which is why this is low and not medium.

### 12-bis.6 Limits, what was not measured, reproducibility

- **tmpfs only, one machine, not idle** (load 1.2-3.4). Absolute µs move by a few percent between commands; every conclusion rests on a ratio between two sizes measured back to back, on a per-item cost, or on a stage decomposition taken in one process.
- **Synthetic fixtures throughout.** No benchmark used `sample/jad` or a real transcript: PH1/PH2/PH4's histories are generated items with 1,500-byte texts, PH6's session files are JSON with a padding key, PH8's documents are one repeated byte, PH11's images are PNGs of a deterministic pattern. Real content carries more distinct values, which moves PH1/PH2/PH6's per-byte costs up and PH7 not at all.
- **Not measured**: any group under `-race` (the benchmarks ran without it); PH9 under a *saturating* tool load (the fixtures sleep, so the run shows the ceiling but not the throughput collapse) and with real MCP servers; PH10 on a cold btrfs or with a git repository that already has history (the fixture workspace is built and committed inside the benchmark); PH11 at the 64 M and 400 M `max_pixels` values (extrapolated from 20 MP) or with a real photographic JPEG (only PNG in, PNG/JPEG out); PH2/PH3 inside a live HTTP run; PH12 over HTTP (the app layer was read, not exercised); the memory behaviour of any group under GC pressure (allocation totals are reported, pause attribution is not).
- **PH11's cache was not exercised**: each `resizeDataURL` call in the benchmark uses a fresh `Options`, so the memo (`cache_entries`) never hits; in production the second round for the same image is free, which is why the finding is scoped to first sight of an image per session.
- **One `pprof`-style attribution only** (PH11's stage table), taken with `time.Since` around individual calls in a test, not with a CPU profile; it is used to rank stages, not to quote per-function times.
- Reproducibility: the four probe files are listed in 12-bis.1 and were removed with `/tmp/p2b2m`; all of them build only on package-local or exported symbols of `internal/session`, `internal/sessionfs`, `internal/imagestore` and `internal/imageresize` (`BuildRequest`, `makeCompletedEvent`, `responseTraceDetails`, `responseTokens`, `responseFunctionCalls`, `automaticCompactionTrigger`, `decodeJSONObject`, `jsonNumberFloat`, `pendingToolCalls`, `runToolBatch`, `ListSessionFiles`, `CatalogETag`, `fileDisplayName`, `fileCategory`, `fileScope`, `CollectSessionFiles`, `defaultSessionFileListingSettings`, `Load`, `Resolve`, `LoadSessionConfig`, `WriteSessionFile`, `validateSessionFile`, `Store.Rehydrate`, `Externalize`, `resizeDataURL`, `scale`, `encodePNG`, `encodeJPEG`) and re-create in one file per package.

### 12-bis.7 Decisions this measurement opens

1. **P2B2-27 — bound the encoder, or leave it and document it.** **Recommendation:** switch `pngEncoder` to `png.DefaultCompression` and try JPEG first for an opaque image above a pixel budget; it is a two-line change with no configuration surface and it removes a multi-second stall, and the golden output is unaffected because the result is cached and never written to `messages.jsonl`. The alternative (a `max_resize_millis` or a work budget) is a new setting for a non-problem.
2. **PH5's publish latency — reorder or leave.** The publish runs under `executeToolRound`'s mutex (`runner_tools.go:246-253`), which serializes a slow observer across the wave. **Recommendation:** leave it (the mutex protects `byCallID`, and the publish order is what the client expects) but note in the code that the observer is called under the lock, so a future streaming change does not put real work there.
3. **PH8 + P2B2-10 — the fix now has a number.** Ten references to one 8 MiB document cost 54 ms and 339 MB per load. **Recommendation:** keep §12 decision 5's answer (reuse `max_bytes` as a read budget + refuse duplicate paths) and treat this measurement as its justification; do **not** add a separate size setting.
4. **PH10's checkpoint under `r.mu` — move `Finish` out.** **Recommendation:** take the checkpoint's end snapshot after releasing the run lock (or asynchronously with a join before the next run reports complete), because it is 154 ms of a run's tail at 20,000 files and it blocks the next run for no correctness reason. Small, but it is the one row here that is pure fix with no trade-off.
5. **PH9 / P2B2-15 (B-C8) — close it, or measure contention once more.** The ceiling is N×limit and nothing else throttles it, so the decision is the one §12 decision 11 already asks for (a process-wide semaphore with a documented default, or a change to `max_concurrent_runs`'s default). **Recommendation:** close B-C8 as "bounded by configuration, not a constant" (the performance plan's own wording) and add the semaphore only if a saturating measurement with real tools shows a collapse; that measurement needs a real tool mix, which this step could not produce.
