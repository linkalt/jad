## 1. Understanding
- p2b2 contains leaf sessionfs settings/file helpers plus the session runner. Session config normalizers feed `app.Run`; the runner serializes a session turn, streams provider events, persists tool results, and fans out tool calls with a per-response limit. Session file listing is separate from workspace listing and currently has an unbounded root scan.

## 2. Review hypotheses
- H1 (verified): `CollectSessionFiles` checks deny rules against the lexical path while accepting a symlinked workspace root; a canonical-target deny can be bypassed.
- H2 (verified): `listSessionFiles` reads all entries and every matching per-file-bounded session JSON without an entry or aggregate-byte cap; `ProfileSessions` rescans on profile-catalog listing.
- H3 (verified): state-context prompt documents are individually bounded but all are read and concatenated before the aggregate `max_bytes` check.
- H4 (verified): `runToolBatch` limits workers per response only; there is no shared worker semaphore, and the default global run cap is zero.
- H5 (verified): storage collision checks use cleaned path strings without resolving symlink aliases, allowing distinct profiles to target the same storage file.
- H6 (verified): `PersistInputWithImages` externalizes image data before transcript validation rejects objects without a valid `type`; this can consume persistent image quota.
- H7 (verified sound): D-1 panic recovery covers both worker execution and completion callbacks; the targeted panic regression test passed.
- H8 (disproved): the token-total addition cannot overflow on runs with an enabled configured cap: `max_run_tokens` is at most 1e12, each response total is safe-integer bounded, and the cap is checked before another tool round. No cap means the feature is intentionally disabled.

## 3. Findings

### P2B2-R4-01  Deny rules can be bypassed through a symlinked workspace root
- severity: medium
- lens: B security
- location: `backend-go/internal/sessionfs/files.go:24-29,199-207` (caller: `backend-go/internal/app/session_settings.go:74-91`)
- evidence: [read] `CollectSessionFiles` resolves the workspace root for containment, but builds traversal paths from the original `root`. `allowedByNativeReadPolicy` tests `deny` rules only against the lexical `path`; it then accepts a path within the original root. If root is a symlink alias (accepted by `EvalSymlinks`) and a deny rule names the canonical target path, the deny check misses while the root-containment branch accepts the entry. An authorized session-files listing caller can therefore receive names from a directory its policy denies. Existing symlink test covers a symlinked file, not a symlinked root.
- suggested fix: apply deny rules to both `path` and `resolvedPath`; add a test with a symlinked workspace root and a deny rule using the canonical target.
- effort: S
- prior art: new

### P2B2-R4-02  Session config listing reads every session file without a listing budget
- severity: medium
- lens: C performance
- location: `backend-go/internal/sessionfs/session_files.go:25-56` (`ProfileSessions`: 73-93)
- evidence: [read] `listSessionFiles` calls `os.ReadDir(root.Directory)` and retains all entries, then opens and reads each ID-named JSON file (up to `maxInternalJSONFileBytes`, 4 MiB) to derive its name/category/scope before appending metadata to `infos`. The helper has no count/page or aggregate-byte cap. `ProfileSessions` is called on each profile-catalog request by `app.ListCatalogFiles` (`app/catalog_files.go:36-60`), so repeated listings rescan every matching session file. I/O scales with total file bytes and memory with entry count.
- suggested fix: paginate or add configured entry and aggregate-byte limits, and expose truncation/cursor semantics to the list caller.
- effort: M
- prior art: new

### P2B2-R4-03  State-context prompt documents are aggregated only after all files are read
- severity: medium
- lens: C performance
- location: `backend-go/internal/sessionfs/state_context_settings.go:193-208,212-236`; per-file reader: `backend-go/internal/sessionfs/session.go:1120-1137`
- evidence: [read] `stateContextTriggerPrompt` reads every configured document into `texts` before `normalizeStateContextTrigger` checks combined header+prompt against `MaxBytes`. Each file permits up to 8 MiB (`native_config_file.go:18`), while aggregate `max_bytes` tops out at 10 MiB (`native_process_settings.go:21`); `prompt_documents` has no count/total limit. A config can repeat a document many times and force reads/allocations far beyond the eventual 10 MiB rejection. The 4 MiB settings-file cap limits the list encoding, not the total referenced data. This is not a repeat of the bounded per-file read fix (33a1264); the missing bound is aggregate/early rejection.
- suggested fix: track accumulated prompt bytes and reject before reading/appending a document that would exceed the configured aggregate; optionally reject duplicate paths.
- effort: S
- prior art: new (distinct from fixed 33a1264 per-file bound)

### P2B2-R4-04  Tool workers have only a per-response ceiling, not a global ceiling
- severity: medium
- lens: C performance
- location: `backend-go/internal/session/runner.go:598-600`; `backend-go/internal/session/tool_batch.go:105-126`; configuration: `backend-go/internal/sessionfs/tool_settings.go:19-20`
- evidence: [read] one run forwards `MaxParallelToolCalls` to `executeToolRound`; each batch starts `min(limit, len(calls))` goroutines. The setting defaults to 8 and accepts up to 64. The scoped runner has no shared worker semaphore; different sessions run independently (the outer app lock is per session at `backend-go/internal/app/bound_runner.go:29-34`). The server-level concurrent-run default is `0` (`backend-go/internal/serverconfig/defaults.go:54`; the setting/test describes this as no cap), so total workers can grow as concurrent runs × 64. This re-confirms the open B-C8 concern; not a measured cost.
- suggested fix: add a configurable process-wide tool-worker budget/shared semaphore (or a bounded run admission default that also covers non-HTTP callers); preserve a documented opt-out if needed.
- effort: M
- prior art: B-C8 open (audit_plan.md:118)

### P2B2-R4-05  Profile storage collision checks do not resolve symlink aliases
- severity: medium
- lens: A correctness
- location: `backend-go/internal/sessionfs/storage_paths.go:88-111,115-141`; resolver: `backend-go/internal/sessionfs/session.go:1158-1166` and `backend-go/internal/sessionfs/roots.go:824-829`
- evidence: [read] configured paths are made absolute/clean but are not symlink-resolved; both `validateProfileStoragePaths` and `validateAllStoragePaths` key collisions on `filepath.Clean(entry.Path)`. Distinct paths such as `profiles/a/messages.jsonl` and `profiles/b/messages.jsonl` with a symlinked parent alias can reach the same filesystem file and pass. This defeats the loader’s cross-profile storage separation (which `storage_paths_test.go:22-36` asserts for defaults) and can mix/corrupt profile transcripts or caches. The config author/local filesystem is the actor; no remote exploit is established.
- suggested fix: compare resolved existing path components (or reject symlinked storage paths) when enforcing distinct transcript/cache storage; add a profile-alias regression case.
- effort: M
- prior art: new

### P2B2-R4-06  Rejected input can consume image-store quota before validation
- severity: medium
- lens: B security
- location: `backend-go/internal/session/runner.go:177-201`; downstream validation: `backend-go/internal/transcript/input_history.go:55-70`; image write: `backend-go/internal/imagestore/store.go:96-129,456-496`
- evidence: [read] `PersistInputWithImages` calls `images.Externalize(item)` for every normalized input item before `AppendInputItemsAt` validates the object and required `type`. For example, a run request with `{"image_url":"data:image/png;base64,<valid unique PNG>"}` is accepted by `NormalizeInput` as an object; `Externalize` stores its `image_url`, then transcript validation rejects the missing `type`. The request fails but the content-addressed image remains on disk and counts against the configured per-session image-store quota; repeated authorized requests with unique images can exhaust that quota and prevent later valid images from being stored. No cleanup or rollback is performed on the validation error.
- suggested fix: validate the complete input batch before externalizing images, or roll back newly written image blobs if transcript append/validation fails.
- effort: S
- prior art: new

## 4. Performance hypotheses for measurement
- H01: `listSessionFiles` does full `ReadDir` + per-session read and sort, `session_files.go:31-56`. workload: 1k/10k/100k valid session JSONs, varying file size; benchmark: existing `BenchmarkListSessionsProfiles`; expected O(N + total bytes) time and O(N) retained entries.
- H02: state-context docs are repeatedly read before the aggregate cap, `state_context_settings.go:193-208,212-236`. workload: many references to one 8 MiB document in a ≤4 MiB setting; benchmark: proposed `BenchmarkNormalizeStateContextPromptDocuments` with e.g. 2/10/100 references; expected allocations/I/O scale with reference count despite rejection at 10 MiB.
- H03: tool goroutines scale by concurrent runs, `tool_batch.go:105-126`; `tool_settings.go:19-20`. workload: N independent sessions each returning 64 calls; benchmark: proposed `BenchmarkConcurrentRunnerToolBatches` with N runners and blocking fake tools; expected peak workers approach 64×N without global admission.

- `session_files.go` rejects non-regular/symlink entries with `SessionFileID` and reads settings through the bounded regular-file helper; create-in-other-root ID collision guard is present (aa38621; not re-raised).

- `runner.go` propagates context to provider stream and tool execution; response turn close is deferred on incomplete streams; tool outputs are persisted in call order after all workers settle.
- Token usage uses provider-reported safe-integer totals; `max_run_tokens` is bounded to 1e12 and checked before another tool round, while a final answer may complete above the cap by design (DECISIONS.md run-token-cap decision). The input/output fallback sum also fits int64; no cap-enabled overflow path found.
- Leaf-setting normalizers generally provide explicit defaults and bounded numeric settings; relevant settings and layout cases passed targeted tests. The main `Run` method remains long, but response, tool execution, and token-limit helpers are already split across neighboring files, so no separate D finding was filed.
