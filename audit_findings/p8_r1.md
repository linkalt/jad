## 1. Understanding note

The phase has three layers:

1. **Journal (`transcript/jsonl.go`, `line_index.go`).** One `Journal` per `messages.jsonl`, with a mutex `j.mu` for every read and write. Appends go to the tail after repairing a partial last line (`repairTrailingPartialLine`, reads backwards in 64 KB chunks). Durability is `process`, `turn` or `strict`; `turn` and `strict` fsync the file and, on creation, its directory. `ReplaceRecords` (compaction, reset) and `front_compact` rewrite the whole file by temp file plus rename and bump `generation`. An in-memory `lineIndex` (per journal, lazily built, extended by reading only new bytes, validated by a 4 KB tail hash and generation) makes the idempotency check `appendFileIfAbsent` cheap (this is the F-07 fix; `containsLine`).
2. **Turns (`turn.go`, `recovery.go`).** A `ResponseTurn` stages output items in `items.jsonl`/`index.jsonl` in a staging directory, writes a `manifest.json` through a temp file plus rename at each step, renders a canonical final line, and commits by `appendFileIfAbsent` into the journal. `TurnStore.Recover` replays staged turns on start: a rendered final line is appended if absent, and a committed manifest is checked by `containsHashText` (a full scan, recovery only).
3. **Derived read state (`input_history*.go`, `maintenance.go`, `cursor_cache.go`, `compaction_memo.go`).** `InputHistory` memoizes the expansion of `messages.jsonl[0:offset]` and checks it with a 64 KB checkpoint hash plus generation. A compaction cache (`compaction-cache.json`, with `source_sha256` and `source_bytes`) substitutes for the prefix; on every cache hit `cacheSourceIsTranscript` re-hashes the whole transcript when its size equals `source_bytes` (which is the normal case). Cursor cache, usage cache and run-error cache are derived files removed by `removeDerivedFiles`.

Images: `imagestore.Store` writes data URLs (decoded, content-sniffed) as `<sha256>.<ext>` files and replaces them with references in the transcript; `Rehydrate` restores data URLs before a request; `OpenWithin` checks size and identity before reading. `imageresize.Resizer` rewrites `input_image` parts of an outgoing request, memoised by URL hash with a bounded FIFO. `imagedata` decodes and sniffs base64 for the HTTP run input and for `read_image`. `contentlibrary` lists and reads prompt, template and skill markdown from configured directories, re-reading the setting and the tree on each call.

Lifecycle: `app` creates one shared journal and turn store per session through `openSharedSession` (`app/resolver.go:962`), plus one per sub-agent (`app/subagent.go:209`). `imagestore.Store` and `imageresize.Resizer` are created per run (`app/bound_runner.go:51,68`, `app/subagent.go:90`, `app/session_settings.go:146`).

Configuration: `image_store` (`sessionfs/image_store_settings.go`: min 16 KiB, max file 20 MiB, max total 1 GiB), `image_resize` (cache_entries default 64, max 4096), turn-store durability and metadata from `sessionfs`.

## 3. Findings

Format per `audit_plan.md` 5.1. Severity follows 5.1. Evidence labels: [read], [trace], [test], [unmeasured].

### P8-R1-01  Rewritten transcript and compaction-cache renames have no directory fsync
- severity: medium
- lens: A correctness (durability)
- location: backend-go/internal/transcript/jsonl.go:126 (`ReplaceRecords`), backend-go/internal/transcript/maintenance.go:653 (`backupTranscript`), backend-go/internal/transcript/maintenance.go:793 (`writeCompactionJSONAtomic`), backend-go/internal/transcript/front_compact.go:279 (`prefixTemp` publish); the cursor cache does it right at backend-go/internal/transcript/cursor_cache.go:275.
- evidence: [read] In `turn` and `strict` mode the file is fsynced before rename, but no caller fsyncs the parent directory after `os.Rename`. `ReplaceRecords` is called from `CompactHistory` (maintenance.go:181) and `Reset` (maintenance.go:668). `writeCompactionCache` writes the cache twice with the same helper (maintenance.go:752-768). A crash after the rename can leave the directory entry pointing at the previous file, so the cache's `source_sha256`/`source_bytes` no longer match and the cache is discarded (cacheSourceIsTranscript returns false, maintenance.go:820-834), or the previous transcript comes back. The second case reverts a compaction. Impact is limited to a power loss or kernel crash (a process crash after rename is safe). The cache case is self-healing; the transcript-revert case loses the compaction, not the data. No test covers a directory sync on these paths (dir_sync_test.go covers only the commit path). [test] `go test -run TestDirectorySyncPerStep|...` passed, which proves only the commit path.
- suggested fix: add `syncDirectory(filepath.Dir(path))` after the rename in `writeCompactionJSONAtomic`, `backupTranscript` and `front_compact` (when durability is not process), matching `cursor_cache.go:272-283`; add a `dirSyncHook` assertion to `dir_sync_test.go` for `Reset` and `CompactHistory`. Files: transcript/jsonl.go, maintenance.go, front_compact.go, dir_sync_test.go.
- effort: S
- prior art: new (related to P-012..P-014, which covered commit only; the compaction paths were not in them)

### P8-R1-02  contentlibrary reads whole files and the whole tree on every request, with no size cap
- severity: low
- lens: C performance; B boundary (size limit)
- location: backend-go/internal/contentlibrary/library.go:313 (`os.ReadFile` in `readAsset`), :66-99 (`List`), :101-160 (`Read`), :232-265 (`markdownFiles`), backend-go/internal/contentlibrary/settings.go:58 (`loadDirectories` re-reads the setting per call, documented at settings.go:24-27).
- evidence: [read] `List` walks every prompt, template and skill tree, reads and parses every `.md` file in full (`readAsset` calls `os.ReadFile` and `parseMarkdown` with no size limit), and sorts. `Read` walks the same trees with `filesForKind`, computes `assetID` (`filepath.Abs` plus sha256) for each file, and calls `readAsset` only on the match (library.go:116-131), so its cost is the walk and the per-file hash, not a read of every file. The setting is re-read on each call (`loadDirectories`, settings.go:58). Reachability: token holder only (handler.go:320-327), so this is a cost, not an exposure. Workload: a library with many or large files; the size of one file is limited only by disk. [unmeasured] The benchmark `BenchmarkLibraryList1000MarkdownFiles` exists (library_benchmark_test.go:11) and was not run here.
- suggested fix: `readAsset` could check `info.Size()` against a cap (for example 1 MiB) before `ReadFile`; `List` could cache by path and mtime if the list cost matters. Files: contentlibrary/library.go.
- effort: S
- prior art: new

### P8-R1-03  Image writes are not fsynced, and the dedupe check compares size only
- severity: low
- lens: B boundary (content integrity); A durability
- location: backend-go/internal/imagestore/store.go:479-481 (dedupe by name and size), :491 (`writeAtomic`), :602-626 (`writeAtomic`, no `Sync`).
- evidence: [read] `writeAtomic` writes the temp file and renames it without `Sync` and without a directory sync. After a crash the image file can be empty or partly written under its final name; the next `putPayload` then accepts it because `info.Size() == size` only when the size matches, and `Open` checks the content against the name (store.go:520-559, `http.DetectContentType`), so a corrupt file surfaces as "stored image content does not match its name" on read rather than silently. Consequence: a referenced image can become unreadable after power loss (rehydrate then substitutes a placeholder, see store.go:206-212 "Missing"). The dedupe size check does not verify content, but `Open` does, so this is an availability issue, not a silent corruption. Low, because it needs a power loss while the image is written.
- suggested fix: sync the temp file before rename (as `writeJSONAtomic` does when `sync` is set, turn.go:698-723), or accept the risk and record it. Files: imagestore/store.go.
- effort: S
- prior art: new

### P8-R1-04  The image store mutex covers the first-write directory scan and file I/O (B-C5, still open)
- severity: low
- lens: C performance; A locks held across I/O
- location: backend-go/internal/imagestore/store.go:479-491 (`s.mu` held over `os.Stat`, `directorySize` and `writeAtomic`), backend-go/internal/app/bound_runner.go:51,68 and backend-go/internal/app/subagent.go:90 (one new Store per run).
- evidence: [read] Re-confirms B-C5 (audit_performance_plan.md:84) on HEAD 632ebed. The lock is per Store, and a Store is built per run, so the lock is not shared across runs; contention is within one run's parallel tool calls. The scan (`directorySize`, store.go:629-644, `ReadDir` plus `Info` per entry) runs once per Store, on its first new image, and the cost is linear in the number of stored images, and it repeats in every run. [unmeasured] The prior measurement (P-007, performance plan) put it at about 2.5 µs per file.
- suggested fix: one shared Store per image directory in the resolver (the audit_audit.md:96 recommendation); do not shard the directory. Files: app/bound_runner.go, app/subagent.go, app/session_settings.go, app/image_resize.go.
- effort: M
- prior art: B-C5 re-confirmed (still open)

### P8-R1-05  Lock-held observer runs a usage read and an SSE publish inside the commit
- severity: low
- lens: A locks held across callbacks
- location: backend-go/internal/transcript/turn.go:343 (`t.mu.Lock`), :405 (observer call), :424-434 (`callCommitObserver`); backend-go/internal/httpapi/executor.go:78-92, :156-169 (`publishRunUsage`); backend-go/internal/session/runner_response.go:122-126.
- evidence: [read] `CommitWithObserver` holds the turn mutex while the observer runs. The httpapi observer calls `publishRunUsage`, which reads the run usage (a transcript read) and publishes an event. I traced the lock graph: the usage read takes the TurnStore and Journal locks, not `t.mu`, so there is no cycle (H10 disproved), and the commit is already complete at that point. The effect is that a slow SSE publish or usage read delays only the release of this turn's handle. Low; no deadlock found.
- suggested fix: none required; if the observer ever calls `Commit` or `StageOutputItem` on the same turn, it deadlocks, so a comment on `CommitWithObserver` stating that rule would help. Files: transcript/turn.go.
- effort: S
- prior art: new

## 4. Performance hypotheses (section 5.3)

- H-P1: `readTranscriptItemsMemo` copies the whole memo slice per read.
  - location: backend-go/internal/transcript/input_history_memo.go:96-108 (`result = make([][]byte, len(memo.items)); copy(...)`).
  - workload: a run of N rounds over a transcript of T items; each round copies T slice headers (24 bytes each). At 10k items that is 240 KB per round.
  - benchmark: `BenchmarkRunRoundsHistory` and `BenchmarkRunRoundsHistoryCompacted` (input_history_benchmark_test.go:15-197), existing.
  - expected: linear in T per round, small absolute cost (slice headers only; item bytes are shared). The fix would be to return the memo slice read-only, but the doc at input_history_memo.go:58-60 says callers must treat results as read-only, so the copy is the defensive version. Likely not significant.
- H-P2: `ReadRecordsRange` and `ReadCompleteRecordsRange` hold `j.mu` for the whole read, including the expansion callback (jsonl.go:255-281, :345-418). Callers: run start history (`app/history.go:205`), web UI usage scan (`app/catalog.go:463,535`) and cursor/turn-start (`app/turn_starts.go:56`).
  - workload: a large transcript read (for example the usage scan of a 50 MB file) blocks every appender of the same journal, which is the current run's commit.
  - benchmark: none exists for lock hold time; propose `BenchmarkJournalReadWhileAppending` (new fixture: 10 MB journal, one goroutine reading the full range, one timing append latency).
  - expected: append latency grows with the read duration; sign of the effect is unmeasured.
- H-P3: (dropped) the whole-file hash of H2 runs only when the size equals `source_bytes`, which is not the steady state after compaction. Keep `BenchmarkReadHistoryCompactedLargeTranscript` (compaction_hash_benchmark_test.go:13-77) as the check if that changes.
- H-P4: `lineIndex.hashes` has no bound (line_index.go:70-105). Memory is 32+ bytes per line plus map overhead, so about 100 bytes per line; a 50 MB transcript of about 100k lines is about 10 MB. Benchmark: `BenchmarkLineIndexMemory` (memory_benchmark_test.go:137-176), existing.
- H-P5: `imagestore` `directorySize` per run (see P8-R1-04). Benchmark: `BenchmarkDirectorySize` (scan_benchmark_test.go:14), existing; `BenchmarkPutPayloadParallel` (put_contention_benchmark_test.go:20), existing.
- H-P6: `contentlibrary` `List` reads every file per request, and `Read` walks the tree and hashes every candidate path (see P8-R1-02). Benchmark: `BenchmarkLibraryList1000MarkdownFiles` (library_benchmark_test.go:11), existing; a single-read benchmark is missing.
- H-P7: `imageresize` decode outside the lock on a miss, with `CacheEntries` 64 by default (sessionfs/image_resize_settings.go:21). A miss costs a full decode and resize (apply.go:195), so an image that is re-sent each round is decoded once per run only when cached; with `CacheEntries` at its 64 default and more than 64 distinct images, the FIFO evicts and every round re-decodes. Benchmark: `BenchmarkApplyHistoryWithoutImages` (apply_benchmark_test.go:12) exists but has no images; a new `BenchmarkApplyHistoryManyImages` with 100 distinct images and a 64-entry cache would measure the thrash.
