## 1. Understanding

- `Handler.route` (handler.go:298) authenticates with sha256+ConstantTimeCompare (handler.go:427), gates browser origins by exact match (handler.go:410), and dispatches. All paths except `/api/health` need the bearer token.
- A run is an `activeRun` in `runRegistry` (registry.go). `executeRun` (executor.go:33) runs on its own goroutine. `Handler.Close` only cancels run contexts (registry.go:444).
- SSE: each subscriber has an `eventQueue` with a byte budget. An overflowing non-terminal frame closes the queue, so a slow consumer is dropped and never blocks `publish`. Late subscribers register while "holding" and receive a snapshot built outside `r.mu`. This part is sound.
- Run start order: turnQueue (FIFO per key) -> session lock (in-process) -> try transcript lock -> resolve -> `beginRunFrom` under `mutationMu` -> release session lock. Maintenance handlers use the mutation gate (`mutations` map) + session lock + transcript lock.
- `webui` is a transcript/stream normalizer (no static asset serving, no embed). The "embedded web UI serving" risk area does not exist in these 5 packages, and there is no `go:embed` for a UI anywhere in `internal/` (only contentlibrary, tool_smith, exec templates). `memorytrace` is an opt-in env sampler that writes only to stdout.

## 3. Findings

### P3-R1-01  Shutdown cancels runs but does not wait for them; resolver closes under live runs
- severity: medium
- lens: A correctness
- location: httpapi/registry.go:444-455 (`close`), httpapi/handler.go:283-287; app/service.go:119-127; cmd/jad/main.go:118-125
- evidence: [read] `runRegistry.close` calls `run.stop()` (cancel only) for every run and returns. `Service.Close` then closes `s.api` and immediately `s.resolver.Close()` (MCP managers, stores) while `executeRun` goroutines are still unwinding (final transcript commit, `recordRunFailure`, `finish`). In main.go `service.Close()` runs before `ShutdownHTTPServer`, so SSE handlers are still being served while the resolver is closed. The 176fd7d class: Close returns before the work it owns has stopped. A test could start a run blocked in a fake tool, call `Handler.Close()`, and assert `run.done` is closed.
- suggested fix: in `runRegistry.close`, after cancelling, wait on each `run.done` bounded by the shutdown timeout (the registry already holds the run list; `done` exists). Files: httpapi/registry.go.
- effort: S
- prior art: new (D-3 fixed the HTTP server deadline, not this)

### P3-R1-02  Out-of-order interaction notifications can re-publish a settled question
- severity: medium
- lens: A correctness
- location: interactions/broker.go:100-127,186-217 (`Request`/`Extend` call `notify` after unlock), interactions/broker.go:263-272, httpapi/interaction_state.go:19-80
- evidence: [read] `Extend` unlocks, then `notify(&pending, nil)`. A concurrent `Reply` (or timeout) settles, unlocks, then `notify(nil, ended)`. If the Reply notify runs first, `setPendingInteraction` sees `pendingInteraction == nil` and returns (interaction_state.go:37-40). The late Extend notify then sets `pendingInteraction` to a question nobody waits on and publishes `interaction` + `ui.message` with `Pending`. Nothing clears it: `finish` calls `Cancel`, which returns early because `b.entry == nil` (broker.go:208-212), so no clearing event is sent. Late subscribers replay the stale question until retirement. The same window exists between `Request`'s `notify(&pending)` and a very fast Reply/timeout (small timeouts). Narrow, but the client shows a dead approval dialog and a 409 on answer.
- suggested fix: deliver notifications under `b.mu` ordering (a sequence number on notify; `setPendingInteraction` drops a stale one), or have `finish` always publish a clearing event when `r.pendingInteraction != nil`. Files: interactions/broker.go, httpapi/registry.go (finish).
- effort: S-M
- prior art: new

### P3-R1-03  Finished runs retained by time only; failed/aborted runs keep their content cache and partial file for the whole retention
- severity: low (medium if `run_state_retention_ms` is raised; max 24 h per audit_audit.md B-C1 note, sessionfs/roots.go:169 default 30 s)
- lens: C performance / A
- location: httpapi/registry.go:786-823 (`finish`), :457-473 (`retire`), :754-763 (`disposeContent`); httpapi/executor.go:130-133,152-157
- evidence: [read] re-confirmed B-C1: `maxRuns` counts only running runs (registry.go:333). Each retained run keeps `terminal` (`ui.message` and `completed` both embed the whole final message, so two copies), `latestMessage`, `latest`, `liveImages` (decoded inline images, unbounded per run, live_images.go:25-35) and the content cache until `retire` runs. `disposeContent` is called only from `retire`; `setCommittedMessage` closes the cache only on a committed response. A failed or aborted run therefore keeps its spilled `.partial` file and `.owner` file (run_content_cache.go:255-289) on disk and its fallback memory for the whole retention window. The `time.AfterFunc` (registry.go:820) is not stopped by `close` (harmless, one wake).
- suggested fix: call `disposeContent` (cache and liveImages) in `finish`, since after the terminal events nothing reads them (late subscribers get `terminal`); cap retained runs per key (keep the last N). Files: httpapi/registry.go.
- effort: S
- prior art: re-confirmed B-C1 (ACCEPT-LOW); the early-dispose part is new

### P3-R1-05  http_debug: error text and some credential names are not redacted; pruning runs once per process
- severity: low
- lens: B security / D
- location: httpdebug/transport.go:28 (`sensitiveHeaderPattern`), :117 (`"error": err.Error()`), :309-363 (`initialize`/`prune`), :20-26
- evidence: [read] D-5 items are present (redactURL, header pattern, 0600/0700 modes). Gaps: (a) the pattern lacks `token`, `secret`, `x-amz-security-token`-style names, so a custom header such as `X-Auth-Token` or `X-Secret` passes through (`auth` alone is not in the header pattern; only `authorization`); the query pattern is wider than the header pattern. (b) The transport error `err.Error()` is written raw; Go's `*url.Error` already prints the URL without userinfo, but a base_url with a credential query is printed unredacted (`Get "https://h/v1?key=..."`), bypassing `redactURL`. (c) The `MaxTotalBytes` comment says "when a run starts logging, the oldest files beyond it are removed" but `prune` runs only in `initialize`, once per `Transport` (sync.Once). `newFileLogger` is created per `NewTransport`, i.e. per session config load (app/resolver.go:509), so a long-lived process only prunes on a new transport. The directory can exceed `max_total_bytes` without bound between loads.
- suggested fix: widen the header pattern to `token|secret|auth|key|cookie`; redact via `redactURL` or strip the URL in the `err` text; prune after N new files or at each `reserve`. Files: httpdebug/transport.go.
- effort: S
- prior art: D-5 fixed (verified in part); remainder new

## 4. Performance hypotheses

- H1: `setPendingInteraction` holds `r.mu` across a spilled-cache file read plus a full-message marshal, registry.go:687-704 / interaction_state.go:56-66.
  workload: a 5-50 MB streamed answer spilled to the partial file, 1 SSE subscriber, a draft interaction fires mid-stream.
  benchmark: new `BenchmarkSetPendingInteractionLargeCache` in httpapi (fixture: cache with `memoryLimit` small and 20 MB appended); measure concurrent `publish` latency during the call.
  expected: lock hold time scales with content size (ms to tens of ms per call).
- H2: each retained run keeps two full copies of the final message in `terminal` (`ui.message`, `completed`) plus `latestMessage`/`latest`; memory per retained run is about 3-4x message size, and failed runs keep the content cache and the spilled partial file until retire, registry.go:786-823.
  workload: 1,000 runs finished within `run_state_retention_ms` at 1 MB final text; retention 30 s default, 24 h max.
  benchmark: existing `BenchmarkFinishedRunRetention` (httpapi/memory_retention_benchmark_test.go:69) with an added failed-run shape.
  expected: heap per retained run linear in final message size; independent of subscribers.
- H3: per text delta, `webui.Increments` is run twice (`appendOnlyPartIndex` in the emitter, executor.go -> message_stream_emitter.go:162-178, and again in `messageFrames`, registry.go:640-654); each does `strings.HasPrefix(after, before)` and `partsEqual` over the whole previous text part, plus `cloneStreamMessage` on emit.
  workload: one 200 KB text part streamed in 2,000 deltas, coalescing 120 ms (about 8 publishes/s).
  benchmark: existing `BenchmarkStreamEventPipelineLongText` (event_pipeline_benchmark_test.go); compare 10 KB vs 200 KB part.
  expected: cost per publish proportional to part text length; the prior plan measured it as flat for one text part, so this is likely small (the `HasPrefix` and string equality are memcmp-fast). Low priority.
- H4: `readAllChunked` + `json.Valid` + `scanRunBodyObject` + `parseValidRunInput` make about 3 passes plus an output buffer, about 4x body (test TestReadRunBodyAllocationStaysNearFourTimesTheBody already pins it); a 16 x 25 MB-image request is capped by `runBodyLimit` at about 2.1 GB (`MaxMaxRequestImages` 16 x `MaxMaxRequestImageBytes` 25 MB, serverconfig) before any limit bites, handler.go:822-827.
  workload: server configured at the maximum image limits, 4 concurrent uploads.
  benchmark: existing `BenchmarkReadRunBody*` (run_body_benchmark_test.go) with the 16x25 MB shape; also resident memory with `max_concurrent_runs` unset.
  expected: peak heap about 4 x body per in-flight start (the cap is the operator's choice, so a hardening note only).
- H5: `serveSSE` with `sse_write_timeout_ms` = 0 has no write deadline at all (handler.go:760-767), so a stalled reader pins a goroutine and its queue (bounded by `maxQueue`, then closed by `push`, so only the goroutine remains blocked in `w.Write`).
  workload: 1,000 clients that connect and never read, with the timeout set to 0.
  benchmark: existing `BenchmarkStalledSubscriberMemory` (memory_retention_benchmark_test.go:139) covers the queue; add a goroutine count with timeout 0.
  expected: goroutines scale with stalled connections until TCP keepalive/`IdleTimeout` ends them. Default is 30 s, so this is a configuration case.

## 6. Checked and sound

- Auth: sha256 of the candidate compared with `subtle.ConstantTimeCompare` against a stored hash (handler.go:427-435); token length and CR/LF validated at construction (handler.go:162). All `/api/*` except health are behind it; OPTIONS answered before auth by design.
- CORS: exact-origin map; a disallowed `Origin` gets 403 on every route, including health; no wildcard; `Vary: Origin` set.
- Body limits: every body reader wraps `http.MaxBytesReader` (readRunBody, readInteractionBody, readSettingsObject, readCheckpointRestoreRequest, readFrontCompactMessageID, catalog PUT x2); run bodies get the image allowance on top but the non-image part is re-checked against `max_body_bytes` (handler.go:908); `readAllChunked` does not size from Content-Length (test exists).
- SSE publisher: `eventQueue.push` never blocks; overflow closes that subscriber and `publish` deletes it under `r.mu`; heartbeat and per-chunk write deadlines in `serveSSE`; subscribe/snapshot invariant (hold, release) reviewed and consistent; terminal events always queued.
- `retire` / `finish` idempotency: `finish` is guarded by status; `retire` removes by pointer; `running` counter decremented once.
- Run start ordering (turnQueue enter/leave, `once` guard on leave, ctx cancel leaves queue); `lockSessionAndTranscript` releases in the right order and on every error path.
- `keyedLocker` refcount deletion is correct.
- Delete flow (`stopSessionRuns`): stops, waits on `done` with timer and ctx; one shared timer across runs (bounded by the total).
- Error text to clients: `clientRunErrorMessage` and `writeJSONError` hide detail (non-StatusError -> "internal server error"); the cause is logged only at 5xx (request_observer.go). Panic recovery on request and run goroutines (D-1) present; `http.ErrAbortHandler` re-panicked.
- Image routes: `nosniff`, `Content-Security-Policy: sandbox`, position parsed strictly; live images only for the current run; cache headers match the content-addressed vs non-addressed split.
- `memorytrace`: opt-in via env, no content, ticker stopped with the last run, `recover` around the writer; ok. `httpdebug`: file modes 0600/0700, body caps on request and response, wire bytes via `GetBody`, writer goroutine drains queue, errors only logged.
- `messageStreamEmitter`: timer callback clears `e.timer` under the lock; `discard` stops the timer; `push` ownership documented.
- `interactions.Broker`: timers stopped on settle; `Request` always returns after cancel; `Reply` after expiry settles as timeout; ids are crypto/rand v4 UUIDs.
- gofmt and vet clean for the 5 packages.
